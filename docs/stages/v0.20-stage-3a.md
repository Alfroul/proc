## 实施决策（stage 3a 内拍板，按 brainstorm 步 15 规则记录）

### 决策 A：`--no-thinks` → `--reasoning off`（brainstorm 决策 4 事实性更正）

**本机实测**（2026-08-15，`llama-server --help` on b8685）：
b8685 **没有 `--no-thinks` flag**。等效能力已迁移到通用 flag：

```
-rea, --reasoning [on|off|auto]   Use reasoning/thinking in the chat
                                  (default: 'auto' (detect from template))
```

`--reasoning off` 与 `--no-thinks` 意图完全一致（禁用 thinking mode，ADR-0030
D6）。brainstorm 决策 4 的**设计意图不变，flag 名按实际版本更正**。其余 flag
的存在性确认（`--jinja` / `--ctx-size` / `--chat-template` / `--special` 都在
help 清单）由决策 F 的组合行为实验进一步修正（2 个不传）。

### 决策 B：就绪检测走 `/health` 轮询，不解析 stdout

brainstorm 决策 6 伪码写「等 "HTTP server listening on" stdout 行」。落地改
为 **HTTP GET `/health` 轮询**（250ms 间隔，startup_timeout 上限，默认 120s）：

1. 不依赖子进程日志格式（跨 llama.cpp 版本稳定）
2. `/health` 返回 200 即 model loaded，语义精确
3. stdout → null；stderr → piped + 后台 drain 线程（防 pipe buffer 满阻塞），
   只保留尾部 ~8KB 环形缓冲，**超时时拼进错误消息**供诊断（模型路径错 /
   显存不足 / flag 不识别一眼可见）

### 决策 C：`stream()` 惰性 spawn 用 `stream::once + try_flatten`

`LlmProvider::stream` 不是 async fn（trait 决策 2），但首次调用需要 async
setup（spawn + 等就绪）。落地：

```rust
fn stream(...) -> ProviderStream<'static> {
    let inner = self.inner.clone();       // Arc<Inner>，满足 'static
    Box::pin(futures_util::stream::once(async move {
        let server = inner.ensure_server().await?;
        inner.post_chat_stream(server, messages, tools, options).await
    })
    .try_flatten())
}
```

provider struct 改 `Arc<LlamaCppProviderInner>`（server 句柄 +
`tokio::sync::Mutex` 惰性 spawn，跨 await 安全）；`new(server_path, model_path)`
签名不变（stage 1 测试兼容），新增 `with_options()` 供 stage 3b 传
agent.toml 启动参数。

### 决策 D：complete() 非流式 / stream() SSE 两条独立路径

vs「complete = collect(stream)」统一路径：llama-server 原生支持非流式
（`"stream": false` 返完整 JSON），分开实现各自更简单直接（~80 行 vs 共享
聚合器 ~120 行），且非流式路径少一层 SSE 解析出错面。两条路径共享请求体
构造 + tool_calls 解析（`build_request_body` / `parse_tool_calls` 纯函数）。

### 决策 E：SpawnOptions 预留 `chat_template` 扩展点

brainstorm 决策 4 拍板固定 `--chat-template gemma`。但 agent.toml
`[default].model` 本就支持换模型（qwen 等），硬编码 gemma 模板与非 gemma 模型
矛盾。落地 `SpawnOptions { chat_template: Option<String> }` 用户显式覆盖位
（默认 None 不传 flag，见决策 F 实测更正）。

### 决策 F：启动 flag 实测矩阵（推翻 brainstorm 决策 4 的 2 个 flag）

本机 llama-server b8685 系统性实验（curl 矩阵 + nvidia-smi 验证）推翻
brainstorm 决策 4 假设的 3 个 flag 中的 2 个：

| flag | brainstorm 假设 | b8685 实测 | 落地 |
|---|---|---|---|
| `--no-thinks` | 存在 | **不存在**；等效迁移到 `--reasoning off`（`-rea`） | 传 `--reasoning off` |
| `--chat-template gemma` | 正常 | **与 `--jinja` 组合把 user content 渲染丢掉**（`prompt_tokens=3`、模型自由续写 `_4 is a Large Language Model...`）；不传时 GGUF 自带 gemma 模板 + `--jinja` 正确渲染（`prompt_tokens=23`、回答正确） | 不传（决策 E 覆盖位保留） |
| `--special` | 解析 tool special tokens | **副作用 content 尾部泄漏 `<turn|>` 字面量**；tool_calls 解析由 server 模板层处理，不依赖它 | 不传 |

实测关键数据：正确 flag 组合下 E2B 单步 tool call 完整工作——
`tools` 请求返 `finish_reason:"tool_calls"` + `{"name":"proc_ls",
"arguments":"{\"limit\":1,\"sort\":\"cpu\"}"`（模型正确理解 query + schema）。
设计意图（Gemma 模板正确渲染 + thinking 禁用）不变，flag 集按实测更正；
brainstorm 决策 4 段加更正注记。

### 决策 G：GBNF 规则名不支持下划线（stage 1 grammar bug 修复）

stage 1 嵌入的 `tool_call.gbnf` 用了 `tool_call` 规则名——**llama.cpp GBNF
语法规则名只允许 `[a-zA-Z0-9-]`**，含下划线导致整个 grammar 被 llama-server
**静默忽略**（不报错、不约束，输出自然语言）。二分实验定位：`tool_call` /
`a_b` 规则名被忽略，`tc` / `str` 生效；改名 `tool-call` 后完整 grammar 生效
（`Tell me a story` 输出被强制为 `{"tool_calls": []}` JSON）。

修复：规则名 `tool_call` → `tool-call`（JSON key 字面量 `"tool_calls"` 是
字符串内容不受限）；grammar 文件头注释记录实测结论；测试加防回归断言
（所有规则名不含下划线）。**grammar 字段本身真实生效**（极简
`root ::= "yes"` 实验强制输出 "yes"）——brainstorm 风险 2 解除，且比
预期更好：不需要 fallback 到 `response_format.json_schema` 路线。

## 已知风险（stage 3a 实施时关注）

### 风险 1：`--reasoning off` 对 Gemma 4 E2B 的实际效果

决策 A 更正 flag 名后，`--reasoning off` 是否真把 E2B thinking 关掉需实测
（TTFT < 1s 即生效；若仍 5s+ 说明模板侧还在注入）。mitigate：本机集成测试
观察 complete 耗时；不达标再查 `--reasoning-format none` 组合。

### 风险 2：llama-server 不接受请求体 `grammar` 字段

llama.cpp 扩展字段（非 OpenAI 标准）。mitigate：实测带 grammar 的 complete
请求；若 400 则改用 `response_format.json_schema` 路线（stage 3b 决策）。

### 风险 3：reqwest 在 async 上下文死锁（brainstorm 风险 6）

agent v0.20 仅 CLI `proc agent ask` 入口（自建 runtime，不走 MCP server
runtime）。mitigate：provider 不自建 runtime，`#[tokio::test]` 单 runtime
验证；MCP 集成留 v0.21 评估。

### 风险 4：Windows 子进程清理（Drop 时 llama-server 的 CUDA 线程）

`kill()` 在 Windows 是 `TerminateProcess`（强杀），CUDA 上下文由 OS 回收。
mitigate：kill + wait 双调用防僵尸；集成测试断言 drop 后进程退出。

### 风险 5：真实测试拖慢全量回归

模型加载 ~5-10s + 推理 ~2-5s，单测试文件 ~30s。mitigate：真实测试合并为
1-2 个 `#[tokio::test]`（一个函数内串行 spawn→health→complete→stream→drop），
skip 路径 CI 零开销。
