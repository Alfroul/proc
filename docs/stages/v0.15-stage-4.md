## ROI 来源（cycle 末段 Review + 收尾合一段）

**v0.13 模式对比**：v0.13 cycle 方案 c 是「baseline + 报告 + Review + 收尾」4 stage（stage 3 Review + stage 4 收尾**分两段**）。v0.15 cycle 同样 4 stage，stage 4 Review + 收尾**合并**（与 v0.14 cycle 方案 A 的 stage 5 同款合并模式）。

**合并理由**（参考 v0.14 stage 5 doc §ROI 来源）：
1. v0.15 cycle 是「中重 cycle」（业务代码 ~1700 行 = stage 1 ~430 + stage 2 ~870 + stage 3 ~440），Review 报告 + 收尾动作量级相当，合一段让 cycle 节奏更紧凑
2. v0.13 cycle 4 stage 全程不动业务代码，Review + 收尾分两段是因为 Review 阶段需要单独 commit；v0.15 业务代码已落地，Review 段 + 收尾段可以连续在同一会话产出（Review 报告 + 收尾文档同步合并一个 commit）
3. stage 4 工作量 ~250 行（REVIEW-v0.15 ~200 + 收尾 ~50），与 stage 3（~440 行）/ stage 2（~870 行）量级偏轻，单会话能完成

**风险**：合并让单会话工作量略增，但 Review 段的 P1 修复 + 收尾段的 CHANGELOG 同步可以一起 commit（无中间态），减少 commit 数量。

## 已知风险

### 风险 1：REVIEW-v0.15 P1 / P2 数量不确定性

stage 4 撰写时点预计 P1 集中在文档完整性（stage 1 doc 头部 ✅ 缺 / brainstorm 表 ⬜ 未改 / 14 tool miscount 文档化），P2 集中在 brainstorm FAQ + stage 2/3 doc 已知风险段（MonitorManager 持久化 / metrics sparkline / per-process disk_io / metrics_smart vs proc_smart 合并入口等候选）。**已 mitigate**：任务 2 §1.6 段在 Review 时按实际发现填，P1 数 N（预计 1-3）/ P2 数 M（预计 1-3）。

### 风险 2：Cargo.lock 同步失败

`cargo build --release` 自动同步 `Cargo.lock`，但如 Cargo.lock 含本地依赖（无）或 platform-specific 依赖可能不一致。**已 mitigate**：stage 4 任务 5 跑 `cargo build --release --no-default-features` 验证；如失败，手动 `cargo update -p proc --precise 0.15.0` 修正。

### 风险 3：git tag v0.15.0 时机

按 v0.14.0 / v0.13.0 同款规则，**stage 4 commit 完成后等用户确认再 push tag**（不在 stage 4 自动 push）。stage 4 commit 含本地 tag 创建（`git tag -a v0.15.0 -m "..."`），但 tag 不在 commit 内（git tag 是仓库级 ref，独立于 commit）。**已 mitigate**：stage 4 完工 commit 后单独跑 `git tag -a v0.15.0`，与 v0.14.0 同款「等用户确认 push」原则。

### 风险 4：CONTEXT.md 本地状态升级可能遗漏

CONTEXT.md 术语段（line 204）+ 演进历史段（line 216）「开发中，2026-07-06 启动」需改为「已落地，2026-07-06 发布」，stage 4 收尾时容易忘（与 v0.14 stage 5 收尾同款规则）。**已 mitigate**：任务 9 显式列两段状态升级 + 演进历史加 stage 4 行，stage 4 完工时按验收标准 `grep "v0.15 阶段 4" CONTEXT.md` 验证。
