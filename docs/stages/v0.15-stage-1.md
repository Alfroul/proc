## 设计决策（本阶段拍板，stage 2/3 不动）

### 决策 1：rmcp tool_router 跨 module 收集能力

**问题**：brainstorm §v0.15 cycle 模块重构段提「需验证 rmcp 0.11 是否支持跨 module 收集 #[tool] 方法」。

**调研结论**（context7 rmcp 官方文档，2026-07-06 验证）：
- `#[tool_router]` 宏**只收集它所标注的 impl 块内**的 `#[tool]` 方法。子 module 里 `impl ProcMcpHandler { #[tool] ... }` 块**不会被主 mod 的 tool_router 收集**。
- 替代方案：`ToolRouter` 实现 `Add` trait 可合并多个 router（`router_a + router_b`），但需要每个子 module 独立 `#[tool_router]` impl + 主 mod 显式合并，boilerplate 更多。
- 第二替代：`SyncTool` / `AsyncTool` trait-based 模式，每个 tool 独立 struct impl trait。最灵活但 boilerplate 最多。

**本阶段决策**：**Strategy A** — 保持单个 `impl ProcMcpHandler` 块在 `handler/mod.rs`，所有 17 + 15 = 32 个 `#[tool]` 方法都在这个块里。子 module 只放 Args struct + 业务 helper 函数（不在子 module 里写 `#[tool]` 方法）。这样：
- rmcp 0.11 限制零风险
- 子 module 文件可以独立编译（无 rmcp 依赖）
- stage 2/3 各 Slice 只动子 module，不动主 mod.rs 的 impl 块（surgical 原则）
- 既有 17 个 tool 行为零回归（impl 块结构不变）

### 决策 4：stub 返回格式

每个新 tool 的 stub helper 返 placeholder JSON：
```rust
pub fn make_flows_json(_limit: Option<usize>) -> Value {
    json!({
        "ok": true,
        "stub": true,
        "stage": "v0.15-stage-2",
        "message": "proc_flows tool schema is registered; business logic lands in stage 2",
        "received_limit": _limit,
    })
}
```

理由：
- `ok: true` 让 client（如 mcp-inspector）调用时不报错，能验证 schema 正确生成
- `stub: true` 让 LLM / client 能识别「这是占位返回」避免误用
- `stage` 字段的版本标记让 stage 2/3 完工时容易 grep 验证替换
- `received_*` 字段保留参数 echo，方便 stage 2 调试 schema 反序列化

### 任务 6：写 ADR-0024（`docs/adr/0024-mcp-handler-module-split.md`）

**结构**：
- Status: Accepted（v0.15.0 阶段 1 落地）
- 背景：v0.7 落地 `src/mcp/handler.rs` 单文件 1156 行 17 tool。v0.15 cycle 加 15 tool 后会涨到 ~2000+ 行，违反单文件可读性原则（参考 v0.6 main.rs 拆 cli/ 子模块的对称操作）。
- 决策：拆 `handler.rs` → `handler/{mod.rs, cli.rs, inspect.rs, metrics.rs}`，子 module 边界按 brainstorm §v0.15 cycle 模块重构 段定（cli = cat 1+3 写操作，inspect = cat 2，metrics = cat 4）。
- 关键约束（决策 1 调研结论）：rmcp 0.11 `#[tool_router]` 只收集当前 impl 块内的 `#[tool]` 方法，不支持跨 module 收集。所以 32 个 `#[tool]` 方法都保留在 `handler/mod.rs` 单 impl 块里，子 module 只放 Args struct + helper 函数。
- 备选方案：
  - (a) 单文件保持（涨到 ~2000 行）— 否决：违反可读性，未来扩展更难
  - (b) 用 `ToolRouter::add` 合并多个子 module 的 router — 否决：boilerplate 多（每个子 module 独立 `#[tool_router]` impl + 主 mod 显式合并）
  - (c) 用 `SyncTool` / `AsyncTool` trait 模式 — 否决：每个 tool 独立 struct，boilerplate 最多
  - (d) 把 32 个 `#[tool]` 方法都搬进子 module 的 `impl ProcMcpHandler` 块，主 mod 用 `use cli::*; use inspect::*; ...` — 否决：rmcp 不收集子 module impl 块，编译失败
- 结果：子 module 独立编译 / stage 2/3 各 Slice 文件级隔离 / 主 mod.rs impl 块结构稳定（新加 tool 不动 17 既有 tool） / 净新增 ~250 行
- Migration path：v0.7 既有 17 tool 行为零回归（impl 块结构不变，只是文件物理位置改）；外部 client（Claude Desktop / Cursor）无感知
- 相关 ADR：ADR-0009（MCP server 设计）/ v0.6 main.rs → cli/ 子模块拆分（同款 surgical 原则）

**完成**：文件创建 + ~120 行 + Status Accepted。
