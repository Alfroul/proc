## 已知风险

### 风险 1：CI 测试策略的未知挂点（本地无法复现类）

1744 测试在 CI runner 的行为只能远端验证——除已取证的 `real_path_does_not_panic` 外可能还有本地绿 CI 挂/失败的测试（无 Docker / 无 GPU / 无 smartctl / 无模型 / 权限差异）。**缓解**：stage 1 摸底清单（自跳过类 vs 危险类）+ `timeout-minutes` 兜底 + stage 3 迭代预算；首次 push 后仍有红属预期范围非失败。

### 风险 2：msrv pin 的漂移复发

pin ~11 包后，未来任何 `cargo update` / 新依赖引入都可能再漂移（icu/image/time 是活跃链）。**缓解**：接受为常规维护（msrv job 就是漂移探测器）；msrv 处置 B（升 rust-version）是根治选项但放弃 1.85 口径——拍板点。

### 风险 3：rmcp ignore 的安全叙事（面试场景）

面试官可能问「为什么 audit 里有 ignore」。**缓解**：stage 1 暴露面评估写实（stdio 不监听 TCP / HTTP transport 使用面）+ TD 追踪 + ADR-0037 记录决策依据——有记录的工程判断经得起追问。

### 风险 4：macOS `--no-default-features` 编译性未知（macOS 选项 B 路径）

本地无 macOS 环境无法预验；若该档在 macOS 也编译不过，选项 B 落空需回退 C（移除 job）。**缓解**：stage 1 依赖图 + cfg 结构推演给概率判断；远端迭代兜底。（本风险仅当选 B 路径时成立）

### 风险 5：miri 修好后「跑什么」仍是开放问题

198 unsafe 全在 NT FFI 层，miri 不支持 Win32 调用——job 范围重定义（纯逻辑子集）可能让覆盖面很小，叙事上要诚实（与 unsafe-audit「miri 如实声明不可用」口径一致，不粉饰）。

### 风险 6：push 中间态红（窗口期观感）

stage 2 完工 push 后到全绿前的中间红 run 若被面试官/评估者看到略损观感。**缓解**：修复集中在一次 push + stage 3 快速迭代；badge 只在全绿后激活（README 无断言远端状态的既有纪律延续）。

## FAQ

### Q1: 本地已有 gate 脚本，为什么还要修远端 CI？

防线分层（v0.26 stage 2 设计）：gate 是本地自愿防线（pre-push opt-in），required checks 是远端强制防线——后者前提是 CI job 全绿，这正是 stage-2 doc 设置说明悬空兑现的原因。且 PR / 换机 / 协作场景只有远端防线兜底；badge 是评估者 10 分钟视图里「工程成熟度」的显性信号（v0.26 展示冲刺的最后一块占位）。

### Q2: check job 6h 挂死为什么是「实际工程问题」？

每次 push 到 master 都消耗一档 runner 6 小时（GitHub 免费额度内也占排队/并发额度），且 6h 里 5h50m 是纯挂死无任何输出——`timeout-minutes` 缺失是配置缺陷；根因测试（真实 WinVerifyTrust 调用在 runner 上挂死）属于「本地绿 ≠ CI 绿」的典型样本，CI 测试策略不修它还会撞下一个。

### Q3: msrv 失败为什么与 proptest 无关？

09-02 run 日志的 "requires rustc 1.86/1.88" 清单是 icu_*/image/serde_with/time/instability 等传递依赖，无 proptest——stage 2 声明「proptest 1.11.0 MSRV 1.85」正确；真因是 lockfile 里这些包的版本在 1.85 发布线之后升过了它的 MSRV（这些包自己升了 rust-version 声明）。

### Q4: macOS job 移除（选项 C）会不会自相矛盾（CI 矩阵里少一个平台）？

ADR-0022（v0.12 起 Windows-only）是已拍板平台决策——macOS job 的存在意义从来不是「支持 macOS」，而是「`--no-default-features` feature 卫生检查」。若该档在 macOS 也编不过（风险 4），job 的原始设计意图已失效，移除 + ADR 注记比维护一个永远红的 job 更诚实；亮点条「三 workflow」口径相应微调。

### Q5: 远端验证依赖 push，节奏怎么控？

push 是用户拍板项（手册「绝不允许」段）：stage 2 完工报告附「建议 push 验证」指令包，用户拍板后 push → stage 3 会话观察远端状态并迭代。若首 push 全绿则 stage 3 直接收尾；有红则按取证-修复循环处理（属 stage 3 预算内）。
