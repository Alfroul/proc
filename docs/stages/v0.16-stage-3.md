## 设计决策（stage 3 拍板）

### 决策 1：sidecar_present + source_healthy 双字段区分

`make_bookmarks_list_json` 返回 `sidecar_present: bool` + `source_healthy: bool` 两个字段，让 agent 区分 3 种状态：

| 状态 | sidecar_present | source_healthy | bookmarks |
|---|---|---|---|
| 录屏无 sidecar | `false` | `true`（没东西可校验）| `[]` |
| sidecar 存在 + fresh（size/mtime 匹配 + magic OK + 可反序列化）| `true` | `true` | loaded |
| sidecar 存在但 stale（size/mtime 不匹配 / 损坏 / magic 错）| `true` | `false` | `[]` |

**理由**：单 `sidecar_present` 字段无法区分「无 sidecar」与「sidecar 过期」——前者是正常状态（用户从未加书签），后者是异常状态（录屏被重写 / sidecar 与当前录屏不匹配）。agent 看到 `source_healthy: false` 时知道需要提醒用户「书签数据可能与当前录屏不一致」。

**实现路径**：
1. 录屏文件不存在 → `{ ok: false, error: "录屏文件不存在: <path>" }`（brainstorm §决策 6 路径安全）
2. `let sidecar_path = BookmarkFile::sidecar_path(path); let sidecar_present = sidecar_path.exists();`
3. `let file = BookmarkFile::try_load(path);`（返 `Option<BookmarkFile>`，区分 fresh vs stale）
4. `let (source_healthy, bookmarks) = match file { Some(f) => (true, f.bookmarks), None => (sidecar_present == false, vec![]) }` — 没 sidecar 时 source_healthy=true，有 sidecar 但 try_load 失败 source_healthy=false

### 决策 2：make_bookmarks_add 双路径 frame_idx 校验

`make_bookmarks_add_json(file_path, frame_idx, label, dry_run)` 入口先校验 frame_idx 范围，再调 `BookmarkFile::add`。

**校验路径**：
- VT100 路径（`is_vt100_file(path) == true`）：`frame_idx < VtPlayer::total_frames()`
- v3 路径：`frame_idx < Player::total_frames()`
- 校验失败 → `{ ok: false, error: "frame_idx=<N> 超出范围（总帧数=<M>）" }`（与 brainstorm §Q2 同款）

**timestamp_secs 提取**（v3 + VT100 双路径，参考 brainstorm §Q4）：
- v3 路径：`player.frame_at(frame_idx).timestamp`（直接取 UiFrame.timestamp）
- VT100 路径：从 `time_range_ms()` 内插
  ```rust
  let (start_ms, end_ms) = player.time_range_ms();
  let ts_secs = if total > 1 {
      let span = end_ms.saturating_sub(start_ms);
      let ts_ms = start_ms + span * (frame_idx as u64) / (total as u64 - 1);
      ts_ms / 1000
  } else {
      start_ms / 1000  // 单帧录屏：避免除零
  };
  ```

**label 默认值**（brainstorm §proc_bookmarks_add 入参段）：
- `label = Some(s)` 且 `s` 非空 → 用 s
- `label = None` / `Some("")` → 默认 `format!("书签 #{}", file.bookmarks.len() + 1)`（id 自增前的 len+1，与 stage 2 `add` 内部 id 算法一致）

**dry_run 路径**（brainstorm §决策 4 + brainstorm §proc_bookmarks_add）：
- `dry_run = true` → 仍调 `add`（计算 id + label）但**不写 sidecar**，返 `sidecar_written: false + dry_run: true`
- `dry_run = false` → 调 `add` + 写 sidecar，返 `sidecar_written: bool`

### 决策 3：sidecar 写失败兜底（替代 BookmarkFile::write 静默路径）

`BookmarkFile::write` 内部 `_ = std::fs::write(...)` 静默失败（[`src/record/bookmark.rs::write`](../../src/record/bookmark.rs)）。MCP 路径需要让 agent 知道写失败（brainstorm §决策 7）。

**实现**：handler/record.rs 加私有辅助 `write_sidecar(file: &BookmarkFile, prec_path: &Path) -> bool`：

```rust
fn write_sidecar(file: &crate::record::BookmarkFile, prec_path: &std::path::Path) -> bool {
    let text = match serde_json::to_string_pretty(file) {
        Ok(s) => s,
        Err(_) => return false,
    };
    let sidecar_path = crate::record::BookmarkFile::sidecar_path(prec_path);
    std::fs::write(sidecar_path, text).is_ok()
}
```

**失败时返回**（brainstorm §决策 7）：`{ ok: true, sidecar_written: false, warning: "..." }`——业务逻辑成功（in-memory BookmarkFile 已更新）+ 写盘失败警告，让 agent 决定是否重试。

### 决策 4：make_bookmarks_edit 先查后改（避免重复遍历）

`make_bookmarks_edit_json(file_path, id, label, dry_run)`：

1. 录屏文件不存在 → `ok: false + error`
2. `let mut file = BookmarkFile::load_or_empty(path);`
3. 找 bookmark by id → 找不到 `{ ok: false, error: "书签 id=<N> 不存在" }`（与 brainstorm §proc_bookmarks_edit 同款）
4. 记录 `old_label`（让 agent 看到改动 diff）
5. dry_run=true → 返 `ok: true, dry_run: true, sidecar_written: false, old_label, new_label`
6. dry_run=false → 调 `file.edit_label(id, new_label.clone())` + write

**注意**：`BookmarkFile::edit_label` 也返 bool（找到 / 没找到），但我们已经在 step 3 找过一次。这里仍调 `edit_label` 让它做实际修改（让 BookmarkFile API 保持纯净，不绕过它直接修改 bookmarks 字段）。

### 决策 5：make_bookmarks_delete 先查后删（保留被删 bookmark 信息）

`make_bookmarks_delete_json(file_path, id, dry_run)`：

1. 录屏文件不存在 → `ok: false + error`
2. `let mut file = BookmarkFile::load_or_empty(path);`
3. 找 bookmark by id → 找不到 `{ ok: false, error: "书签 id=<N> 不存在" }`
4. 记录 `frame_idx + label`（让 agent 知道删了什么——brainstorm §proc_bookmarks_delete 返回字段集）
5. dry_run=true → 返 ok + dry_run + sidecar_written: false + frame_idx + label
6. dry_run=false → 调 `file.remove(id)` + write

**理由**：delete 返 frame_idx + label 让 agent 在批量删除时能确认「这次删的是帧 100 的 'CPU 飙升' 书签」，避免误删。

### 决策 6：stage 3 不动 mod.rs 的 #[tool] 方法签名

与 stage 2 §决策 5 同款——`#[tool]` 方法体仍只 1-2 行调子 module helper，仅在 record.rs 子 module 替换 stub helper 为真实业务实现。impl 块结构稳定 → 既有 32 tool 零回归 + stage 1 已落地的 3 个真实业务 helper（replay_info / replay_search / eject_status）不动。

description 字符串 stage 1 已写完整字段说明（如 `proc_bookmarks_add` 的 description 已含 `dry_run` + `frame_idx` + `sidecar_written` 字段说明），stage 3 不改。

## 已知风险

### 风险 1：VT100 frame_idx 内插公式可能有 off-by-one

**低风险**：VT100 内插公式 `start_ms + (end_ms - start_ms) * frame_idx / (total - 1)` 在 total=1 时除零。

**mitigate**：if total > 1 走内插 / else 走 `start_ms / 1000`（单帧录屏 edge case，stage 3 决策 2 已写）。测试用例覆盖多帧 VT100。

### 风险 2：stale sidecar 测试触发 size/mtime 变化可能 flaky

**低风险**：与 `bookmark.rs::try_load_stale_returns_none_when_source_mtime_differs` 同款——mtime 测试需要文件系统精度足够。Windows 文件系统精度有时 1s。

**mitigate**：测试 sleep 1.1s 后改写源文件确保 mtime 真的变。或者改 size（写更长内容）触发 size 变化（不依赖 mtime）。

### 风险 3：load_or_empty 在文件不存在时仍返 empty BookmarkFile

**低风险**：`BookmarkFile::empty_for(prec_path)` 调 `std::fs::metadata`，失败时返 (0, 0) + 空 BookmarkFile——`add/edit_label/remove` 不会报错，会写入空 sidecar 到不存在路径下（write 失败但 is_ok 是 false）。

**mitigate**：handler 顶部先 `if !path.exists()` 校验，不让 load_or_empty 接触不存在路径。

### 风险 4：dry_run=true 时 file.add 已经把 in-memory BookmarkFile 改了

**低风险**：dry_run=true 路径里 `file.add(...)` 修改了 `file.bookmarks`，但因为不调 write_sidecar，sidecar 文件不变。dry_run=true 后 file 变量直接 drop，无副作用。

**mitigate**：dry_run=true 仍调 `add` 是为了让返回字段 `id` 是真实的下一个 id（不是 mock 值）。这是设计取舍——agent 看 id 才能知道「真正写入后会是 id=6」。

### 风险 5：测试 fixture 写真实 sidecar 文件可能与 BookmarkFile::write 不一致

**低风险**：测试用 `BookmarkFile::write` 写 sidecar fixture，但 handler 用 `write_sidecar`（自定义包装）。两者底层都是 `serde_json::to_string_pretty + std::fs::write`，但 BookmarkFile::write 失败静默。

**mitigate**：测试 fixture 调 `BookmarkFile::empty_for + add + write`（用业务模块自己的 API）；handler 用 `write_sidecar` 验证 MCP 路径错误透出。两条路径独立测试。
