## 已知风险与回退

**风险 1：stage 3 + stage 4 commit 拆分错误**
- 现状：stage 3 + stage 4 改动在 `src/replay/controller.rs` / `src/app.rs` / `src/tui/replay_panel.rs` 三文件里交织（搜索 + 倒放都在同几行附近），无法精准按 hunk 拆
- 缓解：方案 a 合并 stage 3 + stage 4 为一个 commit（推荐），commit message 注明合并即可；强拆 hunk 风险大于收益
- 回退：如选方案 b 拆 hunk 出错，`git reset --soft HEAD~1` 回退最近 commit 重新拆

**风险 2：REVIEW-v0.14 发现 P0（阻断 v0.14.0 发布）**
- 现状：stage 1-4 落地后基线 1242 passed / 0 failed / 3 ignored 全过，预计 P0 = 0
- 缓解：如出现 P0（如 v3 文件格式 bug / 兼容性破坏 / 测试失败），立即停 stage 5，fix P0 后再启 stage 5（与 v0.13 stage 3 同款规则——P0 阻断则 Review 不能完工）
- 回退：P0 fix 完成后重启 stage 5

**风险 3：REVIEW-v0.14 P1 数量超预期**
- 现状：预计 P1 集中在完整性段（CONTEXT / CHANGELOG / README / brainstorm 同步缺漏），与 v0.13 stage 3 同款模式
- 缓解：P1 修复不动业务代码（仅 docs/* 改动），P1 数量多也只是文档工作量，不影响 cycle 闭环
- 回退：如 P1 > 10（如出现 review 发现多个 hot path 设计问题），评估是否拆 stage 5a（Review + P1 修复）+ stage 5b（收尾 + tag）；默认 stage 5 单段完成

**风险 4：CHANGELOG 阶段汇总与各 stage doc 任务清单不一致**
- 现状：CHANGELOG `[Unreleased]` 段已经有 stage 1-4 简短条目（stage 1-4 落地时累加），stage 5 收尾段需整合 + 加 stage 5 阶段汇总 + 关键数字表
- 缓解：CHANGELOG 阶段汇总按 stage doc 验收标准对照（每个 stage 的「必须」段复制到 CHANGELOG 对应阶段）
- 回退：如发现 stage N doc 描述与 CHANGELOG 不一致，以 stage doc 为准（stage doc 是 stage 落地时的契约）

**风险 5：git tag v0.14.0 后发现严重 bug**
- 现状：stage 5 完工 → tag v0.14.0 → 用户 push → 发现严重 bug
- 缓解：v0.14.0 patch（v0.14.1）走快速 fix flow（参考 v0.12.1 / v0.12.2 patch 流程），不破 v0.14.0 tag
- 回退：v0.14.0 tag 不动（历史不可变），bug fix 走 v0.14.1 / v0.15.0

**回退策略**：stage 5 失败 → 不动 src/ 业务代码（stage 5 全程不动），仅回滚 docs/* 改动 + Cargo.toml / Cargo.lock + tag。`git reset --soft HEAD~1` 回退最近 commit 重新做 stage 5。
