### 决策 3：stub 返回格式（与 v0.15 stage 1 同款）

每个新 tool 的 stub helper 返 placeholder JSON：

```rust
pub fn make_replay_info_json(_file_path: &str) -> Value {
    json!({
        "ok": true,
        "stub": true,
        "stage": "v0.16-stage-2",
        "message": "proc_replay_info tool schema is registered; business logic lands in stage 2",
        "received_file_path": _file_path,
    })
}

pub fn make_replay_search_json(_file_path: &str, _query: &str, _limit: Option<usize>) -> Value {
    json!({
        "ok": true,
        "stub": true,
        "stage": "v0.16-stage-2",
        "message": "proc_replay_search tool schema is registered; business logic lands in stage 2",
        "received_file_path": _file_path,
        "received_query": _query,
        "received_limit": _limit,
    })
}

// bookmarks 4 个 stub helper 同款格式，stage 字段 "v0.16-stage-3"
```

理由（与 v0.15 stage 1 决策 4 同款）：
- `ok: true` 让 client（如 mcp-inspector）调用时不报错，能验证 schema 正确生成
- `stub: true` 让 LLM / client 能识别「这是占位返回」避免误用
- `stage` 字段的版本标记让 stage 2/3 完工时容易 grep 验证替换
- `received_*` 字段保留参数 echo，方便 stage 2 调试 schema 反序列化

### 决策 4：CONTEXT.md 新术语 4 个

- **McP RecordCategory**：v0.16 cycle 给 7 个新 tool 分的 3 档类别枚举（`Replay` / `Bookmarks` / `UsbStatus`），用于 stage 2/3 拆 Slice 时的工作量估算与子 module 边界对齐。Replay 类别（2 tool：info / search），Bookmarks 类别（4 tool：list/add/edit/delete），UsbStatus 类别（1 tool：eject_status）。
- **ReplaySearchQuery**：`proc_replay_search` tool 入参的 query 字符串类型文档化——`: <FilterExpr>` 走 `parse_frame` 路径（5 维度：timestamp / cpu / mem / name / anomaly.severity）/ 无 `:` 前缀走 `build_frame_substring_expr` substring 模式（regex escape 元字符）。与 v0.14 stage 3 落地的 `ReplaySearch.input` 同款契约。
- **BookmarkAction**：`proc_bookmarks_*` tool 的 action enum 文档化（`add` / `edit` / `delete`），让返回 JSON 的 `action` 字段在 CONTEXT 术语段有正式定义。dry_run=true 时 action 字段仍标 `add` / `edit` / `delete`（dry_run 是 modifier，不改 action 类型）。
- **EjectSuggestion**：`proc_eject_status` tool 返回的 `suggestion` 字段 4 档枚举（`eject_now` / `kill_locks` / `unknown_drive` / `unavailable`），让 agent 一眼看到下一步建议（解决「kill 进程后不知道是否成功」痛点）。

### 任务 4：写 ADR-0025a（`docs/adr/0025a-mcp-replay-search-agent-schema.md`）

**结构**（参考 ADR-0023 格式）：
- Status: Accepted（v0.16.0 阶段 1 落地）
- 背景：v0.14 stage 3 落地 FilterExpr FrameField 5 维度（timestamp / cpu / mem / name / anomaly.severity）+ apply_frame，TUI 路径有 ReplaySearch 状态机。v0.16 cycle 需要把这能力暴露给 LLM agent，agent 视角的 schema 设计候选：(a) 一次性返所有命中帧 / (b) 分页 / (c) limit 截断。
- 决策：选 (c) limit 默认 100 + truncated 字段 + match_count 字段。理由：分页（offset）让 agent 多次调用增加复杂度，一次性返所有可能 payload 过大（30min session × cpu>50 命中 5000+ 帧 × 500B = 2.5MB），limit 截断是折中——agent 大多数场景 100 帧够用，需要更多时调高 limit。
- 关键设计点：
  1. query 入口双路径：`: <FilterExpr>` 走 parse_frame / 无 `:` 走 build_frame_substring_expr（regex escape 元字符防注入）
  2. matches[] 字段含 frame_idx + timestamp + cpu_usage + memory_used + matched_processes[] + anomaly_severity
  3. VT100 录屏不支持 search（无结构化帧）返 ok=false + error
  4. 长录屏性能 ~9s/30min session 可接受（agent 一次性调用，与 brainstorm §proc_replay_search 性能段同款）
- 备选方案：
  - (a) 一次性返所有命中帧（否决：payload 过大风险）
  - (b) 分页 offset + limit（否决：agent 多次调用复杂，过早优化）
  - (d) 异步路径 + progress notification（否决：rmcp 0.11 progress notification 文档稀少，留 v0.17+ cycle 评估）
- 结果：agent 视角 schema 简单（limit + truncated）/ 与 proc_flows / proc_docker_events 同款 limit 模式 / 长录屏性能可接受
- Migration path：v0.14 TUI 路径不动；MCP 路径新增独立 helper
- 相关 ADR：ADR-0009（字段裁剪原则）/ v0.14 stage 3 落地的 FrameField 5 维度（CONTEXT.md 演进历史）

**完成**：文件创建 + ~150 行 + Status Accepted。

### 任务 5：写 ADR-0025b（`docs/adr/0025b-mcp-record-not-exposed.md`）

**结构**：
- Status: Accepted（v0.16.0 阶段 1 落地，决策 v0.16 cycle 不暴露 record）
- 背景：v0.15 brainstorm §主题 D2 锁定「D2 操作 + 录屏类（v0.16）：写操作（kill / docker-rm / monitor-add-remove）+ 录屏 v2（record / replay / bookmarks）」。其中 record 实装层面有 TTY 限制（v0.6 落地的 `R` 键录制走 `tui::setup_terminal() + tui::run_app()`，MCP server 是 stdio 单工无 TTY）。
- 决策：v0.16 cycle **不暴露** `proc_record_start` / `proc_record_stop`。7 tool 范围只覆盖 replay / bookmarks / usb_status（决策 1）。
- 理由（详见 brainstorm §决策 1）：
  1. 录屏需要 TTY（MCP stdio 无 TTY 是技术硬约束）
  2. 替代路径（worker 持续采样 SystemSnapshot → UiFrame → 喂 Recorder）工作量大且收益边际（agent 高频录屏不是典型场景）
  3. 录屏敏感数据保护（v0.6 落地的 pending_record_confirm 确认弹窗）需 MCP-level confirm 机制，留 v0.17+ cycle 评估
  4. agent 视角应聚焦「分析已有录屏」，用户视角负责「主动录屏」
- 备选方案：
  - (a) 暴露 record 走 TUI 子进程（否决：MCP stdio 无 TTY，子进程 spawn TUI 会失败）
  - (b) 暴露 record 走 worker 持续采样（否决：worker 与 MCP stdio 生命周期管理复杂 + 录制期间 ~5% CPU 影响主路径）
  - (c) 推迟到 v0.17+ cycle 评估（推荐，本 ADR 选此）
- 结果：v0.16 cycle 7 tool 范围（6 录屏 + 1 USB status）聚焦 replay/bookmarks/usb_status，cycle 内聚强；agent 视角与用户视角分工清晰
- Migration path：v0.17+ cycle 评估方案 (a) spawn 子进程 / (b) worker 持续采样 / confirm 机制设计
- 相关 ADR：ADR-0009（MCP server）/ brainstorm §决策 1（v0.16 cycle 范围排除 record 的理由）

**完成**：文件创建 + ~130 行 + Status Accepted。

## 已知风险

### 风险 1：rmcp tool_router 收集 38 个 tool 时编译失败

**低风险**：v0.15 stage 1 已验证 rmcp 0.11 可收集 32 个 tool，6 个新 tool（共 38）远低于 rmcp 限制（无文档化上限）。`cargo check` 编译通过即证伪此风险。

**mitigate**：如编译失败，stage 1 改设计为合并部分 tool（如 bookmarks 4 个合并为 1 个含 action enum 的 tool，参考 ADR-0023 inspect 合并思路）。但 brainstorm 已决策 4 个独立 tool（add/edit/delete 语义不同，schema 不同），优先按计划走。

### 风险 2：JsonSchema derive 在 ReplaySearchArgs 含 Option<usize> 字段

**低风险**：v0.15 cat 1 已大量使用 `Option<usize>`（FlowsArgs / DockerEventsArgs 等），rmcp 0.11 + schemars 0.8 已验证支持。

**mitigate**：如编译失败，改字段类型为 `Option<u64>`（与既有 `proc_metrics_disk_io` 的 `Option<String> device` 同款），但预期不需要。

### 风险 3：record.rs 子 module 与既有 `crate::record` 命名冲突

**低风险**：`src/mcp/handler/record.rs` 是 `crate::mcp::handler::record`，与 `crate::record`（[`src/record/`](../../src/record/)）是不同路径。Rust 模块系统天然区分。

**mitigate**：handler/record.rs 内部调 `crate::record::Player::open(...)` / `crate::record::BookmarkFile::load_or_empty(...)` 用全限定路径，避免 `use crate::record::*;` 与本子 module 名字冲突。

### 风险 4：CONTEXT.md 术语名歧义（"McP RecordCategory"）

**低风险**：v0.15 cycle 已用 `McpToolCategory`（cat 1/2/4 三档），v0.16 加 `McP RecordCategory`（replay/bookmarks 两档）容易混淆。

**mitigate**：术语描述段明确「McP RecordCategory 是 v0.16 cycle 子集分类，与 v0.15 McpToolCategory 不重叠（v0.15 类别不含 record 子 module）」。或考虑改名为 `McpRecordSubcategory` / `RecordToolCategory` 让区分更明显——本 stage 1 doc 选 `McP RecordCategory` 是与 v0.15 术语对称，stage 4 Review 时若发现混淆可统一改名。
