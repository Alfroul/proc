## 任务清单

### 1. 加 criterion dev-dependency

**文件**：`Cargo.toml`

- `[dev-dependencies]` 段加 `criterion = "0.5"`（最新稳定版，含 plotters / itertools 默认 feature；如与 Rust MSRV 1.85 冲突则降到 `criterion = "0.4"` 并在 stage doc 注明）
- `[profile.bench]` 段（如不存在则新建）：`lto = "thin"` + `codegen-units = 1`（与 release 对齐，避免 benchmark 数字与 release 行为不一致）

**验证**：`cargo bench --no-run` 编译通过（不真跑）。

### 2. 创建 `benches/` 目录 + 6 个 benchmark 文件

**目录结构**：
```
benches/
├── bench_rebuild_sorted_cache.rs   # 搜索 + 排序 hot path
├── bench_refresh_heavy.rs          # HeavyWorker 单轮（sysinfo 全量重采）
├── bench_tui_draw.rs               # ratatui TestBackend 单帧渲染
├── bench_record_serialize.rs       # UiFrame bincode 序列化
├── bench_filter_expr_apply.rs      # EvalCtx / NetworkEvalCtx apply
└── bench_search_hot_path.rs        # 搜索按键 → rebuild 全链路
```

每个 benchmark 文件结构：
- `criterion_group!` + `criterion_main!`（criterion 标准入口）
- 每个被测函数写 3 档 fixture：100 / 500 / 1000 进程
- 使用 `criterion::black_box` 防止优化器消除
- `Throughput::Elements(process_count)` 标注让 criterion 输出 per-element 数字

### 3. 写 fixture builder（共用模块）

**文件**：`benches/common/mod.rs`（或内联到每个 bench 文件，按复杂度决定）

- `fn make_processes(n: usize) -> Vec<ProcessInfo>` — 生成 n 个 fake ProcessInfo（pid 1..n / random cpu_usage / random memory / Arc 化 name / 含 parent_chain）
- `fn make_filter_expr() -> FilterExpr` — 构造典型 FilterExpr AST（`cpu > 5 AND name =~ /chrome/`）
- `fn make_ui_frame(processes: Vec<ProcessInfo>) -> UiFrame` — 构造典型录屏帧（含 cpu_history / mem_history / processes）

**关键**：fixture 不能依赖运行时环境（不调 sysinfo / 不读真实进程），完全 fake 数据。这让 benchmark 在任何机器 / CI 都能跑（虽然按决策表 B 不在 CI 跑，但本地复现性要保证）。

### 4. 写 6 个 benchmark

#### 4.1 `bench_rebuild_sorted_cache.rs`
- 测 `src/app.rs::rebuild_sorted_cache` 全链路（pid_to_idx 构建 + sort + filter）
- 两档 query mode：Substring (`chrome`) / FilterExpr (`cpu > 5 AND name =~ /chrome/`)
- fixture：100 / 500 / 1000 进程
- 对照 v0.6 stage 6 实测（38.2 µs / 6.1 µs）

#### 4.2 `bench_refresh_heavy.rs`
- 测 HeavyWorker 单轮（`src/collect.rs::HeavyWorker::run_poll_loop` 抽出单次迭代）
- 不调真实 sysinfo，mock 一组 ProcessInfo 后跑「Arc clone + parent_chain 批量 + query_throttle_batch mock」链路
- fixture：100 / 500 / 1000 进程
- 关注点：每周期堆分配次数（criterion `Throughput::Bytes` 配合 alloc counter，或先用时间代理）

#### 4.3 `bench_tui_draw.rs`
- 测 `src/tui/` 单帧 `draw` 调用（用 ratatui `TestBackend`，不依赖终端）
- 5 个 panel 各一个 case：process_table / port_table / monitor_sidebar / docker_panel / detail_view
- fixture：500 进程的 SystemSnapshot
- 关注点：format! 风暴（process_table.rs:71-159）+ handles to_lowercase（detail_view.rs:69-72）

#### 4.4 `bench_record_serialize.rs`
- 测 `bincode::serialize(&ui_frame)` 单帧序列化
- fixture：100 / 500 / 1000 进程的 UiFrame（含 cpu_history + mem_history + processes）
- 关注点：长 session（30min+ = 1800 frames × 1000 进程）的累计 IO 成本

#### 4.5 `bench_filter_expr_apply.rs`
- 测 `FilterExpr::apply(&EvalCtx)` / `apply_network(&NetworkEvalCtx)` 各种表达式
- case：(a) `cpu > 5`（单 field 比较）(b) `name =~ /chrome/i`（regex）(c) `cpu > 5 AND mem > 100mb`（复合）(d) `sni in ("a", "b", "c", ...)`（HashSet lookup，v0.12 阶段 5 TD-29 落地）
- fixture：500 进程 / 500 flows

#### 4.6 `bench_search_hot_path.rs`
- 测搜索按键 → rebuild_sorted_cache 全链路（覆盖 SearchState 增量 + rebuild + render）
- case：query 长度 1 / 10 / 50（验证 v0.6 stage 6 增量 lowercase 优化）
- fixture：500 进程

## 注意事项

### A. criterion 版本兼容性
- 默认装 `criterion = "0.5"`。若与 Rust MSRV 1.85 冲突（criterion 0.5 要求 Rust 1.70+，应该 OK），降到 `0.4` 并在 stage doc 注明
- 避免 `criterion = "0.6"`（如已发布）—— 锁版本避免 cycle 中途大版本变更

### B. fixture 不能依赖运行时环境
- 所有 fixture 用 fake 数据（不调 sysinfo / 不读真实进程 / 不依赖 admin 权限）
- 这让 benchmark 在 user / CI / developer 机器上数字有可比性

### C. benchmark 不进 CI
- 决策表 B：criterion 在 GitHub Actions 共享 runner 抖动大，仅本地手跑
- 后续如要做 performance guard，考虑 self-hosted runner 或 release 前手跑

### D. 不优化、只测
- 本 stage 严禁任何「顺手优化」——哪怕看到明显的 format! 风暴也不要改
- 优化留给 stage 3+，本 stage 只建 baseline
- 任何优化冲动 → 写到 stage 2 报告的「候选优化点」清单

> ### 数字环境
> - **CPU**: 13th Gen Intel(R) Core(TM) i7-13700HX（16 cores / 24 threads / 2.1 GHz base）
> - **RAM**: 16 GB（16,886,128,640 bytes）
> - **Machine**: Acer Predator PHN16-71（笔记本）
> - **OS**: Microsoft Windows 11 家庭中文版（Version 10.0.26200.8037，64-bit）
> - **Rust**: rustc 1.95.0 (59807616e 2026-04-14) / cargo 1.95.0 (f2d3ce0bd 2026-03-21)
> - **release profile**: lto=thin, codegen-units=1, opt-level=3
> - **bench profile**: lto=thin, codegen-units=1（与 release 对齐）
> - **测试时间**: 2026-07-04
> - **criterion 版本**: 0.5
> - **测试机器负载状态**: 默认后台（无主动 CPU 重负载）
> - **sample_size**: 100（criterion 默认）；warmup 3s；measurement 5s

### 1. `bench_rebuild_sorted_cache` — 搜索 + 排序 hot path

| fixture | mean | low | high | throughput |
|---|---|---|---|---|
| substring/100 进程 | 28.60 µs | 27.77 µs | 29.38 µs | 3.50 Melem/s |
| substring/500 进程 | **116.38 µs** | 114.74 µs | 118.03 µs | 4.30 Melem/s |
| substring/1000 进程 | 234.18 µs | 230.86 µs | 237.39 µs | 4.27 Melem/s |
| filter_expr/100 进程 | 28.33 µs | 27.16 µs | 29.30 µs | 3.53 Melem/s |
| filter_expr/500 进程 | **130.57 µs** | 128.08 µs | 133.00 µs | 3.83 Melem/s |
| filter_expr/1000 进程 | 272.50 µs | 264.68 µs | 280.91 µs | 3.67 Melem/s |

**对照 v0.6 stage 6 实测**：500 进程 substring 38.2 µs（v0.6 老数字，仅 sort）。本次 substring/500 = 116.38 µs（含 filter + pid_to_idx + sort 完整链路，比 v0.6 仅 sort 多了 2 步）。**注意：不是回归** —— v0.6 数字是「sort only」阶段实测，本次是「rebuild_sorted_cache 全链路」，两者口径不同。

### 2. `bench_refresh_heavy` — HeavyWorker 单轮 parent_chain 批量

| fixture | mean | low | high | throughput |
|---|---|---|---|---|
| 100 进程 | **1.380 ms** | 1.366 ms | 1.393 ms | 72.5 Kelem/s |
| 500 进程 | **8.567 ms** | 8.415 ms | 8.712 ms | 58.4 Kelem/s |
| 1000 进程 | **16.473 ms** | 16.230 ms | 16.710 ms | 60.7 Kelem/s |

**显著发现**：parent_chain 批量构建（v0.11 阶段 5 落地的 R17 评分依赖）在 1000 进程下达 **16.5 ms** —— 接近 16.6 ms 帧预算（60 FPS），每周期 1 次开销沉重。每进程平均 16.5 µs（build_parent_chain 遍历链 + clone Vec<(u32, String)>）。**这是侦察报告疑点 5「parent_chain 每周期 clone 到 Vec」的实测验证**，stage 2 应作为 top 优化候选。

### 3. `bench_tui_draw` — ratatui TestBackend 单帧渲染

| fixture | mean | low | high | throughput |
|---|---|---|---|---|
| 100 进程 | **1.098 ms** | 1.085 ms | 1.113 ms | 91.0 Kelem/s |
| 500 进程 | **3.021 ms** | 2.975 ms | 3.074 ms | 165.5 Kelem/s |
| 1000 进程 | **5.621 ms** | 5.531 ms | 5.717 ms | 177.9 Kelem/s |

**对照 v0.6 stage 8 实测**：draw < 15 ms（用户无感）。本次 1000 进程 5.6 ms 远低于 15 ms 阈值 —— **TUI 渲染层 format! 风暴（侦察报告疑点 2）不是瓶颈**，至少在 1000 进程档不阻塞主线程。ratatui diff 够用，无需 v0.6 stage 8 主动放弃的脏矩形优化。

### 4. `bench_record_serialize` — UiFrame bincode 序列化

| fixture | mean | low | high | throughput |
|---|---|---|---|---|
| serialize/100 进程 | 2.369 µs | 2.312 µs | 2.426 µs | 42.2 Melem/s |
| serialize/500 进程 | 8.711 µs | 8.592 µs | 8.830 µs | 57.4 Melem/s |
| serialize/1000 进程 | **13.991 µs** | 13.869 µs | 14.128 µs | 71.5 Melem/s |
| deserialize/100 进程 | 10.171 µs | 10.139 µs | 10.206 µs | 9.83 Melem/s |
| deserialize/500 进程 | 74.606 µs | 71.121 µs | 77.504 µs | 6.70 Melem/s |
| deserialize/1000 进程 | **160.36 µs** | 155.78 µs | 165.14 µs | 6.24 Melem/s |

**长 session 累计 IO 成本**（侦察报告疑点 6）：30min session × 0.5 FPS（30 frame/s 录屏）× 1000 进程 = 1800 × 14 µs ≈ **25 ms 总 serialize 时间**。**完全可忽略**。但 deserialize（reader 路径）开销约 serialize 的 5-12 倍 —— replay 时如需 seek 多帧，可能成为体验瓶颈。stage 2 评估。

### 5. `bench_filter_expr_apply` — FilterExpr apply 4 类表达式

| case | mean | low | high | throughput |
|---|---|---|---|---|
| (a) `cpu > 5`（500 进程）| 19.123 µs | 18.709 µs | 19.573 µs | 26.2 Melem/s |
| (b) `name =~ /chrome/i`（500 进程）| **126.11 µs** | 124.46 µs | 127.65 µs | 3.96 Melem/s |
| (c) `cpu > 5 AND mem > 100mb`（500 进程）| 35.608 µs | 34.558 µs | 36.672 µs | 14.0 Melem/s |
| (d) `sni in (...)` HashSet（500 flows）| 84.692 µs | 83.162 µs | 86.564 µs | 5.90 Melem/s |

**regex 路径最慢**（126 µs vs cpu_gt 19 µs，6.6x）—— regex::Regex is_match 在 500 进程上每进程约 250 ns。这是 v0.7 阶段 4 落地 FilterExpr 的固有开销，不在 stage 3+ 优化范围（regex crate 自身优化空间有限）。HashSet lookup 路径（v0.12 阶段 5 TD-29 落地）在 500 flows 上 85 µs ≈ 170 ns/flow —— O(1) contains 在中等规模下表现良好。

### 6. `bench_search_hot_path` — 搜索按键 → filter 全链路

| query 长度 | mean | low | high | throughput |
|---|---|---|---|---|
| len_1（"c"）| 37.587 µs | 35.279 µs | 39.502 µs | 13.3 Melem/s |
| len_10（"cccccccccc"）| 100.36 µs | 98.841 µs | 101.94 µs | 4.98 Melem/s |
| len_50（"c" × 50）| 70.809 µs | 68.980 µs | 72.601 µs | 7.06 Melem/s |

**注意 len_50 < len_10**（70 µs < 100 µs）—— 因为 len_50 query `cccc...c`（50 个 c）在进程名 `chrome.exe` 上 `contains` 提前返回 false（chrome 只含 1 个 c），name_lower.contains 很快结束；len_10 query `cccccccccc` 同样不命中 chrome，但每次 contains 比对多 5-10 字符后才放弃。**v0.6 stage 6 增量 lowercase 优化在 ASCII 输入下确实生效**（每按键约 30-100 µs 全链路，远低于 16.6 ms 帧预算）。

### 关键洞察

1. **真瓶颈 1：parent_chain 批量**（16.5 ms @ 1000 进程）—— 接近 16.6 ms 帧预算，每周期 1 次沉重。stage 2 优先级 #1。
2. **假瓶颈：TUI format! 风暴**（5.6 ms @ 1000 进程）—— 远低于 15 ms 阈值，不是 stage 3+ 优化目标。
3. **假瓶颈：录屏 serialize**（14 µs @ 1000 进程）—— 完全可忽略。
4. **假瓶颈：搜索按键**（70-100 µs）—— 远低于帧预算。
5. **关注点：regex FilterExpr**（126 µs @ 500 进程）—— 中等开销，scaling 看进程数。stage 2 评估是否值得动 regex crate 调用方式（如预编译缓存）。

stage 2 报告会基于这些数字 + 侦察报告 5 个疑点，按 ROI 排序产出 stage 3+ 优化清单。
