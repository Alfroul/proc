## 任务清单

### 1. 加 criterion dev-dependency

**文件**：`Cargo.toml`

- `[dev-dependencies]` 段加 `criterion = "0.5"`（最新稳定版，含 plotters / itertools 默认 feature；如与 Rust MSRV 1.85 冲突则降到 `criterion = "0.4"` 并在 stage doc 注明）
- `[profile.bench]` 段（如不存在则新建）：`lto = "thin"` + `codegen-units = 1`（与 release 对齐，避免 benchmark 数字与 release 行为不一致）

**验证**：`cargo bench --no-run` 编译通过（不真跑）。

### 2. 创建 `benches/` 目录 + 6 个 benchmark 文件

**目录结构**：
```
benches/
├── bench_rebuild_sorted_cache.rs   # 搜索 + 排序 hot path
├── bench_refresh_heavy.rs          # HeavyWorker 单轮（sysinfo 全量重采）
├── bench_tui_draw.rs               # ratatui TestBackend 单帧渲染
├── bench_record_serialize.rs       # UiFrame bincode 序列化
├── bench_filter_expr_apply.rs      # EvalCtx / NetworkEvalCtx apply
└── bench_search_hot_path.rs        # 搜索按键 → rebuild 全链路
```

每个 benchmark 文件结构：
- `criterion_group!` + `criterion_main!`（criterion 标准入口）
- 每个被测函数写 3 档 fixture：100 / 500 / 1000 进程
- 使用 `criterion::black_box` 防止优化器消除
- `Throughput::Elements(process_count)` 标注让 criterion 输出 per-element 数字

### 3. 写 fixture builder（共用模块）

**文件**：`benches/common/mod.rs`（或内联到每个 bench 文件，按复杂度决定）

- `fn make_processes(n: usize) -> Vec<ProcessInfo>` — 生成 n 个 fake ProcessInfo（pid 1..n / random cpu_usage / random memory / Arc 化 name / 含 parent_chain）
- `fn make_filter_expr() -> FilterExpr` — 构造典型 FilterExpr AST（`cpu > 5 AND name =~ /chrome/`）
- `fn make_ui_frame(processes: Vec<ProcessInfo>) -> UiFrame` — 构造典型录屏帧（含 cpu_history / mem_history / processes）

**关键**：fixture 不能依赖运行时环境（不调 sysinfo / 不读真实进程），完全 fake 数据。这让 benchmark 在任何机器 / CI 都能跑（虽然按决策表 B 不在 CI 跑，但本地复现性要保证）。

### 4. 写 6 个 benchmark

#### 4.1 `bench_rebuild_sorted_cache.rs`
- 测 `src/app.rs::rebuild_sorted_cache` 全链路（pid_to_idx 构建 + sort + filter）
- 两档 query mode：Substring (`chrome`) / FilterExpr (`cpu > 5 AND name =~ /chrome/`)
- fixture：100 / 500 / 1000 进程
- 对照 v0.6 stage 6 实测（38.2 µs / 6.1 µs）

#### 4.2 `bench_refresh_heavy.rs`
- 测 HeavyWorker 单轮（`src/collect.rs::HeavyWorker::run_poll_loop` 抽出单次迭代）
- 不调真实 sysinfo，mock 一组 ProcessInfo 后跑「Arc clone + parent_chain 批量 + query_throttle_batch mock」链路
- fixture：100 / 500 / 1000 进程
- 关注点：每周期堆分配次数（criterion `Throughput::Bytes` 配合 alloc counter，或先用时间代理）

#### 4.3 `bench_tui_draw.rs`
- 测 `src/tui/` 单帧 `draw` 调用（用 ratatui `TestBackend`，不依赖终端）
- 5 个 panel 各一个 case：process_table / port_table / monitor_sidebar / docker_panel / detail_view
- fixture：500 进程的 SystemSnapshot
- 关注点：format! 风暴（process_table.rs:71-159）+ handles to_lowercase（detail_view.rs:69-72）

#### 4.4 `bench_record_serialize.rs`
- 测 `bincode::serialize(&ui_frame)` 单帧序列化
- fixture：100 / 500 / 1000 进程的 UiFrame（含 cpu_history + mem_history + processes）
- 关注点：长 session（30min+ = 1800 frames × 1000 进程）的累计 IO 成本

#### 4.5 `bench_filter_expr_apply.rs`
- 测 `FilterExpr::apply(&EvalCtx)` / `apply_network(&NetworkEvalCtx)` 各种表达式
- case：(a) `cpu > 5`（单 field 比较）(b) `name =~ /chrome/i`（regex）(c) `cpu > 5 AND mem > 100mb`（复合）(d) `sni in ("a", "b", "c", ...)`（HashSet lookup，v0.12 阶段 5 TD-29 落地）
- fixture：500 进程 / 500 flows

#### 4.6 `bench_search_hot_path.rs`
- 测搜索按键 → rebuild_sorted_cache 全链路（覆盖 SearchState 增量 + rebuild + render）
- case：query 长度 1 / 10 / 50（验证 v0.6 stage 6 增量 lowercase 优化）
- fixture：500 进程

## 注意事项

### A. criterion 版本兼容性
- 默认装 `criterion = "0.5"`。若与 Rust MSRV 1.85 冲突（criterion 0.5 要求 Rust 1.70+，应该 OK），降到 `0.4` 并在 stage doc 注明
- 避免 `criterion = "0.6"`（如已发布）—— 锁版本避免 cycle 中途大版本变更

### B. fixture 不能依赖运行时环境
- 所有 fixture 用 fake 数据（不调 sysinfo / 不读真实进程 / 不依赖 admin 权限）
- 这让 benchmark 在 user / CI / developer 机器上数字有可比性

### C. benchmark 不进 CI
- 决策表 B：criterion 在 GitHub Actions 共享 runner 抖动大，仅本地手跑
- 后续如要做 performance guard，考虑 self-hosted runner 或 release 前手跑

### D. 不优化、只测
- 本 stage 严禁任何「顺手优化」——哪怕看到明显的 format! 风暴也不要改
- 优化留给 stage 3+，本 stage 只建 baseline
- 任何优化冲动 → 写到 stage 2 报告的「候选优化点」清单
