## 候选方向评估（拍板会话 2026-08-22）

### 方向 1：GBNF 开关 vs 更强模型（优先级 1）

**数据依据**（`docs/eval/e2b-70q-v0.22.md`）：output_degraded 21/70（30%），典型形态是 proc_finish 语法泄漏成正文 + `<eos>` 重复循环——「收尾语法」而非「调工具」是 E2B 最大瓶颈（tool 通道排除退化/环境后 ~85% 正常）。

**GBNF 路径（零代码）**：

- 开关即配置：`agent.toml [llama-cpp] grammar_file = "tool_call"`（`src/agent/builder.rs:83` 已接线 → `CompleteOptions.grammar` → llama-server 请求体 `grammar` 字段）
- grammar 内容（`src/agent/grammars/tool_call.gbnf`）强制输出 `{"tool_calls":[{"name":...,"arguments":...}]}` JSON 形状——与 `tool_choice=Required` + proc_finish 循环语义上兼容（所有输出本来就是 tool call JSON，proc_finish 是其中之一）
- **关键风险（未验证）**：v0.20 stage 3a 只验证过「grammar 字段真实生效」（极简 `root ::= "yes"` 实验）+ 规则名 bug 修复，**grammar + tools 协议 + Required + proc_finish 的完整 agent 循环从未实测**。潜在坑：llama-server 对 grammar 与 tools 同时传递的解析优先级、长 answer 文本在 grammar string 规则下的表现、退化是否会转移形态（如 JSON 内字段退化）
- **验证路径**：QUICK 26 条冒烟先行（~19m）→ 链路兼容再挂 FULL；失败则降级（关 GBNF，记录实验结论归档）

**更强模型路径（需下载）**：

- 本地库存实测确认：仅 `gemma4-e2b`（Q4_K_M 2.9G）+ `gemma4-e2b-uncensored`（社区微调非能力升级）两变体——复测必须下载
- 候选（Q4_K_M 量级）：

| 候选 | 权重大小 | RAM/VRAM 估算 | 预期收益 | 备注 |
|---|---|---|---|---|
| Gemma 4 E4B | ~3GB | 宽裕（16GB 机器稳） | 退化↓ + wrong_tool 部分↓ | 同家族，GGUF 模板/`--jinja` 路径兼容性最有把握 |
| Qwen 7-8B | ~4.5GB | 宽裕 | wrong_tool↓ + chain_incomplete↓（多步规划） | 异家族，模板需冒烟验证 |
| Qwen 14B | ~9GB | **紧张**：权重+KV+系统+TUI 接近 16GB 上限（有 CUDA 时主要吃 VRAM，取决于显卡容量） | 同上更明显 | 慢（query 均时或上探 90-120s → FULL ~2h+）；是否可行取决于用户 GPU VRAM |

- 同时改善 wrong_tool 10 + chain_incomplete 7（L2 多步规划是 E4B/14B 相对 E2B 的主要能力跃迁点）
- 时长外推（观察 4 校准）：E2B 40.6s/query → FULL 47m；更大模型按比例上探，QUICK 实测后再外推 FULL

**两路正交零 harness 改动**：改一个变量（grammar 开关 or `--model`）跑 FULL + `--compare eval-e2b-70q.json new.json` 即出对比列。**这是「数据驱动决策」cycle 的自然延续——v0.22 建好测量层，v0.23 用测量层选路**。

**唯一可能的代码改动点**：`EvalRunMeta` 目前不记录 grammar/prompt 版本（只有 provider/model/attempts/max_steps/git_describe）——多变量实验矩阵需要 run meta 或文件名能区分变量。零代码方案 = 文件名区分（`eval-gbnf-70q.json` / `eval-e4b-70q.json`）；代码方案 = meta 加 ~20 行字段 + 测试。拍板点。

### 方向 3：proc_record_start/stop agent 侧支持（优先级 3，~100 行）

**连续推迟史**：v0.21 决策 8（confirm 通道落地后成本 ~100 行）→ v0.22 决策 6（零 tool 变更干净基线）。**v0.22 基线已落，原推迟理由弱化**：

- **本会话新证据**：recording 场景 5 条 query（L0 2 + L1 2 + L2 1）的 expected_tools 全是 `proc_replay_info` / `proc_replay_search` / `proc_bookmarks_list`——**零 query 依赖 proc_record_start/stop**，且 catalog 47 名单不变（两 tool 早在名单内，只是 dispatch 返「不支持」）。**落地对 70q 基线零影响**——「catalog 一变数据不可比」的顾虑对本项实际不成立
- eval 走 complete 路径无 confirm 通道，写 tool 一律 blocked JSON → record tool 在 eval 里永远不真实执行，基线天然稳定

**工程范围**：

- 现状：`src/agent/tools/dispatch.rs:225` `execute_confirmed_tool` 对两 tool 返 err_json「需要跨调用子进程保活的持久状态」；`confirm_summary` 文案已就位（dispatch.rs:126-127）
- 落地：AgentSession 层（TUI 长生命周期会话）持有 record handle 跨 tool 调用保活（参考 ADR-0029 record_handle pattern + MCP 层 `proc mcp` 既有实现）；CLI ask 单轮路径继续拦截（进程退出录制即死，返回「仅 TUI 会话支持」）
- **语义边界（需单独设计，~半天）**：录制范围（agent 调 record_start 时刻起录整个终端屏幕？）/ 停止时机（模型显式调 proc_record_stop / 会话 teardown 自动 stop 落盘防孤儿 / Ctrl+D 退出时） / 录制中用户继续对话的行为
- 规模：业务 ~100 行 + 语义设计 + 测试 ~150-250 行（TUI session 端到端 + 孤儿录制清理 + CLI 拦截不变）

### 方向 4：prompt 措辞优化（优先级 4，~0 行文本）

**素材**（两处实证）：

1. **L2 反问缺参 4 条**（#19/#25/#26/#29「请提供盘符/PID/路径」）——合理行为但 eval 记失败（expected 链未走）。system.md 可加引导：「缺参时先尝试无参/列表 tool 枚举可用对象（如 proc_eject_status 列出所有盘），不要直接反问用户」
2. **写操作发现链措辞敏感**（REVIEW-v0.21 观察 3 + v0.22 归档 #21：模型直接声明「我不能执行系统操作」不走 proc_help 发现链）——现 system.md line 20「写操作（kill / 删容器 / 释放 USB）已被平台拦截：在答案里解释影响并给出等价 proc 命令行」**可能诱导模型跳过发现链直接文字解释**。措辞改向：「需要执行写操作时，先 proc_help 找到对应 tool 并调用；被拦截后在答案里解释并给等价命令行」

**与方向 1 正交可组合，但实验设计需变量隔离**——一次只变一个变量（否则归因不清）。prompt v2 单独出一列对比（一次 FULL 47m）或作为「最优配置组合验证」最后一列。

**风险**：prompt 是所有 query 的公共变量——改坏会全局回归（v0.20 stage 3b 实测教训：few-shot 示例导致 E2B 角色扮演编造数据，最终全删）。修订稿需小步（上述 2 处）+ QUICK 冒烟 + FULL 验证，不大改结构。

### 方向 5：RAG 历史经验召回（方向 B，v0.20 既定 v0.23+）

- 数据源已就位（session JSONL 留档），但**模型底座未定**——方向 1/2 的结论（GBNF 是否默认开 / 默认模型选谁）是 RAG 的前置：RAG 召回注入会增大 context 负担，在 E2B 能力边界（L2 5%）下收益存疑，配更强模型才可能兑现
- 规模 ~1500 行+（检索方案选型：keyword / 本地 embedding / 简化 SQL；注入位置与预算；评估口径）——完整 cycle 主题
- **建议 v0.24 主体**，v0.23 出「最优配置」决策作为其底座

### 方向 6：Multi-agent 协作（方向 D）

- v0.20 brainstorm 原文「推迟 v0.23+」，v0.22 说法「v0.24+ 既定」——**本文件澄清：v0.24+，且排在 RAG（方向 B）之后**（协作 agent 的价值依赖单 agent 能力上限先拉满）
- 本 cycle 不动

## 已知风险（按拍板后范围定稿）

### 风险 1：GBNF 与 tools 协议链路不兼容

**问题**：grammar + tool_choice=Required + proc_finish 完整循环从未实测；llama-server 对两者同传的解析优先级未知；退化可能转移形态（JSON 字段内退化）。
**mitigate**：QUICK 26 条冒烟先行；不兼容即关开关 + 负结果归档（本身有价值）；`is_degraded_output` 不依赖语法形态，退化转移仍可检测。

### 风险 2：新模型模板/启动参数不兼容——**已排除**

决策 2 拍板不下载，本 cycle 无新模型列。条目保留备查：v0.24+ 下载更强模型时重新启用（Qwen 系模板与 Gemma 不同需 QUICK 冒烟；14B 在 16GB 机器可能 swap）。

### 风险 3：prompt 修订全局回归

**问题**：prompt 是公共变量，改坏全局（v0.20 few-shot 教训）。
**mitigate**：只做 2 处小修不动结构；QUICK 冒烟对比；FULL 验证；git 可即时回滚（prompt 是编译进 binary 的 include_str，回滚 = revert + rebuild）。

### 风险 4：record 跨调用保活的生命周期边界

**问题**：录制中会话 teardown / Ctrl+D / panic 的孤儿录制进程；CLI ask 单轮路径语义（进程退出录制即死）。
**mitigate**：teardown 自动 stop 落盘（复用 App::shutdown 防孤儿模式）；CLI ask 维持拦截文案改「仅 TUI 会话支持」；测试覆盖孤儿清理路径。

### 风险 5：实验矩阵挂机时长的用户负担

**问题**：3 次 FULL（GBNF 列 / prompt v2 列 / 组合终验列）总挂机 ~2.5h（按 E2B 基线 47m/次外推）。
**mitigate**：漏斗式矩阵（决策 5）已是最低次数；QUICK 冒烟实测均时后再外推 FULL；结果 JSON 每 query 实时落盘中途崩不丢；GBNF 冒烟失败则矩阵缩为 2 次（prompt v2 + 终验）。

### 风险 6：TD-56 model ID 404 修复打断对照跑——**已排除**

决策 3 拍板不跑 Sonnet 对照，TD-55~57 继续 open。条目保留备查：有 key 后跑对照时重新启用（`DEFAULT_MODEL` 404 时按 error body 调一次，~5 行）。

## FAQ

### Q1: 为什么 v0.23 不直接做 RAG（v0.20 不是排了 v0.23+ 吗）？

**A**: 排期是滚动的（v0.20「v0.22+」→ v0.22 记录「v0.23+」），但实质理由是依赖：RAG 注入增大 context 负担，在模型能力上限未拉满（E2B L2 5%）且最优配置未定（GBNF 开不开 / 默认模型是谁）前做 RAG，收益无法归因。v0.23 出「最优配置」决策，v0.24 RAG 才有干净底座。

### Q2: GBNF 为什么不直接改默认开，还要实验？

**A**: (1) 链路兼容性未验证（风险 1）；(2) eval 基线纯净原则——v0.22 基线是 GBNF off 跑的，对比列必须同口径先出数据；(3) 退化若转移形态（JSON 字段内），「消灭泄漏」的预期不成立。数据说话后再改默认（决策 4）。

### Q3: 提案 1 工程量这么少，够格一个 cycle 吗？

**A**: cycle 的交付物不限于代码——v0.23（提案 1）交付的是**决策数据 + 归档 + 配置定优**，与 v0.22 交付「测量层」是同一主线的两段。若嫌轻，提案 2 加 record 工程补饱满。纯挂机段（阶段 3）会话工作少的问题由阶段拆分缓解（挂机前的矩阵设计 + 挂机后的归档分析都是会话工作）。

### Q4: record_start/stop 落地为什么不破 eval 基线？

**A**: 三层原因：(1) 70 query 中零条 expected 依赖这两个 tool（recording 场景 expected 全是 replay/bookmark）；(2) catalog 47 名单不变（两 tool 早已在册，只是 dispatch 行为从「不支持」变真实执行）；(3) eval 走 complete 路径无 confirm 通道，写 tool 永远 blocked——行为变更在 eval 口径下不可见。

### Q5: 实验变量为什么不一次全组合？

**A**: 全组合 = 2(GBNF) × N(模型) × 2(prompt) 次 FULL，挂机爆炸且多数组合无决策价值。漏斗式：单变量列定各自增益 → 最优组合终验一列（即默认配置候选）。
