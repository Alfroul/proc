### 阶段 1：ADR-0018 + Schannel ETW schema 调研

> **独立会话指令**：`阅读 CONTEXT.md 和 docs/stages/v0.10-stage-1.md，完成所有任务后确认完成`
>
> **预测性 doc**：实际启动时再细化。

**目标**：产出 v0.10.0 cycle 设计文档（ADR-0018）+ 调研 Schannel ETW event 196 schema + 跑通最简 Schannel session 验证框架。

**前置依赖**：v0.9.0 已 tag（ProcessFlow 已有 sni / ja4 / bytes 字段，Windows 用户也想有这能力）。

**任务清单**（预测）：

1. **写 ADR-0018**（`docs/adr/0018-windows-schannel-sni.md`）
   - Status: Accepted
   - Context: Windows 没有 eBPF，但 ETW `Microsoft-Windows-Schannel` event 196 含 SNI 字段（Win10 1809+）。复用 v0.7 阶段 7 disk_io_etw 手写 ETW 框架
   - Decision: 手写 windows-rs ETW Schannel session（不引 schannel-rs），event 196 解析 SNI + 关联 PID
   - Alternatives: schannel-rs crate（不维护）；FiddlerCore（商业）；网络栈 WinDivert（性能差，需驱动签名）
   - Consequences: 仅 Win10 1809+；event 196 schema 非文档化需逆向

2. **event 196 schema 调研**
   - Win10 1809+ Schannel 加了 event 196（Operations 196 = `EventId_SslServerCertBinding`）
   - 用 `logman query providers Microsoft-Windows-Schannel` 看 provider
   - 用 `xperf -on ProcThread -f kernel.etl` + 触发 TLS handshake → 解析 ETL 看 event 196 真实 schema
   - 字段（社区逆向）：PEB ProcessId / ServerName (UTF-16 LE) / CertificateHash / ...

3. **复用 disk_io_etw 框架**
   - `src/disk_io_etw/{mod.rs,provider.rs,thread_map.rs}` 的 ETW session + ProcessTrace + EventRecordCallback 模式
   - 阶段 2 抽公共 ETW 框架到 `src/etw_common/`（如阶段 1 估为 1 天则不做，留 v0.10.1）
   - 推荐先复用粘贴（surgical），不抽公共

4. **跑通最简 Schannel session**
   - `src/schannel_etw/{mod.rs,provider.rs,parser.rs}`（骨架）
   - StartTraceW 开 Schannel session
   - OpenTraceW + ProcessTrace 阻塞
   - callback 收 event 196 → 打印 raw UserData hex
   - 触发 curl https://example.com → 看 callback 输出

**验收标准**：
- ADR-0018 文件存在，Status: Accepted
- event 196 schema 字段已记录（offset / 类型 / 编码）
- 最简 Schannel session 跑通，curl 触发后 callback 打印 event 196 hex

**容量预估**：~400 行（ADR 200 + 骨架 200），工具调用 30-50 次。
