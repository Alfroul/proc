## 设计决策（本阶段拍板）

### 决策 1：项 1 P2-R1 try_clone 简化方案 — 单次 try_clone + expect（panic 语义保留）

`make_record_start_json` 当前 line 1099-1103：

```rust
.stdout(std::process::Stdio::from(
    log_file.try_clone().unwrap_or_else(|_| log_file.try_clone().unwrap()),
))
```

stage 2 改为单次 `try_clone` + `expect`（保留 panic 语义 — 让 try_clone 真失败时 MCP server 重启而非悄悄走错路径）：

```rust
let stdout_log = log_file
    .try_clone()
    .expect("try_clone log_file 失败（fd 耗尽？）");
cmd.stdout(std::process::Stdio::from(stdout_log))
    .stderr(std::process::Stdio::from(log_file));
```

**理由**（vs REVIEW-v0.17 建议的 fallback inherit）：try_clone 失败时 inherit 子进程 stdout 会污染 MCP stdio transport（agent 解析 JSON-RPC 失败），比 panic 更糟。expect 让真失败时 server 重启，与原 unwrap_or_else(unwrap) 行为等价但去掉双重 fallback 冗余。

### 决策 2：项 2 varint 切换 — header 永远 fixint + frame/footer 按 version 选 config

`bincode::deserialize(&header_buf)` （reader.rs:69）保持不变 — header 永远走 fixint 让 reader 拿到 `header.version` 后再分支。`options_for_version(version >= 4)` 切换 varint 只影响 frame + footer 序列化（writer/reader 已用 options_for_version，无需改动）。

| version | header | frame/footer |
|---|---|---|
| 1 / 2 / 3 | fixint | fixint（兼容层，旧文件可读）|
| 4+（v0.18 新文件）| fixint | **varint**（新文件 size 更小 ~10-15%）|

`RecordingFooter::header_version` 字段记录 header.version（镜像一份），sanity check 仍走 fixint footer 自身字段（footer 用 options_for_version(version) 序列化 → v4 文件 footer 是 varint）。

### 决策 3：项 4 auto-stop — `shutdown.rs` 加 `request()` 函数 + timer thread spawn

`shutdown.rs` 当前只有 `init()`（注册 Ctrl+C handler）+ `requested()`（poll flag）。stage 2 加 `request()` 函数让 timer thread 主动 flip flag：

```rust
pub fn request() {
    if let Some(flag) = FLAG.get() {
        flag.store(true, Ordering::SeqCst);
    }
}
```

`run_record_headless` 去 `_duration` 下划线前缀 + 在 `crate::shutdown::init()` 后插入：

```rust
if let Some(secs) = duration {
    std::thread::spawn(move || {
        std::thread::sleep(std::time::Duration::from_secs(secs));
        crate::shutdown::request();
    });
}
```

**与 brainstorm 决策 4 拍板对齐**：子进程 timer 随 child 退出自动终止（无 zombie timer）+ MCP handler 不持 timer 状态（timer 在子进程内）+ 复用 v0.6 落地的 `shutdown::requested()` 干净退出路径。

`make_record_start_json` spawn 时加 `.arg("--duration").arg(secs.to_string())`（如 `duration_secs` Some）+ **移除 warning 字段**（line 1135-1139，auto-stop 已实装不需 warning）。

### 决策 4：项 3 SubscribePushWorker 注册表 value — `Peer<RoleServer>` 替换 `()`

stage 1 Spike 用 `Arc<Mutex<HashMap<SubscriberId, ()>>>` 占位。stage 2 调研 rmcp 0.11 源码确认：

- `RequestContext<RoleServer>::peer` 字段是 `pub`（`Peer<RoleServer>` = `ClientSink` type alias）
- `SubscribeRequestParam { pub uri: String }` 只有 uri，**无 subscriber_id 字段**（client 不需要传 ID，server 自己分配 / 用 uri 作 key）
- `Peer::notify_resource_updated(&self, ResourceUpdatedNotificationParam { uri }) -> Result<(), ServiceError>` 是 push API

**stage 2 注册表设计**：

```rust
pub struct SubscribePushWorker {
    /// 注册表：uri → Peer<RoleServer>
    /// stdio transport 单 client 假设；SSE 多 client 待 v0.19+ cycle 升级为 Vec<Peer>
    subscribers: Arc<Mutex<HashMap<String /* uri */, Peer<RoleServer>>>>,
    /// push task 是否已 spawn（防重复 spawn，lazy spawn 第一次 subscribe 时）
    task_spawned: Arc<Mutex<bool>>,
}
```

stage 1 Spike 的 `SubscriberId = u64` type alias **保留**（re-export 仍工作，未来 SSE multi-client 落地时复用作 internal id）。

### 决策 5：项 3 `ResourceRoute` trait `subscribe`/`unsubscribe` 签名调整

stage 1 Spike stub 签名 `fn subscribe(&self, uri: &str, subscriber_id: u64) -> Result<(), String>`。stage 2 调研结论：rmcp SubscribeRequestParam 无 subscriber_id，所以 subscriber_id 参数无用。**签名改为**：

```rust
fn subscribe(&self, uri: &str, peer: Peer<RoleServer>) -> Result<(), String>;
fn unsubscribe(&self, uri: &str) -> Result<(), String>;
```

`ProcMcpHandler` impl 时调 `self.subscribe_push_worker.subscribe(uri, peer)` / `unsubscribe(uri)`。`ServerHandler::subscribe` impl（rmcp 强制签名）内部把 `(request.uri, context.peer)` 转交给 `ResourceRoute::subscribe`。

### 决策 6：项 3 push task spawn 策略 — lazy spawn + tokio::spawn

第一次 client subscribe 时 lazy spawn 1s tick push task（避免无 subscriber 时空跑 worker）。push task 用 `tokio::spawn`（proc 已在 tokio runtime 上下文 — `run_mcp_serve` block_on）持 `Arc::clone(&subscribers)`，1s tick 遍历调 `peer.notify_resource_updated`。peer.push 失败（client 断开）→ 从注册表移除（drop Arc<Peer> 让 push task 下 tick 不再调）。

push task 进程退出时自动 cancel（tokio runtime shutdown 时所有 task cancel）— 无需显式 shutdown signal。`SubscribePushWorker::shutdown` 方法保留（stage 1 Spike no-op，stage 2 仍 no-op，预留未来 graceful shutdown）。

### 决策 7：项 3 push task 执行 — 单 worker 单 task（不 spawn 多个）

每个 SubscribePushWorker 实例 spawn **一个** push task（不是每个 subscribe 一个），task 内部 1s tick 遍历注册表所有 subscriber。理由：

- 与 brainstorm 决策 3「1s tick 遍历注册表 push 增量」描述对齐
- 多 task 同 tick 会让 client 收到并发 notify（rmcp 内部 serialize，但增加 lock contention）
- 单 task 与 v0.17 stage 3 `run_snapshot_worker`（单 worker 单 thread）模式延续
