#### 1.1 代码质量审查

- `benches/common/mod.rs` fixture builder：

## 注意事项

### A. 本 stage 不优化、只 Review
- 与 stage 2 同款规则：本 stage **不动业务代码**
- 看到任何「顺手优化」冲动 → 写到 P2 清单，归档 tech-debt 留 v0.14+
- Review 报告产出后 → 输出 stage 4 启动指令包 → 硬停止，等用户启动 stage 4

### B. 方案 c 的特殊性
- v0.13 cycle 是「性能验证 cycle」，stage 1-2 不动业务代码
- 因此 stage 3 Review 范围比 v0.12 stage 6（合并 Review + 收尾）小很多
- P0 应该 = 0；P1 集中在完整性（CONTEXT 演进历史 / stage docs ✅ / README banner / CHANGELOG）
- P2 大概率是「建议 v0.14 cycle 加 bench 覆盖 port_table / monitor_sidebar 等」

### C. P0 / P1 / P2 判定标准
- **P0**：阻断 v0.13.0 发布（如：bench 编译失败 / Cargo.toml 版本冲突 / 关键文档缺失）
- **P1**：cycle 内闭环（如：CONTEXT 演进历史漏行 / stage doc ✅ 标记漏 / PERF-BASELINE 数字 stddev 标注不一致）
- **P2**：归档 v0.14+（如：未覆盖的 hot path bench / TD-47 parent_chain 优化建议）
