### 阶段 5：切片 D — BoringSSL / LibreSSL 兼容（symbol offset 表）

> **独立会话指令**：`阅读 CONTEXT.md 和 docs/stages/v0.9-stage-5.md，完成所有任务后确认完成`

**目标**：扩展阶段 2 的 OpenSSL uprobe 到 BoringSSL（Chrome / Android / 部分云原生）和 LibreSSL（OpenBSD）。维护一个 symbol offset 表，运行时自动选择。

**前置依赖**：v0.9 阶段 2-3 已完成（OpenSSL 路径已跑通）。

**任务清单**（预测）：

1. **BoringSSL symbol 调研**
   - BoringSSL 是 Google 维护的 OpenSSL fork，Chrome / Android / gRPC 默认
   - `SSL_write` symbol 命名相同，但 offset 可能不同
   - 装包：`apt install libboringssl-dev` 或从源码 build
   - 调研：BoringSSL 是否仍以 `SSL_write` 命名导出？offset 与 OpenSSL 几？

2. **LibreSSL 调研**
   - LibreSSL 是 OpenBSD fork，部分 Linux 发行版（Alpine 早期）也用
   - 同上调研

3. **symbol offset 表**（`src/ebpf/compat.rs` 新文件）
   ```rust
   pub enum TlsLib {
       OpenSSL { version: TlsVersion },  // 1.0 / 1.1 / 3.x
       BoringSsl,
       LibreSsl,
   }
   
   pub struct TlsLibSpec {
       pub lib_path: &'static str,        // /usr/lib/.../libssl.so.3
       pub ssl_write_offset: u64,         // symbol offset
       pub ssl_read_offset: u64,
       pub detection_magic: &'static [u8], // ELF 文件 hash 用于识别
   }
   
   pub fn detect_tls_lib(pid: u32) -> Option<TlsLibSpec> {
       // 读 /proc/<pid>/maps 找 libssl.so.* 或 libboringssl.so
       // 比对 magic hash 返回 TlsLibSpec
   }
   ```

4. **运行时多 uprobe attach**
   - 进程启动时 detect_tls_lib(pid) → 选择对应 spec
   - 对每个发现的 TLS lib 路径，attach 一个 uprobe 实例
   - 多 uprobe 共享同一个 ring_buf，event 里带 lib_type 字段区分

5. **测试**（`tests/test_tls_compat.rs`）
   - mock detect_tls_lib 返回不同 spec，验证 attach 行为
   - 集成测试（可选）：装 BoringSSL + Chrome，跑 proc flows → curl https://example.com + chromium https://example.com → 两个 flow 都有 SNI

**验收标准**：
- detect_tls_lib 能识别 OpenSSL / BoringSSL / LibreSSL 三种
- 每个 lib 跑通 uprobe（手动测试）
- compat.rs 表完整

**容量预估**：~500 行（detect + spec table + multi-attach 300 + 测试 200），工具调用 30-50 次。**注意**：BoringSSL / LibreSSL 实际安装可能复杂，可以视进度决定是否做完整集成测试，或只做 detect 逻辑 + 文档标注「手动验证留 v0.9.1」。
