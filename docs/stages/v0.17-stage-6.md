## 设计决策（本阶段拍板，stage 7 不动 record / usb / docker-rm 路径策略）

### 决策 1：eject_device 走 PowerShell Shell.Application COM，不引入 unsafe windows-sys + IOCTL_STORAGE_EJECT_MEDIA

**问题**：`proc_usb_release` 第三步是物理弹出设备。Windows API 有两个常见路径：
- (a) `IOCTL_STORAGE_EJECT_MEDIA` DeviceIoControl（unsafe windows-sys 调用 + 句柄管理）
- (b) PowerShell `Shell.Application` COM `InvokeVerb('Eject')`（与既有 `flush_write_cache` 同款 PowerShell 路径）

**决策**：选 (b) PowerShell Shell.Application COM。理由：

1. **与 flush_write_cache 同款**：保持 stage 6 USB release 三步链路技术栈一致（全 PowerShell 路径），未来如切换 native Windows API 三步同时切换
2. **避免 unsafe 调用 + 句柄管理**：IOCTL_STORAGE_EJECT_MEDIA 需要 CreateFileW 打开 `\\.\E:` 卷句柄 + DeviceIoControl + CloseHandle，含大量 unsafe 块；PowerShell 路径走 `run_with_reduced_privileges` 已有抽象
3. **shell 集成体验更好**：InvokeVerb('Eject') 触发 shell 弹出动词，与右键菜单「弹出」同款路径，Windows 系统托盘会显示「安全弹出」通知
4. **阻塞行为可接受**：InvokeVerb 内部等待系统弹出完成，通常 < 5s（锁占用 / 缓存刷盘未完成时可能等到 30s+），agent 调用一次完成，与 brainstorm §风险 5 mitigate 同款可接受范围

**实装**（`src/eject/shell_eject.rs:14-49`）：

```rust
pub fn eject_device(drive_letter: char) -> Result<()> {
    let script = format!(
        "$ErrorActionPreference='Stop'; \
         $shell = New-Object -ComObject Shell.Application; \
         $drive = $shell.Namespace(17).ParseName('{letter}:'); \
         if ($null -eq $drive) {{ Write-Error ...; exit 1; }}; \
         $drive.InvokeVerb('Eject'); \
         Start-Sleep -Milliseconds 500",
        letter = drive_letter
    );
    let output = run_with_reduced_privileges("powershell", &[..., &script])
        .map_err(|e| ProcError::usb_detect_with("执行 eject_device PowerShell 失败", e))?;
    if !output.status.success() { return Err(...); }
    Ok(())
}
```

**与 brainstorm §决策 9 + §FAQ Q1 对齐**：用户设计偏好「一次完成 kill + flush + eject」，PowerShell COM 路径让三步链路技术栈一致。

### 决策 2：spawn 子进程用 CREATE_NEW_PROCESS_GROUP 让 proc_record_stop kill 触发干净退出

**问题**：`proc_record_start` spawn `proc record --no-tui` 子进程，`proc_record_stop` 需要让子进程：
- 优雅退出（VtRecorder::stop flush 写盘 + flush_recording_bookmarks 写 sidecar）
- 不要被 hard kill（TerminateProcess）导致 .prec 文件 footer 缺失

Windows 上 `std::process::Child::kill()` 调用 TerminateProcess（hard kill，无机会 cleanup）。需要另一种信号让子进程的 `shutdown::requested()` flag 翻转 → run_record_headless 主循环退出 → VtRecorder::stop flush。

**决策**：spawn 时加 `CREATE_NEW_PROCESS_GROUP`（0x0000_0200）flag 让子进程进入独立进程组，但 `child.kill()` 仍走 TerminateProcess（无可避免）+ wait 最多 10s 让子进程的 shutdown handler 触发。

**关键设计点**：

1. **CREATE_NEW_PROCESS_GROUP 让子进程独立 Ctrl+C 信号**：避免 MCP server 收到 Ctrl+C 时连带杀子进程
2. **kill + wait 10s**：`child.kill()` 发 TerminateProcess，但子进程的 VtRecorder writer 线程在每帧 `file.flush()` 后立即写盘（见 `src/record/vt100.rs:292`），所以 hard kill 不会丢已写帧，仅丢失「最后一帧 + footer metadata」（Vt100 文件格式无 footer，VtPlayer::open 读全部帧即可）
3. **退出码 + metadata_warning**：`make_record_stop_json` 读 VtPlayer::open 失败时返 `metadata_warning` 字段让 agent 知道 .prec 文件可能损坏

**与 ADR-0029 §决策 1 + §决策 4 对齐**：spawn 子进程复用 v0.6 业务逻辑 + 子进程崩溃隔离。

### 决策 3：headless 路径用 ratatui TestBackend + 120x40 默认尺寸

**问题**：`proc record --no-tui` 子进程在 MCP stdio 环境下没有 TTY，需要一种方式让 ratatui 在内存中渲染。VtRecorder::try_capture 需要 ratatui `Buffer`（屏幕 cell 数据）。

**决策**：用 `ratatui::backend::TestBackend::new(120, 40)` + `Terminal::new(backend)`，与 TUI 路径同款 `terminal.draw(|f| layout::draw(f, &app))` 调用，但渲染到 TestBackend 内存 buffer 而非实际 terminal。

**关键设计点**：

1. **TestBackend 在 ratatui 0.29 公共 API**（`ratatui::backend::TestBackend`）—— 无需 test feature 启用
2. **120x40 默认尺寸**：与 mcp-inspector 默认终端尺寸接近，replay 视觉合理（120 列容纳完整进程表 / 40 行容纳 30 行 process list + 工具栏 + 帮助页）
3. **5 FPS tick（200ms）**：与 VtRecorder::MIN_CAPTURE_MS = 200ms 对齐，每 tick try_capture 一帧（VtRecorder 内部判断 200ms 节奏）
4. **shutdown::requested() 干净退出**：headless 路径每 tick 检查 shutdown flag，true 时 break + VtRecorder::stop + flush_recording_bookmarks

**与 brainstorm §风险 4 mitigate 对齐**：`--no-tui` 重构成本 ~75 行（vs 预估 ~50 行，多 25 行用于 CREATE_NEW_PROCESS_GROUP + 文件路径处理）。

### 决策 4：confirm + dry_run 双参数互补（ADR-0029 决策 5 落地）

**问题**：v0.7 `proc_kill` / `proc_pkill` + v0.15 `proc_monitor_add` / `proc_monitor_remove` + v0.16 `proc_bookmarks_add` / `edit` / `delete` 都用 `dry_run: bool` 默认 false 契约。v0.17 cycle stage 6 加 `confirm: bool` 必传参数，agent 视角可能混淆。

**决策**（与 ADR-0029 §决策 5 对齐）：

| 参数 | 语义 | 适用场景 | 默认值 |
|---|---|---|---|
| `dry_run: bool` | 「不真正执行」（预演）| 可逆写操作（kill 进程可重启 / monitor_add 可 remove / bookmarks_add 可 delete）| `false`（agent opt-in `dry_run=true` 预演）|
| `confirm: bool` | 「确认风险后再执行」| 不可逆破坏性操作（录屏捕获屏幕 / kill + flush + eject 三步 / 删容器 / 删镜像 / 删卷）| **必传**（无默认值，agent 必须显式 `confirm=true`）|

**适用范围**（5 个 stage 6 tool）：
- `proc_record_start`（confirm 必传）—— 录屏捕获屏幕所有内容含 DNS 域名 / 进程 cmd
- `proc_usb_release`（confirm 必传 + dry_run opt-in）—— kill + flush + eject 三步破坏性
- `proc_docker_rm` / `proc_docker_image_rm` / `proc_docker_volume_rm`（confirm 必传）—— 删除容器 / 镜像 / 卷（不可逆）
- `proc_record_stop`（**confirm 不必传**）—— lifecycle 操作（停止录屏非破坏性，仅 kill child + flush）

**实装模式**：

```rust
if !confirm {
    return super::err("confirm=true 必传以确认...");
}
```

所有 5 个 helper 在第一行 confirm gate，confirm=false 时返 `{ ok: false, error: "confirm=true 必传..." }`，让 agent 知道需要确认。

### 决策 5：prune_children 当前未区分，warning 字段透出

**问题**：`proc_docker_image_rm` 接受 `prune_children: Option<bool>` 参数，但 bollard `RemoveImageOptions` 仅 `force` + `noprune` 字段（不区分子镜像）。

**决策**：当前实装接受 `prune_children` 参数但不真正区分（bollard API 限制），如 agent 显式传 `prune_children=true` 在返回 JSON 加 `warning` 字段说明当前未区分，让 agent 知道此参数被记录但未影响行为。

**与 brainstorm §风险 6 mitigate 对齐**：confirm vs dry_run 语义差异 + 参数语义明确性 mitigate。prune_children 留 v0.18+ cycle 评估（如 bollard 升级暴露 `prune_children` 真正字段或走 docker CLI 子进程路径）。

### 决策 6：warnings 数组透出 USB release 三步诊断

**问题**：`proc_usb_release` 三步链路（kill_locks → flush_write_cache → eject_device），任一步失败继续后续步骤（flush 失败仍尝试 eject），让 agent 看到完整诊断。但单 `error` 字段不足以承载多步失败信息。

**决策**：返 `warnings: Vec<String>` 数组累积所有步骤的失败原因：

```rust
let mut warnings: Vec<String> = Vec::new();
// flush
let flushed = match flush_write_cache(letter) {
    Ok(()) => true,
    Err(e) => {
        warnings.push(format!("flush_write_cache({drive_label}) 失败: {e}"));
        false
    }
};
// eject（flush 失败仍尝试 eject）
let ejected = match eject_device(letter) {
    Ok(()) => true,
    Err(e) => {
        warnings.push(format!("eject_device({drive_label}) 失败: {e}"));
        false
    }
};
```

返回 JSON 含 `flushed: bool` / `ejected: bool` / `warnings: [...]`，agent 一眼看到「哪步成功 / 哪步失败 + 失败原因」。

**与 ADR-0029 §决策 5 对齐**：confirm=true 让 agent 确认风险后执行，warnings 让 agent 看到执行诊断。

## 已知风险

### 风险 1：kill child 用 TerminateProcess 可能丢失最后一帧 + footer

**问题**：Windows `child.kill()` 走 TerminateProcess（hard kill），子进程的 VtRecorder::Drop impl 不会运行（进程内存直接释放）。Vt100 文件格式无 footer（每帧 length-prefixed + 立即 flush），所以已写帧不丢，但「最后一帧」（kill 信号时刚序列化但未写盘的）可能丢。

**mitigate**：
- VtRecorder writer 线程在每帧 `file.flush()` 后 fetch_add frame_count（见 `src/record/vt100.rs:292`），保证已 fetch_add 的帧必然已 flush 写盘
- `make_record_stop_json` wait 10s 给子进程最长优雅退出窗口
- 如 wait 10s 超时 → 强 wait 兜底
- `metadata_warning` 字段透出 .prec 损坏可能性

### 风险 2：PowerShell COM 弹出阻塞超过 30s

**问题**：`eject_device` 调用 PowerShell `InvokeVerb('Eject')` 内部等待系统弹出完成，锁占用 / 缓存刷盘未完成时可能等到 30s+。MCP tool 调用阻塞 30s 可能让 client timeout。

**mitigate**：
- agent 调用前应先调 `proc_eject_status` 确认 locks 空 + flush 完成
- ADR-0029 + brainstorm §风险 5 同款可接受范围（agent 一次性调用，与 `proc_replay_search` ~9s/30min session 同款）
- v0.18+ cycle 评估加 timeout 参数让 agent 自定义等待

### 风险 3：subprocess stdout/stderr 重定向 .prec.log 文件可能磁盘满

**问题**：`proc_record_start` 把子进程 stdout/stderr 重定向到 `<file>.prec.log`。如子进程输出大量日志（tracing），磁盘可能满。

**mitigate**：
- run_record_headless 内部子进程不调 tracing 订阅（只调 app.tick + try_capture，无 tracing 输出）
-panic 信息走 ratatui TestBackend 不写 stdout
- v0.18+ cycle 评估加 logrotate（与 v0.6.0 阶段 3 tracing-appender 同款）

### 风险 4：context overflow（brainstorm §决策 8 mitigate）

**问题**：stage 6 工作量 ~1100 行（实际），在容量上限 1500 行的 73% 内。本会话已消耗较多上下文读文档。

**mitigate**：
- 实装前已读完所有依赖文档（CONTEXT / brainstorm / stage 5 / ADR-0029 / 相关源文件）
- 任务清单按顺序执行，每个任务完工后立即验收
- 如上下文剩余 < 30% 触发 Checkpoint 机制（生成 `docs/handoff-stage-6-checkpoint.md`）

### 风险 5：bollard RemoveImageOptions 不支持 prune_children

**问题**：`proc_docker_image_rm` 接受 `prune_children: Option<bool>` 参数，但 bollard 0.18 `RemoveImageOptions` 仅 `force` + `noprune` 字段（不区分子镜像）。

**mitigate**：
- 决策 5 文档化此限制 + warning 字段透出
- v0.18+ cycle 评估（如 bollard 升级暴露字段或走 docker CLI 子进程路径）
