## 候选方向评估（拍板会话 2026-08-24）

### 方向 1：更强模型底座（决策 2 既定推 v0.24，RAG 的核心前置）

**为什么是核心前置**：RAG 召回注入增大 context 负担，在 E2B 能力边界（L2 full-chain 5%）下收益存疑是 v0.22 以来的既定判断；模型底座先定，RAG 的收益归因才有干净基线（决策 2 原文理由）。双负结论后模型升级是**唯一剩余杠杆**。

**硬约束实测（本会话）**：RTX 4050 Laptop **6GB VRAM**（空闲 5.9GB）+ 16GB RAM。

| 候选 | 权重（Q4_K_M） | VRAM 判定 | 预期收益（对照失败直方图） | 兼容性风险 |
|---|---|---|---|---|
| **Gemma 4 E4B** | ~3GB | ✅ 宽裕（权重 + KV + ctx 8192 稳） | output_degraded↓（更大模型 token 泄漏概率降）+ wrong_tool 部分↓ | **最低**——同家族，GGUF 模板 / `--jinja` / `--reasoning off` 启动路径在 E2B 已验证（LlamaServerHandle stage 3a 三处实测更正的成果直接复用） |
| **Qwen 系 7-8B** | ~4.5GB | 🔶 偏紧可行（KV + TUI + 系统负载余量小，QUICK 实测再定 FULL） | wrong_tool↓ + chain_incomplete↓（7-8B dense 相对 4B effective 是能力档跃迁，L2 多步规划主要改善点） | **中**——异家族：chat template 不同需 QUICK 冒烟；thinking mode 开关语义与 Gemma 的 `--reasoning off` 是否等效未验证 |
| Qwen 14B | ~9GB | ❌ **超出 6GB VRAM 排除**（partial offload 大幅降速，query 均时或上探 90-120s+ → FULL 2h+） | — | — |

（v0.23 brainstorm 候选表更新：14B 行按本会话 VRAM 实测排除。）

**归因方法论**：E4B vs E2B 是**最干净的单变量**（同家族同模板，纯模型规模差）；Qwen vs Gemma 混合家族 + 模板 + 规模三重变量——若 E4B 增益已显著超带，无需 Qwen 列即可拍板；E4B 落带内时 Qwen 列才成为「更大杠杆」的第二次机会。**漏斗式**：E4B 先行，Qwen 按条件触发。

**验证路径**（每步有判定标准，GBNF 冒烟判定的方法论延续）：

1. 下载（用户操作，~3GB）→ `agent.toml` / `--model` 切换
2. **QUICK 26 条冒烟**（~19-30m，均时实测后外推 FULL）：判定链路兼容（模板渲染 / tool_calls 解析 / proc_finish 提取 / 内存占用实测）+ query 均时 → 外推 FULL 时长
3. **FULL 70q 单列**（`eval-e4b-70q.json`，预计 47m-1.5h）→ `--compare eval-e2b-70q.json` 出对比列
4. **按方差带标尺拍板**：净通过差 ≥ +7（显著超带）且 L2 full-chain 有方向性改善 → 换默认（agent.toml 推荐值 + README）；落带内 → 维持 E2B 默认 + 数据归档（负结果同样有价值：E4B 档位不够，Qwen 列决策输入）

**成本**：下载 3-4.5GB（单）/ ~7.5GB（双）+ 挂机 QUICK + FULL 1-2 列。**不下载的后果**：RAG 主体重评（见提案 3 与风险 1）。

### 方向 2：RAG 历史经验召回主体（方向 B，v0.20 既定 → 决策 7 锚定 v0.24）

**一句话**：把历史会话中的成功经验（query → tool 链 → 结论）检索出来注入 agent context，让 agent「见过一次就会第二次」。

**数据源现状（本会话实测，诚实评估）**：

| 语料 | 现状 | 优势 | 劣势 |
|---|---|---|---|
| session JSONL（`~/.config/proc/sessions/`） | 53 文件 / 83K（~3 天） | 真实用户会话，天然持续增长；结构化（SessionEvent 10 kind + 时间戳） | **量薄 + 经验密度低**（开发期测试对话为主）；TextDelta 已聚合但答案质量未筛 |
| eval run JSON（本地 3 run × 70q） | 已留存，结构化干净 | passed query 自带 expected/actual_tools 链——**现成的「成功经验」格式**；零采集成本 | **eval 语料自我污染风险**（见风险 3——对同一 queries.toml 跑 RAG-on 等于检索答案） |

**规模 ~1500 行+**（v0.23 既定预估），三个设计维度（brainstorm 级倾向，stage 1 ADR-0034 定稿）：

**(a) 检索方案选型**——倾向 **keyword 评分（零 deps）**：

| 方案 | 依赖 | 规模 | 判定 |
|---|---|---|---|
| keyword（子串 + 词频评分，BM25-lite） | **+0** | ~150-250 行 | ✅ 倾向——语料百级文件 keyword 完全够用；Cargo deps +0 纪律（v0.22/v0.23 连续双零）延续 |
| 本地 embedding | 新重 dep（fastembed/candle + 模型文件） | ~500 行+ | ❌ 语料量级不匹配（百级文件上向量检索收益无法兑现）+ 违背轻依赖纪律 |
| 简化 SQL（rusqlite） | 新 dep | ~300-400 行 | ❌ 同上——无结构化复杂查询需求 |

**(b) 注入位置与 token 预算**——两个真选项，ADR 定稿：

| 路线 | 机制 | 优势 | 劣势 |
|---|---|---|---|
| **per-query 预注入** | 每 query 检索 top-k 相似历史 query 的成功链，注入 query 前/system 尾部，预算 ~500-1000 token | 不依赖模型主动性——**E2B 级模型上惰性发现链已被证明不可靠**（proc_help 动态发现本身就是 L2 失败模式之一）；可测差异更可能产生 | 每 query 常驻吃预算（entry 4 tool ~600 token 的既有纪律需要扩） |
| **惰性 meta tool**（proc_experience 类） | catalog +1（47→48），agent 主动调取经验 | 零常驻成本，entry-tool 架构（v0.20 Layer 0）天然延伸 | 依赖模型主动发现——在当前能力画像下大概率不被调用，eval 列难出差异 |

**(c) 评估口径**——RAG on/off 对比列同矩阵 + 方差带标尺解读；**污染防护是口径的一部分**（见风险 3）：检索时排除与当前 query 文本相似的历史条目（相似度阈值），或语料只用真实 session（eval trace 仅做语料 bootstrap 备选并明示口径）。**RAG 列跑在哪个模型底座上**随决策 1 结果定（新默认 or E2B 维持）。

**与方向 1 的绑定关系**：原设计「模型底座实验先行出结论，RAG 在拍板后底座上跑」；**拍板后实际形态（决策 1 = D）**——底座拍板不变（E2B 维持默认），RAG on/off 直接在固定 E2B 底座上单变量对比，「底座先定」逻辑以「底座拍板不变」的形式兑现（详见 FAQ Q1）。

### 方向 3：prompt v3（TD-60）搭车

- **素材就绪**：修订 2（写操作发现链）措辞稿独立可用（ADR-0033 附录 A）；v0.23 双列实验中机制 3 处证据可复现（#21 完整执行演示链 / idx63 两轮一致 / idx18 blocked 后行为符合预期），仅因与修订 1 捆绑无法分离归因
- **实验路径**：单独 diff 修订 2（不含修订 1）→ QUICK 冒烟 → FULL 三列（基线 / v3 / 视数据复跑方差列），方差带标尺解读
- **搭车价值**：与模型列同矩阵摊薄挂机成本；TD-60 闭环
- **拍板点**：是否搭车 + **实验底座**——若决策 1 换默认，v3 列应在新默认上跑（v1 基线列需同底座重跑一列，多一次挂机；或 v3 直接对比新底座自身基线列）

### 方向 4：TD-55~57 补验（视 key）

- 有 `ANTHROPIC_API_KEY` 即 1 条命令三连闭环（TD-55 Sonnet 70q 对照 + TD-56 model ID 真实验证 + TD-57 nudge 路径覆盖）：`ANTHROPIC_API_KEY=... proc agent eval --provider anthropic --output eval-sonnet-70q.json`
- **组合价值**：Sonnet 云端档并入模型对比矩阵（E2B / E4B / Sonnet 三档）——「本地小模型 vs 本地中模型 vs 云端大模型」完整光谱一次出齐，云端档 <10 分钟成本极低
- 无 key 则 TD-55~57 第 5 个 cycle open（路径不变）

### 方向 5：GBNF 复测（TD-61）——维持不主动排期

挂 llama-server 升级节点（观察项）。若用户在 v0.24 期间升级 llama.cpp，可按附录 B 判定表顺手重跑冒烟（smoke1 L0 3×2 即可判定），互斥放开则 GBNF 列复入矩阵——**不进 stage 清单，备注留档**。

决策 8 澄清口径不变：协作 agent 的价值依赖单 agent 能力上限先拉满。v0.24 不动；v0.25+ 评估时以 v0.24 模型底座结论 + RAG 结论为输入。

## 已知风险（按拍板后范围定稿）

### 风险 1：E2B 底座上 RAG 收益存疑（既定判断的实验闭环风险）——**决策 1 拍 D 后成为本 cycle 主管线风险**

**问题**：「RAG 注入增大 context 负担，E2B 能力边界下收益存疑」是 v0.22 以来的既定判断（决策 2 原文理由）；拍板不下载后 RAG 就在此底座上做——若通过率增益落方差带内（大概率场景），cycle 的「能力提升」叙事不成立。
**mitigate**（决策 2 口径，ADR-0034 固化）：评估**机制验证为主指标**——检索准不准（召回与人工标注对照）/ 注入有没有被模型用上（session log + trace：模型 answer 是否引用了注入经验、tool 链是否向经验链迁移）；通过率增益按方差带标尺如实解读，涨不涨都归档——**「机制成立但 E2B 兑现不了」与「机制不成立」是两种不同结论**，前者给 v0.25+ 模型底座重启决策留数据输入（与决策 1 归档的候选表呼应）。

### 风险 2：新模型模板/启动参数不兼容——**已排除**

决策 1 拍板不下载，本 cycle 无新模型列。条目保留备查：未来重启模型底座决策（决策 1 归档段）时重新启用——E4B 同家族低风险 / Qwen 异家族需 QUICK 冒烟三判定（模板渲染 / tool_calls 解析 / 内存实测），`SpawnOptions` 覆盖位已留。

### 风险 3：RAG eval 语料自我污染（干净归因的大坑）

**问题**：经验库若含 eval 同款 query（queries.toml 70 条）的成功 trace——RAG-on 跑 eval 等于检索答案，增益是信息泄漏非能力提升。
**mitigate**：(1) 检索时排除与当前 query 文本相似的历史条目（阈值进 ADR-0034）；(2) 语料优先只用真实 session，eval trace 做 bootstrap 备选时明示口径；(3) 归档时报告「排除命中次数」证明防护生效。

### 风险 4：RAG 注入增大 context 吃预算

**问题**：entry 4 tool ~600 token 的既有纪律下，注入段预算失控会挤压有效 context（E2B ctx 8192 本就不富裕）。
**mitigate**：token 预算硬上限进 ADR-0034（~500-1000 token 量级）+ 超限截断策略；注入前后 prompt token 数进 session log 可观测。

### 风险 5：RAG 语料量薄（53 会话 / 83K）

**问题**：经验密度低（开发期测试对话为主），检索 top-k 可能召回低价值条目。
**mitigate**：语料筛选（只索引含成功 tool 链的 query 段）；eval trace bootstrap 备选（污染防护约束下）；机制验证与通过率增益分离归档（风险 1 同款口径）——「检索准 / 被用上」先成立，「涨通过率」按方差带标尺如实解读。

### 风险 6：16GB RAM + 6GB VRAM 边界——**已排除**

决策 1 拍板不下载，本 cycle 无新模型内存压力（E2B Q4 2.9G 现状延续）。条目保留备查：未来下 Qwen 7-8B 时重新启用（QUICK 实测内存 + 均时再定 FULL）。

### 风险 7：挂机负担（矩阵 2-3 列）

**问题**：RAG on 列 + v3 列（+ 视数据复跑方差列）FULL 总挂机 ~1.5-2.5h（E2B 基线 47m/列口径）。
**mitigate**：off 态零新增挂机（复用基线族 `eval-e2b-70q.json` + `eval-best-70q.json` 方差列——v0.24 binary 默认配置与 v0.22/v0.23 run 同口径：RAG off + prompt v1 + E2B，可比性由 ADR-0034 论证）；结果 JSON 每 query 实时落盘（v0.22 起既有）；分散多次挂机；v3 列存疑时才复跑（D4 三分支同款）。

## FAQ

### Q1: 拍板不下载了，RAG 为什么还按 v0.24 做？

**A**: 决策 1（不下载）与决策 2（完整主体）是用户同会话的组合拍板——「RAG 主体重评」的重评结论就是照做，但口径按风险 1 调整：机制验证为主指标（检索准 / 注入被用上——小语料 + E2B 也能验证），通过率增益按方差带标尺如实解读不预设。归因链依然干净：RAG on/off 在固定 E2B 底座上单变量对比（v0.23 决策 2 的「底座先定」逻辑以「底座拍板不变」的形式兑现）。

### Q2: E4B / Qwen 的评估结论还有用吗？

**A**: 有——决策 1 归档段 + 方向 1 评估表留档（候选对比 / 换默认门槛 / QUICK 三判定路径）。未来重启模型底座决策（如 v0.25+ RAG 结论显示「机制成立但 E2B 兑现不了」时）直接复用，不必重评。

### Q3: 语料只有 53 个会话，RAG 值得做吗？

**A**: 这是提案 2 存在的理由。拍板选完整主体的依据：(1) 语料随日常使用持续增长，机制先建好收益后兑；(2) 机制验证（检索准 / 注入被用上）与通过率增益可分离归档——前者小语料也能验证；(3) 决策 7 已两次锚定 v0.24，再推需要显式改判理由（本次拍板未改判）。

### Q4: prompt v3 需要多挂基线列吗？

**A**: 不需要——底座 E2B 不变，v3 列（E2B × RAG off × v3）直接对比同底座 v1 基线族（`eval-e2b-70q.json` + `eval-best-70q.json` 方差列），v3 单变量新增 1 列；存疑时按 D4 三分支复跑定夺。

### Q5: RAG 增益落方差带内怎么办？

**A**: 按机制验证口径分离归档：「机制成立但 E2B 兑现不了」（检索准 + 模型用了经验但通过率不动——给模型底座重启决策留数据输入）vs「机制不成立」（检索不准或模型无视注入——RAG 路线本身关闭或重设计）。两种结论都有决策价值，与 v0.23「负结果以数据关闭路径」同款纪律。RAG 默认值维持 off（agent.toml 注释态推荐），不强制改默认。
