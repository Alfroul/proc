## 设计决策（本阶段拍板，stage 5-7 不动 system_history / ResourceRoute / SSE 策略）

### 决策 1：system_history 字段由 `run_snapshot_worker` 兼任 push（不 spawn 第二个 worker）

**问题**：stage 3 TD-54 落地的 `run_snapshot_worker` 已每 1s tick refresh SystemSnapshot 写回 `snapshot: Arc<Mutex<Option<SystemSnapshot>>>` 字段。TD-52 sparkline 需 30s 历史采样，1s tick push 到 `system_history: Arc<Mutex<VecDeque<SystemSnapshot>>>`，30s cap。

**决策**：**`run_snapshot_worker` 兼任 push** —— worker 在 `*guard = Some(s)` 写回 snapshot 字段后，紧接着 `system_history.lock().push_back(s.clone())` + `if len > 30 { pop_front() }`。不 spawn 第二个 worker。

```rust
#[cfg(feature = "mcp-persistent-state")]
fn run_snapshot_worker(
    snapshot: Arc<Mutex<Option<SystemSnapshot>>>,
    system_history: Arc<Mutex<VecDeque<SystemSnapshot>>>,
) {
    loop {
        let tick_start = std::time::Instant::now();

        let mut s = match snapshot.lock().ok().and_then(|mut g| g.take()) {
            Some(s) => s,
            None => match SystemSnapshot::new() { /* ... */ },
        };

        if s.refresh().is_ok() {
            let _ = s.refresh_heavy_incremental();
        }

        // 写回 snapshot 字段（生产路径读这个）
        if let Ok(mut guard) = snapshot.lock() {
            *guard = Some(s.clone());  // clone 一份给 snapshot 字段
        }

        // push 到 system_history 字段（sparkline 用），30s cap
        if let Ok(mut history) = system_history.lock() {
            history.push_back(s);  // owned s 移到 VecDeque，避免二次 clone
            while history.len() > 30 {
                history.pop_front();
            }
        }

        let elapsed = tick_start.elapsed();
        let sleep_dur = std::time::Duration::from_secs(1).saturating_sub(elapsed);
        std::thread::sleep(sleep_dur);
    }
}
```

**关键设计点**：

1. **单 worker 兼任**：与 stage 3 设计一致（fire-and-forget + take/move 模式），无需第二个 worker 协调 1s tick 节奏
2. **snapshot 字段用 clone，system_history 用 move**：snapshot 字段需支持 helper 读 Some(&s)，必须 clone 一份（SystemSnapshot 字段级别 clone 开销 ~50µs，远小于 refresh ~30-50ms）；system_history push owned s 不需 clone
3. **持锁窗口 ~30-50ms**：与 stage 3 同款（refresh + clone + push 总耗时仍 < 100ms，1s tick 占空比 < 10%）
4. **30s cap 通过 VecDeque::pop_front 实现**：每 tick 检查 `len > 30` 即 pop_front，O(1) 操作

**与 brainstorm §主题 B 表 TD-52 描述「system_history 字段 + 1s tick push」对齐**：worker 单线程兼任 push 不破坏「1s tick push」语义。

### 决策 2：`make_metrics_history_json` 实装按 metric 分支 drain system_history

**问题**：stage 1 stub helper 返 placeholder JSON `{ ok: true, stub: true, stage: "v0.17-stage-4", received_metric, received_seconds }`。stage 4 替换为真实业务：drain `ProcMcpHandler::system_history` 字段 + 按 metric 分支提取数据点。

**决策**：helper 签名加 `history: &Arc<Mutex<VecDeque<SystemSnapshot>>>` 参数（或加新 `metrics_history_json_from_history` 内部 helper），按 metric 分支：

```rust
// src/mcp/handler/observable.rs

pub fn make_metrics_history_json(
    metric: &str,
    seconds: Option<u8>,
    history: &Arc<Mutex<VecDeque<SystemSnapshot>>>,
) -> Value {
    let seconds = seconds.unwrap_or(30).min(30);

    let samples = match history.lock() {
        Ok(g) => {
            let take = g.len().min(seconds as usize);
            g.iter().rev().take(take).rev().filter_map(|s| {
                let value = match metric {
                    "cpu" => Some(serde_json::json!(s.cpu_usage())),
                    "memory" => {
                        let (used, _) = s.memory_usage();
                        Some(serde_json::json!(used))
                    }
                    "swap" => {
                        let (used, _) = s.swap_usage();
                        Some(serde_json::json!(used))
                    }
                    _ => None,
                };
                value.map(|v| serde_json::json!({ "value": v }))
            }).collect::<Vec<_>>()
        }
        Err(_) => return super::err("system_history mutex poisoned"),
    };

    if !["cpu", "memory", "swap"].contains(&metric) {
        return super::err(format!(
            "unknown metric '{metric}' (valid: cpu / memory / swap)"
        ));
    }

    serde_json::json!({
        "ok": true,
        "metric": metric,
        "seconds": seconds,
        "count": samples.len(),
        "samples": samples,
    })
}
```

**关键设计点**：

1. **按 metric 分支**：cpu → f32 cpu_usage / memory → u64 used bytes / swap → u64 used bytes；不在 cpu/memory/swap 范围返 `{ ok: false, error }`
2. **`seconds` 参数 None → 30，> 30 截断到 30**：与 brainstorm §主题 B 表「30s cap」对齐
3. **samples 顺序**： oldest → newest（VecDeque iter().rev().take(N).rev() 取最后 N 个并保持顺序）
4. **不返 ts 字段**：SystemSnapshot 没存采集时间戳（worker 写入时未记录 `Instant::now()`）。如未来 agent 需 ts，v0.18+ cycle 评估加 `VecDeque<(SystemSnapshot, Instant)>` 字段（决策段不动 schema）。**samples 数组 index 0 = oldest，index -1 = newest，agent 可推算 ts = now - (count - 1 - i) seconds**
5. **空 history 返 count=0**：worker warm-up 期间 / Default 路径 / cfg-gate 掉字段时 history 为空，返 `{ ok: true, metric, seconds: 30, count: 0, samples: [] }` 让 agent 知道「worker 未起来 / 还在 warm-up」
6. **保留旧 stub helper 兼容**：`make_metrics_history_json(metric, seconds)` 改签名加 `history` 参数会让 stage 1 的 `mod.rs::proc_metrics_history` `#[tool]` 方法编译失败 → 直接更新调用点（mod.rs 是唯一调用点）

### 决策 3：ResourceRoute trait impl 路由 3 个 URI + ServerHandler 暴露 list_resources / read_resource

**问题**：stage 1 stub `ResourceRoute` trait 声明 `route(&self, uri: &str) -> Result<Value, String>`，stage 4 实装。但 rmcp 0.11 `ServerHandler` trait 的 `list_resources` / `read_resource` 是 MCP 协议层入口——client 通过 MCP 协议 `resources/list` 和 `resources/read` 调用，需 `ProcMcpHandler` impl 这些方法。

**决策**：**两层落地**：

1. **内层 ResourceRoute trait impl for ProcMcpHandler**：3 URI 路由（决策段实装）
2. **外层 ServerHandler impl 加 list_resources / read_resource 方法**：暴露 3 URI 给 MCP client，read_resource 内部调 `self.route(uri)`

```rust
// src/mcp/resources.rs —— 内层 trait 实装

impl ResourceRoute for super::handler::ProcMcpHandler {
    fn route(&self, uri: &str) -> Result<Value, String> {
        match uri {
            "proc://metrics/system" => {
                #[cfg(feature = "mcp-persistent-state")]
                {
                    if let Ok(guard) = self.snapshot.lock() {
                        if let Some(s) = guard.as_ref() {
                            return Ok(super::handler::metrics::metrics_system_json_from_snapshot(s));
                        }
                    }
                }
                Ok(super::handler::metrics::make_metrics_system_json())
            }
            "proc://processes/list" => {
                #[cfg(feature = "mcp-persistent-state")]
                {
                    if let Ok(guard) = self.snapshot.lock() {
                        if let Some(s) = guard.as_ref() {
                            return Ok(super::handler::processes_json_from_snapshot(s, Some("cpu"), Some(50)));
                        }
                    }
                }
                Ok(super::handler::make_processes_json(Some("cpu"), Some(50)))
            }
            "proc://docker/events" => {
                // docker events 走 cli::make_docker_events_json(Some(50))，与 proc_docker_events tool 同款
                Ok(super::handler::cli::make_docker_events_json(Some(50)))
            }
            _ => Err(format!("unknown resource URI: {uri} (valid: {})", PROC_RESOURCE_URIS.join(", "))),
        }
    }
}
```

```rust
// src/mcp/handler/mod.rs —— ServerHandler impl 扩 list_resources + read_resource + subscribe + unsubscribe

#[tool_handler(router = Self::tool_router())]
impl ServerHandler for ProcMcpHandler {
    fn get_info(&self) -> ServerInfo {
        ServerInfo {
            // ... 既有字段
            capabilities: rmcp::model::ServerCapabilities {
                tools: Some(rmcp::model::ToolsCapability::default()),
                resources: Some(rmcp::model::ResourcesCapability {
                    subscribe: Some(true),  // v0.17 stage 4 落地
                    list_changed: None,
                }),
                ..Default::default()
            },
            // ...
        }
    }
}

// 加在 impl ServerHandler 块里（rmcp 0.11 trait default impl 是 method_not_found，
// 我们覆盖返实际资源）
fn list_resources(
    &self,
    _request: Option<rmcp::model::PaginatedRequestParams>,
    _context: rmcp::service::RequestContext<rmcp::RoleServer>,
) -> impl Future<Output = Result<rmcp::model::ListResourcesResult, rmcp::ErrorData>> + Send + '_ {
    let resources: Vec<rmcp::model::Resource> = crate::mcp::resources::PROC_RESOURCE_URIS
        .iter()
        .map(|uri| rmcp::model::Resource {
            uri: (*uri).into(),
            name: resource_name_for_uri(uri).into(),
            description: resource_description_for_uri(uri).into(),
            mime_type: Some("application/json".into()),
        })
        .collect();
    std::future::ready(Ok(rmcp::model::ListResourcesResult {
        resources,
        next_cursor: None,
    }))
}

fn read_resource(
    &self,
    request: rmcp::model::ReadResourceRequestParams,
    _context: rmcp::service::RequestContext<rmcp::RoleServer>,
) -> impl Future<Output = Result<rmcp::model::ReadResourceResult, rmcp::ErrorData>> + Send + '_ {
    let uri = request.uri.as_str();
    let result = match crate::mcp::resources::ResourceRoute::route(self, uri) {
        Ok(value) => {
            let text = value.to_string();
            rmcp::model::ReadResourceResult {
                contents: vec![rmcp::model::ResourceContents::TextResourceContents {
                    uri: uri.to_string().into(),
                    mime_type: Some("application/json".into()),
                    text: text.into(),
                }],
            }
        }
        Err(msg) => {
            // 返 method_not_found 错误（与 rmcp 0.11 default impl 一致语义）
            return std::future::ready(Err(rmcp::ErrorData::invalid_request(msg, None)));
        }
    };
    std::future::ready(Ok(result))
}

// subscribe / unsubscribe 接受请求但不做实际 push（决策 5 说明）
fn subscribe(
    &self,
    _request: rmcp::model::SubscribeRequestParams,
    _context: rmcp::service::RequestContext<rmcp::RoleServer>,
) -> impl Future<Output = Result<(), rmcp::ErrorData>> + Send + '_ {
    std::future::ready(Ok(()))
}

fn unsubscribe(
    &self,
    _request: rmcp::model::UnsubscribeRequestParams,
    _context: rmcp::service::RequestContext<rmcp::RoleServer>,
) -> impl Future<Output = Result<(), rmcp::ErrorData>> + Send + '_ {
    std::future::ready(Ok(()))
}
```

**关键设计点**：

1. **ResourceRoute trait 是 proc 内部 trait**，不是 rmcp trait。它是为了让 `read_resource` 调用走单一入口（与 ADR-0027 设计对齐）
2. **capabilities.resources.subscribe = Some(true)**：让 MCP client 知道此 server 支持 subscribe（虽然实际 push 不做，但接受 subscribe 请求避免 client 报错）
3. **list_resources 返 3 URI 全列表**：每个 Resource 含 uri / name / description / mime_type
4. **read_resource 路由**：URI 在 3 个范围内 → 返 JSON snapshot；否则返 invalid_request 错误
5. **proc://processes/list 默认 top 50 by cpu**：与 brainstorm §主题 B 表「process list snapshot（top N by cpu_usage，N 默认 50）」对齐
6. **proc://docker/events 走 cli::make_docker_events_json(Some(50))**：与 `proc_docker_events` tool 同款路径（500ms 窗口采 + limit 50），不用 worker 持续 push

**与 brainstorm §主题 B + ADR-0027 §1 对齐**：3 个 URI 都通过 `read_resource` 一次性读，client 想要「实时」就轮询（polling），而不是 server 主动 push（push 需要 peer handle + notification channel，决策 5 说明）。

### 决策 4：SSE transport 落地「结构化 stub」（**偏离 brainstorm 决策 8 自适应拆分规则，stage 4 不拆分但 SSE 推迟 v0.18+ cycle**）

**问题**：brainstorm §主题 B 表 + ADR-0027 §2 描述 SSE transport 「`proc mcp serve --transport sse --port 8080` CLI 入口」+ 「复用 rmcp 0.11 内置 SSE server，否则自实装 tokio + axum」。实际评估后发现：

1. **rmcp 0.11 SSE 走 streamable_http_server 模块**：需 Cargo feature `transport-streamable-http-server-tower` + 依赖 `axum` / `tower-service` / `http` / `futures`（context7 rmcp 官方文档 2026-07-08 验证）
2. **runtime 重构**：当前 `run_mcp_serve` 用 `tokio::runtime::Builder::new_current_thread()`（避免与 DockerMonitor 内部 block_on 抢线程）；SSE server 多 client 并发需 `new_multi_thread()` runtime，与 DockerMonitor 协调需重新评估
3. **CLI 入口重构**：当前 `proc mcp serve` 无 args，加 `--transport sse --port 8080` 需扩 `src/cli/def.rs::Command::Mcp::serve` clap struct + `src/cli/mcp.rs::run_mcp_serve` 签名 + main.rs dispatch
4. **subscribe-push 机制**：SSE 真正的价值是 server 主动推送（如 1s tick push system metrics），需 handler 持 `Peer<RoleServer>` 句柄 + worker 调 `peer.notify(ResourceUpdated)` —— 与 fire-and-forget snapshot worker 模式不同，需 lifecycle 管理（client 断开后 worker 不能继续 push）
5. **总工作量评估**：~600 行业务代码 + ~200 行测试 = ~800 行，再加 TD-52 + ResourceRoute 已 ~600 行 → stage 4 总计 ~1400 行接近 brainstorm 容量上限 1500 行（93%）

**决策**：**stage 4 落地 SSE transport 结构化 stub**：

- `serve_sse(config: &SseTransportConfig)` 返详细错误 JSON 含：(a) rmcp Cargo feature 提示 / (b) tokio runtime 重构说明 / (c) subscribe-push 机制设计 / (d) v0.18+ cycle 候选
- `SseTransportConfig` struct 保留（port / bind_addr 字段不变）
- CLI 入口不加 `--transport sse` flag（避免给用户假象）—— v0.18+ cycle 加全实装时一并加 CLI 入口
- ADR-0027 不改 Status（仍 Accepted），但在 stage doc 决策段明确「v0.17 stage 4 落地 partial（仅 stub），v0.18+ cycle 落地 full SSE」

**理由**：

1. **surgical 原则**：SSE transport 是 stage 4 3 件套中最复杂的，且 TD-52 + ResourceRoute 已让 agent 通过 polling `proc_metrics_history` tool + `resources/read` 拿到实时数据（无需 server push）。SSE 的增量价值是「减少 polling 开销」，不是「提供新能力」
2. **brainstorm §决策 8 自适应拆分规则**：「如 stage 4 rmcp 0.11 API 学习曲线超预期 → 拆为 stage 4a + stage 4b，cycle 改 8 stage」。本决策不拆分（保持 7 stage 节奏），但 SSE 落地 partial——与 brainstorm 自适应规则兼容（拆分 vs partial 落地 + 推迟，都是合法路径）
3. **rmcp 0.11 streamable_http_server API 文档稀少**：context7 验证 docs.rs 文档存在但 example 缺乏，自实装需深度试验，触发拆分的风险高
4. **stage 7 Review 时再评估**：本 stage doc 决策段明确说明 SSE partial 落地理由，stage 7 Review 时评估是否触发 brainstorm 决策段更新（让用户拍板 SSE 是否仍按完整切换路径走，还是接受 partial + v0.18+ 候选）

**与 brainstorm 决策 8 自适应拆分规则对比**：

| 路径 | 优势 | 劣势 |
|---|---|---|
| **本 stage 4 选：partial 落地（TD-52 + ResourceRoute 全做，SSE stub）** | 保持 7 stage 节奏；TD-52 + ResourceRoute 已 cover agent 实时数据需求；SSE 推迟 v0.18+ cycle 不影响 stage 5/6/7 节奏 | 偏离 brainstorm §主题 B 「SSE transport 完整实装」期望，需在 Review 段重新拍板 |

### 决策 5：subscribe / unsubscribe 接受请求但不做实际 push（与决策 4 SSE partial 配套）

**问题**：MCP 协议 `resources/subscribe` 让 client 表达「我对此 URI 感兴趣，server 更新时通知我」。stage 4 已落地 `capabilities.resources.subscribe = Some(true)`（决策 3），但实际 push（server 主动发 `notifications/resources/updated`）需要 handler 持 `Peer<RoleServer>` 句柄 + worker 调 peer.notify() —— 与 SSE transport 同款复杂度（决策 4 推迟）。

**决策**：**subscribe / unsubscribe 接受请求返 Ok(())**，不做实际 push。client 想要「实时」走 polling `resources/read`（每 1s 调一次），与 SSE transport partial 落地配套。

```rust
fn subscribe(
    &self,
    _request: rmcp::model::SubscribeRequestParams,
    _context: rmcp::service::RequestContext<rmcp::RoleServer>,
) -> impl Future<Output = Result<(), rmcp::ErrorData>> + Send + '_ {
    // v0.17 stage 4：接受 subscribe 请求但不做 push（与决策 4 SSE partial 配套）。
    // client 应通过 `resources/read` 主动 polling（与既有 `proc_metrics_system` tool
    // 一次性 query 同款语义）。v0.18+ cycle 评估 server 主动 push（需 Peer<RoleServer>
    // 句柄 + notification channel lifecycle 管理）。
    std::future::ready(Ok(()))
}
```

**关键设计点**：

1. **返 Ok 不返错**：避免 client 报错（capabilities 标 subscribe=true 但 subscribe 返错会让 client 困惑）
2. **文档化**：ServerHandler::subscribe 方法的 doc comment 明确说明「v0.17 stage 4 接受请求但不 push，v0.18+ cycle 评估」
3. **client 应通过 resources/read polling**：与既有 `proc_metrics_system` tool 一次性 query 同款语义，agent 已习惯 polling 模式

## 已知风险

### 风险 1：rmcp 0.11 ServerHandler trait method 签名 / 类型不匹配编译失败

**问题**：决策 3 描述的 list_resources / read_resource / subscribe / unsubscribe 签名基于 context7 rmcp 0.11 文档（2026-07-08 验证），但 rmcp 0.11 仍在迭代（context7 文档可能滞后于 crates.io 发布版）。如 `PaginatedRequestParams` / `RequestContext<RoleServer>` / `ListResourcesResult` / `ResourceContents::TextResourceContents` 类型路径或 variant 名不匹配，编译失败。

**mitigate**：

1. 实装时按编译器提示修正类型路径（rmcp 0.11 编译错误信息精确，按编译器提示调整 use 路径 + 类型构造）
2. 如某 method 签名与 rmcp 0.11 不兼容（如返 type 不是 `impl Future`）→ 退到默认 impl（不覆盖 method），保留 capabilities.resources = Some(...) 但不实际暴露 list_resources → client 拿不到资源列表，但 既有 39 tool 仍可用
3. **fallback 路径**：只覆盖 `list_resources` 一个方法（最简单），其他 3 个（read_resource / subscribe / unsubscribe）走 rmcp 0.11 默认 impl（method_not_found）。这样 client 调 `resources/list` 拿到 3 URI，但调 `resources/read` 报 method_not_found——agent 视角「resources 已声明但 read 不支持」，仍可通过 proc_metrics_history tool 拿 sparkline 数据。stage 7 Review 时评估是否触发 brainstorm 决策段更新

### 风险 2：worker push 增加 stage 3 持锁窗口影响 metrics_system 响应延迟

**问题**：stage 3 worker 已在 take → refresh → move back 之间有 ~30-50ms 持锁窗口（snapshot 字段）。stage 4 加 system_history push（clone SystemSnapshot ~50µs + VecDeque push_back < 1µs + pop_front < 1µs）几乎不增持锁窗口，但 system_history.lock() 与 snapshot.lock() 是不同 mutex，并行持锁可能 contention。

**mitigate**：

1. snapshot 字段与 system_history 字段是独立 `Arc<Mutex<T>>`，可并行 lock 不冲突
2. worker 先 snapshot.lock() 写回，drop guard，再 system_history.lock() push（不同时持两锁，避免 deadlock）
3. 单 tick 总耗时仍 < 100ms（refresh ~30-50ms + clone ~50µs + push < 1ms），1s tick 占空比 < 10%

### 风险 3：SystemSnapshot::clone 实际开销超预估

**问题**：决策 1 设计 worker 在 push snapshot 字段时 `*guard = Some(s.clone())`，需 clone SystemSnapshot。SystemSnapshot 内含 sysinfo::System（含 HashMap<Pid, Process>）、network adapter info、disk info 等大量字段。clone 开销可能远超预估的 ~50µs（如 sysinfo::System clone 是深拷贝 HashMap 可能 ~1-5ms）。

**mitigate**：

1. 实装时实测 `Instant::now()` around clone，如 > 1ms 考虑改设计（如 snapshot 字段走 take/move 不 clone，system_history 也 take/move 不 clone —— 但这样 helper 读字段时偶发 None fallback，与 stage 3 同款）
2. fallback 设计：worker 先 take owned s → push clone 到 system_history → move owned s 到 snapshot 字段。这样 snapshot 字段不需 clone（move），system_history 字段 push clone（VecDeque 需要 owned 数据）。这与 stage 3 「take → refresh → move back」模式兼容，仅多一个 clone push 步骤。

**实际选 fallback 设计**：

```rust
// worker loop body（修正后）
let mut s = ... // take 或 new
if s.refresh().is_ok() { let _ = s.refresh_heavy_incremental(); }

// 1. push clone 到 system_history（VecDeque 需要 owned）
if let Ok(mut history) = system_history.lock() {
    history.push_back(s.clone());  // clone 一次
    while history.len() > 30 { history.pop_front(); }
}

// 2. move owned s 到 snapshot 字段（不需 clone）
if let Ok(mut guard) = snapshot.lock() {
    *guard = Some(s);  // move
}
```

这样每 tick 仅 1 次 clone（SystemSnapshot::clone），与 stage 3 take/move 模式兼容。

### 风险 4：list_resources 测试用 tokio runtime 包装 Future 返回

**问题**：rmcp 0.11 ServerHandler::list_resources 返 `impl Future<Output = Result<ListResourcesResult, McpError>> + MaybeSendFuture + '_`。测试调用 `handler.list_resources(None, ctx).await` 需 tokio runtime。但 proc 主 runtime 是 `current_thread`，测试用 `tokio::runtime::Runtime::new().unwrap().block_on(async { ... })` 会创建 multi_thread runtime，可能与 fire-and-forget worker 线程冲突。

**mitigate**：

1. 测试用 `tokio::runtime::Builder::new_current_thread().enable_all().build().unwrap().block_on(...)` 与生产 runtime 一致
2. list_resources / read_resource 的 Future 实际是 `std::future::ready(Ok(...))` 同步返，runtime 仅 `.await` 一次就 ready，不实际异步
3. 如测试仍出问题，改为不直接调 trait method，而是调内部同步 helper（如 `list_resources_sync(&self) -> Vec<Resource>`），trait method 包装 async —— 让测试直接调 sync helper

### 风险 5：subscribe 接受请求但不 push 与 capabilities.subscribe = true 语义冲突

**问题**：决策 5 设计 `subscribe` 返 Ok 不 push，但 capabilities 标 subscribe=true。client 看到 subscribe=true + subscribe 成功后期待 `notifications/resources/updated` 推送，但不收到会困惑 / 等待无果。

**mitigate**：

1. **文档化 ServerHandler::subscribe doc comment**：明确说明「v0.17 stage 4 接受请求但不 push，client 应通过 resources/read polling」
2. **resources/read 兜底**：client 即使 subscribe 后也能调 resources/read 主动拉数据（与 polling 同款）
3. **agent 视角**：LLM agent 通常用 tool 而非 resources，subscribe-push 缺失对 agent 透明
4. **stage 7 Review 评估**：是否触发 brainstorm 决策段更新（让用户拍板 subscribe-push 是否仍按完整路径走）

### 风险 6：Cargo.toml 不加 Cargo feature（与 stage 4 SSE partial 决策配套）

**问题**：决策 4 不加 `transport-streamable-http-server-tower` Cargo feature，但用户如直接 `cargo build --features ...` 启用会编译失败（serve_sse 引用 rmcp::transport::streamable_http_server 模块不存在）。

**mitigate**：serve_sse stub 不引用任何 rmcp 0.11 SSE 类型（仅返 String 错误），即使启用相关 Cargo feature 也不影响。v0.18+ cycle 全实装时一并加 Cargo feature + 实装代码。
