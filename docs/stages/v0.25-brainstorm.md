## 已知风险

### 风险 1：TD-53（per-process disk_io）复杂度超预期

**问题**：v0.15 归档理由仍在——NT Kernel Logger 单实例限制 + 启动延迟 ~1s + 非管理员 / x86 fallback 路径复杂；MCP handler 持久 worker 是新接线模式。
**mitigate**：stage 1 逐项终判（ADR-0035 预登记判定标准：fallback 路径清单 + 单实例冲突场景可枚举则做，否则砍掉只保 TD-52/54）；砍 TD-53 不改 cycle 形态（清单是打包非依赖链）。

### 风险 2：MCP handler 持久字段的并发与生命周期

**问题**：`ProcMcpHandler` 加持久共享字段（snapshot / history / worker handle）——跨 tool call 共享引入线程安全与新鲜度问题（TD-54 归档时的 `App::new()` 非 Send + Sync 顾虑）。
**mitigate**：dns_collector 先例模式（v0.12 TD-36）为设计基线；共享的是 `SystemSnapshot`（数据结构）非 `App`；新鲜度语义明示（1s tick 或 TTL，响应加采集时间戳让 agent 可判 stale）。

### 风险 3：空会话治理误伤有用语料

**问题**：延迟创建/退出清理若判定口径错，可能删掉「慢启动但有内容」的会话。
**mitigate**：成功段判定与 RAG corpus 状态机同口径（query_started → ≥1 tool_start → 正常收尾）；治理是「不落盘/清理无 query 文件」非「删除有 query 文件」；ask / eval / AgentPanel 三路径各加回归测试（含 TUI 中途退出的边界）。

### 风险 4：零挂机 cycle 的基线可比性（无 eval 锚时的质量论证）

**问题**：本 cycle 无 eval 列——MCP 响应字段扩展（TD-52/53）与 handler 开销优化（TD-54）理论上可能影响 agent 行为，如何论证不破既有画像？
**mitigate**：(1) tool 语义不变原则——只加响应字段不改既有字段含义，`x-deprecated` 是 hint 非删除；(2) 回归数字 + MCP tool 46 / catalog 47 不变锚；(3) queries.toml 70q 不涉新字段（sparkline 趋势 / per-process disk_io 无对应 query），附录 A 启动时若要验证可加对照列；(4) stage 3 Review 按此口径声明。

### 风险 5：TD 清仓范围蔓延

**问题**：清仓型 cycle 易在执行中发现新债（stage 1 现状核查 TD-11/20/21/22 时尤其）。
**mitigate**：打包清单封闭（stage 1 终判只能**砍**不能**加**——新发现的债记 TD 留档，不在本 cycle 展开）；手册步 15 冲突回拍板流程照常。

## FAQ

### Q1: 五项候选全不可做，这个 cycle 的价值是什么？

**A**: 主线条件（下载意愿 / key / llama-server 升级 / 语料增长）本 cycle 均未齐——与其空转等待，不如清偿积压的工程债：MCP 观测 tool 层补全（TD-52/53/54）让 agent 数据面更完整（未来更强底座上这些是现成弹药）、worker 状态机止损（TD-24）、安全配置 hardening（TD-40）、语料卫生（96/94 实证）为 RAG 复测准备干净主语料。维护窗口是项目节奏的正常段（v0.13 PERF-BASELINE 同款先例）。

### Q2: 空会话治理会不会误删有用语料？

**A**: 见风险 3——判定口径与 RAG 成功段状态机同源，「无 query 事件」才清理；有 query 的文件（现存 2 个）不在治理范围。治理后 RAG 索引行为不变（空文件本就无成功段）。

### Q3: TD-52/53 的 MCP 响应字段变更破坏外部 client 兼容吗？

**A**: 不破坏——JSON 响应**加**字段向后兼容；`proc_smart` 的 `x-deprecated` 是 schema hint（rmcp/JSON-schema 扩展键），tool 本体不删（TD-50 修复方案 a 的「外部 client 可能已集成」顾虑以此规避）。

### Q4: 模型组合设计（附录 A）还能复用吗？

**A**: 能——附录 A 完整保留候选表 / QUICK 三判定 / 判读门槛 / 漏斗条件，决策 2 已预登记 RAG 复测语料口径（维持三基线 run）；未来重启只需重评「拍板时点的下载意愿/磁盘/网络约束」（决策 1 归档语境），设计本身不必重做。

### Q5: 3 stage 的 Review 独立性怎么保证？

**A**: stage 3 尾段 Review 按数据/测试锚审（回归数字 / tool 数不变锚 / 三路径语料回归测试 / ADR-0035 判定标准执行核对），不自评口径；若 stage 3 容量触界（剩余 < 30%）走 Checkpoint 接力（手册步 10），Review 段不压缩。
