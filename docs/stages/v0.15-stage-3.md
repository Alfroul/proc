## 设计决策（stage 3 拍板）

### 决策 1：metrics 走 SystemSnapshot 直采（不 spawn App）

stage 2 `proc_flows` 走 `App::new() + 2s warm-up` 是因为需要 Schannel ETW worker 起来采 SNI 事件。stage 3 的 5 个 metrics 都不需要 worker：

- `metrics_system` / `metrics_disk_io` / `metrics_smart` / `metrics_thermal` 都走 `SystemSnapshot::new() + refresh()`（与 stage 2 `make_export_json` 同款路径，~500ms 开销）
- `metrics_gpu` 走 `GpuCollector::new() + refresh()`（GPU collectors 单独路径，与 sidebar 同款；不走 SystemSnapshot 因为 GpuCollector 独立 module）

agent 多次调 metrics 会每次新建 snapshot（~500ms 开销），可接受（MCP tool 不是高频路径，agent 一次 task 通常调 1-2 次）。

### 决策 2：metrics_smart 与 proc_smart 的关系（stage 1 §决策 4c 待定项落地）

stage 1 标 `proc_metrics_smart` 与 v0.7 既有 `proc_smart` 职责重叠，留 stage 4 Review 决策（3 选项：(a) 废弃 `proc_smart` / (b) `proc_metrics_smart` 返系统级聚合 vs `proc_smart` 单设备 / (c) 移除重复入口）。

**stage 3 落地**：选 **(b)** —— `proc_metrics_smart(device=None)` 返**系统级聚合**（all disks 摘要：device / model / health / temperature / attribute_count，与 sidebar 同款视角），`proc_metrics_smart(device=Some)` 与 `proc_smart(device=Some)` 同款返详细 attributes。`proc_smart` 不动（v0.7 既有 17 tool 之一，surgical 原则）。stage 4 Review 评估是否合并入口或废弃 `proc_smart`（暂留 v0.16+ 候选）。

### 决策 3：metrics_system 字段集

| 字段 | 类型 | 来源 |
|---|---|---|
| `cpu_usage_pct` | f32 | `snapshot.cpu_usage()` |
| `memory` | { used_bytes, total_bytes, pct } | `snapshot.memory_usage()` |
| `swap` | { used_bytes, total_bytes, pct } | `snapshot.swap_usage()` |
| `system_disk` | { used_bytes, total_bytes, pct } | `snapshot.disk_usage()` |
| `uptime_secs` | u64 | `SystemSnapshot::uptime_secs()` |
| `processes_count` | usize | `snapshot.process_count()` |
| `network_interfaces` | Vec<{ name, ipv4 }> | `snapshot.net_adapters()` |
| `tcp_stats` | { established, time_wait, close_wait, listen, retransmitted_segs, reset_segs, failed_connections } | `SystemSnapshot::tcp_stats()` |
| `cpu_temp_c` / `gpu_temp_c` | Option<f32> | `snapshot.temperatures()` |

**sparkline 30 秒历史暂不做** —— 需要持久化 + worker 累积（与 LightWorker 同款 1s tick），MCP 一次性 request-response 模型不适合。stage 4 Review 评估是否加（暂留 v0.16+ 候选，与 v0.7 既有 `proc_diag` 一样一次性快照语义）。

### 决策 4：metrics_gpu 字段集

每个 GPU 一条：

| 字段 | 类型 | 来源 |
|---|---|---|
| `name` | String | `GpuInfo.name` |
| `vendor` | "Nvidia" / "Amd" / "Intel" / "Unknown" | `GpuInfo.vendor` |
| `utilization_pct` | u32 | `GpuInfo.utilization_pct` |
| `vram` | { used_bytes, total_bytes, budget_bytes } | `GpuInfo.vram_*` |
| `temperature_c` | Option<f32> | `GpuInfo.temperature` |
| `power_watts` | Option<f64> | `GpuInfo.power_watts` |

顶层加 `providers: Vec<&str>`（如 `["nvml", "dxgi", "pdh"]`）让 agent 知道哪些数据源生效。无 NVIDIA GPU / 无 DXGI 支持 / 非 Windows → 返 `gpus: [] + note: "no GPU providers available"`。

### 决策 5：metrics_disk_io 字段集

| 字段 | 类型 | 来源 |
|---|---|---|
| `total` | { read_bps, write_bps } | `snapshot.disk_io_speed()` |
| `per_disk` | Vec<{ name, mount_point, read_bps, write_bps }> | `snapshot.per_disk_io_speed()` |
| `disks` | Vec<{ name, mount_point, used_bytes, total_bytes, is_removable }> | `snapshot.all_disks()` |

`device=Some("PhysicalDrive0")` → 过滤 `per_disk` 只返该设备（其他字段保留全部，让 agent 既能看到单设备 IO 也能看上下文）。`device=None` → 返全部。

**per-process disk_io 暂不暴露** —— 需 ETW + thread_map（disk_io_etw worker 模式），MCP 一次性调用启动 ETW session 不实用。stage 4 Review 评估是否加（暂留 v0.16+ 候选，与 v0.7 既有 `proc_ls --sort disk_read` 互补）。

### 决策 6：metrics_thermal 字段集

| 字段 | 类型 | 来源 |
|---|---|---|
| `per_core_freq_mhz` | Vec<u64> | `snapshot.per_core_freq()` |
| `per_core_temp_c` | Vec<Option<f32>> | `snapshot.per_core_temp()` |
| `throttle` | Option<{ max_mhz, current_mhz, mhz_limit, is_throttled, throttle_pct }> | `snapshot.throttle_info()` |
| `reason` | "None" / "Thermal" / "PowerPolicy" / "Idle" / "Unknown" / "Unavailable" | `classify_throttle()` |
| `cpu_temp_c` / `gpu_temp_c` | Option<f32> | `snapshot.temperatures()` |

非 Windows / 无 `PROCESSOR_POWER_INFORMATION` 访问权限 → `throttle: null, reason: "Unavailable"`，`per_core_freq/temp` 仍能从 sysinfo 拿。THERMAL / POWER 标记来自 `classify_throttle`（与 sidebar §268 同款路径）。

### 决策 7：stage 3 不动 mod.rs 的 #[tool] 方法签名

同 stage 2 决策 6 —— `#[tool]` 方法体仍只 1-2 行（`ok_result(metrics::make_metrics_system_json())`），仅在子 module 替换 stub helper 为真实业务实现。impl 块结构稳定 → 既有 32 tool 零回归。

仅更新 5 个 metrics tool 的 `description` 字段（去掉 "Stage 1 stub" 字样，写清返回字段，参考 stage 2 已落地的 10 tool 风格）。

## 已知风险

### 风险 1：metrics_gpu 在无 GPU 环境返空

CI / 容器 / 服务器环境无 NVIDIA / DXGI 支持 → `gpus: []` + `providers: []`。**已 mitigate**：返 `note: "no GPU providers available"`，agent 理解为「无 GPU」而非「错误」。`GpuCollector::detect_providers()` 内部已处理跨平台差异（非 Windows 直接返空）。

### 风险 2：metrics_thermal throttle_info 平台差异

非 Windows / Win11 build < 22000 → `throttle_info: null` + `reason: "Unavailable"`。per_core_freq/temp 仍能从 sysinfo 拿（Linux cpufreq / Windows 注册表）。**已 mitigate**：测试断言「不 panic 即可」（不强求 throttle 字段非 null）。

### 风险 3：metrics_smart 与 proc_smart 重叠（决策 2）

stage 3 落地为 (b) 方案（聚合 vs 单设备），但 `proc_metrics_smart(device=Some)` 与 `proc_smart(device=Some)` 仍 100% 重叠。**已 mitigate**：stage 4 Review 评估合并入口 / 废弃 `proc_smart` / 保持现状（暂留 v0.16+ 候选）。stage 3 不决策。

### 风险 4：SystemSnapshot::new() 多次调用开销

每个 metrics tool call 都 `SystemSnapshot::new()` (~500ms 开销，包含首次 sysinfo 全量采集)。agent 多次调用累积开销大。**已 mitigate**：与 stage 2 `make_export_json` 同款路径（已落地，v0.15 stage 2 commit `8834fd1`），agent 实际不会高频调（典型 task 调 1-2 次）。stage 4 Review 评估是否加 MCP handler 内的 SystemSnapshot 复用（暂留，与 stage 2 风险 1 同款决策）。

### 风险 5：metrics_system sparkline 历史不暴露

brainstorm §类别 4 提「30 秒火花线图历史」，但 MCP 一次性 request-response 模型 + 无 worker 持久化不适合。**已 mitigate**：stage 3 不做 sparkline，文档化为「系统级 metrics 当前快照」语义（与 proc_diag 同款）。stage 4 Review 评估是否加（暂留 v0.16+ 候选）。
