## cycle 决策（拍板记录）

**2026-07-06 用户拍板**：选**主题 D（MCP 全功能暴露 cycle）**，进一步拆为 **v0.15 查询类 + v0.16 操作录屏类**两个 cycle。

**理由**：
1. **agent 价值最大化**：当前 17 tool 让 agent 只能看到 proc 的「概览」（进程列表 / 端口 / Docker 容器），看不到详情页 Tab / 系统指标 / 录屏 v2 — 大量已落地的能力对 LLM 不可见，是 proc 差异化的最大缺口
2. **节奏对比**：v0.13 = 4 stage 轻 cycle / v0.14 = 5 stage 重 cycle / v0.15 = 4 stage 中重 cycle — 三 cycle 形成「轻 / 重 / 中」节奏交替，避免连续两个重 cycle
3. **拆 cycle 降低风险**：v0.15 查询类（14 tool ~1850 行）+ v0.16 操作录屏类（6 tool ~600 行）—— 拆开后 v0.15 是「单一主题 cycle」（MCP 全功能查询类），cycle 内聚强；v0.16 单独 cycle 让录屏 v2 暴露能深做（书签 / 搜索状态机 + sidecar 持久化）
4. **技术决策已拍板**：详情页 6 Tab 合并成 1 个 `proc_inspect(pid, tab=...)` / 写操作默认 `dry_run=false` / secret 默认 mask + `reveal: Option<bool>` opt-in

## 14 个新 tool 详细范围

> 把 CLI 已有但 MCP 未暴露的命令直接转成 MCP tool，工作量小（CLI 路径已有完整实现，handler 只做参数 dispatch + JSON 输出）。

| Tool | 对应 CLI | 范围 | 工作量 |
|---|---|---|---|

| `proc_throttle` | `proc throttle <pid> [on\|off]` | Windows 11 EcoQoS 状态查询 + 🍃 标记；admin 才能切换，非 admin query only | ~50 行 |
| `proc_export` | `proc export --format json\|csv [-o file] [--sort] [--limit]` | 进程数据导出；agent 视角主要用 JSON 输出到 stdout（不写文件） | ~50 行 |
| `proc_docker_inspect` | `proc docker inspect <name>` | 容器详情（bollard::inspect_container） | ~40 行 |
| `proc_docker_images` | `proc docker images` | 本地镜像列表 + in_use 判定 | ~50 行 |
| `proc_docker_volumes` | `proc docker volumes` | 卷列表 + in_use 反查 | ~50 行 |
| `proc_docker_events` | `proc docker events` | 事件流（一次性 drain，非 follow — MCP 是 request-response 不持流） | ~60 行 |

### 类别 2：详情页 Tab 数据合并（1 tool 含 6 tab，~350 行）

> 6 个 Tab 合并成 1 个 `proc_inspect(pid, tab=...)` tool，agent 视角调用简单（一个 tool 名 + 一个 enum 参数），schema 统一，tool 列表不挤 6 个 `proc_inspect_*`。

**`proc_inspect` 入参 schema**：
```rust
#[derive(Deserialize, schemars::JsonSchema)]
pub struct ProcInspectArgs {
    /// 进程 PID
    pub pid: u32,
    /// Tab 选择（默认 summary）
    #[serde(default)]
    pub tab: InspectTab,
    /// 是否 reveal secret 字段（默认 false = mask）。仅 env tab 生效。
    /// secret pattern 12 关键字（KEY/TOKEN/SECRET/PASSWORD/PASSWD/PWD/CREDENTIAL/PRIVATE/AUTH/API/DSN/CONNECTION_STRING）
    /// + *_AUTHORIZATION 后缀 + DATABASE_URL 特例。
    #[serde(default)]
    pub reveal: bool,
}

#[derive(Deserialize, Default, schemars::JsonSchema)]
pub enum InspectTab {
    /// 概要 + R1-R18 风险因子 + signature 9 状态机 + parent_chain（默认）
    #[default]
    Summary,
    /// 环境变量（默认 mask，reveal=true 显示真值）
    Env,
    /// 该 PID 全部监听与连接 + 最近 5 条 DNS 查询
    Network,
    /// 已加载模块（Windows DLL / Linux .so，按路径字母排序）
    Dlls,
    /// 内存映射（VirtualQueryEx / /proc/<pid>/maps 内存区域）
    MemoryMap,
    /// 进程打开的所有句柄（File / RegistryKey / Event / Semaphore / Mutant / ...）
    /// 注：proc_handles 已有独立 tool（v0.7 落地），此处复用同路径
    Handles,
}
```

**返回 JSON schema 按 tab 分支**（不同 tab 返不同字段集）：
- `summary`：进程基本信息 + 18 项风险因子完整描述 + signature_status + parent_chain + 启动路径合规性
- `env`：环境变量列表（KEY=VALUE，secret mask）
- `network`：监听 + 连接 + DNS 历史 5 条
- `dlls`：模块路径 / 基址 / 大小
- `memory_map`：内存区域基址 / 大小 / 状态 / 保护 / 映射文件名
- `handles`：句柄列表（与既有 proc_handles 返同款 schema）

### 类别 4：系统级 metrics（5 tool，~300 行）

> 5 个独立 tool（不合并），让 agent 按需调用避免一次返大量不需要的数据。

| Tool | 范围 | 工作量 |
|---|---|---|
| `proc_metrics_system` | CPU/内存/swap 使用率 + 30 秒火花线图历史 + 系统运行时间 + 网卡 IP | ~70 行 |
| `proc_metrics_gpu` | NVIDIA via NVML（VRAM / 温度 / 功率 / 利用率）+ DXGI（所有 vendor VRAM）+ PDH utilization | ~70 行 |
| `proc_metrics_disk_io` | 每磁盘独立读写速率 + 每进程 I/O 速率（`(pid, start_time)` 键防 PID 复用） | ~60 行 |

## MCP 模块深度调研（cycle 设计基础）

> 本段是 brainstorm 起草阶段的 MCP 模块调研产出，供 stage 1 Spike 设计参考。

### 当前 MCP 架构（v0.7 落地，v0.12 修 TD-36）

**文件结构**：
```
src/mcp/
├── mod.rs           (38 行，run_mcp_serve 入口 + tokio current_thread runtime)
└── handler.rs       (1156 行，ProcMcpHandler 单文件 17 个 #[tool] 方法 + 12 个 JsonSchema 参数 struct)
```

**关键技术点**：
- `rmcp = "0.11"` SDK，features = `["server", "transport-io"]`
- `#[tool_router(server_handler)]` 自动生成 `ServerHandler impl`，每个 `#[tool(name = "proc_xxx")]` 方法被 `ProcMcpHandler::tool_router()` 收集
- 每个 tool 入参用独立 `#[derive(Deserialize, schemars::JsonSchema)]` struct（line 106-203 共 12 个），rmcp 自动生成 JSON schema 给 client
- 持久 `dns_collector: Arc<Mutex<Option<Box<dyn DnsLogCollector>>>>` 字段（v0.12 TD-36 fix），`ProcMcpHandler::new()` 调 `detect_collector()` spawn 一次
- runtime = `tokio::current_thread`（不是 multi_thread），Docker 调用走自己的 rt 避免线程争抢
- stdio transport（不接受 HTTP/SSE）

**17 个已暴露 tool**（grep `name = "proc_` 验证）：
1. `proc_ls` — 进程列表（按 cpu/mem/name/pid/disk_read/disk_write/net_sent/net_recv 排序，limit 裁剪）
2. `proc_tree` — 进程树（递归）
3. `proc_port` — 端口占用（可 kill）
4. `proc_kill` / `proc_pkill` — 终止进程（写操作，无 dry_run）
5. `proc_eject` / `proc_who` — USB 占用 / 反查
6. `proc_handles` — 句柄枚举（v0.5 落地）
7. `proc_priority` / `proc_affinity` — 优先级 / affinity（写操作）
8. `proc_smart` — SMART 磁盘健康
9. `proc_dns` — DNS 查询日志（持久 collector，drain 一次）
10. `proc_diag` — worker metrics JSON
11. `proc_monitor_list` — 监控配置快照（只读，不能 add/remove）
12. `proc_docker_ps` / `proc_docker_top` / `proc_docker_logs` — Docker 3 个 tool

**字段裁剪原则**（v0.7 ADR-0009 落地）：
- `proc_ls` 不返回 `exe` / `cwd` / `user_id`，避免 LLM 上下文泄漏敏感路径
- 其他 tool 默认不返回 cmd 真值（含 secret pattern 时 mask）
- v0.6 env mask 12 关键字 pattern（KEY/TOKEN/SECRET/PASSWORD/PASSWD/PWD/CREDENTIAL/PRIVATE/AUTH/API/DSN/CONNECTION_STRING）+ `*_AUTHORIZATION` 后缀 + `DATABASE_URL` 特例

**未暴露的 CLI 命令 + 能力缺口**（v0.15 cycle 候选）：
- CLI 已有但 MCP 未暴露：`flows` / `throttle` / `export` / `docker inspect/images/volumes/events` / `monitor --add/--remove` / `inspect`（详情页 Tab 入口）/ `top` / `logs`（注：top/logs 是 docker 子命令，已部分通过 docker_top/docker_logs 暴露）
- 详情页 6 个 Tab 数据：当前只暴露 `proc_handles`，缺 summary / env / network / dlls / memory_map
- 系统级 metrics：侧边栏 CPU/内存/GPU/SMART/per-process 网络/降频等系统全貌 agent 看不到
- 录屏 v2（v0.14 落地）：record / replay / search / bookmarks 完全不暴露

### v0.15 cycle 模块重构（stage 1 Spike 任务）

**问题**：当前 `src/mcp/handler.rs` 单文件 1156 行，加 14 个新 tool 后会涨到 ~2000+ 行，违反单文件可读性原则。

**重构方案**（stage 1 Spike 任务）：
```
src/mcp/
├── mod.rs                       (38 行，run_mcp_serve 入口)
└── handler/
    ├── mod.rs                   (~150 行，ProcMcpHandler 主 impl + tool_router 收集)
    ├── cli.rs                   (~600 行，类别 1 CLI 命令 tool + 类别 3 写操作 tool)
    ├── inspect.rs               (~400 行，类别 2 proc_inspect tool 含 6 tab)
    └── metrics.rs               (~300 行，类别 4 系统指标 5 tool)
```

**重构原则**：
- `#[tool_router(server_handler)]` 仍在 `ProcMcpHandler` 主 impl 上（rmcp 限制）
- 每个 tool 方法可以在子 module 里定义，但需要 `impl ProcMcpHandler { ... }` 在主 mod 里展开（或用 `#[tool]` 标注的方法直接在子 module 定义，主 mod 通过 `tool_router` 收集 — 需验证 rmcp 0.11 是否支持跨 module 收集）
- 既有 17 个 tool 的 `#[tool]` 方法和参数 struct 暂不动（避免回归），新 14 个 tool 在子 module 添加
- stage 1 Spike 产出 module 骨架（空 tool 方法 + 占位返回），stage 2 / stage 3 各 Slice 填充业务逻辑

### v0.7 ADR-0009 字段裁剪原则延续

v0.15 cycle 14 个新 tool 的字段裁剪决策：

| Tool | 字段裁剪 |
|---|---|
| `proc_inspect(summary)` | 返回完整风险因子（agent 需要看扣分理由）+ cmd 真值（agent 需要判断是否合法脚本）— 与 v0.7 `proc_ls` 裁剪原则不同（详情页视角比列表视角更深） |
| `proc_inspect(env)` | 默认 mask secret 12 关键字 + `*_AUTHORIZATION` 后缀 + `DATABASE_URL`；`reveal=true` opt-in 显示真值 |
| `proc_inspect(network)` | 返完整远程地址 + 端口（与 `proc_port` 一致） |
| `proc_inspect(dlls/memory_map/handles)` | 返完整路径 + 基址（agent 需要判断是否可疑位置） |
| `proc_flows` | 返 sni / dns_name / remote_addr / bytes_out/in / source（与 CLI `proc flows` 字段一致） |
| `proc_throttle` | 返 EcoQoS 状态 + 🍃 标记 + admin 权限提示（非 admin 时） |
| `proc_metrics_*` | 返完整指标（无敏感数据） |
| `proc_export` | 默认 format=json 输出到 stdout（不写文件），agent 可拿到完整 JSON |
| `proc_docker_inspect/images/volumes` | 返完整 bollard 数据（无敏感字段裁剪） |
| `proc_docker_events` | 一次性 drain（非 follow），返最近 N 条事件（默认 limit 100） |
| `proc_monitor_add/remove` | 默认 `dry_run=false`（与 proc_kill 一致），暴露 `dry_run: Option<bool>` opt-in 预演 |

## 常见问题 FAQ

### Q1: v0.15 cycle 与 v0.7 ADR-0009 字段裁剪原则的关系？

**A**: v0.7 ADR-0009 设计的是**列表视角的字段裁剪**（`proc_ls` 不返 exe/cwd/user_id 避免大量进程的敏感路径污染 LLM context）。v0.15 cycle 的 `proc_inspect` 是**详情页视角**（agent 主动查单个进程 = 已同意看真值），返完整 cmd / exe / cwd 真值。两个视角互补，不冲突。

**例外**：`proc_inspect(env)` 默认仍 mask secret 12 关键字（env 是 secret 高发区，与 v0.6 详情页 env tab 同款契约 — `v` 键显式 reveal）。

### Q2: 写操作（proc_kill / proc_docker_image_rm / proc_bookmarks_delete）的 confirm 机制？

**A**: v0.15 cycle 暴露的写操作（`proc_monitor_add` / `proc_monitor_remove`）默认 `dry_run=false`（与既有 `proc_kill` / `proc_pkill` v0.7 契约一致）。agent 想要预演可以 `dry_run=true` opt-in。

**未来考虑**（v0.16+）：如果用户反馈 agent 误操作（如 Claude 错误 kill 进程），评估加 MCP-level confirm 机制（如 tool 返 `requires_confirm: true` 让 client 提示用户）。v0.15 不做。

### Q3: `proc_inspect` 返回字段 schema 如何让 LLM 理解？

**A**: rmcp 0.11 的 `schemars::JsonSchema` derive 自动从 Rust 类型生成 JSON schema 给 client。`proc_inspect` 用 enum `InspectTab` 让 schema 反映 tab 分支（rmcp 应该支持 enum schema，stage 1 Spike 验证）。

**fallback**：如果 rmcp 0.11 对 enum + 不同 tab 返不同 schema 支持有限，stage 1 改设计为返 ` { tab: "...", fields: {...} }` 通用结构（fields 是 `serde_json::Value`，schema 描述用 doc 注释）。

### Q4: 系统指标 5 个 tool 一次调用 vs agent 多次调用？

**A**: 5 个独立 tool 让 agent 按需调用。典型场景：
- agent 想「快速诊断 CPU 高」→ 只调 `proc_metrics_system` + `proc_ls --sort cpu`
- agent 想「检查磁盘健康」→ 只调 `proc_metrics_smart`
- agent 想「完整诊断」→ 调 5 个（与一次返全部等价，但 agent 自己决定顺序）

合并成 1 个 `proc_metrics(category=...)` 会让 agent 必须知道 category 枚举，UX 反而差。

### Q5: MCP server 性能（14 个新 tool 后启动是否变慢）？

**A**: rmcp 的 `#[tool_router]` 是编译期宏，runtime 不扫描 tool 列表（与 v0.7 落地 17 tool 同款开销）。新增 14 tool 不影响 MCP server 启动延迟。每个 tool 是 lazy 调用（agent 不调不耗资源），与既有 17 tool 一致。

### Q6: v0.15 cycle 是否破坏既有 17 tool 契约？

**A**: 不破坏。stage 1 Spike 重构 `src/mcp/handler.rs` → `src/mcp/handler/{mod,cli,inspect,metrics}.rs` 时，**既有 17 tool 的 `#[tool]` 方法和参数 struct 保持原位**（迁移到 `cli.rs` / `inspect.rs` 等子 module 的对应类别段），schema 不变。stage 4 Review 会验证既有 17 tool 的端到端调用无回归。

### Q7: 录屏 v2 + 操作类为什么推迟到 v0.16？

**A**: 三个理由：
1. **v0.15 单一主题**：查询类（看，不写）让 cycle 内聚强；写操作 + 录屏涉及状态机和持久化，复杂度高
2. **录屏 v2 schema 复杂**：`proc_replay_search` 含 FilterExpr FrameField 5 维度 + matches 状态机 + cursor，agent 视角的 schema 设计需独立评估（一次性返所有命中帧还是分页？匹配数太多时如何 limit？）
3. **写操作 confirm 机制评估**：`proc_bookmarks_delete` / `proc_docker_image_rm` 等破坏性写操作是否需要 MCP-level confirm？v0.16 cycle 单独评估

### Q8: ADR 是否需要更新？

**A**: stage 1 Spike 产出新 ADR：
- `docs/adr/0023-mcp-inspect-tool-merge.md`（详情页 6 Tab 合并成 1 个 proc_inspect tool 的设计决策）
- `docs/adr/0024-mcp-handler-module-split.md`（handler.rs 单文件 → handler/ 子 module 的重构决策）
- 既有 `docs/adr/0009-mcp-server.md` 不动（Status 仍 Accepted，新 ADR 是增量扩展）
