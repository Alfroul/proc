## 实施决策（stage 2 内拍板，按 brainstorm 步 15 规则记录）

### 决策 A：执行排序 = 项 1 → 项 5 → 项 2 → 项 3 → 末段 fixture

brainstorm 风险 3 mitigate 1 拍板：trait 层补全 → ToolRegistry（MockProvider
测试需要 tool schema）→ MockProvider（GGUF 测试不依赖它）→ GGUF scanner →
末段 fixture 文件。基础设施先行，依赖方向无环。

### 决策 B：弃用 gguf crate，手写流式 GGUF metadata parser

stage 1 选型时假设 `gguf` crate 可只读 KV metadata。实施时实读 gguf 0.1.2
源码发现：`GGUFFile::read` 把 header + tensor info 段绑定解析（nom streaming
parser，`pub(crate) fn gguf_header` 不暴露），且输入不完整时 nom `Incomplete`
→ 直接返 `Ok(None)` **丢弃已解析的 header**。对 1.6GB 的 E2B 模型要么全量
读入内存、要么拿不到 metadata，两者都不可接受。

**落地**：`gguf_scan.rs` 手写流式 parser（File + BufReader 顺序读 magic /
version / tensor_count / metadata_count + 逐条 KV，值段可 seek-skip，metadata
段结束即停，~100 行）；**Cargo.toml 移除 gguf dep**。GGUF 格式 v2/v3 的
metadata 编码是公开稳定规范，parser 复杂度低于 ETW 系（v0.11/v0.10 已两次
手写二进制 parser，同档）。

### 决策 C：真实 LLM fixture 录制挪 stage 3b 末段；stage 2 产出 seed fixture

fixtures.md 原计划 stage 2 末段录制，但**录制需要真实 provider**——
LlamaCppProvider 在 stage 3a、AnthropicProvider 在 stage 4、AgentRunner（LLM
响应依赖其 system prompt 最终形态）在 stage 3b。stage 2 只有 MockProvider，
无物可录。

**落地**：stage 2 落地 `record_fixture.rs` 完整录制工具（接口按 fixtures.md
签名，任意 `Box<dyn LlmProvider>` 可注入，stage 3b 用 LlamaCppProvider 实调）
+ **seed fixture**（70 query 合成响应，JSONL 结构合法、确定性回放，供 CI
回放测试与格式验证；真实录制后逐文件覆盖替换）。L0 23 + L1 27 共 50 query
回放测试在 stage 2 即可跑通。

### 决策 D：fixture 行格式加 `query` 字段，query_hash 加载时计算

fixtures.md 格式只有 `query_hash`。手工 / 工具生成 fixture 时必须预先算
SHA-256，且无法肉眼核对 hash ↔ query 对应关系。**落地**：每行加 `query`
字段（query 原文），`MockProvider` 加载时从 `query` 现算 hash 建索引（
self-verifying，行内 `query_hash` 字段若存在则校验一致）。回放匹配键仍是
「最后一条 user message 的 SHA-256 前 16 hex」不变。

另：hash 输入只含 query 文本（不含 provider 名）——录制 provider（gemma /
anthropic）与回放 provider（mock）不同名，含 provider 名会导致永不命中。
`request` 字段存录制时的 provider / messages / tools 供 diff。
