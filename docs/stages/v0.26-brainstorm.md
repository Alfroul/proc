## 基线验证异常记录（两起，均环境/过程观察非回归）

### R1：llama e2e flaky 竞态首次触发（修复并入本 cycle stage 2）

全量默认档**首跑 35/79 行截断、1 failed**——`test_llama_cpp_provider::test_real_llama_server_end_to_end` 清理断言「provider drop 后 llama-server 应已退出」红（`tests/test_llama_cpp_provider.rs:525-530`）。

- **机制**：同二进制内两个真实 server 测试（end_to_end + grammar_constrains_output，均 v0.20 `f171cb9` 引入）默认并行执行；end_to_end 的清理断言用**全局** `tasklist` 检查 llama-server.exe——grammar 测试自己的 server 仍存活时误报。功能断言全过（complete 6.2s 真实推理 / stream 24 deltas）
- **实证**：单跑该二进制绿（27/0，11s）/ 全量复跑绿（1742/0/10，79 行齐）；失败时系统无残留 llama-server 进程
- **历史**：v0.20 引入以来连续 5 个 cycle 基线首跑全绿，本次首次触发——TD-58 同款「首跑红、重跑绿」模式（**注意：非 TD-58 本体**，是另一处 flaky）
- **本 cycle 处置**：**stage 2 修复**（断言改查自身子进程 PID 退出而非全局 tasklist，~30-80 行级测试 + handle 小改）——技术理由：stage 2 的质量门禁（gate 脚本跑测试子集）会随机撞此竞态，修复是门禁可靠性的前置；修复后 TD 直接关闭（不留 TD-62 观察项）

### R2：clippy 默认档红——v0.25 stage 3 遗留 lint，本会话已机械修复

`tests/test_mcp_v0_25_stage_3.rs:24` 触发 `field_reassign_with_default`（`Default::default()` + 逐字段赋值写法；1.95.0 自带老 lint，工具链未变）。该文件由 stage 3 收尾 commit `2297738`（08-31 00:22）引入且 REVIEW-v0.25 声明「clippy 双档全过」——**判定 stage 3 会话漏检**（clippy 跑在测试文件写入之前），REVIEW-v0.25 基线声明在 tag v0.25.0 上不成立（P2 级过程 miss，非业务缺陷）。

- **修复**（本会话）：按 clippy 自荐改为 struct 字面量 `{ pid, start_time, disk_usage, ..Default::default() }`——仅测试 helper、零行为变化；该二进制复跑 8/8 绿；clippy 双档恢复绿

## 已知风险

### 风险 1：demo GIF 依赖用户录制（协作项）

stage 1 交付录制规格（时长/内容清单/工具建议），用户录制后 stage 3 挂载——**不阻塞**：未就绪则 README 占位（`<!-- demo GIF -->`）后补，stage 3 验收不含 GIF 在位。

### 风险 2：竞品对比表信息时效

stage 1 WebSearch 核实 btop / bottom / System Informer / glances 现状，表内标注「as of 2026-09」；不确定项宁缺毋滥（空格 + 「未核实」优于错误信息）。

### 风险 3：展示层数字自创（诚信风险——面试场景放大）

README / performance.md / deep-dive 所有数字强制溯源（来源文件旁注或 Review 抽查核对）；bench 数字必须是本 cycle 实测 log 的转写不是记忆值；**面试官会抽查，错误数字比没有数字更伤**。Review 段抽查 ≥ 10 个数字回溯。

### 风险 4：proptest 在 16GB 机器的开销

cases ~256 + 单 case 微秒级（parser 纯函数无 IO）预期秒级；如 CI/回归时长显著上升，降 cases 或 feature-gate（`#[cfg(feature = "proptest-suite")]`？——不加 feature，直接降 cases，Simplicity First）。

### 风险 5：gate 快档选型失衡

快档过慢（→ hook 被绕过）或过快（→ 覆盖不足）——stage 1 摸底各 test binary 耗时定名单（目标快档 < 3-5 min），stage 2 实测调整；hook 是 opt-in（`core.hooksPath`）不强推，仓库 required checks 是主防线。

### 风险 6：深挖导览范围蔓延

10 条清单 ADR-0036 定稿封闭（只砍不加）；每条 30-45 行预算，超限砍条目不砍深度（深挖三层是价值所在）。

### 风险 7：R1 修复涉及 handle API 变更超预期

预期小改（getter / is_alive 查询）；如需改 spawn 生命周期管理（KillOnDrop / Job 对象）属大改——触发回拍板流程（步 15）不在 stage 2 内偷偷扩。

### 风险 8：README 重构破坏既有用户手册价值

评估者视图**加在顶部**，既有功能/快捷键/CLI/FAQ 段落后移不删（老用户 + 面试官双受众）；重构以段为单位 diff 可审。

## FAQ

### Q1: 展示冲刺 cycle 的价值怎么论证（无 eval 列）？

零挂机 cycle，质量论证四轴（v0.25 先例延续）：① 不变锚（tool 46 / catalog 47 / runtime deps +0）全程保持 ② 回归数字 + gate 脚本新增机器可验证锚 ③ 数字溯源纪律（展示内容不自创）④ Review 段抽查核对（≥ 10 数字回溯 + 展示层完整性 + 门禁有效性）。

### Q2: 为什么门禁在展示层之前（stage 2 先于 stage 3）？

R2 的教训结构化：变更落在人工验证之后 = 门禁失效。stage 2 先把 fmt/clippy/测试子集变成 pre-push 机器门禁，stage 3 的大量 README/文档变更即在门禁保护下进行（clippy/fmt 对 md 不生效，但 stage 3 若顺带动任何 rs 文件即受保护；且 badge 挂接需要 CI 绿状态先稳定）。

### Q3: 深挖导览为什么放仓库（不怕面试官看到「备考材料」）？

文件名与行文中性（`architecture-deep-dive.md`「设计深挖导览」）——内容本身是高质量架构叙事，面试官看到是加分（「候选人对自己的设计决策有三层深挖准备」正是想考察的能力）；备考价值与展示价值同构。

### Q4: 附录 A 什么时候重启？

条件变化即启动（下载意愿 / key 到位 / llama.cpp 升级）——v0.27+ 候选评估时按附录 A 重启纪律只重评三项约束，设计直接复用。秋招结束后（2026-11+）是自然重评窗口。

### Q5: stage 4 Review 与收尾同会话，独立性怎么保证？

按数据锚审不自评：数字溯源抽查清单 / 不变锚核对 / gate 有效性实测（故意引入一个 fmt 违规验证 gate 拦截）/ 展示层完整性（badge 渲染 / mermaid 渲染 / 链接有效）；深挖导览作为该段前半产出，Review 段审它如同审其他 stage 产出。
