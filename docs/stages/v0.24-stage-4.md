## 已知风险（stage 4 实施时关注）

### 风险 1：REVIEW 审查依据二手资料（不重读实现源码）

**问题**：四维度审查以 CHANGELOG stage 段 + ADR-0034 落地注记 + eval 归档为据，不逐文件重读 `src/agent/rag/`——可能漏实现层瑕疵。
**mitigate**：REVIEW 明确标注审查口径（依据归档资料）；实现层疑点如实写「未复核」而非推断；P0/P1 判级从严——本 cycle src 净 diff 8 文件且全过 clippy/回归双档（本会话开工复核），结构风险低。

### 风险 2：tag 打错难撤

**问题**：annotated tag 打在错误 commit 或 push 后才发现问题，撤回成本高（push 过的 tag 要 force 才能覆盖）。
**mitigate**：tag 前核对 `git log` 确认 HEAD 即 stage-4 commit；**push 等用户确认**（本阶段不自动 push——打错时本地 `git tag -d` 零成本）。

### 风险 3：收尾文档间的数字漂移 + 勘误边界

**问题**：REVIEW / CHANGELOG / README / brainstorm 总结四处引用同批数字（回归 / 净 diff / 四列矩阵 / 机制验证），手抄易漂移；勘误（ignored 9→10）与既有记录并存易生新混乱。
**mitigate**：数字以本 doc 任务 2 收集值为唯一来源（src +921/-7 / tests +723 / docs +1381 / 回归 1689→1725 + 1713→1749 / 四列 32/35/37/27 / degraded 21/19/9/24）；写完交叉 grep 复核（`1725` / `-12` / `37/70` 等关键数字在四处一致）；勘误只改数字一处一行（brainstorm + CHANGELOG 各一处），commit message 明示勘误——grep「1725/0/9」确认归零。
