## 设计决策（本阶段拍板，stage 3-7 不动 parent_chain 类型）

### 决策 1：`parent_chain` 元组类型 `(u32, String)` → `(u32, Arc<str>)`

参考 v0.6.0 阶段 4 落地的 `ProcessInfo.name: Arc<str>` 模式（line 546）+ `name_lower: Arc<str>`（line 573）+ `exe / cwd / user_id: Option<Arc<str>>` 同款 serde 透明传递模式：

```rust
// src/collect.rs:588 — 字段类型变更
- #[serde(default)]
- pub parent_chain: Vec<(u32, String)>,
+ #[serde(default)]
+ pub parent_chain: Vec<(u32, std::sync::Arc<str>)>,
```

**关键设计点**：

1. **serde 透明传递**：`Arc<str>` 序列化 / 反序列化行为与 `String` 等价（serde 给 `Arc<T>` 提供 `impl Serialize` / `Deserialize` 透明转发到 `T`）。新代码读旧 `.prec` 文件（v0.16 String 序列化）→ Arc<str> 反序列化无障碍；旧代码读新 `.prec` 文件同理。**无需写迁移层 / 兼容 shim**。
2. **零 heap alloc 优势**：`build_parent_chain` body 用 `Arc::clone(&parent_proc.name)` 替换 `parent_proc.name.to_string()` —— Arc refcount 是原子计数 inc，无 heap alloc；老路径每元素都 `String::from(to_string)` 分配 + 拷贝。
3. **`Default::default()` 字段不变**：`parent_chain: Vec::new()`（空 Vec，无元素就无类型差异）。
4. **`PartialEq` derive 不变**：`Arc<str>: PartialEq` 比较底层 str 内容（指针不同但内容相同则相等），现有 `ProcessInfo: PartialEq` derive 行为保持。
5. **`Debug` derive 不变**：`Arc<str>: Debug` 输出与 `String: Debug` 等价。

**与 v0.6 `name: Arc<str>` 落地差异**：v0.6 改 `name` 时同时改了 `FrameProcess.name`（line 191 仍 `String`，保留 serde 兼容）；本 stage `parent_chain` 在 `FrameProcess` 中**根本没有该字段**（录屏文件不存 chain，replay 路径用不到），所以无需触碰 `FrameProcess`，只改 `ProcessInfo`。

### 决策 2：`build_parent_chain` 零 heap alloc 实装

```rust
// src/security/lineage.rs:149 — 函数签名 + body
- pub fn build_parent_chain(pid: u32, processes: &HashMap<u32, ProcessInfo>) -> Vec<(u32, String)> {
+ pub fn build_parent_chain(pid: u32, processes: &HashMap<u32, ProcessInfo>) -> Vec<(u32, std::sync::Arc<str>)> {
      let mut chain = Vec::new();
      let mut visited: HashSet<u32> = HashSet::new();
      visited.insert(pid);
      let mut current = pid;
      while chain.len() < MAX_PARENT_CHAIN_DEPTH {
          // ... 中间逻辑不动 ...
-         chain.push((parent_pid, parent_proc.name.to_string()));
+         chain.push((parent_pid, std::sync::Arc::clone(&parent_proc.name)));
          current = parent_pid;
      }
      chain
  }
```

**关键设计点**：

1. **Vec 自身仍分配**：返回 `Vec<(u32, Arc<str>)>` 时仍 alloc Vec header（24 bytes）+ elements buffer（每元素 12 bytes：u32 + Arc 指针 8 bytes padding 对齐）。这是「单次 Vec 分配」而非「每元素 String 分配」。1000 进程单轮：1000 次 Vec 分配 + 0 次 String 分配，vs 旧路径 1000 Vec + ~32000 String 分配（按 32 深度链）。
2. **`chain.clone()` 在 collect.rs:964 也变便宜**：clone Vec 时元素是 `Arc::clone` 原子 inc，无 String 拷贝。`heavy_parent_chain_pass` 写回 1000 进程的 chain 时，1000 次 Vec clone（每 ~100-500 字节）vs 旧 1000 Vec + ~32000 String clone。
3. **HashMap 内嵌 tests `make_proc` helper 仍用 `Arc::from` 构造 name**：测试 fixture 路径不在乎 alloc 数量，只验功能正确。

### 决策 4：测试 fixture 字面量统一改 `Arc::from("...")`

`tests/test_lineage.rs` 的 `make_proc` helper（line 12-45）+ 13 处测试调用点 + `src/security/lineage.rs` 内嵌 tests 5 处 `vec![(N, "...".to_string())]` 字面量统一改为：

或更精炼地定义 helper：

```rust
// tests/test_lineage.rs 顶部加 helper
fn chain(pairs: &[(u32, &str)]) -> Vec<(u32, std::sync::Arc<str>)> {
```

## 已知风险

### 风险 1：`Arc<str>` 上 `.as_str()` 编译失败

**问题**：`src/security/lineage.rs` line 200 / 209 / 231（内嵌 + 外部）+ `src/tui/detail_view.rs` line 373 / 411 用 `n.as_str()`，其中 `n` 是 `&String`（旧）→ `&Arc<str>`（新）。`Arc<str>` 没有 `.as_str()` 方法（与 `String` 不同），编译会失败。

**mitigate**：cargo check 时立刻发现；统一改 `n.as_ref()`（Arc<str>: AsRef<str>）或 `&**n`（Deref）。优先 `as_ref()` 风格统一。

### 风险 2：serde JSON 旧格式兼容性

**问题**：v0.16 旧 `.prec` 文件用 bincode 序列化 `Vec<(u32, String)>`。v0.17 改 `Vec<(u32, Arc<str>)>` 后，bincode 是否能读旧文件？

**mitigate**：serde 给 `Arc<T>` 的 impl 是透明转发（`#[derive]` 内部用 `serialize`/`deserialize` 直接转发到底层类型），bincode 看到的是相同的 byte layout。验证方式：写测试 `parent_chain_serde_legacy_json_round_trip`（决策 5），用旧格式 JSON 反序列化到新结构，断言 chain 内容等价。如测试通过 → bincode 也透明（同款 serde 接口）。

### 风险 3：bench baseline 文件不存在

**问题**：`cargo bench --bench bench_refresh_heavy -- --baseline v0.16` 要求本机先存 v0.16 baseline。如未存，criterion 报错。

**mitigate**：fallback 直接跑 `cargo bench --bench bench_refresh_heavy`，肉眼对比 commit `2aab60e` 前后两次跑的 alloc 数字（参考 PERF-BASELINE-v0.13 报告 v0.16 状态）。

### 风险 4：PartialEq derive 行为差异

**问题**：`ProcessInfo` derive PartialEq，新字段 `Vec<(u32, Arc<str>)>` 的 PartialEq 比较：Arc<str> 是指针比较还是内容比较？

**mitigate**：Rust 标准库 `impl PartialEq for Arc<T>` 是**内容比较**（`fn eq(&self, other: &Arc<T>) -> bool { self.deref() == other.deref() }`），与 `String: PartialEq` 等价。既有依赖 `ProcessInfo: PartialEq` 的测试（test_security / test_scorer_concurrency 等）行为不变。

### 风险 5：`json!` 宏 Arc<str> 兼容性

**问题**：`src/mcp/handler/inspect.rs:159` `json!({ "name": pname })` 中 pname 旧是 `&String` / 新是 `&Arc<str>`。json! 宏内部用 `serde_json::Value::from`，是否接受 Arc<str>？

**mitigate**：`serde_json` 提供 `impl From<Arc<str>> for Value`（v1.0+ 标准 impl），透明接受。验证方式：`cargo test --release -q test_mcp_v0_15` 全过（test_mcp_v0_15.rs:266 断言 parent_chain 是 array）。

### 风险 6：测试 helper `make_proc` 调用点遍历不全

**问题**：`tests/test_lineage.rs::make_proc` helper 有 13 处调用点，如遗漏 1 处 `vec![(N, "..".to_string())]` 字面量 → type mismatch 编译失败。

**mitigate**：用 `grep '\.to_string()' tests/test_lineage.rs` 找全所有字面量；cargo check 编译失败时 grep 错误信息定位遗漏点。
