## 设计决策（stage 2 拍板）

### 决策 1：dry_run 默认 false（与 brainstorm 同款）

`proc_monitor_add` / `proc_monitor_remove` 默认 `dry_run=false`（直接执行），与既有 `proc_kill` / `proc_pkill` v0.7 契约一致。agent 想要预演可以 `dry_run=true` opt-in。

dry_run 路径只返 preview JSON（不含副作用），与 `make_pkill_json` 同款。注意：`MonitorManager` 是 in-memory 的（无磁盘持久化），每次 `new()` 都是空表，所以 stage 2 的 `monitor_add` / `monitor_remove` 仅在 process 内有效。stage 4 Review 评估是否加配置持久化（暂留，与 v0.7 既有的 `proc_monitor_list` 行为一致 — 都是空表起步）。

### 决策 2：字段裁剪 — 详情页视角 vs 列表视角

`proc_inspect(summary)` 返**完整 cmd / exe / cwd 真值**（详情页视角，agent 主动查单个进程 = 已同意看真值）。v0.7 `proc_ls` 列表视角裁剪 exe/cwd/user_id（避免大量进程的敏感路径污染 LLM context）。两视角互补不冲突（详见 brainstorm §v0.7 ADR-0009 字段裁剪原则延续 + FAQ Q1）。

例外：`proc_inspect(env)` 默认仍 mask secret 12 关键字（`is_secret_key`），`reveal=true` opt-in 显示真值（与 v0.6 env_reveal 同款契约）。

### 决策 3：proc_flows 走 App::new() + 2s warm-up

`proc_flows` 需要 Schannel ETW worker 起来才能采到 SNI 事件，与 `make_diag_json` 同款 `App::new() + 2s warm-up` 路径。worker 不可用（非 admin / x86 / session 占用）→ `flows: []` + `worker: "unavailable"` 提示字段。

agent 多次调 `proc_flows` 会每次 spawn App（~2s 开销），可接受（MCP tool 不是高频路径，agent 一次 task 通常调 1-2 次）。

### 决策 4：proc_docker_events 一次性 drain（非 follow）

MCP 是 request-response 模型，不能 follow event stream。stage 2 实装走 `bollard::events` + 短超时（500ms）drain 一批，按 `limit` 截断（默认 100）。返 `{ ok, count, events[] }`，每个 event 含 `action / container_id / container_name / timestamp_unix`。

### 决策 5：proc_inspect 字段裁剪 — tab 分支返不同 schema

| Tab | 字段集 | 复用源 |
|---|---|---|
| Summary | 基本信息（pid/name/cpu/mem/cmd/exe/cwd/parent_pid/start_time/run_time/throttled/signature_status）+ parent_chain + risk_factors | `ProcessInfo` + `SecurityScorer::score` |
| Env | env_vars[]（key/value/is_secret，secret 默认 mask） | `inspect::env::collect_env` + `env_mask::mask_value` |
| Network | listening[]（PortEntry，local_addr/local_port/state）+ established[] + dns_recent[]（最近 5 条 DNS 查询） | `port_map::find_ports_by_pid` + DNS collector drain |
| Dlls | dlls[]（path/base_addr/size） | `inspect::dlls::collect_dlls` |
| MemoryMap | regions[]（base_addr/size/state/protection/name） | `inspect::memory::collect_memory` |
| Handles | handles[]（与 proc_handles 同 schema：kind/name/raw_handle/granted_access） | `inspect::handles::collect_handles` |

返 `serde_json::Value` 而非强类型 schema —— 不同 tab 字段集差异大，schemars 无法精确表达 oneOf return schema（ADR-0023 §负面 同款注释）。

### 决策 6：stage 2 不动 mod.rs 的 #[tool] 方法签名

`#[tool]` 方法体仍只 1-2 行（`ok_result(cli::make_flows_json(args.limit))`），仅在子 module 替换 stub helper 为真实业务实现。impl 块结构稳定 → 既有 17 tool 零回归（与 stage 1 决策 1 / ADR-0024 同款 surgical 原则）。

仅更新 10 个 stage 2 tool 的 `description` 字段（去掉 "Stage 1 stub" 字样，写清返回字段）。

## 已知风险

### 风险 1：proc_flows / proc_diag 路径 spawn App（慢）

每次调 `proc_flows` 都 `App::new()` + 2s warm-up，agent 多次调用累积开销大。**已 mitigate**：与既有 `make_diag_json` 同款路径（v0.7 已落地），agent 实际不会高频调（典型 task 调 1-2 次）。stage 4 Review 评估是否加 MCP handler 内的 App 复用（暂留）。

### 风险 2：proc_monitor_add/remove 无持久化

`MonitorManager::new()` 是 in-memory 空表，每次 MCP tool call 都新建。stage 2 实装的 monitor 加 / 删只在单次 tool call 内有效，跨调用丢失。**已 mitigate**：与既有 `proc_monitor_list` v0.7 行为一致（都空表起步）。stage 4 Review 评估加配置文件持久化（v0.16+ 候选）。

### 风险 3：InspectTab enum schemars 生成 oneOf schema

`InspectTab` 是 6 变体 enum，stage 1 落地时已验证 schemars 能正确生成 oneOf schema（编译过 + tool_router 收集到 32 个 tool）。stage 2 实装路径不动 enum 定义，仅扩 helper 体。**风险已清零**。

### 风险 4：proc_docker_events 短超时 drain（可能采不到事件）

500ms drain 可能在低活跃 docker daemon 上采不到任何事件，返空数组。**已 mitigate**：返 `{ ok: true, count: 0, events: [], note: "no events in 500ms window" }`，agent 理解为「暂时无事件」而非「错误」。
