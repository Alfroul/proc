## 关键决策

### 决策 1：cycle 结构——拆分 F 先行，C 留 v0.22 ✅

**v0.21 = F（TUI AgentPanel）单主主题 + 小项穿插；C（Eval + Observability）完整 eval 基础设施留 v0.22**。

理由见「候选方向评估」段。备选方案：
- (a) **拆分 F 先行**（✅ 拍板）：单主题 4 stage，容量可控，演示能力最快落地
- (b) 合并双主题（~3500 行 5-6 stage）：一次出两个能力点，但史上最大 cycle + 两主题互相拖延
- (c) 拆分 C 先行：先量化再 UI，但演示能力推迟一个 cycle

**用户拍板**：✅ (a)（2026-08-18）。

### 决策 2：写操作 confirm 通道——做 ✅

TUI 面板提供 y/n 确认，8 个写 tool 从「拦截返 blocked」升级为「确认后放行」。理由：

1. 这是 F 超越「聊天 UI」的最大能力增量——agent 从只读问答变成「帮你杀进程 / 弹 U 盘」的完整闭环，也是演示杀手锏核心
2. v0.20 dispatch 拦截设计天然预留了升级路径（blocked JSON 是「无确认通道」的降级，不是终态）
3. ADR-0008/0029 的 `confirm: bool` 必传契约语义不变——Approved 即用户代传 `confirm: true`

成本：ReAct loop 中途暂停等用户输入的新 async 流程（oneshot reply），~350-400 行（项 3）。CLI ask 路径拦截语义**不变**（非交互无通道）。

**用户拍板**：✅ 做（2026-08-18）。

### 决策 3：多轮对话 history——做 ✅

AgentSession 持 conversation messages（滑动窗口 system + 最近 12 轮），支持连续追问。chat 面板的基本预期，成本低（~90 行）。截断策略用代码常量不预加配置（v0.20「不预实现」原则延续）。

**用户拍板**：✅ 做（2026-08-18）。

### 决策 4：L2 处置——手动演示进 F，系统验收留 C ✅

L2 系统验收（真实 E2B 录制 20 query + 通过率口径 + 失败模式分析）本质是 eval 素材——E2B 多步预期低通过率（v0.20 L1 三步链 query 已暴露边界），价值是「能力边界实测数据」，与 C 主题内聚。F cycle 里用 TUI 面板手动演示多步 query 零额外代码且效果最好。

**用户拍板**：✅ 手动演示进 F / 系统验收留 v0.22 C-cycle（2026-08-18）。

**4 stage = 1 Spike + 2 Slice + Review+收尾合并段**（phased-project skill 自适应规则：Slice ≤ 2 时 Review 与收尾合并，末段自含验收 + 修复）。

### 决策 8（默认 surgical 排除，非拍板阻塞项）：proc_record_start/stop 不进 v0.21 ✅

REVIEW-v0.20 候选 5「正好随 TUI AgentPanel 评估」——评估结论：**推迟 v0.22+**。理由：

1. v0.20 dispatch 降级原因是「跨调用子进程保活」；confirm 通道落地后启用成本已降至 ~100 行（headless 子进程 `proc record --no-tui --duration N` 路径，无 TUI 嵌套冲突）
2. 但「agent 启动录屏」的语义边界复杂（录制范围是否含 agent 自身操作 / 停止时机），需单独设计
3. v0.21 聚焦 F 不分心；confirm 通道本身就是本 cycle 的写操作能力增量

同类默认排除（stage 1 落地时如有异议按 brainstorm 步 15 更新）：~~AgentPanel 入口键 `A`（Shift+A）+ 命令面板双通道~~ → **stage 1 实测更正（2026-08-18）：palette 唯一入口**。原计划 `A` 键与既有全局绑定冲突——`try_handle_tab_switch` 的「打开告警弹窗」（v0.7 落地，help_panel 全局段文档化，且在面板分发**之前**拦截，process_panel 的 `A` deselect_all 实际是被遮蔽的死绑定）。按 stage-1 doc 风险 2 预授权 fallback 执行：命令面板 `switch_to_agent_panel` 条目唯一入口（`CommandAction::SwitchPanel(AppMode::Agent)`，dispatch 零改动）+ 回归锚测试 `test_a_key_still_toggles_alert_popup`。**stage 3 前可重拍板**（迁移告警弹窗键位或另选键），见 ADR-0031 stage 1 落地注记。

## ADR-0031：TUI AgentPanel + AgentSession 流式会话架构（stage 1 落地骨架）

- **标题**：TUI AgentPanel + AgentSession 流式会话架构
- **Status**：Proposed（v0.21 stage 1 Spike 落地骨架 → Accepted）
- **Context**：
  - v0.20 `stream()` 三 provider 全实装但零消费方（唯一消费是测试断言）
  - CLI ask 非交互无确认通道，dispatch 拦截 8 个写 tool 返 blocked JSON
  - TUI 是 proc 主入口（AppMode 10 变体 + PanelController 模式成熟）；AgentRunner complete-only 单轮无 conversation history
  - TUI 主循环是同步 crossterm 事件循环，agent 是 async（tokio）——v0.20 风险 6 明确推迟到本 cycle 评估跨 runtime 集成
- **Decision**：
  - **D1：AgentSession 独立会话层**——专用 `std::thread` + 自有 tokio Runtime + `std::sync::mpsc` SessionEvent 通道桥接同步 TUI 主循环（WorkerManager 同款模式，TUI tick 内 try_recv drain）
  - **D2：runner 流式变体 `run_streaming`**——消费 `provider.stream()` 逐 delta 产出（TextDelta 透传）；complete-only 既有路径零改动（CLI ask 保持非流式批处理语义）
  - **D3：写操作 confirm 通道**——dispatch 写 tool 拦截升级为 `ConfirmRequest`（tool_name + arguments + 影响摘要 + oneshot reply）；Approved → `confirm: true` 真执行（ADR-0008/0029 契约），Denied → blocked JSON（模型转向解释）；CLI ask 拦截语义不变
  - **D4：多轮 conversation**——session 持 history 滑动窗口（system prompt + 最近 12 轮，代码常量）
  - **D5：按需 spawn 核心约束延续**——进入面板首次 query 才 spawn llama-server，退出面板 Drop kill（v0.20 决策 6 延续，日常使用零影响）
  - **D6：streaming 渲染节流**——TextDelta 在 tick 边界批量 append + 既有 pending_redraw 机制，不逐 delta 全量重绘
- **Consequences**：
  - AppMode 11 变体；App 加 `agent_panel` 字段（AgentPanelController）
  - dispatch 双模式（blocked 拦截 / confirm 通道）
  - 上下文窗口管理成为运行时关注点（滑动窗口 + 溢出降级提示）
  - confirm 挂起时的生命周期需显式收尾（退出面板 / Ctrl+C → Denied reply + cancel flag）
- **与既有 ADR 关系**：
  - 建立在 ADR-0030（内置 agent 基座）之上——本 ADR 是其 UI 消费层
  - 复用 ADR-0008（self-mitigation policy）+ ADR-0029（confirm 契约）——写操作 confirm 语义
  - 复用 ADR-0012（PanelController 模式）——AgentPanelController 同款
  - 复用 ADR-0010（command palette）——palette 入口注册
  - 参考 ADR-0019（worker 生命周期）——session 线程 + channel 模式

## 已知风险

### 风险 1：TUI 同步主循环 × async agent 的 runtime 集成（v0.20 风险 6 延续）

**问题**：TUI 主循环是同步 crossterm 事件循环；agent streaming 是 async（tokio + reqwest SSE）。直接在主循环 block_on 会卡死 UI。

**mitigate**：
1. AgentSession 专用 `std::thread` + 自有 tokio Runtime（与 TUI 完全解耦）
2. `std::sync::mpsc` 事件通道——async 侧 send（std Sender 线程安全），TUI tick 内 `try_recv` 非阻塞 drain（WorkerManager 同款既有模式）
3. stage 2 集成测试覆盖「session 线程send / 主线程 drain」端到端（ScriptedProvider 零 LLM）

### 风险 2：confirm 挂起时的生命周期

**问题**：AwaitingConfirm 状态下用户退出面板 / 退出 proc / Ctrl+C——oneshot reply 未决，runner 协程悬挂，llama-server 子进程可能不清理。

**mitigate**：
1. AgentSession Drop 时对 pending ConfirmRequest 发 Denied + 置 cancel flag，runner 走收尾路径
2. LlamaServerHandle Drop kill 模式已有（v0.20 stage 3a 实测无僵尸）
3. stage 2 集成测试覆盖「confirm 未决时 drop session 不挂死」（带超时断言）

### 风险 3：E2B 流式行为未实测

**问题**：v0.20 验收全走 `complete()` 非流式；llama-server SSE 流式 + `tool_choice=required` + proc_finish 组合下，E2B 的 stream 表现（tool_calls 分片 / EndTurn 时机 / proc_finish 调用）未验证。

**mitigate**：
1. stage 2 末段用真实 E2B 跑 2-3 query 流式冒烟（`#[ignore]` 测试，本机 llama-server）
2. LlamaCppProvider 的 SSE 分帧 + ToolCallAccum 已在 v0.20 stage 3a 实测过（`proc_ls {"limit":1,"sort":"cpu"}` 正确生成）——风险集中在 runner 流式循环的聚合逻辑，ScriptedProvider 可先全覆盖
3. 如冒烟发现 E2B 流式不可靠，stage 3 面板可降级为「tool 步骤流式 + 最终文本一次性」（事件面不变，仅 TextDelta 粒度变粗）

### 风险 4：多轮 conversation 的 ctx 溢出

**问题**：16K ctx + 动态扩 tools（6K 预算）+ 多轮历史，连续追问容易 prompt 溢出（v0.20 单轮已把 ctx 从 8192 提到 16384）。

**mitigate**：
1. history 滑动窗口（system + 最近 12 轮，常量 `MAX_HISTORY_TURNS`）
2. 溢出时 LlmError 降级为面板 Error 事件 + 提示「对话过长，已开启新对话」（不清空 history 由用户手动重开）
3. stage 2 测试：构造超长 history 断言截断行为

### 风险 5：写操作放行的安全边界

**问题**：confirm 放行后 proc_kill / proc_usb_release 等**真实执行**，误操作不可逆。

**mitigate**：
1. ConfirmRequest 强制展示影响摘要（summary 按 tool 构建：kill → 目标进程列表；docker_rm → 容器名；usb_release → 盘符）
2. Denied → blocked JSON（模型转向解释 + 等价命令行，与 v0.20 行为一致）
3. CLI ask 路径拦截语义不变（非交互无通道）
4. 与 ADR-0008 self-mitigation policy 对齐：`confirm: true` 仅在用户显式 y 后传入

### 风险 6：stage 2 容量 ~1350 行达阈值 90%

**问题**：phased-project skill 铁律 19 单阶段 ≤ 1500 行；stage 2（session + streaming + confirm 协议三层）估算 ~1350 行，接近上限。

**mitigate**：
1. v0.20 stage 2 1630 行（8% 超）先例——实施时如上下文告急触发 Checkpoint 接力，不硬撑
2. stage 2 内排序：项 1 session 基础 → 项 2 streaming → 项 3 confirm（前两项完成即可进 stage 3 的面板开发，confirm 协议若告急可 Checkpoint 接力）
3. E2B 流式冒烟（`#[ignore]`）放 stage 2 最末，不挤占主线

## FAQ

### Q1: 为什么 C（Eval + Observability）拆到 v0.22？

**A**: 决策 1 五条理由——零依赖耦合 / 合并成史上最大 cycle / F 更快拿到演示能力 / C 的设计在 F 落地后范围更清楚（TUI session 的 observability 素材只有 F 存在后才能纳入）/ eval 雏形已存在推迟无风险。v0.20 的 A+E 合并成立是因为 E 是 A 的内部组件（agent 需要 provider）；F+C 是平行主题。

### Q2: confirm 通道为什么 TUI 独有？CLI ask 为什么保持拦截？

**A**: CLI ask 是非交互批处理（`proc agent ask "..."` 一条命令出结果），没有等待用户输入的通道——v0.20 拦截是正确设计不是欠账。TUI 面板是长交互会话，y/n 确认天然存在。两路径共用 dispatch 层双模式：blocked 拦截（无通道）/ confirm 通道（有通道），语义都来自 ADR-0008/0029 的 `confirm: bool` 契约。

### Q3: AgentSession 为什么独立线程 + 自有 Runtime？

**A**: TUI 主循环是同步 crossterm 循环，直接 block_on async 会卡死 UI。proc 已有成熟模式：WorkerManager 的 worker 都是「独立线程 + channel + tick drain」（v0.6 起）。AgentSession 同款——async 侧全部封闭在 session 线程内，与 TUI 只通过 `std::sync::mpsc` 交互，零 runtime 纠缠。这也是 v0.20 风险 6 明确「推迟到 v0.21 TUI AgentPanel 评估」的答案。

### Q4: streaming 渲染为什么按 tick 批量 append？

**A**: ratatui 是全量重绘模式，逐 delta 重绘在流式高频输出下浪费且闪烁。TextDelta 先进事件通道，TUI tick（既有节奏）边界一次性 drain 聚合 append 到当前 assistant 段落 + pending_redraw。用户感知仍是「逐字流出」（tick 间隔远小于生成速度）。

### Q5: 多轮 history 的截断策略？

**A**: 滑动窗口 = system prompt + 最近 12 轮（常量 `MAX_HISTORY_TURNS`）。不预加配置项（v0.20「不预实现」原则）。窗口超限截断最旧轮；ctx 溢出（tools 6K + history 12 轮仍超）降级 Error 事件提示用户开新对话。

### Q6: L2 为什么只手动演示不系统验收？

**A**: 决策 4——L2 系统验收（真实录制 + 通过率 + 失败模式分析）本质是 eval 素材（E2B 多步预期低通过率，价值是能力边界数据），与 v0.22 C 主题内聚。F cycle 手动演示多步 query 零代码且演示效果最好。

### Q7: proc_record_start/stop 为什么仍不启用？

**A**: 决策 8——confirm 通道落地后启用成本已降至 ~100 行（headless 子进程路径），但「agent 启动录屏」的语义边界（录制范围 / 停止时机）需单独设计。v0.21 聚焦 F；推迟 v0.22+ 评估。

### Q8: v0.21 需要下载新模型吗？

**A**: 不需要。默认用现有 `gemma4-e2b\gemma-4-E2B-it-Q4_K_M.gguf`，`agent.toml` `[llama-cpp]` 段 v0.20 已配好（server_path + search_paths 开箱即用）。更强模型复测是 v0.22 C-cycle 的 eval 素材（决策 7）。
