## 实施决策（stage 3b 内拍板，按 brainstorm 步 15 规则记录）

### 决策 A：tool 执行层复用 MCP `make_*_json` helper（不重复实现）

agent 的 47 tool 执行入口不重写业务逻辑，直接调 `src/mcp/handler/` 各
`make_*_json(...)` 函数（ADR-0030「复用同一套 tool 的 Rust API」）。新建
`src/agent/tools/dispatch.rs`：

- `pub fn execute_tool(registry: &ToolRegistry, name: &str, args: &Value) -> ToolResult`
- 每个 tool 一行 dispatch：从 `args: &serde_json::Value` 提取类型化参数
  （`args.get("pid").and_then(|v| v.as_u64())` 风格）→ 调对应 `make_*_json` →
  `Value::to_string()` 作 content；`ok:false` 的返回值标 `is_error=false`
  （业务失败让 LLM 自己读 JSON 语义，只有 dispatch 异常才 `is_error=true`）
- `proc_help` 分支调既有 `tools::help::execute(registry, category)`

**3 个依赖 MCP handler 持久状态的 tool 降级处理**（agent CLI 单 query 生命周期
没有 handler 级持久状态）：

| tool | MCP 路径 | agent 路径 |
|---|---|---|
| `proc_dns` | `make_dns_json_from_collector`（v0.12 TD-36 持久 collector） | `make_dns_json(tail)`（mod.rs 既有现场采集版——agent 单 query 一次性采集语义正确） |
| `proc_metrics_history` | `make_metrics_history_json`（handler `system_history` 状态） | `make_metrics_history_json_no_state`（observable.rs 既有 no-state 变体） |
| `proc_record_start` / `proc_record_stop` | handler `record_handle` 跨 tool call 保活 child | 返回 `ok:false + "agent 内暂不支持启动录屏（需跨调用保活子进程），请用 proc record 命令"`（L0/L1 query 不含这两个 tool；v0.21 TUI AgentPanel 评估） |

### 决策 B：写操作 tool 全部拦截（confirm gate，复用 ADR-0008/0029 契约）

`proc agent ask` 是**单轮非交互** CLI——system prompt 教的「先解释 + 等 y/n」
流程没有交互通道，模型若直接 `proc_kill(confirm=true)` 会真杀进程。落地：

- `WRITE_TOOL_NAMES` 常量：`proc_kill` / `proc_pkill` / `proc_usb_release` /
  `proc_docker_rm` / `proc_docker_image_rm` / `proc_docker_volume_rm` /
  `proc_record_start` / `proc_record_stop`
- dispatch 层拦截：返回 `ok:false + "写操作已拦截：CLI ask 模式非交互，请让
  用户用 proc kill / proc eject 等命令直接执行"`——模型拿到错误结果后会向
  用户解释 + 给出等价命令行（符合 few-shot 示例 3 的教学意图）
- L0/L1 验收不受影响：4.5 / 4.6 / 8.3~8.5 的期望主 tool 是
  `proc_eject_status` / `proc_monitor_*`，写 tool 只是链路中间步（被拦截 →
  模型解释 → 最终回答非空即通过）

### 决策 C：GBNF grammar 不进 ReAct 主循环（agent.toml `grammar_file` 显式启用逃生舱）

stage 3a 实测遗留设计点：grammar 约束下模型**只能**输出 `{"tool_calls":[...]}`
JSON——与自然语言最终回答互斥。若 loop 每轮都带 grammar，模型永远无法产出
最终回答（需要「grammar 轮 + 无 grammar 总结轮」二段式，每 query 多一次
LLM 调用）。落地：

- **默认不启用**：OpenAI tools 协议下 llama-server 模板层解析 tool_calls 可靠
  （stage 3a 实测 `finish_reason:"tool_calls"` + arguments 正确），grammar 是
  「乱码保命手段」不是主路径
- `CompleteOptions.grammar` 通道保留（provider 已接线）；agent.toml
  `[llama-cpp].grammar_file = "tool_call"` 配置时才启用（用户显式 opt-in 逃生舱，
  供 L0/L1 实测乱码率超标时切换）
- 二段式 grammar loop 留 v0.21（若实测需要）

### 决策 D：AgentRunner 走 `complete()` 非流式 + 空响应重试一次

- CLI ask 是单 query 批处理场景，流式渲染收益低（v0.21 TUI AgentPanel 才需要
  streaming）；complete 一次拿全量响应让 loop 状态机最简
- loop 每轮：`provider.complete(messages, tools, options)` → 有 `tool_calls` →
  逐个 execute → 拼 `Message{role: Tool, tool_results}` 追加 → 下一轮；
  无 tool_calls → 终止返最终回答
- **空响应重试**：E2B 偶发 `content 空 + 无 tool_calls`（乱码/模板抖动）→ 追加
  一条 assistant 占位 + nudge（「请基于以上信息直接回答用户问题」）重试 1 次；
  仍空 → 返「模型未产出有效回答」+ 已收集的 tool 结果摘要
- `max_steps` 兜底：达到上限时若最后一条 assistant 有文本就用之；否则输出
  「未能在 N 步内完成」+ trace 摘要（不 panic 不死循环）

### 决策 E：tool result 截断 + PII 过滤（送 LLM 前）

- **截断**：`MAX_TOOL_RESULT_CHARS = 16_000`（E2B ctx 8192 token ≈ 32K 文本，
  16K chars 留一半给对话）；超长截断 + `...[truncated, 原 N chars]` 后缀，
  按 char 截（UTF-8 安全）。proc_ls 默认 limit=20（schema description 已引导
  模型传 limit，截断是兜底）
- **PII 过滤**：`apply_pii_filter(content) -> String`——regex 扫
  `("?(KEY|TOKEN|SECRET|PASSWORD|PASSWD|PWD|CREDENTIAL|PRIVATE|AUTH|API|DSN)"?\s*[:=]\s*)"?<value>"?`
  模式（关键字集合复用 `src/inspect/env_mask.rs::SECRET_PATTERNS` 12 项），
  命中值替换为 `mask_value` 同款 `{前2字符}***({len} B)`。defense-in-depth：
  `proc_inspect(env)` 的 MCP 层 reveal=false 已 mask 一层，agent 层再兜一层
  （cmd 字符串 / 路径里的 `--api-key=xxx` 等散落形态）

### 决策 F：system snapshot 轻量注入（`{{SYSTEM_SNAPSHOT}}`）

runner 启动时采集一次 `SystemSnapshot::new() + refresh()`，把 4 行摘要
（OS / CPU 使用率 / 内存使用 / 进程数）替换进 `SYSTEM_PROMPT` 的
`{{SYSTEM_SNAPSHOT}}` 占位符。~500ms 一次性开销可接受；详细数据让模型调
`proc_metrics_system` 拿（prompt 只给背景锚点，防止模型瞎猜环境）。

### 决策 G：CI loop 测试用 test-local ScriptedProvider（MockProvider 保持单轮语义）

MockProvider 回放匹配键是「最后一条 user message」的 hash——ReAct loop 中
tool 结果轮（Role::Tool 追加后）最后一条 user message 不变 → 重复命中同一
fixture → 同一 ToolCall 死循环。MockProvider 的用途保持 stage 2 语义
（单轮 complete/stream 回放）不变；**agent loop 逻辑测试用测试文件内定义的
`ScriptedProvider`**（`Mutex<VecDeque<CompleteResponse>>` 逐 complete 弹出一个，
脚本化「轮 1 返 ToolCall → 轮 2 返最终文本」），零 LLM 调用且精确控制多轮。

### 决策 H：provider 构造链（CLI flag > agent.toml > 代码默认）

### 决策 I：小模型可靠循环 = `tool_choice=required` + `proc_finish` 控制 tool（实测驱动，推翻 brainstorm 附录 C few-shot 方案）

**实测发现**（2026-08-16，本机 E2B curl 矩阵实验 A~G，手动 spawn llama-server
迭代 prompt 避免 6 分钟级 release 重建）：

1. **brainstorm 附录 C 的 3 个 few-shot 对话示例对 E2B 是负效果**——模型把
   示例里的 `[tool_call: proc_ls(...)]` 记号 / 示例叙事当成了回答模板，
   直接在 content 里角色扮演「调用工具 + 编造结果」（编造的 PID 就是示例里的
   假数据 1234/5678），不发真实结构化 tool_calls。改自然语言记号也一样。
   → **system.md 移除全部对话示例**，改为「类别路由表」式策略行（USB →
   proc_help(usb) 等逐类映射 + 严禁凭空编造数据）。
2. **auto 模式下 E2B 对「听起来能直接回答」的 query 倾向直接文字回答**（不调
   tool、泛泛而谈）——即使策略行写明「必须先调 proc_help 发现」。auto 下
   还会在第 2 轮过早停止（拿到 metrics 结果后不再深挖）。
3. **`tool_choice: "required"` llama-server b8685 真实支持**——强制本轮必调
   tool，与 OpenAI 协议字段一致。

**落地**（实验 G 验证：卡顿 query 完美 3 轮 metrics → ls → finish）：

- `CompleteOptions` 加 `tool_choice: Option<ToolChoice>`（Auto / Required），
  LlamaCppProvider 透传请求体（顺带补 top_p / top_k 透传，stage 3a 漏接）
- AgentRunner 每轮 tools = entry 4 + **`proc_finish` 控制 tool**（loop 内部
  信号，不进 ToolRegistry catalog、不进 dispatch），所有轮
  `tool_choice=Required`——要结束必须显式调 `proc_finish(answer="...")`
  提交答案；runner 拦截该调用提取 answer 作 final_text（EndTurn）
- 效果：① 首轮不可能凭空文字回答（必调 tool 或 finish）② 不会中途过早
  停止（要停必须 finish）③ 全程结构化
- 与决策 C 的关系：grammar 仍不进主循环（proc_finish 的 answer 在 arguments
  JSON 字符串里，grammar 的 `{"tool_calls":[...]}` 形状约束与它兼容性未验证，
  逃生舱不变）
- FixtureRecorder 同步用 Required（不带 proc_finish，entry 4 强制选一）——
  录到的首响应必是真实 tool call
- MockProvider 回放忽略 options，不受影响；Text-only fixture 在 loop 中走
  「无 tool_calls + content 非空 → EndTurn」兼容路径

### 决策 J：proc_help 发现的 tool 必须动态加入 tools 数组（首轮验收实测教训）+ spawn_blocking 执行 + 上下文预算收紧

**首轮真实验收失败**（L0 8/23 / L1 9/27，9640s）暴露三个问题：

1. **OpenAI 协议下模型只能调用请求 `tools` 数组里声明的 tool**——两层架构的
   「proc_help 返回 schema 文本」让模型知道了 Layer 1 tool 的存在，但它**无法
   发出未声明 tool 的调用**（llama-server 模板层只渲染已声明 tool），于是
   docker / usb / dns / monitor / flow / recording 六个场景的 query 全部回落到
   entry 工具打转（proc_help → proc_ls 循环到 max_steps）。
   **修正**：`expand_tools_for_help_calls`——每轮 tool_calls 里若有
   `proc_help(category=X)`，把 registry 中 X 类别 schema 去重后加入后续轮的
   tools 数组（`ACTIVE_TOOLS_TOKEN_BUDGET = 6000` 封顶；`category` 缺省不扩——
   43 个 schema 会爆预算）。两层架构语义不变（entry 起步 + 按需加载），
   只是「加载」从纯文本升级为文本 + tools 数组双通道。
2. **dispatch 的同步 helper 内嵌 block_on 在 async 上下文 panic**——
   `DockerMonitor::connect` 自建 `Runtime::new().block_on(...)`（MCP 路径靠
   rmcp 的 spawn_blocking 保护），agent 的 `rt.block_on(runner.run)` 直接调
   会 "Cannot start a runtime from within a runtime"。**修正**：
   `execute_tool_calls` 走 `tokio::task::spawn_blocking`（tool panic 捕获为
   is_error 结果不炸 loop）。
3. **8192 ctx 溢出**——多轮 + 16K tool result 累积出 12K token prompt
   （llama-server 400 `exceed_context_size_error`）。**修正**：
   `MAX_TOOL_RESULT_CHARS` 16K → 8K + agent 版 proc_ls 字段瘦身（省略 cmd /
   virtual_memory / disk+net 速率 / start_time / run_time，详情走
   proc_inspect）+ ctx 8192 → 16384（agent.toml + 真实测试显式；6GB VRAM
   无压力）+ 验收单 query 重试 3 → 2 次（整 loop 重试成本高，首轮验收 2.7h）。

## 已知风险（stage 3b 实施时关注）

### 风险 1：E2B L0 验收不达标（brainstorm 风险 1，29.4% 单步成功率）

**mitigate**：few-shot 3 示例 + entry tool 4 个子集已就位；空响应重试兜底；
某 query 反复失败时单 query 多试 2 次取最优（验收测试内 per-query 重试）；
仍不达标 → 启用 agent.toml `grammar_file = "tool_call"` 走 grammar 路线对比。

### 风险 2：真实测试时长（50 query × 2+ LLM 调用 × 3-10s ≈ 10-20 分钟）

**mitigate**：单 `#[tokio::test]` 串行复用一个 llama-server 实例（模型加载
~5-10s 只一次）；`#[ignore]` 默认不进 CI；验收与录制两个测试也串行跑。

### 风险 3：VRAM 残留进程（6GB 卡同机 1 实例上限）

**mitigate**：测试前置 `Get-Process llama-server` 检查残留并报错提示清理
（PowerShell `Get-Process llama-server | Stop-Process -Force`）；连续起停留
~2s 驱动回收窗口；Drop 路径 stage 3a 已验证无僵尸。

### 风险 4：MockProvider 多轮回放死循环（决策 G）

agent loop 若直接接 MockProvider，tool 轮 hash 不变重复命中同一 fixture。
CI loop 测试一律用 ScriptedProvider；MockProvider 仅单轮断言。

### 风险 5：PII regex 误伤正常内容

`API` / `KEY` 关键字过宽（如 JSON 字段 `"keyboard"` 不含独立 KEY 不伤，但
`"api_version"` 含 API 会误 mask 值）。**mitigate**：仅匹配 `[:=]` 紧邻赋值
形态 + 值长度 ≥ 8 才 mask（短值多为枚举/version）；dispatch 测试覆盖
`"api_version": "v1"` 不被误伤 case。
