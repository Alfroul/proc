### 阶段 1：TD-19 ebpf Linux 真实编译验证（WSL2）

> ⏸ **主动推迟**（v0.8.0 cycle，2026-06-28）— 用户主要用 Windows 开发，TD-19 Linux 真机 / WSL2 验证推迟到 v0.9.0 cycle 启动前再评估。stage 2/3/4 不依赖 stage 1。
>
> **独立会话指令**：`阅读 CONTEXT.md 和 docs/stages/v0.8-stage-1.md，完成所有任务后确认完成`
>
> **开工前只需阅读**：`CONTEXT.md`（EbisuBpfWorker / ProcessFlow / FlowAggregator 术语）、`docs/stages/v0.8-stage-1.md`、`docs/adr/0016-ebpf-flow-graph.md`（v0.7 阶段 8 设计）、`src/ebpf/`（现状代码）。**不需要读其他 v0.7 stage doc**。

**目标**：在 WSL2 真实环境跑通 v0.7.0 在 Windows 会话写出来但未验证的 eBPF 代码。具体跑通三条命令：
1. `cargo +nightly build -p proc-ebpf --target bpfel-unknown-none --release`（内核态 ELF 编译）
2. `cargo build --release --features ebpf`（userspace + ebpf feature）
3. `sudo cargo test --release --features ebpf --test test_ebpf_flow -- --ignored`（端到端真实运行）

跑通后 `proc flows` 应显示活跃 flow；端口面板按 `F` 进入 Flow 子视图应有数据。

**前置依赖**：v0.7.0 已 tag（commit 615f8b7）。**本阶段必须在 Linux 环境**（WSL2 / Linux VM / 裸机），Windows 跑不了 bpf-linker。

**环境准备**（开工前一次性配好）：

```bash
# WSL2 Ubuntu 22.04+（Windows 11 自带 WSL2 默认内核 5.15+，满足 ≥ 5.10 要求）
wsl --install -d Ubuntu-22.04

# 进入 WSL2 后
sudo apt update && sudo apt install -y build-essential clang llvm libelf-dev
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source ~/.cargo/env
rustup toolchain install nightly --component rust-src
cargo +nightly install bpf-linker
git clone https://github.com/Alfroul/proc.git && cd proc
```

**依赖测试**（开工时跑，验证基线 + 暴露问题）：

```bash
# 1. 先确认非 ebpf 路径在 Linux 跑通（基线）
cargo test --release -q                          # 应 ≥ 910 passed / 0 failed
cargo build --release                            # 默认 build 无 ebpf，应通过

# 2. 跑 ebpf 路径（预期失败，记录所有报错）
cargo +nightly build -p proc-ebpf --target bpfel-unknown-none --release 2>&1 | tee /tmp/ebpf-kernel-build.log
cargo build --release --features ebpf 2>&1 | tee /tmp/ebpf-userspace-build.log
```

**任务清单**：

1. **修内核态 ELF 编译报错**（`src/ebpf/ebpf-ebpf/src/main.rs` + `Cargo.toml`）
   - 跑 `cargo +nightly build -p proc-ebpf --target bpfel-unknown-none --release` 看报错
   - 预期问题（按 ADR-0016 Consequences 段标注）：
     - aya-ebpf 0.1.1 API 签名（`TracePoint::attach` 真实参数 / `RingBuf::try_from` 用法）
     - tracepoint arg offset：`sys_enter_connect` 偏移 16 / `sched_process_exit` 偏移 24（不同内核可能不同，用 `sudo cat /sys/kernel/debug/tracing/events/syscalls/sys_enter_connect/format` 实测）
     - `bpf_current_task_start_time` 占位 0（v0.7 留 TODO）—— 用 aya-tool BTF binding 补完，或保留 0 + 文档标注
   - 每个 error 一个 commit：`fix(ebpf): kernel ELF compile - <具体修了什么>`

2. **修 userspace ebpf feature 编译**（`src/ebpf/{worker.rs,elf_loader.rs,mod.rs}`）
   - 跑 `cargo build --release --features ebpf` 看报错
   - 预期问题：
     - `include_bytes!("ebpf-ebpf/target/bpfel-unknown-none/release/proc-ebpf")` 路径硬编码（v0.7 写死）—— 验证相对路径在 Linux 是否成立，不行改用 `env!("CARGO_MANIFEST_DIR")` 拼接
     - aya 0.13 `TracePoint::attach` / `RingBuf::try_from` 真实签名（v0.7 是猜的）
     - ELF 加载顺序：先 attach ring_buf 再 attach tracepoint（或反过来，看 aya 文档）

3. **跑 ignored 集成测试**（`tests/test_ebpf_flow.rs`）
   - `sudo cargo test --release --features ebpf --test test_ebpf_flow -- --ignored`
   - 这些测试 v0.7 标了 `#[ignore]` 因为 Windows 跑不了，Linux 应该能跑
   - 跑不通的 case 改 mark `#[ignore = "Linux TD-19: <具体原因>"]` 留 v0.8.1 修

4. **手动启动验证**
   - `sudo ./target/release/proc flows`（CLI 模式，应显示活跃 flow）
   - `sudo ./target/release/proc`（TUI 模式，端口面板按 `F` 进入 Flow 子视图应有数据）
   - 在另一个 terminal 跑 `curl https://example.com` 触发 connect + DNS，验证 flow 出现 + dns_name 关联

5. **更新 ADR-0016 + tech-debt**
   - `docs/adr/0016-ebpf-flow-graph.md` Consequences 段补「Linux 实测数据」（内核版本 / aya API 真实签名 / tracepoint offset 实测值）
   - `docs/tech-debt.md` TD-19 标 ✅ Fixed in v0.8.0 阶段 1，补 commit hash

**验收标准**：
- `cargo +nightly build -p proc-ebpf --target bpfel-unknown-none --release` 通过
- `cargo build --release --features ebpf` 通过
- `sudo cargo test --release --features ebpf --test test_ebpf_flow -- --ignored` ≥ 90% case 通过（剩下少量 case 标 ignore 留 v0.8.1）
- `sudo ./target/release/proc flows` 在 Linux 真实显示活跃 flow（手动验证）
- 端口面板按 `F` 进入 Flow 子视图有数据
- 全量回归 `cargo test --release -q`（无 ebpf feature）仍 ≥ 910 passed / 0 failed
- TD-19 标 Fixed

**容量预估**：100-300 行修改（取决于 v0.7 暴露多少问题）+ 0 新测试文件（v0.7 已写 16 case + 21 内联），工具调用 ≤ 50 次。**如超 600K 上下文**（修的问题比预期多），触发 Checkpoint：把已修的 commit 推上去，剩余报错记到 checkpoint 文件，开新会话继续。
