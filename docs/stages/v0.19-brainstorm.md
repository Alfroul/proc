### 决策 2：runtime 切换路径（用户已拍板 ✅）

**stdio 保 current_thread，SSE 走 multi_thread**——按 transport 类型分支选 runtime：

```rust
// src/mcp/mod.rs
fn build_runtime(kind: &TransportKind) -> anyhow::Result<tokio::runtime::Runtime> {
    match kind {
        TransportKind::Stdio => {
            // stdio 单 client IO-bound，current_thread 足够
            // 与 v0.7~v0.18 11 个 cycle 既有 stdio 路径保持一致（零回归风险）
            tokio::runtime::Builder::new_current_thread()
                .enable_all()
                .build()
        }
        TransportKind::Sse(_) => {
            // SSE 多 client 并发，multi_thread worker pool
            // axum + tower StreamableHttpService 需 multi_thread 才能并发处理 request
            tokio::runtime::Builder::new_multi_thread()
                .worker_threads(4)
                .enable_all()
                .build()
        }
    }
    .map_err(Into::into)
}
```

**DockerMonitor block_on 真实风险评估**（v0.18 stage 4 stub 注释「runtime 重构」具体化）：

| 维度 | 现状（v0.18）| v0.19 SSE 切 multi_thread 后 |
|---|---|---|
| DockerMonitor runtime | 独立 `Runtime::new()`（multi_thread 默认）| 不变（独立 runtime） |
| MCP runtime | `current_thread` | stdio `current_thread` / SSE `multi_thread` |
| docker tool 调用路径 | MCP runtime → docker runtime `block_on`（跨 runtime）| 不变（docker 仍走自己 runtime）|
| **真实风险** | 无（docker runtime 独立）| **multi_thread worker thread 被 docker `block_on` 阻塞** —— 多 client 并发调 docker tool 时 worker thread 被占满 |
| mitigate | — | worker_threads(4) ≥ 一般 client 数；docker `block_on` 通常 < 1s（bollard list_containers 实测）；stage 2 加 worker thread pool 占用监控日志（如 `tokio::runtime::Metrics`） |

**为什么 v0.18 stage 4 stub 注释说「避免和 docker runtime 抢线程」是 misleading**：

实际上 docker runtime 独立，**不会**抢 MCP runtime 的线程。v0.18 既有注释是 v0.17 stage 4 早期评估时的保守说法，v0.19 stage 1 Spike 用 context7 + cargo tree 验证 docker runtime 完全独立。真实风险是 multi_thread worker thread 被 docker 同步 `block_on` 阻塞，但 worker_threads(4) 足够覆盖一般使用场景（> 4 个并发 client 同时调 docker tool 概率低）。

**备选方案**：
- (a) stdio + SSE 都切 multi_thread（v0.18 stdio 路径需重新回归测试 11 个 cycle 累积路径，工作量大）
- (b) **stdio 保 current_thread，SSE 走 multi_thread**（推荐 ✅）：stdio 路径零回归，SSE 路径独立验证
- (c) stage 2 内 A/B 测试 current_thread + SSE 撑 3 client（延后决策但增复杂度）

**用户拍板**：✅ (b)。

### 决策 3：multi-client 注册表数据结构（用户已拍板 ✅）

**`HashMap<String, Vec<Peer<RoleServer>>>`**——v0.18 既有 `HashMap<String, Peer>` 升级 value：

```rust
// src/mcp/subscribe_worker.rs（v0.19 stage 2 升级）
pub struct SubscribePushWorker {
    /// 注册表：uri → Vec<Peer>（多 client 同 URI 独立订阅）
    /// v0.18 stage 2: HashMap<String, Peer<RoleServer>>（stdio 单 client）
    /// v0.19 stage 2: HashMap<String, Vec<Peer<RoleServer>>>（SSE multi-client）
    subscribers: Arc<Mutex<HashMap<String, Vec<Peer<RoleServer>>>>>,
    task_spawned: Arc<Mutex<bool>>,
}
```

**subscribe 逻辑**：
```rust
let mut guard = self.subscribers.lock()?;
let vec = guard.entry(uri.to_string()).or_default();
if !vec.iter().any(|p| /* peer identity 检测，stage 1 Spike 调研 rmcp Peer Eq/Hash */) {
    vec.push(peer);
}
```

**unsubscribe 逻辑**：
```rust
let mut guard = self.subscribers.lock()?;
if let Some(vec) = guard.get_mut(uri) {
    vec.retain(|p| /* 反向 identity 检测 */);
    if vec.is_empty() {
        guard.remove(uri);
    }
}
```

**push task 改造**：
```rust
let snapshot: Vec<(String, Vec<Peer>)> = subscribers
    .lock()?
    .iter()
    .map(|(k, v)| (k.clone(), v.clone()))
    .collect();
let mut join_set = JoinSet::new();
for (uri, peers) in snapshot {
    for peer in peers {
        join_set.spawn(async move {
            let params = ResourceUpdatedNotificationParam { uri: uri.clone() };
            (uri, peer, peer.notify_resource_updated(params).await)
        });
    }
}
// 收集 fail peer 一次性清理
while let Some(res) = join_set.join_next().await {
    if let Ok((uri, peer, Err(_))) = res {
        if let Ok(mut g) = subscribers.lock() {
            if let Some(vec) = g.get_mut(&uri) {
                vec.retain(|p| /* identity 检测 != fail peer */);
            }
        }
    }
}
```

**Peer identity stage 1 Spike 调研子任务**：rmcp 0.11 `Peer<RoleServer>` 是否实现 `Eq` / `Hash` / `PartialEq`？如否，是否有 `Peer::id()` / `Peer::session_id()` 等方法拿 client 标识？用 context7 查 rmcp docs。

**备选方案**：
- (a) `HashMap<String, Vec<Peer>>`（推荐 ✅）：v0.18 既有结构最小升级
- (b) `HashMap<(String, ClientId), Peer>`：扁平 key，需 ClientId（rmcp Peer 是否暴露未知）
- (c) `DashMap`：并发 HashMap，sharded lock 更细粒度，但加 dep + 学习曲线

**用户拍板**：✅ (a)。

## 已知风险

### 风险 1：rmcp 0.11 streamable_http_server feature 学习曲线

**问题**：rmcp 0.11 `transport-streamable-http-server` feature 是 v0.19 cycle 新引入的 rmcp 能力，与既有 `transport-io`（stdio）路径独立。stage 4 落地的 stdio transport 未触及 streamable_http 路径，文档相对稀少（context7 docs 验证，2026-07-13）。

**影响**：如 rmcp 0.11 `StreamableHttpService::new` API 签名或 `SessionManager` trait 与 brainstorm §项 3 描述不符，stage 2 实装时可能需重写 service_factory closure / session_manager 实现。

**mitigate**：
- stage 1 Spike 用 context7 + docs.rs 查 rmcp 0.11 `StreamableHttpService::new` / `SessionManager` / `StreamableHttpServerConfig` 完整 API
- stage 1 Spike 写一个最小 PoC（10 行 main）验证 axum + StreamableHttpService 能跑起来 client 连接
- 如 API 与 brainstorm 描述差异大 → 触发自适应拆分（stage 2a 项 1+2+4 / stage 2b 项 3），cycle 改 4 stage

### 风险 2：axum + tower deps 与 rmcp 内部版本对齐

**问题**：rmcp 0.11 内部用特定版本的 axum / tower / tower-http。如 proc Cargo.toml 显式加的 axum 0.7 / tower 0.5 / tower-http 0.6 与 rmcp 内部版本不一致，cargo 会编译两份 deps（duplicate deps）—— 编译时间增加 + 类型不兼容（rmcp 内部 `StreamableHttpService` 期望的 axum `Router` 与 proc 显式加的 axum `Router` 不是同一类型）。

**影响**：编译失败 / 类型不匹配 / Cargo.lock 锁版本困难。

**mitigate**：
- stage 1 Spike 用 `cargo tree -d` 检查 rmcp 内部 axum / tower 版本
- Cargo.toml 显式版本与 rmcp 内部对齐（context7 docs 显示 rmcp 0.11 用 axum 0.7，stage 1 Spike 验证）
- 如版本对齐困难 → fallback 到决策 4 备选方案 (b)（rmcp feature 转发，仅启 rmcp feature 不加 axum 直接 dep）

### 风险 3：runtime 分支切换破坏既有路径

**问题**：v0.7~v0.18 11 个 cycle 累积的 stdio transport 路径都基于 `current_thread` runtime。v0.19 项 1 runtime 分支切换可能让既有 stdio 路径走 multi_thread（如 CLI flag 解析有误），破坏 1425 passed / 0 failed 回归基线。

**影响**：stdio transport 路径回归失败是 P0 级问题（agent 用 stdio 接入 Claude Desktop / Cursor 是主路径）。

**mitigate**：
- stage 2 内严格按排序（项 1 runtime 分支优先），stdio 路径用决策 2 (b) 保持 `current_thread`（零回归）
- stage 2 加回归测试：`test_stdio_transport_uses_current_thread_runtime` / `test_sse_transport_uses_multi_thread_runtime`（用 `TokioHandle::current()` 检测 runtime 类型？需 stage 1 Spike 调研 tokio runtime 类型检测 API）
- stage 3 Review 段手动验证 mcp-inspector stdio 路径（既有 1425 测试基线 + 新增 SSE 测试）

### 风险 4：multi_thread runtime worker thread 被 docker block_on 占用

**问题**：multi_thread runtime worker_threads(4) 下，docker tool 调用走 `DockerMonitor::connect()` → `runtime.block_on(...)`（docker runtime 是独立的，但 block_on 是同步阻塞当前 MCP runtime worker thread 的调用）。多 client 并发调 docker tool 时 worker thread 可能被占满（4 个 client 同时调 docker → 4 worker thread 全占 → 第 5 个 client 等）。

**影响**：多 client 重 docker 操作场景下 SSE transport 响应延迟。但 docker `block_on` 通常 < 1s（bollard list_containers 实测），且 > 4 个并发 client 同时调 docker tool 概率低（proc MCP tool 主要是 read 操作）。

**mitigate**：
- worker_threads(4) ≥ 一般 client 数（与 brainstorm §决策 2 mitigate 对齐）
- stage 2 加 worker thread pool 占用日志（`tokio::runtime::Metrics` API，stage 1 Spike 调研是否启用）
- 长期路径：v0.20+ cycle 评估 docker tool 改 `spawn_blocking`（让 docker `block_on` 走 blocking pool 而非 worker pool），但本 cycle 不做

### 风险 5：rmcp Peer identity API 学习曲线

**问题**：决策 3 multi-client 注册表升级依赖 rmcp `Peer<RoleServer>` 的 identity 检测（subscribe 时 vec 去重 / unsubscribe 时 vec retain / push task fail peer 清理）。rmcp 0.11 `Peer<RoleServer>` 是否实现 `Eq` / `Hash` / `PartialEq`，或是否有 `Peer::id()` / `Peer::session_id()` 方法拿 client 标识，stage 1 Spike 调研未做。

**影响**：如 Peer 不实现 Eq 且无 id() 方法，subscribe 时无法去重（同 client 多次 subscribe 同 URI 会 push 重复 vec 项）。

**mitigate**：
- stage 1 Spike 用 context7 查 rmcp 0.11 `Peer<RoleServer>` struct 完整 impl 块
- 如 Peer 不实现 Eq → fallback 到用 `Peer::session_id()` 或 `RequestContext::extensions` 拿 client 标识作 secondary index
- 如以上都不可行 → 接受 subscribe 重复 push（client 自己 dedup），stage 3 Review 标 P2 finding 推迟 v0.20+ cycle

### 风险 6：3 stage 节奏 stage 2 单段容量

**问题**：stage 2 单段实装 4 项 ~580 行（业务 ~405 + 测试 ~175），约 39% 上限。虽远低于 1500 行阈值，但 4 项主题分散（runtime / 注册表 / push task / SSE 入口），上下文切换开销大。项 3 SSE 入口最复杂放最后，axum 学习曲线可能让上下文消耗比预期快。

**影响**：如 stage 2 上下文快满时项 3 SSE 入口未完成，可能触发 Checkpoint 接力。

**mitigate**：
- stage 2 内严格按排序（项 1 → 项 2 → 项 4 → 项 3），项 3 放最后让前 3 项先 commit
- 如项 3 触发 Checkpoint → 生成 `docs/handoff-stage-2-checkpoint.md`，新会话续项 3
- 项 3 如工作量超预期 → 触发自适应拆分（stage 2a 项 1+2+4 / stage 2b 项 3），cycle 改 4 stage

## FAQ

### Q1: v0.19 cycle 为什么不合并到 v0.18 cycle 末段？

**A**: 三个理由：
1. **v0.18 cycle 已 tag**：v0.18.0 已 commit + tag（`35bc301`），cycle 边界已锁定，追加破坏 git 历史清晰度
2. **v0.18 cycle 是残留项补全**：4 项都是 v0.17 Findings 推迟项（< 50 行级别小修），与 v0.19 cycle SSE transport full 实装（~265 行 axum + tower + rmcp StreamableHttpService 集成）性质不同
3. **v0.19 cycle 引入新 deps**：axum + tower + tower-http 是 proc 历史上首次引入 web framework，应有独立 Review 段评估 deps 影响面

### Q2: 为什么项 1 runtime 分支选 (b) stdio current_thread / SSE multi_thread 而非 (a) 统一切 multi_thread？

**A**: 决策 2 拍板 (b) 的核心理由是**零回归**：

1. v0.7~v0.18 11 个 cycle 累积的 stdio transport 路径（1425 passed / 0 failed 测试基线）都基于 `current_thread` runtime，统一切 multi_thread 需重新回归测试所有 stdio 路径
2. stdio 单 client IO-bound 场景 `current_thread` 足够（与 v0.7 stage 2 ADR-0009 决策对齐），切 multi_thread 收益有限
3. SSE 多 client 并发场景才需要 multi_thread（axum + tower StreamableHttpService 需 multi_thread 才能并发处理 request）

(a) 统一切 multi_thread 的优势是代码路径统一，但回归面太大（11 cycle 累积路径）。v0.19 cycle 是轻量 cycle（~900 行），不应承担 11 cycle 回归面。

### Q3: 项 3 SSE 入口为什么选 axum 而非 hyper 直接路由？

**A**: 决策 4 拍板 axum + tower 直接 deps 的核心理由是**与 rmcp 内部对齐**：

1. rmcp 0.11 `StreamableHttpService` 实现 `tower_service::Service` trait，axum 0.7 内部也用 tower（context7 docs 验证），类型对齐
2. axum 提供 `Router` / `axum::serve` 等高层 API，比 hyper 直接路由少 ~150 行代码
3. rmcp 0.11 内部用 axum 0.7，proc Cargo.toml 显式加 axum 0.7 与 rmcp 内部对齐（避免 duplicate deps）

hyper 直接路由优势是更轻量（无 axum dep），但 rmcp 已隐式拉 axum（通过 tower），proc 显式加 axum 不会增加实际编译成本。

### Q4: 为什么 v0.19 cycle 不做 graceful shutdown / Auth / CORS / TLS？

**A**: 决策 6 拍板推迟 v0.20+ cycle 的理由：

| 能力 | 推迟理由 |
|---|---|
| graceful shutdown | v0.18 stage 2 `SubscribePushWorker::shutdown` 已是 no-op 占位（REVIEW-v0.18 P2-S3），proc 进程退出时 tokio runtime shutdown 自动 cancel 所有 task，graceful shutdown 是「nice to have」非「must have」 |
| Auth（Bearer token）| bind-addr 默认 `127.0.0.1` 已避免外网暴露（决策 6 安全考量），Auth 是生产部署时才需要 |
| CORS | 仅 Web dashboard 集成时才需要（浏览器 fetch 跨域），proc MCP server 主要 client 是 Claude Desktop / Cursor（非浏览器） |
| TLS | 仅远程 agent 集成时才需要（公网传输），本机 + LAN 场景 bind-addr 已足够 |

v0.19 cycle 是轻量 cycle（~900 行），4 项生产级特性合计 ~300-500 行，超 cycle 容量。v0.20+ cycle 如评估到生产部署需求再落地。

### Q5: 项 4 push task 并发改造为什么用 JoinSet 而非 join_all？

**A**: `tokio::task::JoinSet` 相对 `futures::future::join_all` 的优势：

1. **fail peer 一次性清理**：JoinSet 的 `join_next().await` 返 `Result<T, JoinError>`，可逐个判断 peer 失败 + 收集 fail peer 一次性从注册表清理（vs join_all 等所有 future 完成才能清理）
2. **abort 能力**：JoinSet 的 `abort_all()` 在 worker shutdown 时主动取消所有 push task（vs join_all 无法中途取消）
3. **backpressure**：JoinSet 默认无界但可配 `build()` 限并发度（如 max_concurrent_pushes=10），避免 100 个 client 同 URI 订阅时一次性 spawn 100 个 task

但 JoinSet 的限制是 `Peer::notify_resource_updated` 是 `&self` 方法，需 `peer.clone()` 后 spawn（Peer 是 Arc 包装可 cheap clone）。stage 1 Spike 验证 Peer Clone 是否 cheap。

## 快速开始

```bash
# 克隆与构建
git clone https://github.com/Alfroul/proc.git
cd proc
cargo build --release

# TUI 模式（v0.19 cycle 不动 TUI 主路径）
./target/release/proc.exe

# CLI 模式
./target/release/proc.exe diag                          # worker metrics
./target/release/proc.exe ls --sort cpu                 # 进程列表

# MCP server 模式（v0.19 cycle stage 2 加 SSE transport 入口）
./target/release/proc.exe mcp serve                                       # stdio MCP server（默认 current_thread runtime）
./target/release/proc.exe mcp serve --transport sse --port 8080           # SSE transport（multi_thread runtime，默认 bind 127.0.0.1）
./target/release/proc.exe mcp serve --transport sse --port 8080 --bind-addr 0.0.0.0  # SSE 全网卡（用户显式 opt-in）
```
