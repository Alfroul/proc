## 任务清单（4 项业务实装）

### 项 1：runtime 分支切换（~90 行，~1.5h）

**落地范围**：

- `src/mcp/mod.rs::build_runtime(_kind)` stub → match 分支：
  - `TransportKind::Stdio` → `Builder::new_current_thread().enable_all().build()`（v0.7~v0.18 既有路径零回归）
  - `TransportKind::Sse(_)` → `Builder::new_multi_thread().worker_threads(4).enable_all().build()`（多 client 并发 + axum + tower StreamableHttpService 需要）
- `src/mcp/mod.rs::run_mcp_serve()` 重构签名 `run_mcp_serve(kind: TransportKind) -> anyhow::Result<()>`：
  - 加 TTY 提示分支（stdio 走 stdin/stdout 才需要 TTY 检查 / SSE 走 HTTP 跳过）
  - 按 kind 选 runtime + dispatch 到 `handler::serve()` (stdio) 或 `transport::serve_sse(config)` (Sse)
- `src/cli/mcp_cmd.rs::run_mcp` 从 CLI flags (`transport: String, bind_addr: String, port: u16`) 构造 `TransportKind`（`build_transport_kind` helper），传给 `run_mcp_serve(kind)`
- 测试：stage 1 build_runtime stub 测试改为 stage 2 match 分支测试（`build_runtime_returns_current_thread_for_stdio` / `build_runtime_returns_multi_thread_for_sse`，用 `Handle::runtime_flavor()` 检测）

### 项 2：multi-client 注册表升级（~170 行，~3h）

**落地范围**：

- `src/mcp/subscribe_worker.rs`：
  - 注册表 value 类型升级 `Vec<Peer<RoleServer>>` → `Vec<Arc<Peer<RoleServer>>>`（让 push task 失败 cleanup 走 `Arc::ptr_eq` 精确 retain）
  - 加 `type SubscribeRegistry = HashMap<String, Vec<Arc<Peer<RoleServer>>>>` 类型别名（clippy `type_complexity` mitigate）
  - `subscribe(uri, peer)` 业务：`Arc::new(peer)` 包装后 push（**stage 2 已知限制**——subscribe 跨调用不做 dedup，rmcp 0.11 `Peer` 不暴露 public identity API）
  - `unsubscribe(uri)` 业务：清空整个 vec + vec 空时 remove entry（**stage 2 已知限制**——SSE multi-client 下 A client unsubscribe 会清掉 B client 同 URI 订阅；stdio 单 client 场景正确）

**stage 2 已知限制 + v0.20+ 改进方向**：

| 限制 | stage 2 行为 | v0.20+ 改进方向 |
|---|---|---|
| subscribe dedup | 不做（每次 `context.peer.clone()` 返新 Peer 值，wrap 成新 Arc）| 从 `RequestContext::extensions` 拿 `mcp-session-id` HTTP header（SSE 路径）作 client identity |
| unsubscribe precise removal | 清空整个 vec | 同上，用 mcp-session-id 走 `vec.retain(|p| !identity_match)` 精确移除 |

push task 失败 cleanup 用 `Arc::ptr_eq` 精确 retain 已落地（项 4），作为 stage 2 兜底机制——client 断开时 push 失败的 peer 会被精确移除（不影响其他 client）。

### 项 4：push task 并发改造（~55 行，~1h）

**落地范围**：

- `src/mcp/subscribe_worker.rs::spawn_push_task` 改双层 for 循环为：
  1. snapshot 注册表 `Vec<(String, Vec<Arc<Peer>>)>`（持锁窗口短）
  2. `tokio::task::JoinSet::spawn` 并发调每个 `Arc<Peer>::clone` 的 `notify_resource_updated`
  3. `join_next().await` 逐个判断 fail peer + `Arc::ptr_eq(p, &failed_arc)` 一次性从 vec retain 精确清理
  4. vec 空时 remove 整个 entry

**JoinSet 相对 join_all / 顺序 for 的优势**（与 ADR-0027 §6.3 + brainstorm FAQ Q5 对齐）：
- fail peer 一次性清理：`join_next().await` 逐个判断 vs `join_all` 等所有 future 完成
- abort 能力：`abort_all()` 在 worker shutdown 时主动取消（预留 graceful shutdown）
- backpressure：可配 `JoinSet::build()` 限并发度（v0.20+ cycle 评估）

## stage 2 关键设计决策

### 决策 1：rmcp 0.11 Peer identity API 不可用 → stage 2 兜底策略

**stage 1 Spike 假设**（ADR-0027 §6.3）：用 `Arc::ptr_eq(p1, p2)` 做 vec 去重，前提是「Peer 内部 Arc 包装，cheap clone 后 pointer 一致」。

**stage 2 调研结论**（context7 rmcp 0.11 docs + 源码验证 2026-07-14）：

- `Peer<R>` struct 字段全是 private（`tx` / `request_id_provider` / `progress_token_provider` / `progress_timeout_watchers` / `info`），外部无法访问内部 Arc
- `Peer` impl `Clone` 但不 impl `Eq` / `Hash` / `PartialEq`
- `Peer::new` 是 `pub(crate)`，proc 测试无法构造 Peer 实例
- `LocalSessionHandle::id() -> &SessionId` 仅 SSE 路径可用（stdio 无 session 概念）
- HTTP header `mcp-session-id` 通过 `Extension<http::request::Parts>` 在 tool handler 拿（SSE-only）

**stage 2 兜底策略**：

1. **存储升级**：`Vec<Peer>` → `Vec<Arc<Peer>>`，proc 控制 Arc 包装让 push task 失败 cleanup 走 `Arc::ptr_eq` 精确 retain（stored Arc 与 spawned Arc::clone 共享同一 allocation）
2. **subscribe dedup 不做**：每次 `context.peer.clone()` 返新 Peer 值（即使同 client 多次调用），wrap 成新 Arc 无法跨调用去重。**依赖 push task 失败 cleanup 兜底**——client 断开后下一次 push 失败，对应 Arc<Peer> 被精确移除
3. **unsubscribe 清空整个 vec**：MCP 协议 `UnsubscribeRequestParam` 只有 `uri` 不携带 client identity，rmcp 0.11 `Peer` 也不暴露 public identity API。stdio 单 client 场景正确；SSE multi-client 场景下 A client unsubscribe 会清掉 B client 同 URI 订阅（B 想继续订阅需 client-side 重 subscribe）

**v0.20+ cycle 改进方向**：从 `RequestContext::extensions` 拿 `mcp-session-id` HTTP header（SSE 路径）作为 client identity，让 subscribe dedup + unsubscribe precise removal 走 mcp-session-id 字符串作 secondary index。详见 ADR-0027 §6.3 fallback 段。

### 决策 2：service_factory closure 返 `std::io::Error` 而非 `Infallible`

**stage 1 Spike 假设**（ADR-0027 §6.2）：service_factory closure 返 `Result<S, Error>`，Error 类型未明确。

**stage 2 实测修正**（cargo build error 验证 2026-07-14）：rmcp 0.11 `StreamableHttpService::new` 签名要求 closure 返 `Result<S, std::io::Error>`，不是 `Infallible`。stage 2 用 `|| Ok::<ProcMcpHandler, std::io::Error>(ProcMcpHandler::new())` 占位（`ProcMcpHandler::new` 不会失败）。

### 决策 3：tower_http `CorsLayer` 不引入（brainstorm §决策 6 推迟范围）

**stage 1 Spike 评估**：tower_http 已在 Cargo.toml，是否在 stage 2 加 `CorsLayer::very_permissive()` 让 SSE server 支持浏览器跨域。

**stage 2 决策**：不在 stage 2 引入。理由：
- brainstorm §决策 6 拍板 CORS 推迟 v0.20+ cycle
- tower_http 默认 feature 不含 `cors`，需加 `features = ["cors"]` 到 Cargo.toml
- stage 2 SSE server 主要 client是 mcp-inspector / Claude Desktop（非浏览器），CORS 不必要
- v0.20+ cycle 如评估到 Web dashboard 集成才落地

### 决策 4：SseTransportConfig socket_addr 仅接 IP 字面量

**stage 2 决策**：`socket_addr()` 解析 `(bind_addr, port)` 时拒绝 hostname（如 `"localhost"`），仅接受 IP 字面量（`"127.0.0.1"` / `"0.0.0.0"`）。

**理由**：
- ADR-0027 §6.4 bind-addr 安全默认要求用户显式 opt-in 全网卡监听，IP 字面量更明确
- TcpListener::bind 接受 hostname 会触发 DNS 解析（异步），让 socket_addr 同步解析避免运行时 surprise
- 测试场景：`test_serve_sse_rejects_invalid_bind_addr_gracefully` 验证 hostname 返 Err 不 panic
