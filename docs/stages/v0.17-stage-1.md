### 决策 3：stub 返回格式（与 v0.16 stage 1 决策 3 同款）

每个新 tool 的 stub helper 返 placeholder JSON：

```rust
    })

pub fn make_usb_release_json(_confirm: bool, _drive: &str, _kill_pids: &[u32], _dry_run: Option<bool>) -> Value {
    json!({
        "ok": true,
        "stub": true,
        "stage": "v0.17-stage-6",
        "message": "proc_usb_release tool schema is registered; business logic lands in stage 6",
        "received_confirm": _confirm,
        "received_drive": _drive,
        "received_kill_pids": _kill_pids,
        "received_dry_run": _dry_run,

}

// docker_rm 3 个 stub helper 同款格式，stage 字段 "v0.17-stage-6"
// metrics_history stub helper stage 字段 "v0.17-stage-4"
```

理由（与 v0.16 stage 1 决策 3 同款）：
- `ok: true` 让 client（如 mcp-inspector）调用时不报错，能验证 schema 正确生成
- `stub: true` 让 LLM / client 能识别「这是占位返回」避免误用
- `stage` 字段的版本标记让 stage 4/6 完工时容易 grep 验证替换
- `received_*` 字段保留参数 echo，方便 stage 4/6 调试 schema 反序列化

### 决策 4：`ProcMcpHandler` 加 3 个持久字段 stub（TD-54 + TD-52 + record 暴露前置）

参考 v0.12 TD-36 持久 dns_collector 模式（`dns_collector: Arc<Mutex<Option<Box<dyn DnsLogCollector>>>>` 字段），v0.17 cycle stage 1 给 `ProcMcpHandler` struct 加 3 个持久字段 stub：

```rust
pub struct ProcMcpHandler {
    // ... 既有字段（dns_collector / monitor_manager 等）...

    /// v0.17 stage 3 TD-54 落地：MCP handler 持久 SystemSnapshot，1s tick refresh
    /// stage 1 Spike 仅声明字段 + Default 返 None，stage 3 实装 worker spawn + refresh 逻辑
    #[cfg(feature = "mcp-persistent-state")]
    pub snapshot: Arc<Mutex<Option<SystemSnapshot>>>,

    /// v0.17 stage 4 TD-52 落地：sparkline 30s 历史，1s tick push
    /// stage 1 Spike 仅声明字段 + Default 返空 VecDeque，stage 4 实装 worker push 逻辑
    #[cfg(feature = "mcp-persistent-state")]
    pub system_history: Arc<Mutex<VecDeque<SystemSnapshot>>>,

    /// v0.17 stage 6 record 暴露落地：spawn `proc record` 子进程 handle
    /// stage 1 Spike 仅声明字段 + Default 返 None，stage 6 实装 spawn + lifecycle 管理
    #[cfg(feature = "mcp-persistent-state")]
    pub record_handle: Arc<Mutex<Option<std::process::Child>>>,
}
```

**stage 1 Spike 不实装 worker spawn 逻辑**——仅声明字段 + `Default` 返 `None` / 空 `VecDeque`。stage 3/4/6 各 Slice 实装 worker spawn + refresh / push / spawn 逻辑。

**`mcp-persistent-state` feature flag**：stage 1 Spike 加新 feature flag（在 `Cargo.toml` `[features]` 段），默认开启。理由：(1) 让 `ProcMcpHandler::Default` 在测试路径不强制 spawn worker（与 v0.12 TD-36 `dns_collector` Default 返 None 同款规则）；(2) 如未来贡献者需关闭持久字段（如最小化 build），可 `--no-default-features` 关闭。

**Clone derive**：`Arc<Mutex<T>>` 字段自动 Clone 共享（与 `dns_collector` 同款），rmcp 内部 clone handler 时共享同一 snapshot / system_history / record_handle 实例。

### 决策 5：CONTEXT.md 新术语 8 个

stage 1 Spike 给 CONTEXT.md 加 8 个新术语（v0.17 cycle 5 主题对应）：

- **PersistentHandlerState**：v0.17 cycle 给 `ProcMcpHandler` 加的 3 个持久字段统称（`snapshot` / `system_history` / `record_handle`）。与 v0.12 TD-36 持久 `dns_collector` 同款 `Arc<Mutex<T>>` 模式延续。stage 1 Spike 声明字段 + Default 返 None / 空 VecDeque；stage 3/4/6 各 Slice 实装 worker spawn 逻辑。
- **Vt100ToUiFrameConverter**：v0.17 cycle 主题 F 落地的 VT100 字节流转码 UiFrame 转换器（`src/record/vt100_to_uiframe.rs`）。stage 1 Spike 声明 struct + trait stub；stage 5 实装增量解析 + 累积屏幕 buffer + 30 FPS 切片为 UiFrame。临时转码路径（决策 6 拍板方案 a），不破坏原 VT100 文件。
- **ResourceRoute**：v0.17 cycle 主题 B 落地的 rmcp 0.11 Resource subscribe trait（`src/mcp/resources.rs`）。stage 1 Spike 声明 trait stub；stage 4 实装 `proc://metrics/system` / `proc://processes/list` / `proc://docker/events` 等资源 URI 路由 + client 订阅后 worker 1s tick 推送增量。
- **SseTransport**：v0.17 cycle 主题 B 落地的 SSE transport 容器（`src/mcp/transport.rs`）。stage 1 Spike 声明结构 + trait stub；stage 4 实装 `proc mcp serve --transport sse --port 8080` CLI 入口，长连接场景替代 stdio。
- **ConfirmRequired**：v0.17 cycle 写操作 confirm 机制标记（ADR-0029 落地）。`proc_record_start` / `proc_usb_release` / `proc_docker_rm` / `proc_docker_image_rm` / `proc_docker_volume_rm` 5 个 tool 都 `confirm: bool` 必传。与既有 `dry_run: bool` 默认 false 契约互补（dry_run 是「不真正执行」/ confirm 是「确认风险后再执行」）。
- **RecordSubprocess**：v0.17 cycle record 暴露方案 (a) spawn `proc record` 子进程路径（ADR-0029 落地，决策 4 拍板）。`proc_record_start` tool spawn `proc record --no-tui --output <path>` 子进程，handler 持 `record_handle: Arc<Mutex<Option<Child>>>` 字段跨 tool call 保活；`proc_record_stop` kill child + 等待 `.prec` 文件 flush。与 v0.6 落地的 `R` 键 TUI 路径并行（`--no-tui` flag 让 record 走 headless 路径）。
- **HeadlessRecord**：v0.17 cycle stage 6 落地的 `proc record --no-tui` flag 路径。让 record 走 headless 模式（不 attach TUI），与 v0.6 落地的 `R` 键 TUI 路径并行。stage 1 Spike 加 flag 声明 + stub 分支返 "v0.17-stage-6 未实装" 错误；stage 6 实装 headless 路径（recorder / bookmark / anomaly detection 复用 v0.6 业务逻辑）。
- **SparklineHistory**：v0.17 cycle stage 4 TD-52 落地的 30s 历史采样。`ProcMcpHandler` 加 `system_history: Arc<Mutex<VecDeque<SystemSnapshot>>>` 字段，1s tick push 一次，30s cap。`proc_metrics_history` tool（或 `proc_metrics_system` 加 `history` 字段，stage 4 决策）返 sparkline 数据点。

  3. `--no-tui` flag 重构：让 `proc record` 走 headless 路径，与 v0.6 落地的 `R` 键 TUI 路径并行
- 关键设计点：
  1. spawn 子进程复用 v0.6 落地的 `run_record` 业务逻辑（recorder / bookmark / anomaly detection），不重写
  2. MCP handler 不持 worker 状态（与 v0.12 TD-36 持久 dns_collector 模式不同，dns_collector 是查询类 worker 持有成本低，record worker 是录制类 worker 持有成本高）
  3. 子进程崩溃隔离（record worker 崩溃不影响 MCP server）
  4. `confirm` vs `dry_run` 语义差异：dry_run 是「不真正执行」/ confirm 是「确认风险后再执行」—— 互补不冲突
- 备选方案：
  - record 暴露方案 (b) MCP handler 启 worker 线程（否决：worker 持续运行影响主路径 + lifecycle 管理复杂）
  - record 暴露方案 (c) 推迟到 v0.18+ cycle（否决：v0.17 cycle 用户拍板全做）
  - confirm 机制方案 B 两次调用 token（否决：复杂，无需 token 状态机）
  - confirm 机制方案 C 仅文档警告（否决：agent 视角不明确，需显式 confirm=true）
- 结果：record 暴露 + 写操作 confirm 机制 schema 落地，stage 6 实装 spawn 子进程 + `--no-tui` headless 路径 + 5 个 tool 业务逻辑
- 相关 ADR：ADR-0009（MCP server）/ v0.16 ADR-0025b（record 不暴露推迟项）/ v0.6 落地的 pending_record_confirm TUI 路径

**完成**：4 份 ADR 文件创建 + 各 ~150 行 + Status Accepted。

- 子 module 骨架严格按决策 7 / 决策 8 代码示例，不扩业务逻辑

### 风险 2：rmcp 0.11 tool_router 收集 46 个 tool 时编译失败

**低风险**：v0.16 stage 1 已验证 rmcp 0.11 可收集 39 个 tool，7 个新 tool（共 46）远低于 rmcp 限制（无文档化上限）。`cargo check` 编译通过即证伪此风险。
