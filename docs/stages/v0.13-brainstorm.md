## 候选方向（5 个 theme）

### Theme A：性能 baseline cycle（推荐 — 用户已选）

**Scope**：建立 criterion benchmark suite + 瓶颈分析报告 + 按优先级优化

**核心问题**：
- v0.6 stage 6 实测的 baseline（rebuild_sorted_cache 38.2 µs / top-N 6.1 µs / draw < 15ms）已经 5+ cycle 没更新；v0.7-v0.12 加了 FilterExpr / signature async / parent_chain / Flow view / Schannel ETW 一堆新代码路径，旧 baseline 失效
- 没有 benchmark suite 意味着每次优化的「快了多少」靠感觉；性能优化最大陷阱是「凭感觉」（v0.6 stage 8 脏矩形教训：直觉是瓶颈，实测发现根本不是）
- 用户报「卡」时无法定位是哪个 worker / 哪段渲染 / 哪个评分入口

**侦察报告关键发现**（2026-07-04 会话产出，详见 brainstorm 下方「侦察发现」段）：
1. CONTEXT.md 与代码不一致：HeavyWorker 周期文档写 1.5s，代码实际 `HEAVY_REFRESH_INTERVAL = 2s`
2. TUI 渲染层 format! 风暴（process_table 每行每帧 5+ 次 format!）
3. parent_chain 每周期 clone 到 Vec（每进程每 2s 一次堆分配）
4. 录屏 UiFrame bincode 每帧全量序列化（长 session 文件体积未优化）
5. refresh_heavy 主线程路径 vs HeavyWorker 路径可能有重复工作

**工作量预估**：
- stage 1 baseline 基础设施：~250 行（criterion dev-dep + 6 个 benchmark + sidecar 文档修复）
- stage 2 瓶颈分析：~150 行（PERF-BASELINE 报告）
- stage 3+ 优化：每 stage ~200-400 行，数量由 stage 2 报告决定

**周期预估**：2 stage 必做（baseline + 报告）+ N stage 优化（N=0~4），1-3 周

**收益**：
- benchmark suite 建立后，后续每个 cycle 都受益（performance guard）
- 用户报 bug 时附 criterion 数字，定位成本降一半
- 顺手清掉文档不一致（1.5s → 2s）

**风险**：低。stage 1-2 不动业务代码，只加 benches/ + 改注释；stage 3+ 每个优化有 before/after 数字对比，不引回归

### Theme B：直接打已知可疑点（备选 — 凭直觉优）

**Scope**：跳过 baseline 直接优化侦察发现的 5 个疑点

**风险**：高。可能优化了根本不是瓶颈的东西，与方案 A 相比缺 before/after 数字守护，不推荐

### Theme C：tech-debt 清零（备选 — 单薄）

**Scope**：清 TD-40 + TD-41 + 加 benchmark suite 防退化

**风险**：低，但 cycle 单薄（两个理论风险 TD），可作方案 A 的 sidecar

### Theme D：新功能（用户面向）

候选：录屏回放 v2（书签 + 倒放 + 时间轴搜索）/ 多 Inspector 对比 / Flow 视图时间窗口聚合 / 用户报 bug 一键诊断包

**风险**：方向多，每个独立 1 cycle。可与方案 A 串行（v0.13 性能 + v0.14 新功能）

### Theme E：代码质量 / 重构

**Scope**：App 上帝对象继续拆（v0.6-v0.7 拆过 5 个 controller，但 App 仍 ~1500 行）+ 测试分层覆盖率分析

**风险**：低，长期维护性，无 user-visible 变化

## 推荐方案：Theme A（性能 baseline cycle）

**用户已确认选 A**（2026-07-04 会话）。理由：

1. **科学化**：benchmark baseline 一旦建立，后续每个 cycle 都受益。v0.6 stage 6 实测数据用过 5+ cycle，下一次再不更新就过期 1 年了
2. **安全性**：stage 1-2 不动业务代码，零回归风险；stage 3+ 每个优化有 before/after criterion 数字对比
3. **降维护成本**：用户报「卡」时附 criterion 数字，省一轮来回
4. **顺手收益**：清掉 CONTEXT.md 与代码不一致（1.5s → 2s），零风险交付
5. **承上启下**：v0.11 / v0.12 都是「功能 / 平台」驱动，v0.13 转「品质 / 稳定性」让 proc 进入生产可用档

## 常见问题 FAQ

### Q1: 为什么不直接做 stage 3+ 优化清单？
**A**: stage 2 报告没出之前，无法判断哪个 hot path 是真瓶颈。可能侦察报告里列的 5 个疑点全部都不是瓶颈（v0.6 stage 8 脏矩形就是这种 case）。先测后优避免「凭感觉优化」陷阱。

### Q2: stage 1 的 6 个 benchmark 够不够？
**A**: 6 个覆盖了已知 hot path（搜索 / 排序 / heavy refresh / TUI 渲染 / 录屏序列化 / replay）。stage 2 报告如果发现新 hot path，再补 benchmark。

### Q3: criterion benchmark 在 CI 跑会不会抖动大？
**A**: 不会在 CI 跑（决策表 B 选项）。criterion 在 GitHub Actions 共享 runner 上数字不稳，仅本地用。后续如果要做 performance guard，可考虑 self-hosted runner 或只在 release 前手跑。

### Q4: stage 3+ 的优化会破坏 v0.12 的功能吗？
**A**: 不会。每个 stage 3+ 必须满足：(1) 全量回归 ≥ 1115 passed / 0 failed / 3 ignored；(2) criterion before/after 数字对比，不退化；(3) 不动用户面向的 API / 字段。任何破坏性改动走回溯修复阶段。

### Q5: 如果 stage 2 报告显示「无显著瓶颈」怎么办？
**A**: cycle 缩到 4 stage（baseline + 报告 + Review + 收尾），直接发 v0.13.0 作为「性能验证 cycle」——证明 proc 当前架构无瓶颈，benchmark suite 留作 future 性能 guard。
