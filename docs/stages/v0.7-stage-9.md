**开工前必读**：

- `docs/tech-debt.md` — 验证 TD-1..TD-14 的标记与本阶段产出对齐
- 测试命令

**任务清单**：

1. **代码质量审查（半天）**
   - 模块间耦合度：阶段 5 拆出的 5 个 PanelController 是否真的解耦（App::handle_key 不再写 panel 内联逻辑）
   - 接口一致性：阶段 2 MCP tools 的命名规范 `proc_<subcommand>` 是否 100% 一致
   - 命名规范：v0.7 新增术语是否使用 CONTEXT.md 中定义的命名（FilterExpr / ProcessFlow / EcoQoSState）
   - 代码风格统一：注释格式、错误处理风格（anyhow vs thiserror vs panic）
   - 类型注解 / serde derive 完整性

2. **架构审查（半天）**
   - 对照 `docs/adr/0009-0016`，每个 ADR 的决策是否真的在代码中体现
   - **重点查 ADR-0012（App controller split）**：App 字段数是否真降到 ≤ 20；handle_key 是否真简化
   - **重点查 ADR-0016（eBPF feature flag）**：`cargo build`（不带 feature）是否真的不引入 aya 依赖（验证 `Cargo.lock`）
   - 是否有过度设计（如 FilterExpr 的 OR 分支是否真用到）或设计不足（如 PSI worker 30s 周期是否合理）

3. **安全性审查（半天）**
   - 阶段 1 TD-10 DNS probe restricted_spawn 路径是否正确
   - 阶段 2 MCP server 是否有路径遍历 / 命令注入风险（LLM 输入不可信）
   - 阶段 6 EcoQoS 的 OpenProcess 句柄是否正确 CloseHandle
   - 阶段 7 ETW session 是否在 worker Drop 时正确 stop（不留孤儿 session）
   - 阶段 8 eBPF 加载是否正确卸载（不留孤儿 program）

4. **跨平台一致性（半天）**
   - 阶段 5 PSI / 阶段 6 EcoQoS / 阶段 7 ETW / 阶段 8 eBPF 的 cfg-gate 是否正确（grep `#[cfg(` 全部检查）
   - Linux stub 是否真的返回合理降级值（None / Unknown / 空 Vec），而非 panic
   - 平台支持表（README）是否与代码一致

5. **测试覆盖（半天）**
   - 阶段 2-8 的所有新测试是否真覆盖关键路径
   - 边界条件：FilterExpr 非法语法 / MCP 不存在 tool / EcoQoS 无权限 / ETW 非管理员 / eBPF 无 CAP_BPF
   - 是否有"测试存在但没在 CI 跑"（cfg-gate 写错）
   - 全量回归 `cargo test --release -q` 在 Windows / Linux CI 都通过

6. **文档完整性（半天）**
   - README + CHANGELOG 是否反映 v0.7.0 全部新能力
   - 16 个 ADR Status 是否准确（v0.7 新写的 8 个 Accepted）
   - `docs/tech-debt.md` 标记是否完整（10 项阶段 1 Fixed + TD-6 阶段 5 Fixed + TD-11 决策不修 + TD-12/13/14 状态）
   - CONTEXT.md 术语演进历史是否填了实际落地日期
   - 检查 v0.6 旧 stage-1.md ~ stage-8.md 是否被误改（应该不动）

7. **性能基线对比（半天）**
   - `perf.log` 加 v0.7.0 基线（启动时间 / tick 平均延迟 / 500 进程下内存）
   - 对比 v0.6.0 基线（plan.md 中的"500 进程 × 1.5s 重采下，每秒堆分配减少 90%+"）
   - 不应有显著回退（5% 以内可接受，超过则标记 P1）
   - 命令面板 Ctrl+P fuzzy 速度：1000 个命令项输入延迟应 < 16ms
