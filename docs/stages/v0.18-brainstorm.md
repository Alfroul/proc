### 决策 3：项 3 实装路径（用户已拍板 ✅）

**自建 worker lifecycle**——rmcp 0.11 `ResourceRoute` 是 proc 内部 trait（stage 4 落地时为 polling-push 设计），v0.18 自建 subscribe-push worker lifecycle：

1. **client 调 `resources/subscribe`**：`ProcMcpHandler` impl `ServerHandler::subscribe_resource`（rmcp 0.11 API，如原生支持；否则 proc 内部 `subscribe` 方法）
2. **spawn push task**：worker 持 `Arc<Mutex<HashMap<SubscriberId, Sender<Value>>>>` 注册表，subscribe 时 spawn push task（持 client channel + 1s tick drain `snapshot` push 到 client channel）
3. **client 断开 cancel task**：unsubscribe 时从注册表移除 + drop Sender 让 push task 退出（channel closed）

**stage 1 Spike 调研子任务**：用 context7 查 rmcp 0.11 `ServerHandler::subscribe_resource` / `ResourceSubscriber` API 是否原生支持 subscribe-push。如原生支持 fallback 到原生路径（决策 3 备选）；如不支持确认自建 worker lifecycle 路径。

### 决策 4：项 4 auto-stop 位置（用户已拍板 ✅）

**子进程 `--duration` flag**——与 ADR-0029 决策 4「spawn 子进程复用 v0.6 业务逻辑 + 子进程崩溃隔离」对齐：

1. **CLI 加 `--duration` flag**：`src/cli/def.rs` `Command::Record` 加 `duration: Option<u64>` 字段
2. **`run_record_headless` 内 timer thread**：spawn `std::thread::spawn(move || { sleep N secs; shutdown::request(); })` + 主循环检 `shutdown::requested()` 退出
3. **MCP handler spawn 时传 flag**：`make_record_start_json` spawn 时加 `.arg("--duration").arg(secs.to_string())`（如 `duration_secs` Some）+ 移除 warning 字段

**优势**：
- 子进程 timer 随 child 退出自动终止，无 zombie timer
- MCP handler 不持 timer 状态（与 ADR-0029 决策 4「MCP handler 不持 worker 状态」对齐）
- 复用 v0.6 落地的 `shutdown::requested()` 干净退出路径（与 `--no-tui` headless 路径同款）

## 已知风险

### 风险 1：项 3 rmcp 0.11 subscribe API 学习曲线

**问题**：rmcp 0.11 `ServerHandler::subscribe_resource` / `ResourceSubscriber` API 是否原生支持 subscribe-push 未知。stage 4 落地 `ResourceRoute` 是 proc 内部 trait（polling-push 设计），未触及 rmcp 原生 subscribe API。

**影响**：如 rmcp 0.11 原生 API 与 proc 内部 trait 设计差异大，stage 2 实装时可能需重构 `ResourceRoute` trait 接口。

**mitigate**：
- stage 1 Spike 用 context7 调研 rmcp 0.11 `ServerHandler::subscribe_resource` API（决策 3 调研子任务）
- 如原生支持 → fallback 到「rmcp 原生」路径（决策 3 备选方案），工作量从 ~200 行降到 ~100 行
- 如不支持 → 确认自建 worker lifecycle 路径，stage 2 严格按 stage 1 设计的 state machine 实装

### 风险 2：项 3 worker lifecycle 复杂度

**问题**：subscribe-push worker lifecycle 三步管理（client 连接注册 → spawn push task → 断开 cancel）复杂度高。client 异常断开（网络抖动 / 进程崩溃）时 push task 可能泄漏（zombie task 持续 push 到 closed channel）。

**影响**：如 lifecycle 管理有漏洞，长期运行 MCP server 可能累积 zombie task 占用内存 + CPU。

**mitigate**：
- stage 1 Spike 设计 lifecycle state machine（subscribe → push → unsubscribe / client 断开 → cancel）
- stage 2 加 lifecycle 回归测试（client subscribe + 立即断开 → 验证 push task 退出 + 注册表清空）
- push task 用 `Sender::send` 返 Err 时自动退出（channel closed 检测）

### 风险 3：项 2 TD-45 varint 向后兼容

**问题**：旧文件 fixint / 新文件 varint 兼容层如 version 检测逻辑有误，v0.6~v0.17 各版本旧录屏文件可能无法打开（agent 调 `proc_replay_info` / `proc_replay_search` 时报错）。

**影响**：旧录屏文件无法回放是 P0 级回归问题（与 v0.17 stage 3 落地 fixint 兼容层时的同款风险）。

**mitigate**：
- stage 2 加旧文件回归测试（v0.6~v0.17 各版本录屏文件 fixture，验证 magic + version 检测走 fixint 兼容层）
- v0.18 新文件 varint 等价性测试（varint 写入 + 读取 + 与 fixint 输出对比）
- stage 3 Review 段手动验证 v0.17 旧录屏文件可正常打开

### 风险 4：3 stage 节奏 stage 2 单段容量

**问题**：stage 2 单段实装 4 项 ~495 行（业务 ~365 + 测试 ~130），虽远低于 1500 行上限（33%），但 4 项主题分散（代码清理 / varint / auto-stop / subscribe-push），上下文切换开销大。

**影响**：如 stage 2 上下文快满时项 3 subscribe-push 未完成（项 3 最复杂放最后），可能触发 Checkpoint 接力。

**mitigate**：
- stage 2 内严格按排序（项 1 → 项 2 → 项 4 → 项 3），项 3 放最后让前 3 项先 commit
- 如项 3 触发 Checkpoint → 生成 `docs/handoff-stage-2-checkpoint.md`，新会话续项 3
- 项 3 如工作量超预期 → 触发自适应拆分（stage 2a 项 1+2+4 / stage 2b 项 3），cycle 改 4 stage

## FAQ

### Q1: v0.18 cycle 为什么不合并到 v0.17 cycle 末段？

**A**: 三个理由：
1. **v0.17 cycle 已满**：7 stage ~5540 行 + 4 ADR + 5 主题，再加 4 项 ~820 行 = ~6360 行，超 cycle 容量（与 v0.16 cycle ~810 行对比 v0.17 cycle 已 6.8x 量级）
2. **v0.17 cycle 已 tag**：v0.17.0 已 commit + tag，cycle 边界已锁定，追加破坏 git 历史清晰度
3. **v0.18 cycle 独立让残留项补全有独立 Review 段**：4 项都是 v0.17 Findings 推迟项，独立 Review 让补全质量有独立审查

### Q2: 项 3 为什么不直接用 rmcp 0.11 原生 subscribe？

**A**: stage 4 落地 `ResourceRoute` 是 proc 内部 trait（polling-push 设计），未触及 rmcp 原生 subscribe API。v0.18 stage 1 Spike 用 context7 调研 rmcp 0.11 `ServerHandler::subscribe_resource` API：
- 如原生支持 → fallback 到原生路径（决策 3 备选），工作量从 ~200 行降到 ~100 行
- 如不支持 → 确认自建 worker lifecycle 路径（用户已拍板决策 3）

stage 1 Spike 调研结果决定 stage 2 实装细节，但 cycle 范围（项 3 落地 subscribe-push）不变。

### Q3: 项 4 auto-stop 为什么选子进程 --duration flag 而非 MCP handler timer？

**A**: 与 ADR-0029 决策 4「spawn 子进程复用 v0.6 业务逻辑 + 子进程崩溃隔离」对齐：
1. 子进程 timer 随 child 退出自动终止，无 zombie timer（vs MCP handler timer 需手动 cancel）
2. MCP handler 不持 timer 状态（与「MCP handler 不持 worker 状态」决策对齐）
3. 复用 v0.6 落地的 `shutdown::requested()` 干净退出路径（与 `--no-tui` headless 路径同款）
4. 子进程崩溃时 timer 也随之终止（vs MCP handler timer 需独立检测 child 退出）

### Q4: 项 1 代码清理为什么 v0.17 cycle stage 7 不直接修？

**A**: 按 v0.17 brainstorm §执行中步 11「小修（< 5 处改动）：在当前阶段内直接修复」+ 决策 3「收尾段不动业务代码」——P1-R1 + P2-R1 是代码质量问题（< 5 处改动），但决策 3 明确「收尾段不动业务代码」让 stage 7 Review+收尾段不混入业务修复。v0.18 cycle 在 record 路径相关改动（项 4 auto-stop）时一并清理，与决策 3「留 v0.18+ cycle 在 record 路径相关改动时一并清理」对齐。

### Q5: v0.18 cycle 后 proc 还有哪些方向？

**A**: v0.18 cycle 末段（stage 3 Review）会评估 v0.19+ 候选方向，预计包括：
- **主题 C**：跨平台扩展 cycle（Linux/macOS 重新支持，与 v0.12 ADR-0022 Windows-only 决策可能翻盘）
- **主题 E**：插件系统 cycle（让用户扩展 inspector tab / worker / scoring rule）
- **主题 G**：分布式采集 cycle（多机 proc 联合分析）
- **v0.18 cycle 残留项**：SSE transport full 实装 / bollard prune_children 真正字段 / record 暴露方案 (b) worker 持续采样路径评估 / VT100 永久转码 CLI 子命令

## 开发阶段计划执行手册（每个会话的强制规则）
