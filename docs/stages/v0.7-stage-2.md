> ✅ **v0.7.0 已发布（2026-06-28）**。本阶段任务全部交付，详见 CHANGELOG `[0.7.0]` 段「阶段 2」。

> **独立会话指令**：`阅读 CONTEXT.md 和 docs/stages/v0.7-stage-2.md，完成所有任务后确认完成`
>
> **开工前只需阅读**：`CONTEXT.md`（McpServer 术语）、`docs/stages/v0.7-stage-2.md`、测试命令、`docs/adr/0009-mcp-server.md`（本阶段产出）。

**目标**：基于 `rmcp` 官方 Rust SDK 实现 `proc mcp serve` 子命令，stdio transport，把 proc 的 17+ CLI 子命令暴露为 MCP tools 供 Claude Code / Cursor 等 LLM agent 调用。

**前置依赖**：阶段 1 已完成。

**依赖测试**（开工时跑详情）：

- `cargo test --release --test test_inspector -- --nocapture`（v0.6 键位兼容基线，本阶段不动 TUI）
- `cargo test --release --test test_diag -- --nocapture`（阶段 1 新增 Docker worker 行覆盖）

**技术决策（详见 ADR-0009，本阶段落地）**：

- **用 `rmcp` 官方 Rust SDK**（modelcontextprotocol/rust-sdk），不用 `rust-mcp-sdk` 或 `prism-mcp-rs`：rmcp 是 MCP 协议官方维护，rust-code / Claude Code 都在用
- **stdio transport only**：第一版不上 HTTP/SSE。MCP client（Claude Desktop / Cursor）默认 stdio
- **tool 命名规范**：`proc_<subcommand>`，如 `proc_ls` / `proc_port` / `proc_kill` / `proc_dns` / `proc_handles` / `proc_diag` / `proc_docker_ps` 等
- **每个 tool 是 thin wrapper**：调 `crate::cli::run_subcommand(cmd)` 同款函数，复用 v0.6 已有 17+ 子命令实现，不重写
- **异步 tokio runtime 隔离**：rmcp 用 tokio，proc 主线程是同步。MCP server 走独立子命令分支，不影响 TUI 路径

**任务清单**：

1. **依赖添加（5 min）**
   - `Cargo.toml` `[dependencies]` 加：`rmcp = { version = "0.11", features = ["server", "transport-io"] }`
   - 加：`tokio = { version = "1", features = ["rt-multi-thread", "macros", "io-std", "io-util"] }`（已有 `rt-multi-thread/macros/net/sync/time`，追加 `io-std/io-util`）
   - 加：`schemars = "0.8"`（rmcp 依赖，生成 JSON Schema）
   - 加：`async-trait = "0.1"`（rmcp handler trait）
   - 验证：`cargo build --release` 通过

2. **MCP module 骨架（1 h）**
   - 新建 `src/mcp/mod.rs`：
     - pub fn `run_mcp_serve() -> anyhow::Result<()>`（入口，main.rs 调）
     - 内部用 `tokio::main` 风格 runtime（proc 主线程同步，这里 block_on）
   - 新建 `src/mcp/handler.rs`：
     - `struct ProcMcpHandler`（含 worker 句柄等可选上下文）
     - `#[tool_router]` impl 块，里面 `#[tool(...)]` 标注每个工具方法
     - `#[tool_handler]` impl `ServerHandler for ProcMcpHandler`
   - 新建 `src/mcp/tools.rs`：每个 tool 的实现细节（thin wrapper 调 cli 模块）
   - 验证：`cargo check` 通过

3. **MCP tools 实现（每个 thin wrapper，~30 min × 17 = ~8 h）**
   每个工具的 pattern：
   ```rust
   #[derive(Deserialize, schemars::JsonSchema)]
   struct LsArgs {
       /// Sort field: cpu / mem / name / pid / disk_read / disk_write / net_sent / net_recv
       sort: Option<String>,
       /// Max processes to return
       limit: Option<usize>,
   }

   #[tool(name = "proc_ls", description = "List processes, sorted by cpu/mem/etc")]
   async fn proc_ls(&self, Parameters(args): Parameters<LsArgs>) -> Json<serde_json::Value> {
       // 调 cli::ls::run_ls(args) 同款实现
       // 返回 JSON（不是表格，因为 LLM 不读表格）
   }
   ```
   **必须实现的 tools**（对应 v0.6 CLI）：
   - `proc_ls` / `proc_tree` / `proc_port` / `proc_kill` / `proc_pkill` / `proc_eject` / `proc_who` / `proc_handles` / `proc_priority` / `proc_affinity` / `proc_smart` / `proc_dns` / `proc_diag` / `proc_monitor_list` / `proc_docker_ps` / `proc_docker_top` / `proc_docker_logs`
   - **不实现**（无意义给 LLM）：`proc_record` / `proc_replay` / `proc_export`（这些是给人用的输出）
   - v0.7 阶段 6/7 落地后再追加：`proc_psi` / `proc_throttle` / `proc_disk_io`
   - v0.7 阶段 8 落地后再追加：`proc_flows`（eBPF feature flag）
   - 验证：每实现 4 个 tool 跑一次 `cargo check`

4. **CLI subcommand 注册（10 min）**
   - `src/cli/def.rs` 在 `Command` enum 加：
     ```rust
     #[command(name = "mcp", about = "MCP server mode (stdio transport)")]
     Mcp { subcommand: Option<McpSub> },
     ```
   - `src/cli/mcp_cmd.rs`（新增）：`McpSub` enum，第一版只有 `Serve`，未来扩 `List` / `Inspect`
   - `src/cli/mod.rs::run_subcommand` 加 dispatch：`Command::Mcp { subcommand } => run_mcp(subcommand)`
   - `run_mcp(Serve)` → `crate::mcp::run_mcp_serve()`
   - 验证：`proc mcp serve --help` 显示用法

5. **输出格式（1 h）**
   - **关键：LLM 读 JSON 不读表格**，所有 tool 返回结构化 JSON 而非 comfy-table
   - `ProcessInfo` 已有 serde derive（v0.6 阶段 4 启用 rc feature），直接 `serde_json::to_value(&processes)`
   - 数值字段加 doc comment（LLM 看 schema 理解字段含义）：`cpu_usage: f32 /* 0-100 百分比 */` 等
   - 大字段裁剪：如 `proc_ls` 默认只返回 pid/name/cpu/mem/cmd/security_score，加 `verbose: bool` 返回完整字段
   - 验证：`proc mcp serve` 用 mcp-inspector 连上看 schema

6. **错误处理（30 min）**
   - tool 调用失败 → `CallToolResult::error(vec![text_content(...)])`（不 panic，让 LLM 看到错误）
   - port 不存在 / pid 已死 / docker daemon 不在 → 友好错误消息
   - 验证：测试 mock 一个不存在 PID 调 `proc_kill`，返回 error 不 crash

7. **集成测试 `tests/test_mcp_server.rs`（2 h）**
   - 测试 1：list_tools → 返回的工具数 ≥ 17
   - 测试 2：call_tool("proc_ls", {limit: 5}) → 返回 5 个进程的 JSON
   - 测试 3：call_tool("proc_ls", {sort: "cpu", limit: 3}) → 返回按 cpu 排序的前 3
   - 测试 4：call_tool("proc_kill", {pid: 999999}) → error（不存在）
   - 测试 5：call_tool("proc_diag", {}) → 返回 worker metrics JSON
   - 测试 6：call_tool("proc_docker_ps", {}) → 即使 docker 不在也不 crash（返回空或 error）
   - 验证：6 个测试全部通过

8. **ADR-0009 文档（30 min）**
   - 创建 `docs/adr/0009-mcp-server.md`
   - Status: Accepted
   - Context: v0.7 需把 proc 的进程/网络/DNS/Docker 能力暴露给 LLM agent
   - Decision: 用 rmcp 官方 SDK + stdio + proc_<subcommand> 命名 + thin wrapper
   - Alternatives: rust-mcp-sdk / prism-mcp-rs / 自写协议
   - Consequences: 增加依赖 ~600KB（rmcp + schemars + async-trait），tokio runtime 进入子命令分支
   - 验证：ADR 文件存在且格式正确
