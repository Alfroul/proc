## 设计决策（stage 2 拍板）

### 决策 1：replay_info 双路径分发（v3 UiFrame + VT100）

`make_replay_info_json(file_path)` 入口先调 `is_vt100_file(path)` 分发：

- **VT100 路径**：`VtPlayer::open(path)` → 返 `format: "vt100"` + header 字段（version=2 / start_time / width / height）+ 帧段（frame_count / start_ms / end_ms）。无 footer / 无 anomaly / 无 event / max_cpu / max_mem 字段（VT100 录屏不含结构化系统指标）。
- **v3 UiFrame 路径**：`Player::open(path)` → 返 `format: "uiframe"` + footer 字段（version=3 / hostname / start_time / end_time / duration_secs / frame_count / anomaly_count / event_count / max_cpu / max_mem）。
- **路径共通字段**：`has_bookmarks_sidecar` 检 `<path>.bookmarks.json` 文件是否存在（v3 + VT100 都支持 sidecar，与 brainstorm §Q4 对齐）。
- **失败路径**：文件不存在 / IO 错误 / deserialization 失败 → `{ ok: false, error: <msg> }`（与既有 `make_eject_json` / `make_processes_json` 同款 err helper）。

`size_bytes` 字段走 `std::fs::metadata(path).len()`（v3 + VT100 共通）。

### 决策 2：replay_search 走 FilterExpr + apply_frame + limit 截断

`make_replay_search_json(file_path, query, limit)` 实装走 ADR-0025a 设计：

1. **VT100 路径不支持 search**：`is_vt100_file(path) == true` → 返 `{ ok: false, error: "VT100 录屏不支持 search（仅 v3 UiFrame）" }`。VT100 无结构化帧，无法走 FilterExpr 路径。
2. **v3 路径**：`Player::open(path)` → parse query → 遍历 frames → 截断。
3. **query 双入口**（与 ReplaySearch 同款，[`src/replay/search.rs::reparse`](../../src/replay/search.rs)）：
   - `:` 前缀 → `parse_frame(stripped)`（FilterExpr 模式，5 维度：timestamp / cpu / mem / name / anomaly.severity）
   - 无 `:` 前缀 → `build_frame_substring_expr(query)`（substring 模式，转 `name =~ /query/i` regex）
4. **parse 失败**：返 `{ ok: false, error: <ParseError.msg> }`，不进入遍历路径。
5. **limit 截断**（ADR-0025a 决策）：
   - `limit.unwrap_or(100)` 默认 100
   - 遍历所有 frames，命中收集到 `Vec<usize>`（升序，与 timeline 视觉顺序一致）
   - `match_count = matches.len()`，`returned = min(match_count, limit)`，`truncated = match_count > returned`
   - 截断后取前 `limit` 个 frame_idx 组装 matches[] 字段
6. **matches[] 字段**（ADR-0025a schema）：
   ```json
   {
     "frame_idx": 1234,
     "timestamp": 1759000123,
     "cpu_usage": 85.3,
     "memory_used": 4294967296,
     "matched_processes": ["chrome.exe", "firefox.exe"],
     "anomaly_severity": null
   }
   ```
   - `matched_processes[]` 走 `FrameField::any_match_text` 同款扫描：若 FrameRegex/FrameIn 命中（substring / name regex / name in），列出命中的进程名集合；若 FrameFieldCmp 命中（cpu/mem/timestamp/anomaly.severity 数值或 anomaly severity），`matched_processes` 是该帧所有进程名（让 agent 知道当时跑了什么）
   - `anomaly_severity`：帧内最高 severity（critical > warning > info），无 anomaly 时 null
7. **空 query / 仅 `:`**：parse_frame 失败 → ok=false + error，与 ReplaySearch 同款。

### 决策 3：replay_search 遍历性能可接受（不做异步）

按 brainstorm §Q3 + ADR-0025a 设计：30min × 30FPS × 165µs = ~9s/30min session。MCP client（Claude Desktop / Cursor / mcp-inspector）默认 timeout 通常 30s+，同步遍历可接受。

stage 2 实装走简单 for loop（不引入异步路径 / progress notification），与 [`src/replay/search.rs::recompute_matches`](../../src/replay/search.rs) 同款同步遍历。

### 决策 4：eject_status 4 档 suggestion 决策树

`make_eject_status_json(drive)` 实装走 brainstorm §决策 9 + ADR-0025a 字段裁剪原则：

1. **drive 字符 normalize**（与 [`src/mcp/handler/mod.rs::make_eject_json`](../../src/mcp/handler/mod.rs) 同款）：
   - 取第一个 ascii_alphabetic 字符 + to_uppercase
   - 空字符串 / 无字母 → `{ ok: true, drive: <original>, suggestion: "unknown_drive" }` + `device: null` + `lock_count: 0` + `locks: []`
2. **找设备**：`scan_all_devices()` 遍历找 `drive_letter == letter` 的 RemovableDevice
   - 找不到 → `suggestion: "unknown_drive"` + `device: null` + `ejectable: false`
   - scan_all_devices 失败（错误）→ `suggestion: "unavailable"` + `device: null` + `ejectable: false` + warning 字段
3. **找 locks**：`scan_device_locks(letter)`
   - scan_device_locks 失败 → `suggestion: "unavailable"` + `device: <found>` + `ejectable: false` + warning 字段
   - locks 非空 → `suggestion: "kill_locks"` + `ejectable: false` + `lock_count: N` + `locks: [...]`
   - locks 空 → `suggestion: "eject_now"` + `ejectable: true` + `lock_count: 0` + `locks: []`
4. **device 字段裁剪**（与 `make_eject_json` 同款 + brainstorm 字段集）：
   ```json
   "device": {
     "drive_letter": "E",
     "label": "USB Flash Drive",
     "total_bytes": 32000000000,
     "used_bytes": 8000000000,
     "fs_type": "FAT32",
     "is_removable": true
   }
   ```
   `is_removable` 永远 true（来自 scan_all_devices 只返 removable 设备），但保留字段让 agent schema 一致。
5. **locks 字段裁剪**（与 `make_eject_json` 同款 + brainstorm 字段集）：
   ```json
   "locks": [
     { "pid": 1234, "name": "explorer.exe", "exe_path": "C:\\Windows\\explorer.exe", "risk": "Safe" }
   ]
   ```
   `risk` 字段走 `format!("{:?}", risk)` 给出 `"Critical" / "Warning" / "Safe" / "Harmless"`（与 `make_eject_json` 一致；不取 `HandleRisk::label()` 因为 label 是中文 `"🟢 安全"` 不利 agent 解析）。

### 决策 5：stage 2 不动 mod.rs 的 #[tool] 方法签名

`#[tool]` 方法体仍只 1-2 行（`ok_result(record::make_replay_info_json(&args.file_path))`），仅在 record.rs 子 module 替换 stub helper 为真实业务实现。impl 块结构稳定 → 既有 32 tool 零回归 + stage 1 已落地的 bookmarks 4 stub 不动（stage 3 才填）。

description 字符串 stage 1 已写完整字段说明（如 `proc_replay_search` 的 description 已含 matches[] schema），stage 2 不改。

### 决策 6：matched_processes[] 集合收集策略

`proc_replay_search` 的 `matched_processes` 字段含「该帧中哪些进程名出现在 query 中」：

- **FrameRegex / FrameIn（name 字段）**：扫描帧的 `processes[].name`，列出**真正匹配 regex/HashSet** 的进程名集合（dedup 同名进程）
- **FrameFieldCmp（cpu/mem/timestamp/anomaly.severity）**：query 不针对进程名 → 列出**帧内所有进程名**（让 agent 看到当时跑了什么）
- **空帧（无进程）**：matched_processes=[]

实现策略：检测 expr 是否含 `FrameRegex { field: Name, .. }` 或 `FrameIn { field: Name, .. }`（递归 And/Or/Not），是则扫描匹配，否则全列。stage 2 加私有辅助 `collect_matched_processes(frame, expr)` 在 record.rs。

### 决策 7：anomaly_severity 取最高档

帧的 `anomaly_severity` 字段返「该帧内 anomalies 中 severity 最高档」：

- 优先级：`critical > warning > info > (空)`
- 帧无 anomaly → `null`
- 实现：扫描 `frame.anomalies`，按优先级取 max

agent 看一眼就能知道「这一帧有没有 critical 异常」，不需要扫描整个 anomalies[]。

## 已知风险

### 风险 1：matched_processes 收集逻辑过于复杂

**中风险**：决策 6 让 matched_processes 字段在不同 expr 类型下返不同集合（regex 命中 specific 集合 vs 数值比较全列），实现复杂度高，可能引入 bug。

**mitigate**：stage 2 实装时简化策略——只区分两种情况：(a) `FrameRegex { field: Name }` / `FrameIn { field: Name }` → 扫描匹配；(b) 其他 → 全列。 recursively detect 通过 `expr_contains_name_match(expr)` 私有函数。如复杂度仍超预期，退化为「永远全列所有进程名」（agent 仍可从 cpu_usage / memory_used 判断异常）。

### 风险 2：VT100 测试 fixture 创建复杂

**低风险**：VtRecorder 需要 ratatui::Buffer + Rect area，测试构造略复杂。test_record.rs 没有现成 VT100 fixture 函数。

**mitigate**：参考 [`src/record/vt100.rs::VtFrame::from_buffer`](../../src/record/vt100.rs) + 测试时手动构造 `VtHeader + Vec<VtFrame>` 序列化到文件，不走 VtRecorder 路径。或直接调 `VtRecorder::new(path, area, ...)` + `try_capture` + `stop`。

### 风险 3：parse_drive_letter 私有，stage 2 重新实现

**低风险**：[`src/eject/mod.rs::parse_drive_letter`](../../src/eject/mod.rs) 是私有的（仅 Windows pub usages），handler/record.rs 调用需要在子 module 内重新实现 drive 字符 normalize（与 [`mod.rs::make_eject_json`](../../src/mcp/handler/mod.rs) 同款 inline）。

**mitigate**：直接复制 `make_eject_json` 中的 normalize 逻辑（`chars().filter(|c| c.is_ascii_alphabetic()).collect()`），3 行代码不值得抽 helper。

### 风险 4：测试创建 USB removable device 不可行

**中风险**：`scan_all_devices` 调 Windows API，测试机不一定有 USB 设备插着。所有 `test_eject_status_*` 测试都走「invalid drive / drive not found」路径，无法验证「device found + locks 非空」完整路径。

**mitigate**：测试聚焦 schema 形状 + 4 档 suggestion 枚举值校验，不强求真实设备命中。`test_eject_status_returns_expected_json_shape` 让任意 drive 调用后校验所有字段在（即便 device=null）。完整业务路径靠 stage 4 Review 时手动验证（插 U 盘 + 调 mcp-inspector）。

### 风险 5：长录屏遍历性能 ~9s 让 cargo test 变慢

**低风险**：测试 fixture 用 5-10 帧录屏（不是 54000 帧），遍历 <1ms。性能段（~9s/30min）只是 ADR-0025a 设计参考，不在测试覆盖。

**mitigate**：测试 fixture 都用小录屏（5-10 帧），跑得快。
