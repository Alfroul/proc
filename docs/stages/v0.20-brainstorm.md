### 决策 2：LlmProvider trait 签名 ⏳

**stream 返回 `Pin<Box<dyn Stream>>`** —— 避免 `async-trait` 与 `Stream` trait object 的双重复杂度。

```rust
// src/agent/provider.rs
use futures::stream::BoxStream;

#[async_trait]
pub trait LlmProvider: Send + Sync {
    fn name(&self) -> &str;

    async fn complete(
        &self,
        messages: Vec<Message>,
        tools: Vec<ToolSchema>,
        options: CompleteOptions,
    ) -> Result<CompleteResponse, LlmError>;

    fn stream(
        &self,
        messages: Vec<Message>,
        tools: Vec<ToolSchema>,
        options: CompleteOptions,
    ) -> BoxStream<'static, Result<Delta, LlmError>>;
}

pub enum Delta {
    Text(String),
    ToolCall(ToolCall),
    ToolResult(ToolResult),
    EndTurn { stop_reason: StopReason },
}
```

**为什么不用纯 `async fn stream` 返 `impl Stream`**：`impl Trait` 在 trait method 返回类型中需 Rust 1.75+ 的 `return position impl trait in trait`，且 `Stream` 不是 `std::Stream`（需 `futures` crate）。`BoxStream` 是 `futures::stream::BoxStream<'static, Item>` 别名，已是 `Pin<Box<dyn Stream + Send>>`，最简。

**为什么 `complete` 用 `async_trait` 但 `stream` 不用**：`complete` 一次性返完整响应，`async_trait` 简单；`stream` 返 stream object 不能用 `async_trait`（会包一层 future）。

**备选方案**：
- (a) **`BoxStream` + `async_trait` 仅 complete**（推荐 ⏳）：最简单，proc v0.7~v0.19 MCP handler 已用 `async_trait` 熟悉
- (b) 全 `async_trait`（含 stream 返 `Pin<Box<dyn Stream...>>`）：复杂度高
- (c) 手写 future（无 `async_trait`）：性能最优但代码冗长

**用户拍板**：⏳ 待用户确认（推荐 a）。

### 决策 3：ToolRegistry 两层架构接口 ⏳

**`HashMap<String, ToolSchema>` 全集 + entry / by_category 视图** —— 单一数据源，多视图访问。

```rust
// src/agent/tool_registry.rs
pub struct ToolRegistry {
    tools: HashMap<String, ToolSchema>,
    /// Layer 0：默认 4 个 entry tool 名单
    entry_tool_names: Vec<String>,
    /// Layer 1：分类索引（docker / usb / security / ...）
    category_index: HashMap<ToolCategory, Vec<String>>,
}

impl ToolRegistry {
    pub fn entry_tools(&self) -> Vec<&ToolSchema> { /* 返回 4 个 entry tool */ }
    pub fn tools_by_category(&self, cat: Option<ToolCategory>) -> Vec<&ToolSchema> { /* Layer 1 */ }
    pub fn get(&self, name: &str) -> Option<&ToolSchema> { /* 单个查 */ }
    pub fn total_tokens(&self, names: &[String]) -> usize { /* token 预算监控 */ }
}
```

**proc_help 元 tool 返回什么**：
```rust
// src/agent/tools/help.rs
fn proc_help(category: Option<ToolCategory>) -> Vec<ToolSchema> {
    registry.tools_by_category(category).into_iter().cloned().collect()
}
```

agent 看 `proc_help` 返回的 `Vec<ToolSchema>` 即可知道剩余 tool 的 name / description / parameters，下一步直接调。

**为什么不"动态注册" / "动态卸载" tool**：LlmProvider 接口是 `tools: Vec<ToolSchema>` 入参，每次调用都重新传。ToolRegistry 只决定"传哪些"，不需要动态修改 tools map 本身。

**备选方案**：
- (a) **HashMap + 视图**（推荐 ⏳）：单一数据源 + 多视图，token 监控简单
- (b) 多 ToolRegistry 实例（entry / docker / usb / ...）：实例间同步复杂
- (c) Vec + filter：O(n) 查找，但 proc 46 tool 规模可忽略

**用户拍板**：⏳ 待用户确认（推荐 a）。

### 决策 4：Gemma 4 thinking mode 禁用方式 ⏳


**理由**（搜索结果验证，2026-08-14）：
1. llama-server `--no-thinks` flag 是 Gemma 4 系列专用（b8828+ 支持），强制禁用 `<|think|>` token 注入
2. 不加 flag 时 E2B 默认 thinking，TTFT（首 token 延迟）飙到 5.8s + token 消耗 165-588/任务
3. 加 flag 后 TTFT < 0.3s，20× 加速
4. CLI flag vs request param（`"chat_template_kwargs": {"think": false}`）：flag 更稳定（不依赖 client 每次都传对参数），与 llama.cpp 版本无关

**备选方案**：
- (a) **CLI flag `--no-thinks`**（推荐 ⏳）：启动时一次性禁用，所有 request 默认 non-thinking
- (b) Request param `chat_template_kwargs.think=false`：每次 request 都要传，client 遗忘时 thinking 重新启用
- (c) 不禁用（用 thinking mode 提升推理）：TTFT 5.8s 在交互式 agent 体验差，不可接受

**用户拍板**：⏳ 待用户确认（推荐 a）。

### 决策 5：Mock provider fixture 格式 ⏳

**JSONL（每行一个 JSON 对象）** —— 文本格式可读 + diff 友好 + Git merge 友好。

```jsonl
// tests/fixtures/agent/performance-diagnose-l0.jsonl
{"query_hash":"a1b2c3...","request":{"messages":[...],"tools":[...]},"response_deltas":[{"Text":"查看"},{"Text":"系统"},{"ToolCall":{"name":"proc_metrics_system","args":{}}},{"ToolResult":{...}},{"Text":"当前 CPU 23%..."},{"EndTurn":{"stop_reason":"end_turn"}}]}
{"query_hash":"d4e5f6...","request":{...},"response_deltas":[...]}
```

**为什么不用 bincode**：
1. JSONL 文本格式，开发者可直接看 fixture 内容判断 mock 是否合理
2. Git diff 友好（重新录制只改变某些字段时，diff 清晰）
3. Code review 友好（PR 里能直接看 fixture 改动）
4. bincode 二进制，每次录制变更 git diff 看不出语义

**为什么不用单个 JSON 数组**：
1. JSONL 每行一个对象，追加录制只需 append；JSON 数组要 read-modify-write 整文件
2. 70 query × 平均 50 KB / query = ~3.5 MB，单文件 git 历史膨胀；JSONL 可按场景拆 9 个文件（每个 ~400 KB）

**fixture 文件组织**：
```

├── performance-diagnose-l1.jsonl     # 场景 1 L1（5 query）
├── performance-diagnose-l2.jsonl     # 场景 1 L2（2 query，v0.21 启用）

├── ...（9 场景 × 3 level = 27 文件）
└── README.md                          # 录制说明
```

**备选方案**：
- (a) **JSONL（按场景 × level 拆 27 文件）**（推荐 ⏳）：文本可读 + diff 友好 + 按场景拆
- (b) bincode（单文件）：紧凑但二进制，diff 不友好
- (c) 单 JSON 数组（27 场景合并）：文件大，git 历史膨胀

**用户拍板**：⏳ 待用户确认（推荐 a）。

### 决策 6：llama-server 子进程生命周期 ⏳

**新建独立 `LlmServerHandle`** —— 与 `record_handle` 模式同源但独立（不复用代码，复用 pattern）。

**理由**：
1. `record_handle` 是 `src/mcp/handler/record.rs` 内部 struct，绑死 MCP handler 上下文；LlmServerHandle 是 agent 模块组件，跨 stage / 跨 query 长期保活
2. 生命周期不同：record_handle 跨 MCP tool call 保活（几秒~几分钟）；LlmServerHandle 跨整个 proc 进程生命周期保活（用户启动 agent → 选模型 → 用完 → 退出）
3. 健康检查需求不同：record_handle 不需要健康检查（spawn 后直接 wait）；LlmServerHandle 需要 HTTP `/health` 检查（启动后等 model load 完成）

```rust
// src/agent/llama_server_handle.rs（v0.20 stage 3a 落地）
pub struct LlmServerHandle {
    child: Child,
    port: u16,
    base_url: String,
    shutdown_tx: oneshot::Sender<()>,
}

impl LlmServerHandle {
    pub async fn spawn(model_path: &Path, opts: SpawnOptions) -> Result<Self, SpawnError> {
        // 1. 分配动态端口（bind 127.0.0.1:0 → OS 分配 → 立即释放 → 传给 llama-server）
        // 2. spawn llama-server 子进程（决策 4 flag）
        // 3. 等 "HTTP server listening on" stdout 行（read stdout until pattern）
        // 4. HTTP GET /health 等返 200（model loaded）
        // 5. 返 LlmServerHandle
    }

    pub async fn health_check(&self) -> Result<(), HealthError> {
        // HTTP GET /health，超时 1s
    }

    pub fn base_url(&self) -> &str { &self.base_url }
}

impl Drop for LlmServerHandle {
    fn drop(&mut self) {
        // 1. let _ = self.shutdown_tx.send(());
        // 2. self.child.kill()
        // 3. self.child.wait()（防止僵尸进程）
    }
}
```

**端口分配策略**：`TcpListener::bind("127.0.0.1:0")` → 拿到 OS 分配的端口 → 立即 drop listener → 把端口号传给 `llama-server --port N`。OS 保证 N 在 TIME_WAIT 之前不会再分配。

**核心设计意图：按需 spawn 不影响日常使用**（用户 2026-08-14 明确）：

- `LlmServerHandle::spawn()` 是显式调用，**不是 proc 启动时自动 spawn**
- v0.20 cycle：仅在用户跑 `proc agent ask` 时才 spawn llama-server，命令结束（Drop）→ kill 子进程 + 释放 RAM + 释放端口
- v0.21 cycle：仅在用户按 A 进入 TUI AgentPanel + 选模型时才 spawn，退出面板（Drop）→ kill + 释放
- **日常使用零影响**：用户跑 `proc`（TUI 主路径）/ `proc ls` / `proc mcp serve` 等既有命令时，不 spawn llama-server、不占 4-6GB RAM、不发任何 LLM 网络请求，与 v0.19 proc 体验完全一致
- 这是 v0.20 cycle 隐私架构 + 资源管理的核心约束，stage 2/3 实施时严格保持（违反则回溯修复）

**备选方案**：
- (a) **新建独立 `LlmServerHandle`**（推荐 ⏳）：模块边界清晰，复用 record_handle pattern
- (b) 复用 `record_handle`：耦合 MCP handler 与 agent 模块，违反单一职责
- (c) 不开 server 直接调 llama-cli：每次 query 都 spawn 新进程（model load 5-10s 不可接受）

**用户拍板**：⏳ 待用户确认（推荐 a）。

### 决策 7：ADR 编号 ⏳

**新 ADR-0030 内置 AI agent**——与 ADR-0009 MCP server 决策互补但独立。

1. 内置 agent 是 proc 历史上首次引入"proc 自身调 LLM"能力，与"proc 暴露 MCP tool 给外部 LLM"（ADR-0009）是不同方向
2. Tool registry 两层架构（entry tool + meta-tool discovery）是项目级架构决策，应有独立 ADR

**ADR-0030 大纲**（stage 1 Spike 落地骨架）：

- Status：Accepted（v0.20.0）

- Decision：
  - D1：内置 agent（不再是单纯 MCP server）
  - D2：Tool registry 两层架构（entry tool + proc_help 元 tool）
  - D3：multi-provider（LlamaCpp / Anthropic / Mock）
  - D4：Gemma 4 E2B 本地优先（隐私架构）
  - D5：Mock provider fixture 回放（CI 零 LLM 调用）
  - D6：thinking mode 强制禁用（`--no-thinks`）
- Consequences：proc 二进制体积 +5MB（reqwest + gguf deps）/ Cargo feature `anthropic` opt-in / MockProvider 让 46 tool agent loop 测试零 LLM 调用
- 与 ADR-0009 关系：互补（ADR-0009 是"proc 暴露给外部 LLM"，ADR-0030 是"proc 自身调 LLM"）

**备选方案**：

- (b) 扩 ADR-0009 MCP server 段：agent 是 MCP 的"参考客户端"，但 agent 决策粒度比 MCP server 决策细很多，扩段会让 ADR-0009 失焦
- (c) 不扩不开 ADR：v0.20 cycle 0 ADR，但 agent 是 proc 历史性转向应有 ADR 痕迹

**用户拍板**：⏳ 待用户确认（推荐 a）。

### 决策 8：GBNF grammar 文件位置 ⏳

**嵌入 binary via `include_str!`** —— 编译时静态嵌入，运行时不依赖外部文件。

```rust
// src/agent/grammars/mod.rs
pub const TOOL_CALL_GRAMMAR: &str = include_str!("tool_call.gbnf");

// src/agent/llama_cpp_provider.rs
let opts = CompleteOptions {
    grammar: Some(TOOL_CALL_GRAMMAR.to_string()),
    ..Default::default()
};
```

**理由**：
1. proc 是单二进制工具，不应依赖外部 grammar 文件路径
2. grammar 变更频率低（schema 稳定后基本不动），编译时嵌入代价小
3. 用户安装 proc 后无需额外配置 grammar 文件

**GBNF 文件位置**：`src/agent/grammars/tool_call.gbnf`（源码目录，被 `include_str!` 嵌入 binary）。

**grammar 内容**（stage 3a 实装时细化）：
```bnf
# 强制 tool call 输出为合法 JSON
root ::= "{" ws "\"tool_calls\"" ws ":" ws "[" ws tool_call* ws "]" ws "}"
tool_call ::= "{" ws "\"name\"" ws ":" ws string ws "," ws "\"arguments\"" ws ":" ws object ws "}"
string ::= "\"" ([^"\\] | "\\" .)* "\""
object ::= "{" ws (string ws ":" ws value (ws "," ws string ws ":" ws value)*)? ws "}"
value ::= string | object | number | "true" | "false" | "null"
ws ::= [ \t\n]*
```

**备选方案**：
- (a) **`include_str!` 嵌入 binary**（推荐 ⏳）：单二进制 + 编译时校验
- (b) 外部文件 `~/.config/proc/grammars/tool_call.gbnf`：用户可改但增加配置复杂度
- (c) 不用 GBNF：依赖 Gemma 4 自带 tool use template（搜索结果显示 E2B 偶尔会输出乱码 JSON，GBNF 是保命手段）

**用户拍板**：⏳ 待用户确认（推荐 a）。

  - **D6：thinking mode 强制禁用**——llama-server 启动加 `--no-thinks` flag，避免 E2B TTFT 5.8s
  - **D7：GBNF grammar 嵌入 binary**——`include_str!` 编译时嵌入 tool_call.gbnf，约束 Gemma 4 输出合法 JSON
- **Consequences**：
  - proc 二进制体积 +5-8MB（reqwest + gguf + tokio-stream deps）
  - Cargo.toml 加 `[features] anthropic = []` opt-in
  - 70 query fixture 让 46 tool agent loop 测试零 LLM 调用 + 确定性回归
  - ToolRegistry 让单轮 tool schema token 从 ~15K 降至 ~1.5K（峰值），96% 减少，让 2B 模型也能跑
- **与既有 ADR 关系**：
  - 互补 ADR-0009（MCP server）：ADR-0009 是"proc 暴露给外部 LLM"，ADR-0030 是"proc 自身调 LLM"
  - 复用 ADR-0008（self-mitigation policy）：agent 调用写操作（proc_kill / proc_docker_rm）必须 confirm gate
  - 复用 ADR-0029（record 暴露 + confirm 机制）：写操作 confirm bool 必传
  - 复用 v0.6 secret mask 12 关键字：agent PII 过滤层直接复用

## 已知风险

### 风险 1：E2B agent 成功率 29.4%（搜索结果验证）

**问题**：Gemma 4 E2B 在 τ²-bench Retail agent tool use 评测仅 29.4%，意味着 v0.20 cycle 验收时 ~70% query 会失败（agent 乱调 tool 或不调 tool）。

**影响**：v0.20 cycle 验收标准（L0/L1 共 50 query 必须全部跑通）可能不达标。L0（单步 tool call）E2B 成功率约 70%，L1（单步 + 自然语言总结）约 50-60%。

**mitigate**：
1. **GBNF grammar 强制 JSON 输出**（决策 8）：约束 tool call 格式合法
2. **Few-shot 示例 3 个**（system prompt）：E2B 模仿能力强于推理能力
3. **Tool subset selection**（决策 3 + ToolRegistry）：默认只暴露 4 个 entry tool，减少 E2B 选择困难
4. **接受 L0 验收 L1 尽力**：v0.20 cycle 实际验收标准调整为 L0 23 query 必跑通 / L1 27 query 尽力（≥ 80% 通过率即可）/ L2 不验收
5. **Anthropic 对照路径**（项 8）：同样 50 query 用 Anthropic Sonnet 跑，证明架构可移植（Sonnet 成功率近 100%）

### 风险 2：Gemma 4 thinking mode 陷阱（搜索结果验证）

**问题**：llama.cpp / Ollama 默认对 Gemma 4 E2B 注入 `<|think|>` token 启用 thinking，导致 TTFT 5.8s + token 消耗 165-588/任务。

**影响**：v0.20 stage 3 验收时如忘加 `--no-thinks` flag，agent 单 query 延迟 ~10s，70 query fixture 录制约需 12 分钟（vs 加 flag 后 1 分钟）。

**mitigate**：
- 决策 4 拍板 LlamaServerHandle 启动强制加 `--no-thinks`
- stage 3 集成测试加 `test_llama_server_handle_disables_thinking_mode`（断言启动命令含 `--no-thinks`）
- 文档 ADR-0030 D6 段强调

### 风险 3：stage 2 / stage 3 容量超阈值（自适应拆分风险）

**问题**：stage 2 ~1630 行 / stage 3 ~2020 行都超 phased-project skill 1500 行硬阈值。虽然阈值是"建议"非"强制"，但超阈值会触发上下文消耗过快 → Checkpoint 接力频繁 → cycle 跨会话执行成本高。

**影响**：stage 2 / stage 3 实际执行时可能触发自适应拆分（stage 2a + 2b / stage 3a + 3b），cycle 改 6 stage。

**mitigate**：
1. stage 2 内排序：项 1 LlmProvider trait → 项 5 ToolRegistry → 项 2 MockProvider → 项 3 GGUF scanner（基础设施先行，让 stage 3 有完整抽象层可用）
2. stage 3 内排序：项 4 LlamaCppProvider → 项 6 Agent loop → 项 7 CLI 入口（provider 先行让 agent loop 有 LLM 可调）
3. 如 stage 3 上下文快满（项 4 完成后剩余 < 30%）→ Checkpoint 接力项 6+7 到新会话
4. **预拆分选项**：如 brainstorm 拍板时即决定拆 stage 3 为 3a（项 4）+ 3b（项 6+7），cycle 改 5 stage（更可控但更长）

### 风险 4：fixture 录制工作量大（70 query × 2 模型 = 140 次录制）

**问题**：项 2 MockProvider fixture 录制需要 70 query × 2 provider（Gemma E2B + Anthropic Sonnet）= 140 次录制。Gemma E2B 单 query ~10s（含 thinking mode 禁用），Anthropic ~3s。总录制时间 ~25 分钟（Gemma 12 分钟 + Anthropic 3 分钟 + 重试 / 整理 10 分钟）。

**影响**：stage 2 工作量膨胀，可能挤占其他项实装时间。

**mitigate**：
1. fixture 录制工具（项 2 的 `record_fixture.rs`）支持批量录制（一次性跑 70 query）
2. fixture 录制作为 stage 2 的最后一项（基础设施先落地，agent loop 可用后再录制）
3. v0.20 cycle 接受 fixture 录制工作量（~25 分钟），不强行压缩
4. 备选：先录 L0 23 query（10 分钟），L1/L2 留 v0.21 cycle

### 风险 5：llama-server 端口冲突

**问题**：proc 启动 llama-server 子进程时，如用户机器已有其他 llama-server 实例（端口 8081 占用），spawn 失败或拿到错误响应。

**影响**：用户开发 / 测试时端口冲突导致 agent 启动失败。

**mitigate**：
1. 决策 6 拍板动态端口分配（`TcpListener::bind("127.0.0.1:0")` → OS 分配 → 立即释放 → 传给 llama-server）
2. LlamaServerHandle 启动失败时 friendly error：`"无法启动 llama-server: 端口 N 已占用 / llama-server.exe 路径无效 / model load 失败"`
3. 用户配置 `~/.config/proc/llm_models.toml` 可指定固定端口（如调试时想抓包）

### 风险 6：reqwest + tokio-stream 与既有 tokio runtime 冲突

**问题**：proc 既有 tokio runtime（current_thread + multi_thread 分支，v0.19 落地），reqwest 默认用自己内部 runtime（如未传 client）。混用可能死锁（reqwest 在 current_thread runtime 上 block_on 当前 task）。

**影响**：stdio MCP server 路径（current_thread runtime）下 agent 调用 LLM 时死锁。

**mitigate**：
1. AnthropicProvider / LlamaCppProvider 接受外部 `tokio::runtime::Handle`，不用自己创建 runtime
2. v0.20 cycle agent 仅通过 CLI `proc agent ask` 入口跑（不走 MCP server runtime），避开 runtime 冲突
3. v0.21 cycle TUI AgentPanel 时再评估跨 runtime 集成（如 TUI 主线程 + agent 子线程）

### 风险 7：5 stage 节奏首次试用（v0.15~v0.19 都是 3 stage）

**问题**：proc 项目历史 cycle 节奏都是 3 stage（1 Spike + 1 Slice + Review+收尾），v0.20 首次用 5 stage。phased-project skill 中等项目 3-5 stage 范围允许，但实操时 5 stage 跨会话执行成本高（用户需开 4 次会话完成 cycle）。

**影响**：cycle 完成周期延长（如每次会话间隔 1 天，cycle 总周期 4 天 vs 3 stage 3 天）。

**mitigate**：
1. stage 1 Spike + stage 2 Slice A 可在同一会话连做（基础设施改动相对独立）
2. stage 3 Slice B 必须独立会话（agent 实装上下文密集）
3. stage 4 Review+收尾可独立会话或与 stage 3 末段合并

**用户决策**：是否接受 5 stage 节奏？或选 3 stage + 接受 stage 2 单段 ~2500 行严重超阈值风险？

## FAQ

### Q1: v0.20 cycle 为什么是 5 stage 而非 3 stage？

**A**: 决策 1 拍板 5 stage 的核心理由是**避免单 stage 超阈值触发自适应拆分**：

1. v0.20 cycle 工作量 ~3000 行远超 v0.15~v0.19 cycle 平均 ~900 行
2. 3 stage 模式下 Slice stage 单段 ~2500 行严重超 1500 行硬阈值，phased-project skill 自适应规则强制拆分
3. 5 stage 模式（1 Spike + 2 Slice + Review）下最大 stage ~2020 行（stage 3），超阈值 35% 但可控
4. 提前规划 5 stage 比被动触发自适应拆分更可控（用户预期管理 / commit 边界清晰）

### Q2: 为什么 ToolRegistry 用两层架构而非全 46 tool 一次注入？

**A**: 决策 3 拍板两层架构的核心理由是**让小模型也能跑 agent**：

1. 46 tool 全 schema 注入约 ~15K token（proc tool schema 较复杂，含 confirm / dry_run 等字段）
2. Gemma 4 E2B context 128K，但单轮 tool schema 15K + system prompt 2K + few-shot 3K = 20K，留给对话 + tool result 的空间紧张
3. 两层架构：Layer 0 默认 4 entry tool（~600 token）+ Layer 1 通过 `proc_help(category)` 元 tool 动态加载（峰值 ~1.5K token）
4. **token 减少 96%**（15K → 1.5K 峰值），让 E2B 也能稳定驱动 agent

### Q3: 为什么 v0.20 不做 TUI AgentPanel？

**A**: v0.20 cycle 范围决策（用户已拍板）：

| 维度 | v0.20 cycle | v0.21 cycle |
|---|---|---|
| 范围 | CLI `proc agent ask` 单轮 query | TUI AgentPanel + 流式 chat |
| 工作量 | ~3000 行 | ~2000 行（TUI ratatui 集成 + streaming 渲染）|
| 收益 | 拿到端到端 agent demo，简历可写 | 现场演示杀手锏 |
| 依赖 | v0.20 LlmProvider trait 落地 | v0.20 完成 |

v0.20 是基础设施 + CLI 验证；v0.21 是 UI 层 + 演示能力。分开 cycle 让每个 cycle 容量可控。

### Q4: 为什么 AnthropicProvider 是 opt-in feature 而非默认？

**A**: 用户决策（brainstorm 范围决策 4）：

1. **隐私架构**：默认 build 应该零外部网络依赖（不需要 ANTHROPIC_API_KEY 也能用）
2. **二进制体积**：reqwest + tokio-stream 等 deps 增加 ~2-3MB，opt-in 让默认 build 更轻
3. **简历叙事**：默认本地 LLM 优先 = "隐私优先设计"，是 AI 应用工程师岗位加分项
4. **使用方式**：用户需要云端对照时 `cargo build --release --features anthropic`

### Q5: 为什么 fixture 用 JSONL 而非 bincode？

**A**: 决策 5 拍板 JSONL 的核心理由：

1. **可读性**：开发者可直接看 fixture 内容判断 mock 是否合理
2. **Git diff 友好**：重新录制时 diff 清晰（vs bincode 二进制 diff 看不出语义）
3. **Code review 友好**：PR 里能直接看 fixture 改动
4. **按场景拆 27 文件**：每场景 × level 一个 JSONL 文件，单文件 ~400 KB，git 历史不膨胀

### Q6: Gemma 4 E2B 29.4% 成功率，v0.20 cycle 如何验收？

**A**: 决策 1 + 风险 1 mitigate 调整验收标准：

| Level | v0.20 验收标准 | 实际成功率（E2B）| 通过判定 |
|---|---|---|---|
| L0（单步 tool call）| 23 query 全跑通 | ~70%（GBNF + few-shot 加成）| ≥ 23/23 ✅ |
| L1（单步 + 自然语言总结）| 27 query 尽力 | ~50-60% | ≥ 22/27（80%）✅ |
| L2（多步 ReAct）| 不验收 | ~20-30% | fixture 录制留 v0.21 |
| **Anthropic 对照** | 同 50 query 全跑通 | ~95-100% | ≥ 48/50 ✅ |

L2 不验收的理由：E2B 不具备多步推理能力（29.4% 是单步评测，多步会断崖式下降）。L2 demo 用 Anthropic Sonnet 跑（v0.21 cycle TUI AgentPanel 时演示）。

### Q7: 内置 agent 与 MCP server 的关系？

**A**: 互补关系：

| 维度 | MCP server（v0.7~v0.19）| 内置 agent（v0.20）|
|---|---|---|
| 调用方向 | 外部 LLM → proc（暴露 46 tool）| proc → LLM（proc 是 client）|
| 协议 | MCP JSON-RPC over stdio / SSE | LlmProvider trait（内部 Rust API）|
| 用户场景 | Claude Desktop / Cursor / Windsurf 配置 proc 为 MCP server | 用户在终端 `proc agent ask "..."` |
| Tool 数 | 46（全暴露）| 4 entry + proc_help 元 tool（动态发现）|
| 简历叙事 | "实现 MCP server 暴露给 LLM agent" | "实现端到端 AI agent 应用" |

ADR-0030 显式说明两者互补：MCP server 是"协议层"，内置 agent 是"参考实现"。

### Q8: v0.20 cycle 引入 reqwest + gguf + tokio-stream 三个 deps，是否过重？

**A**: 工作量与收益权衡：

| Dep | 用途 | 二进制体积增加 | 替代方案 |
|---|---|---|---|
| reqwest | AnthropicProvider + LlamaCppProvider HTTP 调用 | ~1.5MB | 手撸 hyper（省 1MB 但 +200 行代码）|
| gguf | GGUF metadata 解析（model name / size / quant）| ~200KB | 手撸 GGUF parser（GGUF 格式简单但 +150 行）|
| tokio-stream | `BoxStream` 类型 + stream 工具 | ~100KB（tokio 已有，子集）| 手撸 Stream wrapper（复杂）|

总二进制体积增加 ~2MB（release build）。与 v0.17 cycle 引入 axum + tower + tower-http（~3MB）同档可接受。

### 示例 2：L1 推理 + 总结（异常诊断）

```

- CPU 78%（偏高）

2. msbuild.exe — CPU 18%（看起来在编译项目）

建议：
1. 关闭不用的 chrome 标签（节省 ~20-30% CPU）
2. 等编译完成（msbuild 通常 1-3 分钟）
3. 如需立即缓解，可用 `proc throttle <msbuild-pid> on` 限速
```

**教学点**：推理类 query 先用 `proc_metrics_system` 看全局，再用 `proc_ls` 深挖，最后给可执行建议（不要只描述问题）。

### 示例 3：写操作 + confirm gate（kill 进程）

```
User: 把 chrome 杀掉

Assistant: 我需要终止 chrome 进程。这会关闭所有 chrome 窗口和标签页，
未保存的工作可能丢失。

涉及进程（从 proc_ls 检测到 3 个）：
- chrome.exe (PID 1234) — 主进程
- chrome.exe (PID 1235) — GPU Process 子进程
- chrome.exe (PID 1236) — Renderer 子进程

确认终止全部 3 个进程吗？(y/n)

User: y

Assistant: [tool_call: proc_pkill(name="chrome.exe", confirm=true, force=false)]

[tool_result: {
  "ok": true,
  "total": 3,
  "killed": 3,
  "failed": 0,
  "results": [
    {"pid": 1234, "result": "Killed"},
    {"pid": 1235, "result": "Killed"},
    {"pid": 1236, "result": "Killed"}
  ]
}]

已成功终止 3 个 chrome 进程。如发现浏览器还有残留窗口，可能是
独立 user-data-dir 启动的实例，可再 `proc ls --filter name=chrome` 确认。
```

**教学点**：写操作必须 (1) 先解释影响 + 列出涉及进程；(2) 等用户输入 y/n；(3) confirm=true 才调；(4) 返回结果后给后续排查建议。
