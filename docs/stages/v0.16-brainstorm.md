## 关键决策（待用户拍板，stage 1 落地前必须确认）

### 决策 1：proc_record_start / stop **不暴露**（v0.16 cycle 范围排除）

**brainstorm §主题 D2** 提「录屏 v2（record / replay / bookmarks）」，但实装层面 `proc_record_start` / `proc_record_stop` 涉及：

1. **录屏需要 TTY**：v0.6 落地的 `R` 键录制路径走 `tui::setup_terminal() + tui::run_app()`（[`src/cli/record.rs::run_record`](../../src/cli/record.rs)），MCP server 是 stdio 单工无 TTY，无法直接 attach TUI
2. **替代路径需要 worker 持续采样**：MCP handler 启 worker 线程采 `SystemSnapshot → UiFrame` 喂 `Recorder::submit_frame`（绕过 TUI 路径），但：
   - 录制期间 worker 持续运行（~30 FPS × 165 µs/frame = ~5% CPU）影响 MCP server 主路径
   - recorder_worker 与 MCP stdio 生命周期管理复杂（client 关闭后 worker 仍跑？）
   - 录屏敏感数据保护（v0.6 落地的 `pending_record_confirm` 确认弹窗）需 MCP-level confirm 机制（与 brainstorm FAQ Q2 + Q7 提的「写操作 confirm 机制」同款待评估）
3. **agent 实际场景**：agent 需要分析「过去发生的」事件，录屏应由**用户主动在 TUI 启动**（`R` 键 + `b` 键加书签），agent 只读 / 操作**已存在的** `.prec` 文件——这是更合理的协作分工

**本 brainstorm 决策**：v0.16 cycle **不暴露** `proc_record_start` / `proc_record_stop`。

**理由总结**：
- TTY 限制是技术硬约束（无 TTY 不能 TUI 录屏）
- 替代路径（worker 采样）工作量大且收益边际（agent 高频录屏不是典型场景）
- 安全 / confirm 机制评估留 v0.17+ cycle（与 brainstorm FAQ Q2 / Q7 同款推迟理由）
- agent 视角应聚焦「分析已有录屏」，用户视角负责「主动录屏」

**brainstorm §主题 D2 文字理解**：「record / replay / bookmarks」中的「record」可解读为「replay 录屏文件」（即所有 tool 都作用于已录制文件），而非「启动新录屏」。本 brainstorm 文档化此理解。

**未来考虑**（v0.17+ cycle 评估）：
- 如果用户反馈 agent 需要主动启动录屏，评估方案 (a) spawn `proc record` 子进程（无 TTY，但子进程可独立写 `.prec`）/ (b) MCP-level confirm + worker 持续采样路径
- 与 brainstorm §Q2 「写操作 confirm 机制」一并评估

- 不含 proc_replay_open（agent 视角不需要 TUI 内打开，已通过 `proc_replay_info` + `proc_replay_search` 覆盖元数据 + 内容查询）

- 选「只读 status」而非「主动 kill + eject」（即 `proc_usb_release`）—— 用户选保守方案，agent 视角走多次调用但每步可控；未来 `proc_usb_release` 评估留 v0.17+ cycle（dry_run=false 默认 + kill_pids 必传 是用户对未来 release tool 的设计偏好，本 cycle 不落地但记录）

### 决策 4：dry_run 默认 false（与 v0.15 同款契约）

`proc_bookmarks_add` / `proc_bookmarks_edit` / `proc_bookmarks_delete` 默认 `dry_run=false`（直接执行 + 写 sidecar），与既有 `proc_kill` / `proc_pkill` v0.7 契约 + `proc_monitor_add` / `proc_monitor_remove` v0.15 stage 2 契约一致。agent 想要预演可以 `dry_run=true` opt-in。

dry_run 路径返 preview JSON（含 `action` + 关键字段 echo + `sidecar_written: false`），与 `make_pkill_json` 同款。

### 决策 5：proc_replay_search 的 limit 与 truncated 字段

**问题**：FilterExpr FrameField 5 维度遍历长录屏可能产生大量命中帧（如 `cpu > 50` 在 30 min × 30 FPS × 高负载 session 上可能命中 5000+ 帧），一次性返会让 payload 过大（每帧 ~200-500 bytes × 5000 = 1-2.5 MB JSON）。

**决策**：
- `limit: Option<usize>` 默认 **100**（与 `proc_flows` 默认 limit 50 / `proc_docker_events` 默认 100 同款数量级）
- 返回 `match_count`（总命中数）+ `returned`（实际返回数）+ `truncated: bool`（match_count > returned）
- 命中帧按 **timestamp 升序** 截断（与 timeline 视觉顺序一致）
- `truncated: true` 时 agent 可二次调提高 limit（与 `proc_flows` 同款交互模式）

**未来考虑**（v0.17+ cycle）：评估加 `offset: Option<usize>` 分页参数（与 brainstorm FAQ Q4 「5 个独立 tool 让 agent 按需调用」同款——若 agent 真有分页需求再加，避免过早优化）。

### 决策 6：file_path 参数安全（路径遍历防护）

**问题**：所有 6 个 tool 都接 `file_path: String` 入参，agent 可传任意路径（含 `../../etc/passwd` / `C:\Windows\System32\config\sam` 等系统敏感文件）。

**决策**：
- **不做路径白名单 / 黑名单**——agent 视角已通过 v0.7 ADR-0009 字段裁剪 + 用户授权（MCP client 跑在用户权限下）天然约束
- **返 `is_vt100_file` / `Player::open` / `BookmarkFile::load_or_empty` 自身的失败路径**：文件不存在 / 不是 `.prec` 文件 / 损坏 → 返 `ok: false + error: <msg>`（与既有 tool 同款）
- 录屏本体不存在时 sidecar 操作返 `ok: false + error: "录屏文件不存在"`（不返"空书签列表"，避免 agent 误以为新建了一个空录屏）

**理由**：MCP server 跑在用户本地权限下（与 `proc replay` CLI 同款），agent 不能突破用户权限。路径遍历防护应在 OS / 用户授权层，不在 MCP 层重复实现（surgical 原则）。

### 决策 7：sidecar 写失败的兜底

**问题**：`BookmarkFile::write` 失败时静默（[`src/record/bookmark.rs::write`](../../src/record/bookmark.rs) 只 `_ = std::fs::write(...)`）。MCP 路径需要让 agent 知道写失败。

**决策**：
- handler 包装 write 调用：`match std::fs::write_to_string(&file) { Ok(()) => sidecar_written: true, Err(e) => sidecar_written: false + warning: e.to_string() }`
- 失败时返 `ok: true`（业务逻辑成功——in-memory BookmarkFile 已更新）+ `sidecar_written: false + warning`，让 agent 决定是否重试或报告
- 与 brainstorm FAQ Q2 「写操作 confirm 机制」评估时一并考虑（v0.17+ cycle）

### 决策 9：USB status tool 设计（用户 2026-07-07 追加）

**问题**：用户痛点「U 盘异常时 kill 进程不知道是否成功」。当前路径 agent 走 `proc_eject(drive="E") → proc_kill(pid) → proc_eject(drive="E")` 三步，每步独立调用，中间态不清晰。

**3 种候选方案**：
- 方案 A（破坏性）：`proc_usb_release(drive, kill_pids, dry_run)` 一次完成 kill + flush + eject —— 用户拍板**否决**（破坏性，dry_run + kill_pids 设计偏好留 v0.17+ cycle）
- 方案 B（保守，**用户选**）：`proc_eject_status(drive)` 只读查询，agent 走多步但每步可控
- 方案 C（扩 proc_eject）：在现有 proc_eject 加 status_only 参数 —— 否决（破坏 v0.7 schema，surgical 原则）

**本 cycle 决策（用户拍板）**：**方案 B** — 加 `proc_eject_status(drive)` 一个 tool，cycle 范围从 6 tool 涨到 7 tool，工作量 +~150 行。

**关键设计点**：
1. **不主动 flush cache**：`flush_write_cache` 是阻塞 3s+ 的 PowerShell 子进程，不适合 MCP 一次性 request-response。agent 想主动 flush 时调独立 tool（未来 `proc_usb_flush_cache` 候选）或现有 `proc_eject` 路径
2. **不主动 kill locks**：与 brainstorm 决策 4 「dry_run 默认 false」对齐——但 USB status 是只读查询不涉及 kill，agent 用 `proc_kill` 显式 kill 后再查 status
3. **suggestion 4 档枚举**让 agent 一眼看到下一步：`eject_now` / `kill_locks` / `unknown_drive` / `unavailable`
4. **ejectable = lock_count == 0**（简化决策，cache_status 字段砍掉——`flush_write_cache` 不查不返）

**未来考虑**（v0.17+ cycle 评估）：
- `proc_usb_release(drive, kill_pids, dry_run=false)` 一次完成 kill + flush + eject —— 用户已表态设计偏好（`dry_run=false 默认 + kill_pids 必传`），留 v0.17+ cycle 评估落地
- `proc_usb_flush_cache(drive)` 主动 flush（如果 agent 需要）
- USB 设备历史 / 插拔事件订阅（与 brainstorm §主题 B 可观测性 cycle 同款方向）

### proc_replay_search

**对应 TUI 路径**：v0.14 stage 3 落地的 `/` 键搜索 + n/N 跳转（[`src/replay/search.rs::ReplaySearch`](../../src/replay/search.rs)）

**入参**：
```rust
#[derive(Deserialize, schemars::JsonSchema)]
pub struct ReplaySearchArgs {
    /// 录屏文件路径（.prec 扩展名，仅支持 v3 UiFrame 格式——VT100 无结构化帧）
    pub file_path: String,
    /// 搜索查询：`: cpu > 80` (FilterExpr) / `chrome` (substring → name =~ /chrome/i)
    pub query: String,
    /// 返回命中帧上限（默认 100，截断时返 truncated: true）
    #[serde(default)]
    pub limit: Option<usize>,
}
```

**返回字段**：
```json
{
  "ok": true,
  "query": "cpu > 80",
  "match_count": 234,
  "returned": 100,
  "truncated": true,
  "limit": 100,
  "matches": [
    {
      "frame_idx": 1234,
      "timestamp": 1759000123,
      "cpu_usage": 85.3,
      "memory_used": 4294967296,
      "matched_processes": ["chrome.exe", "firefox.exe"],
      "anomaly_severity": null
    },
    ...
  ]
}
```

**实现要点**：
- 走 `filter::parse_frame(query)` 或 `filter::build_frame_substring_expr(query)`（与 ReplaySearch 同款）

- 截断 + 升序 + `truncated` 字段
- **VT100 路径不支持**：VT100 文件无结构化帧，返 `ok: false + error: "VT100 录屏不支持 search（仅 v3 UiFrame）"`
- 长录屏性能：30 min × 30 FPS × 165 µs = ~9 秒，可接受（agent 一次性调用，与 brainstorm §proc_replay_search 性能段同款）

**工作量**：~120 行（FilterExpr 复用 + 遍历 + matches 组装 + VT100 兜底）

### proc_eject_status（用户 2026-07-07 追加）

**对应业务模块**：v0.7 落地的 `proc_eject(drive=Some)` 的 status-only 子集（[`src/eject/mod.rs::scan_device_locks`](../../src/eject/mod.rs) + [`RemovableDevice`](../../src/eject/mod.rs) 类型），不调 `flush_write_cache`（[`src/eject/cache.rs`](../../src/eject/cache.rs) 阻塞 3s+ 不适合 status 查询）。

**入参**：
```rust
#[derive(Deserialize, schemars::JsonSchema)]
pub struct EjectStatusArgs {
    /// 驱动器盘符（"E" / "E:" / "E:\\" 都接受，与 proc_eject 同款 normalize）
    pub drive: String,
}
```

**返回字段**：
```json
{
  "ok": true,
  "drive": "E",
  "device": {
    "drive_letter": "E",
    "label": "USB Flash Drive",
    "total_bytes": 32000000000,
    "used_bytes": 8000000000,
    "fs_type": "FAT32",
    "is_removable": true
  },
  "ejectable": false,
  "lock_count": 3,
  "locks": [
    { "pid": 1234, "name": "explorer.exe", "exe_path": "C:\\Windows\\explorer.exe", "risk": "Safe" }
  ],
  "suggestion": "kill_locks"
}
```

**关键设计**：
- **`ejectable` = `lock_count == 0`**：单纯看是否还有占用进程（不查 cache 状态——cache_status 字段砍掉，surgical 原则）
- **`suggestion` 4 档枚举**（agent 视角下一步建议）：
  - `"eject_now"`：lock_count=0，可直接弹
  - `"kill_locks"`：lock_count>0，需 kill 进程
  - `"unknown_drive"`：drive 字符无效 / 非 removable
  - `"unavailable"`：非 Windows / `scan_all_devices` 失败（与 brainstorm 决策 6 平台兜底同款）
- **drive 字符无效 / 非 removable 时返 `ok: true + suggestion: "unknown_drive"`**（不报错让 agent 知道 drive 字符无效但不阻断流程，与既有 `make_eject_json` 同款契约）
- **`is_removable: true` 字段必返**：让 agent 区分「USB 设备」vs「固定硬盘」（drive 字符可能误传，agent 看到 is_removable=false 时知道不是 USB）

**agent 工作流**（解决「kill 后不知道是否成功」痛点）：
1. `proc_eject_status(drive="E")` → `ejectable: false, locks: [{pid: 1234, ...}], suggestion: "kill_locks"`
2. `proc_kill(pid=1234)` → kill 结果
3. `proc_eject_status(drive="E")` → `ejectable: true, lock_count: 0, suggestion: "eject_now"`（确认 kill 生效）

仍需多次调用，但每次调用都有明确状态反馈，agent 不再「盲杀」。

**工作量**：~80 行（driv 字符 normalize + scan_device_locks + device 字段裁剪 + suggestion 决策）

## FAQ

### Q1: 为什么 v0.16 cycle 不包含 docker-rm 写操作？

**A**: 三个理由：
1. **agent 低频**：docker-rm 是不可逆破坏性操作（删除容器 / 镜像 / 卷），agent 极少主动调用，用户在 TUI / CLI 直接做更自然
2. **v0.16 单一主题**：录屏 v2 让 cycle 内聚强（与 v0.15 brainstorm FAQ Q7 同款「单一主题」原则）；docker-rm 是不同领域（容器管理）
3. **写操作 confirm 机制评估**：brainstorm FAQ Q2 提的「破坏性写操作 confirm」与 docker-rm 强相关，留 v0.17+ cycle 单独评估（与 record 启动 confirm 同款推迟理由）

### Q2: proc_bookmarks_add 的 frame_idx 校验为什么必须 < total_frames？

**A**: 防止 agent 传无效 frame_idx（如 `frame_idx: 999999`）导致后续 `player.frame_at(frame_idx)` 返 None → sidecar 持久化了无效书签 → 用户回放时跳转失败。

校验路径：
- v3 UiFrame：`frame_idx < player.meta().frame_count`（v3 footer 的 frame_count 字段）
- VT100：`frame_idx < vt_player.total_frames()`

校验失败返 `ok: false + error: "frame_idx=999999 超出范围（总帧数=54000）"`。

### Q3: proc_replay_search 在 1 小时长录屏上跑要 18 秒，agent 会超时吗？

**A**: MCP 协议本身没有强制 timeout（stdio transport 由 client 决定），主流 client（Claude Desktop / Cursor / mcp-inspector）默认 timeout 通常 30s+，18 秒可接受。

**未来考虑**（v0.17+ cycle）：
- 加 `proc_replay_search_status` tool 让 agent 查询进度（异步路径）
- 或评估用 rmcp 0.11 的 progress notification（与 brainstorm §主题 B 可观测性 cycle 同款方向）

### Q4: VT100 录屏的 bookmarks 怎么处理？

**A**: VT100 录屏也支持 bookmarks（v0.14 stage 2 落地，[`src/record/bookmark.rs::BookmarkFile`](../../src/record/bookmark.rs) 是格式无关的——只看 `frame_idx` + `timestamp_secs`，与 v3 / VT100 解耦）。

但 VT100 的 `timestamp_secs` 字段需要从 `time_range_ms()` 内插（`start_ms + (end_ms - start_ms) * frame_idx / total_frames` / 1000），不像 v3 直接从 `UiFrame.timestamp` 取。

stage 2 / stage 3 实装时统一在 handler 内做格式判断（`is_vt100_file` → VT100 路径 / 否则 → v3 路径），bookmarks CRUD 两条路径都支持。

### Q5: 6 个 tool 的 description 字段要写什么？

**A**: 与 v0.15 stage 2 决策 6 同款——`#[tool]` 方法体 1-2 行调子 module helper，`description` 字段写清返回字段集 + 用法示例（让 client IDE 自动补全时给 agent 提示）。

例：
```rust
#[tool(name = "proc_replay_search")]
/// Search recording frames by FilterExpr or substring.
///
/// Query formats:
/// - Substring: `chrome` (matches any frame containing process named "chrome")
/// - FilterExpr: `: cpu > 80 AND name =~ /chrome/` (5 dimensions: timestamp/cpu/mem/name/anomaly.severity)
///
/// Returns: { ok, match_count, returned, truncated, matches: [{ frame_idx, timestamp, cpu_usage, memory_used, matched_processes[], anomaly_severity? }] }
/// Default limit: 100. Truncated=true when match_count > returned.
/// Only v3 UiFrame format supported (VT100 returns ok=false).
pub fn proc_replay_search(&self, args: ReplaySearchArgs) -> CallToolResult {
    ok_result(record::make_replay_search_json(&args.file_path, &args.query, args.limit))
}
```

### Q6: 6 个 tool 启动开销会让 MCP server 启动变慢吗？

**A**: 不会。rmcp 的 `#[tool_router]` 是编译期宏，runtime 不扫描 tool 列表（与 v0.7 落地 17 tool + v0.15 加 15 tool 同款开销）。新增 6 tool 不影响 MCP server 启动延迟。每个 tool 是 lazy 调用（agent 不调不耗资源），与既有 32 tool 一致。

### Q7: handler 子 module 加第 5 个文件（record.rs）会让 mod.rs impl 块涨到 ~1400 行吗？

**A**: 不会显著涨。mod.rs impl 块只追加 6 个新 `#[tool]` 方法（每个 3-5 行 = ~30 行 + description 字段各 5-10 行 = ~50 行）。v0.15 末 mod.rs ~1300 行，v0.16 末预计 ~1350 行（增长 ~4%，与 v0.15 单文件 ~1180 行相比仍可接受）。

未来 rmcp 升级（如支持 cross-module collection）可进一步拆 mod.rs impl 块（ADR-0024 §负面 已记录此限制）。

### Q8: ADR-0025 选哪个主题（候选 1 vs 候选 2）？

**A**: **两份都产出**（与 v0.15 stage 1 同时产出 ADR-0023 + ADR-0024 同款）。理由：
- 候选 1（replay_search schema）：文档化 stage 2 Slice 的核心设计决策（limit 截断 + 字段裁剪）
- 候选 2（record 不暴露）：文档化 cycle 范围决策（决策 1），让未来贡献者一眼看到「为什么不暴露 record」

两份 ADR 各 ~150 行，stage 1 总 ADR 工作量 ~300 行（与 v0.15 stage 1 ADR-0023 + ADR-0024 ~270 行同款量级）。

## v0.16 cycle 候选 stage 拆分（与 v0.15 对比）

### 方案 A：4 stage（推荐，与 v0.15 节奏对齐）

- stage 1 Spike：handler 子 module 扩 record.rs + 7 tool stub schema + ADR-0025a + ADR-0025b + CONTEXT 术语
- stage 2 Slice：replay 业务逻辑（2 tool：info + search）+ 测试 ~12 case
- stage 3 Slice：bookmarks 业务逻辑（4 tool：list/add/edit/delete）+ 测试 ~18 case
- stage 4 Review + 收尾：REVIEW-v0.16 + CHANGELOG + tag v0.16.0

### 方案 B：3 stage（更紧凑）

- stage 1 Spike + 设计（同方案 A）
- stage 2 Slice：7 tool 业务逻辑全填 + 测试 ~30 case
- stage 3 Review + 收尾

**对比**：
- 方案 A：4 stage / 单 stage 量级均匀（~250 行）/ 测试 case 分两批（replay + bookmarks）/ commit 历史清晰
- 方案 B：3 stage / stage 2 量级偏重（~500 行）/ 测试一次性写完 / commit 数量少

**推荐方案 A**（与 v0.15 节奏对齐 + 单 stage 量级可控），用户如倾向方案 B 在拍板时说明。
