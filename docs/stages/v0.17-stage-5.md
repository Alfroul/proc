## 设计决策（本阶段拍板，stage 6-7 不动 VT100 转码路径策略）

### 决策 1：实装时澄清 ADR-0028 描述的 misreading —— VT100 文件存的是 VtFrame 流（已解析 Buffer cells），不是原始 VT100 字节流

**问题**：ADR-0028 §1 + §3 描述 `Vt100ToUiFrameConverter` 工作流为「VT100 字节流增量解析（CSI / SGR / cursor move / clear 全套 VT500 序列反序列化），累积屏幕 buffer + 当前 SGR 状态」。stage 1 stub API `feed_bytes(bytes: &[u8])` + `snapshot_frame() -> UiFrame` 也是按这个描述设计的。

**实装时澄清**：v0.6 落地的 `VtRecorder::try_capture(buffer: &Buffer, area: Rect)`（`src/record/vt100.rs:317`）在录制时已经把 ratatui `Buffer` 状态（每 cell 的 `symbol() / fg / bg / modifier`）序列化到 `VtFrame.rle: Vec<(u16, CellDump)>`。回放时 `VtPlayer::open` 反序列化得到 `Vec<VtFrame>`，每个 VtFrame 已经是结构化数据（不需要 VT500 序列反序列化）。

**结论**：VT100 文件存的是 VtFrame 流（已解析 Buffer cells），不是原始 VT100 字节流。stage 5 实装不需要扩 VT500 序列解析器（CSI / SGR / cursor move / clear 反序列化）—— `vt100` crate（Cargo.toml 已声明 `vt100 = "0.15"`）仅用于 `docker exec` 交互式终端路径（`src/app.rs:108 container_exec_vt: Option<vt100::Parser>`），与录屏 / 回放路径无关。

**影响**：
- 工作量从 ~1100 行收缩到 ~700 行（去除 VT500 parser ~400 行不必要的实装）
- API 改为 `convert_frame(&VtFrame) -> UiFrame`（1:1 映射，VtRecorder 已 5 FPS 切片，不需 30 FPS 重切片）
- ADR-0028 §4「VT500 序列解析器扩工作量风险」段说明的拆分条件（> 200 行）不触发，stage 5 单段落地

**与 brainstorm §风险 5 mitigate 对齐**：决策段文档化 misreading 纠错历史，与 v0.17 brainstorm §cycle 定位段「TD-46 误读说明」同款模式。

### 决策 2：API 改为 `convert_frame(&VtFrame) -> UiFrame`（1:1 mapping）

**问题**：stage 1 stub API `feed_bytes(&mut self, bytes: &[u8]) -> Result<(), String>` + `snapshot_frame(&self) -> Result<UiFrame, String>` 假设输入是字节流。但实际 VT100 文件存 VtFrame 流，调用方需先把 VtFrame 序列化成 bytes 再喂给 converter，converter 内部反序列化回来 —— 多余的 ser/deser 往返。

**决策**：API 改为接受 `&VtFrame` 直接转换：

```rust
// src/record/vt100_to_uiframe.rs

pub struct Vt100ToUiFrameConverter {
    start_time: u64,        // anchor: header.start_time（unix epoch secs），用于 timestamp_ms → timestamp_secs 换算
    hostname: String,       // RecordingHeader.hostname 字段值
    frame_count: u64,       // 已转换的帧数
    seen_process_names: std::collections::HashSet<String>, // 累积出现过的进程名（去重）
}

impl Vt100ToUiFrameConverter {
    pub fn new(start_time: u64, hostname: String) -> Self;

    /// 把一个 VtFrame 转换为 UiFrame（1:1 映射）。
    ///
    /// VtRecorder 已按 MIN_CAPTURE_MS = 200ms（5 FPS）节奏切片，
    /// 不做 30 FPS 重切片（VtFrame 之间无中间帧数据）。
    pub fn convert_frame(&mut self, vt: &VtFrame) -> UiFrame;

    /// 转换统计（完工后调用，写 footer 元数据用）。
    pub fn stats(&self) -> Vt100TranscodeStats;
}

#[derive(Debug, Clone, Default)]
pub struct Vt100TranscodeStats {
    pub frame_count: u64,
    pub unique_process_count: usize,
    pub hostname: String,
}
```

**关键设计点**：

1. **1:1 mapping**：每个 VtFrame 转一个 UiFrame（不合并 / 不拆分），与 VtRecorder 5 FPS 切片节奏一致
2. **`start_time` anchor**：VtFrame.timestamp_ms 是相对录制起始的毫秒（`self.start_time.elapsed().as_millis()`），转换 UiFrame.timestamp 时加上 `header.start_time`（unix epoch secs）让它与 v3 footer 的 start_time / end_time 同 epoch
3. **`seen_process_names` 累积去重**：跨帧记录出现过的进程名，转换完工后写 stats 让 agent 看到录屏全 session 涉及的 unique 进程数（VT100 路径独有的 metadata，v3 路径没有这个统计）
4. **`hostname`**：从环境变量构造（与 `RecordingHeader::default` 同款逻辑），让临时 v3 文件的 header.hostname 字段有值

**与 stage 1 stub API 不兼容**：stage 1 stub 的 `feed_bytes` + `snapshot_frame` 完全删除（仅 stub 阶段，无外部调用方），换成 `convert_frame` + `stats`。stage 1 doc 头部 ✅ 标记不变（API 重命名是 stage 5 实装细节，stage 1 spike 的「struct + 方法签名骨架」目标达成）。

### 决策 3：UiFrame 字段填充策略（VT100 路径独有）

**问题**：UiFrame 有 25+ 字段（mode / status_message / cpu_usage / memory_used / processes / tree_nodes / port_entries / anomalies / usb_devices / monitors / docker_containers / docker_events / ops / nav 等）。VT100 路径只存了屏幕 cell 文本，没有这些结构化数据，需决策填充策略。

**决策**：按 ADR-0028 §4「UiFrame 字段填充策略」落地：

| UiFrame 字段 | 填充策略 | 理由 |
|---|---|---|
| `timestamp` | `header.start_time * 1000 + vt.timestamp_ms`（unix epoch ms） | 与 v3 footer 同 epoch，让 FilterExpr `timestamp >= "..."` 能跨 VT100 / v3 路径 |
| `mode` | `"VT100"` 字面量 | 让 search `mode =~ /VT100/` 能识别 VT100 转码帧 |
| `status_message` | `None` | VT100 路径无 status 状态机 |
| `cpu_usage` | `0.0` | VT100 字节流无系统指标 |
| `memory_used` / `memory_total` | `0` / `0` | 同上 |
| `net_down` / `net_up` | `0` / `0` | 同上 |
| `cpu_history` / `mem_history` | `vec![]` | 同上 |
| `processes` | `extract_process_names_from_rle(&vt.rle)` 解析 | 从屏幕文本提取进程名（pid/cpu/memory 不可得，填占位值） |
| `search_query` / `sort_field` | `""` / `"Name"` | VT100 路径无搜索状态 |
| `process_view_mode` | `0`（List） | 默认值 |
| `tree_nodes` | `vec![]` | VT100 路径无树视图 |
| `port_entries` / `port_*` | `vec![]` / 默认 | 同上 |
| `connection_diff` | `Default::default()` | 同上 |
| `anomalies` | `vec![]` | **VT100 路径无 anomaly 标记**（ADR-0028 §4 明确） |
| `usb_*` / `monitors` / `docker_*` | `vec![]` | VT100 路径无对应数据 |
| `ops` | `vec![]` | 同上 |
| `nav` | `Default::default()` | 同上 |

**`extract_process_names_from_rle` 策略**（`src/record/vt100.rs` 新增 helper）：

```rust
/// 从 VtFrame 的 RLE cells 提取进程名候选（Windows .exe / 通用可执行名 pattern）。
///
/// VT100 录屏的屏幕文本是终端渲染结果，无法精确还原 ProcessInfo 全字段，
/// 但能识别「name.exe」 / 「name」等单词作为 search `name =~ /<pattern>/`
/// 命中线索。pid/cpu/memory 字段填占位值（pid=0, cpu=0.0, memory=0）。
pub fn extract_process_names_from_rle(rle: &[(u16, CellDump)]) -> Vec<FrameProcess>;
```

**`FrameProcess` 占位值**：
- `pid: 0`（VT100 路径无 pid 信息）
- `name: <提取的进程名>`
- `cpu: 0.0` / `memory: 0` / `disk_read: 0` / `disk_write: 0`

**关键设计点**：
1. **processes 数组 dedup**：同一帧内重复出现的进程名只保留一次（避免 search `name =~ /chrome/` 时同一帧命中多次误判）
2. **提取规则**：扫描每行 cell 文本，匹配 `\b[\w\-\.]+\.exe\b`（Windows 可执行名 pattern）或 `\b[\w\-]{3,30}\b`（通用单词，排除太短 / 太长噪声）
3. **跨帧累积**：converter 的 `seen_process_names` 字段记录所有出现过的进程名，stats() 返 unique count

**与 ADR-0028 §4 对齐**：决策段细化「`processes` 字段填充当前屏幕 buffer 的进程名集合」描述，落地具体规则。

### 决策 4：临时转码路径 —— `<file>.tmp.v3` 文件生命周期由调用方管理

**问题**：ADR-0028 §2 描述临时转码路径 `Vt100ToUiFrameConverter 转码到 <file>.tmp.v3 → Player::open(<file>.tmp.v3) → replay 完成后删 <file>.tmp.v3`。但临时文件生命周期管理需明确（replay 失败 / panic 时谁来清理？MCP 路径 vs CLI 路径同款清理？）。

**决策**：**`convert_vt100_to_v3_file` 一次性 helper + RAII 包装**：

```rust
// src/record/vt100_to_uiframe.rs

/// 一次性把 VT100 `.prec` 文件转码为 v3 `.prec` 临时文件。
///
/// 流程：
/// 1. VtPlayer::open(src) 读全部 VtFrame
/// 2. Recorder::start(dst) 启动 v3 writer
/// 3. for each VtFrame: converter.convert_frame(vt) → recorder.submit_frame(ui)
/// 4. recorder.stop() 写 footer + close
/// 5. 返 Vt100TranscodeStats（frame_count / unique_process_count / hostname）
///
/// 失败模式（返 Err）：
/// - VtPlayer::open 失败：源文件不是 VT100 或损坏
/// - Recorder::start 失败：目标路径不可写 / 磁盘满
/// - 转换过程无需 IO，纯内存，不会失败
pub fn convert_vt100_to_v3_file(
    src: &std::path::Path,
    dst: &std::path::Path,
) -> Result<Vt100TranscodeStats, String>;

/// 临时 v3 文件 RAII wrapper —— Drop 时自动删除文件。
///
/// 让 CLI / MCP 路径用 `let _tmp = TranscodedTempFile::new(path)?;` 持有，
/// 退出作用域时自动清理（即使 panic 也清理，与 tempfile::TempPath 同款语义）。
pub struct TranscodedTempFile {
    path: std::path::PathBuf,
    keep: bool,
}

impl TranscodedTempFile {
    pub fn new(path: std::path::PathBuf) -> Self;
    pub fn path(&self) -> &std::path::Path;
    pub fn keep(mut self); // disown（如调用方想保留临时文件用于 debug）
}

impl Drop for TranscodedTempFile {
    fn drop(&mut self) {
        if !self.keep {
            let _ = std::fs::remove_file(&self.path);
        }
    }
}
```

**调用方模式**：

```rust
// src/cli/record.rs::run_replay VT100 分支
let tmp_path = file.with_extension("prec.tmp.v3");
let stats = convert_vt100_to_v3_file(file, &tmp_path)?;
let _cleanup = TranscodedTempFile::new(tmp_path.clone());
// 后续走 v3 Player 路径
let player = Player::open(tmp_path)?;
// ... replay ...
// _cleanup drop 时自动删 tmp_path
```

**关键设计点**：

1. **RAII 清理**：Drop impl 保证 panic 也清理，与 `tempfile::TempPath` 同款语义
2. **`keep()` opt-out**：debug 场景调用方 `keep()` 后 Drop 不删，让用户检查转码后文件
3. **MCP 路径同款**：`make_replay_info_json` / `make_replay_search_json` VT100 分支也用 `TranscodedTempFile`，临时文件生命周期 = tool 调用周期（每次 MCP tool 调用都重新转码，与 brainstorm §风险 5 已 mitigate「多次调用累积 ~3s × N 开销」对齐）
4. **临时文件路径**：`<file>.tmp.v3`（保留原文件 stem 让用户能联想，加 `.tmp.v3` 后缀让 IDE / git 识别为临时）

**与 ADR-0028 §2 对齐**：决策段细化「replay 完成后删 <file>.tmp.v3」生命周期管理，与 v0.6 落地的 `VtRecorder::Drop` impl 同款 RAII 模式延续。

### 决策 5：replay 路径集成 —— VT100 检测后透明转码，调用方无感

**问题**：当前 `src/cli/record.rs::run_replay`（line 51）和 `src/mcp/handler/record.rs::make_replay_info_json`（line 136）/ `make_replay_search_json`（line 218）已分支 `is_vt100_file(path)`，VT100 路径用 `VtPlayer::open` + 走单独路径。stage 5 改为 VT100 自动转码到临时 v3 文件，走 v3 Player 路径。

**决策**：**三层透明转码**：

1. **CLI `proc replay <file>`**：VT100 → 转码到 `<file>.tmp.v3` → `Player::open` → 走 v3 replay 路径（用户得到 search / 倒放 / 书签能力）；转码失败 fallback 走 `VtPlayer` 正向 replay（与 ADR-0028 §2 设计对齐）
2. **CLI `proc replay <file> --info`**：VT100 → 转码 → 从 v3 Player 读 footer 输出完整元数据（hostname / max_cpu / anomaly_count 等 VT100 路径原本没有的字段）
3. **MCP `proc_replay_info` / `proc_replay_search`**：VT100 → 转码 → 走 v3 路径返完整 JSON（`proc_replay_search` 不再返「VT100 录屏不支持 search」错误）

**修改点**：

| 文件 | 函数 | 改动 |
|---|---|---|
| `src/cli/record.rs` | `run_replay` | VT100 分支：转码 + Player::open(tmp) 替代 VtPlayer::open |
| `src/cli/record.rs` | `run_replay_info` | VT100 分支：转码 + 输出 v3 footer 元数据替代 VT100 header |
| `src/cli/record.rs` | `run_vt100_replay` | **保留**（fallback 路径，转码失败时走），但改为 private helper |
| `src/mcp/handler/record.rs` | `make_replay_info_json` | VT100 分支：转码 + 返 v3 footer JSON（保留 `format: "vt100-transcoded"` 标识） |
| `src/mcp/handler/record.rs` | `make_replay_search_json` | VT100 分支：转码 + 走 v3 全帧遍历（删除「不支持 search」错误） |

**关键设计点**：

1. **fallback 保留**：转码失败（VT100 字节流损坏 / 临时文件路径不可写）→ 走原 `VtPlayer` 正向 replay 路径，与 ADR-0028 §2 「转码失败 → fallback 走 VtPlayer 正向 replay」对齐
2. **MCP `format` 字段标识**：`make_replay_info_json` VT100 转码后返 `format: "vt100-transcoded"`（vs 原 `"vt100"`），让 agent 知道「这是 VT100 转码后的 v3 数据，可享受全部 v3 能力」
3. **不破坏既有 VtPlayer / VtRecorder 路径**：v0.6 落地的 VT100 正向 replay 路径保留（fallback + 用户显式选 VT100 路径的兜底），不删 `VtPlayer` / `run_vt100_replay`

**与 brainstorm §主题 F 表「replay 路径集成 VT100 自动检测 + 临时转码」对齐**。

## 已知风险

### 风险 1：转码开销超预估（决策 5 mitigate）

**问题**：brainstorm §风险 5 估算 30 min × 30 FPS × 1000 进程 VT100 文件转码 ~3s。但实际 VtRecorder 是 5 FPS（不是 30 FPS），30 min session = 9000 帧（不是 54000 帧），单帧转换纯内存 < 1ms，预估实际 ~1-2s。

**mitigate**：
- 实装时实测 `Instant::now()` around `convert_vt100_to_v3_file`，记入 stage 5 完成报告
- 如 > 5s 触发 v0.18+ cycle 评估永久转码 CLI 子命令（brainstorm §风险 5）

### 风险 2：进程名提取误报 / 漏报（决策 3 mitigate）

**问题**：从屏幕文本提取进程名是启发式（regex `\b[\w\-\.]+\.exe\b`），可能：
- 误报：屏幕显示「Please visit https://example.com/chrome.exe」会被误识别为 chrome.exe 进程
- 漏报：屏幕显示「chrome」(无 .exe 后缀)不会被识别

**mitigate**：
- 测试覆盖多种屏幕文本 pattern（任务 4 测试 6 + 7）
- VT100 路径 processes 字段本来就是「线索」性质（pid/cpu/memory 占位），不破坏 v3 路径的精确数据
- 用户如反馈误报多 → v0.18+ cycle 评估加白名单 / 黑名单 TOML 配置（与 lineage_rules.toml / path_rules.toml 同款契约）

### 风险 3：临时文件清理失败（决策 4 mitigate）

**问题**：`TranscodedTempFile::Drop` 调 `std::fs::remove_file`，可能因文件被占用 / 权限问题失败。Windows 上 Player::open 持有 File handle 期间不能删（直到 Player drop）。

**mitigate**：
- Drop impl 用 `let _ = std::fs::remove_file(&self.path);` 忽略错误（与 v0.6 VtRecorder::Drop 同款语义）
- 调用方需先 drop Player 再 drop TranscodedTempFile（通过作用域顺序保证）
- 残留临时文件不影响功能（用户可手动删 `<file>.tmp.v3`）

### 风险 4：MCP 路径每次调用都重新转码（决策 5 + brainstorm §风险 5 mitigate）

**问题**：MCP `proc_replay_info` / `proc_replay_search` 每次调用 VT100 文件都触发转码（~1-2s）。agent 多次调用累积 ~3s × N。

**mitigate**：
- 与 brainstorm §风险 5 同款可接受范围（agent 一次性调用，与 `proc_replay_search` ~9s/30min session 同款）
- v0.18+ cycle 评估永久转码 CLI 子命令 `proc replay --convert <file>`（决策 6 段说明）

### 风险 5：context overflow（brainstorm §决策 8 mitigate）

**问题**：stage 5 工作量 ~700 行（收缩后），仍在容量上限 1500 行的 47% 内。但本会话已消耗较多上下文读文档，需关注剩余容量。

**mitigate**：
- 实装前已读完所有依赖文档（CONTEXT / brainstorm / stage 4 / ADR-0028 / 相关源文件）
- 任务清单按顺序执行（任务 1 → 2 → 3 → 4 → 5），每个任务完工后 commit 风格推进（但实际 stage 5 单 commit）
- 如上下文剩余 < 30% 触发 Checkpoint 机制（生成 `docs/handoff-stage-5-checkpoint.md`）
