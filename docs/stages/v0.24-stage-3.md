## 已知风险（stage 3 实施时关注）

### 风险 1：挂机顺序破坏变量隔离（本阶段头号风险）

**问题**：system.md 经 include_str 嵌入 binary，v3 commit 落地后无配置开关可回退——若 RAG-on 列跑在 v3 binary 上，该列变成 E2B × v3 × RAG-on 三变量，对基线族的归因全部作废。
**mitigate**：目标段「挂机顺序硬约束」+ 任务 5/6 顺序死定（代码 commit → RAG-on 列 → v3 commit → v3 列）；归档时以各列 `EvalRunMeta.git_describe` 核对 binary 对应关系；brainstorm 风险 7 的「分散多次挂机」天然契合此顺序。

### 风险 2：spawn 4→5 参动 4 个既有测试文件

**问题**：签名变更触碰 test_agent_panel / v0_21_stage_2 / v0_22_stage_3 / v0_23_stage_2 四文件的 spawn 调用点。
**mitigate**：纯机械补 `None`（v0.22 stage 3 spawn 3→4 参同款先例，当时 3 个调用点）；这些测试全绿即「SessionEvent / session 层形状零改动」的验证锚。

### 风险 3：eval_corpora 相对路径的 cwd 依赖

**问题**：`eval_corpora = ["eval-e2b-70q.json", …]` 按 cwd 解析——从非仓库根目录跑 eval 时三份基线 JSON 找不到。
**mitigate**：挂机指令明示「从仓库根目录跑」（任务 6 步骤 1）；路径解析失败走 stage 2 静默降级（警告 + 跳过该源不 panic），索引仍含 session 语料；绝对路径亦可填。

### 风险 4：RAG-on 列增益落方差带内（大概率场景——brainstorm 风险 1 既定）

**问题**：「E2B + RAG 收益存疑」是既定判断，本 cycle 口径本就是机制验证为主指标、不预设涨通过率。
**mitigate**：D5 两分结论框架——「机制成立但 E2B 兑现不了」（检索准 + 被用上 + 通过率带内）给 v0.25+ 模型底座重启决策留数据输入，与「机制不成立」（检索不准 / 无视注入）分离归档；默认值维持 off，不强制改默认。

### 风险 5：stderr `[rag]` 行的输出干扰

**问题**：on 态每 query 一行 stderr——TUI alt-screen 场景下理论上可能污染终端（eval 挂机是 CLI 场景无此问题）。
**mitigate**：`RagIndex::build`（stage 2）与 `SessionRecorder` 已有 eprintln 先例，行为契约一致；off 态（默认）零输出；TUI + RAG on 的实机验证不在本阶段矩阵内（eval 挂机全走 CLI）。
