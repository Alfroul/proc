## 关键决策

### 决策 1：eval runner 载体——CLI 子命令 `proc agent eval` ✅

**理由**：(1) eval 是测量工具不是测试——独立可执行、参数化（provider/model/level/attempts）是第一诉求；(2) 跨 run/模型对比天然是 CLI 形态（`--compare a.json b.json`）；(3) 复用 builder 构造链 + `dirs_config_dir()` 零新建模式；(4) `AgentSub` 已是子命令结构（scan/ask），加第 3 变体自然。备选方案：

- (a) **CLI 子命令**（✅ 拍板）：如上
- (b) 测试内 harness 升级（`#[ignore]` test 写文件）：改动小，但报告产出/参数化/跨模型对比都别扭，test harness 不该产报告
- (c) 独立 bin（src/bin/eval.rs）：与 CLI 子命令无实质差别，还多一个入口维护

**用户拍板**：✅ (a)（2026-08-19）。

### 决策 2：L2 验收口径——不设硬线 + 双口径报告 ✅

E2B 预期低通过率（v0.21 决策 4 已定性「能力边界实测数据」），设硬线只会验收 flaky。报告记录双口径：**full-chain**（expected 链全部命中 / 20）+ **chain-step**（链步命中数 / 总链步数）；失败 query 归 ChainIncomplete / NoToolCall 等模式。数据价值 > 门槛价值——更强模型复测（v0.23+）时这组数字才是对比基线。L0/L1 硬线**保留在 stage_3b 既有 `#[ignore]` 验收测试不动**（回归锚），eval runner 默认 report-only 不 gate。

**用户拍板**：✅ 不设硬线 + 双口径（2026-08-19）。

### 决策 3：Observability 范围——全套（log + 时间戳 + 指标）✅

预拍板明确「TUI session 观测纳入 eval 设计」（v0.21 决策 1 理由 4）。落地：session 层时间戳 + JSONL log + 指标提取库 + `proc agent session-info` 薄展示。关键设计约束：**SessionEvent 8 变体形状零改动**（时间戳在 session 层包装记录，不进事件本体——apply_event 全部测试零破坏）；**运行时 UI 零改动**（观测是离线诉求，不逐 delta 显示指标）。session log 默认开启（本地工具零上传、单会话几百 KB；agent.toml `[session].log = false` 可关）；不做轮转/清理（不预实现）。

**用户拍板**：✅ 全套（2026-08-19）。

### 决策 4：更强本地模型——不下载，v0.22 只跑 E2B 基线 ✅

本地现有仅 E2B 两变体（uncensored 是社区微调非能力升级），复测需下载。用户拍板不下载：v0.22 产 E2B 单模型 70 query 基线（L0/L1 复测 + L2 首跑）；`--compare` 对比能力照常内建（harness 不依赖第二个模型存在），未来下载更强模型后 1 条命令即出对比列。REVIEW-v0.21 观察 3（写操作发现链边界）的量化验证在本基线内完成。

**用户拍板**：✅ 不下载（2026-08-19）。

### 决策 5：TD-55~57 / TD-58 处置 ✅

无 `ANTHROPIC_API_KEY`：TD-55~57 继续 open（有 key 后 eval runner 一条命令闭环三连——Sonnet 对照 + model ID 真实验证 + nudge 路径覆盖）；TD-58 观察项不动（整个 v0.21 cycle 仅再现 1 次，连续 cycle 再现才修）。

**用户拍板**：✅ 继续 open / 观察（2026-08-19）。

### 决策 6（默认 surgical 排除）：proc_record_start/stop 继续推迟 v0.23+ ✅

v0.21 决策 8 遗留（confirm 通道落地后成本 ~100 行）。评估结论继续推迟：(1) v0.22 保持**零 tool 变更的干净 eval 基线**——catalog 一变，L0/L1/L2 数据与前值不可比；(2) 「agent 启动录屏」语义边界（录制范围 / 停止时机）需单独设计；(3) eval cycle 聚焦不分心。

**用户拍板**：✅ 推迟 v0.23+（2026-08-19）。

### 决策 7：stage 节奏——4 stage ✅

**4 stage = 1 Spike + 2 Slice + Review+收尾合并段**（phased-project skill 自适应规则：Slice ≤ 2 时 Review 与收尾合并；v0.21 同款）。备选：5 stage（实跑独立——否决：E2B 全量是用户挂机行为不是会话内工作，独立 stage 会空转）/ 3 stage（obs 并入 eval stage——否决：单 stage ~1400-1600 行逼近铁律 19 上限）。

**用户拍板**：✅ 4 stage（2026-08-19）。

## ADR-0032：Eval harness + session Observability 架构（stage 1 落地骨架）

- **标题**：`proc agent eval` 评测 harness + session observability
- **Status**：Proposed（v0.22 stage 1 Spike 落地骨架 → Accepted）
- **Context**：
  - v0.20 stage 3b QUERY_TABLE 验收 runner（`#[ignore]` test + 常量表 + eprintln）已验证 50 query 确定性口径，但泛化（数据文件化 / 结果持久化 / 失败分类 / 跨模型对比）超出 test harness 形态
  - v0.21 AgentSession/AgentPanel 落地后，session 行为（TTFT / streaming / confirm）首次可观测，但事件流仅进 TUI 不留档
  - L2 20 query seed 从未系统实跑；E2B 写操作发现链边界（REVIEW-v0.21 观察 3）需量化
- **Decision**：
  - **D1：eval runner = CLI 子命令**——`AgentSub::Eval`；复用 builder 构造链与 `--provider/--model` 解析；complete 路径（与 stage_3b 验收同款），不动 `run`/`run_streaming`
  - **D2：70 query 数据文件编译进 binary**——`src/agent/eval/queries.toml` + `include_str!`（与 GBNF 同款）；`[[query]] = {scenario, level, text, expected_tools}`；L2 链 2-3 个有序 tool
  - **D3：判定与失败分类确定性**——expected_tools 保序子序列命中 + text_ok；FailureMode 6 变体从 RunnerOutcome 判定；不上 LLM-as-judge；eval 默认 report-only 不 gate（L0/L1 硬线保留在既有 `#[ignore]` 验收测试）
  - **D4：L2 双口径**——full-chain + chain-step，不设硬线（能力边界数据）
  - **D5：observability 在 session 层旁路**——SessionLogEntry 时间戳包装（SessionEvent 形状零改动）+ SessionRecorder JSONL（`[session].log` 默认 true）+ analyze_session_log 指标提取 + session-info 薄 CLI；运行时 UI 零改动；不做轮转/清理（不预实现）
- **Consequences**：
  - `AgentSub` 2 → 4 变体（Eval / SessionInfo）
  - eval 结果 JSON 与 markdown 报告成为 cycle 间可比资产；`--compare` 是未来模型对比的即插接口
  - session log 默认写盘（单会话几百 KB，可关）
  - 既有 `#[ignore]` 验收测试（stage_3b/stage_4）保留为回归锚，与 queries.toml 存在 query 文本重复（冻结锚 vs 演进数据源的取舍，见 FAQ Q6）
- **与既有 ADR 关系**：
  - 建立在 ADR-0030（内置 agent 基座）+ ADR-0031（AgentSession/面板）之上——本 ADR 是测量与观测层
  - 复用 ADR-0008 self-mitigation 语境（eval 不触碰写 tool；confirm 行为仅观测）

## 已知风险

### 风险 1：E2B FULL 70 query 挂机稳定性（4.5-6.5h）

**问题**：v0.20 50 query FULL 实测 2.7-4h；加 L2 20 条多步链 + attempts=2，时长上探 6.5h。长时运行 llama-server 崩溃 / 连接失效会废掉整晚。

**mitigate**：
1. 惰性重 spawn 自愈已实测（REVIEW-v0.21 观察 2——连接级故障下一次请求自动重建 server，零为此代码）
2. eval runner 单 query LlmError 不中断后续（attempts 用尽记失败模式继续跑完）
3. 结果 JSON 每 query 实时落盘（非跑完一次性写）——中途崩已跑数据不丢
4. QUICK 模式先冒烟（~27 query）确认链路再挂 FULL

### 风险 2：session log 磁盘行为

**问题**：默认写盘是行为变更；高频 TextDelta 会产生大量行。

**mitigate**：
1. 单会话体量实测预期几百 KB（TextDelta 按 tick 聚合后的粒度记录，不逐 delta 落盘——记录粒度与 TUI drain 同款）；stage 3 测试断言单 query 行数上限
2. `[session].log = false` 一键关；写入失败静默降级不影响会话
3. 不做轮转/清理（不预实现；累积成问题再治理）

### 风险 3：L2 expected chain 标注主观性

**问题**：L2 链（如 proc_help(usb) → proc_usb_release）从 seed 工具链意图反推，标注者主观——链定得过严 full-chain 会虚低。

**mitigate**：
1. 口径用保序子序列（不要求相邻、允许中间插其他 tool），宽松明确
2. queries.toml 人类可读可审（stage 1 交付物，用户过目）
3. chain-step 口径天然稀释标注严格度的影响

### 风险 4：stage 2 容量与范围蔓延

**问题**：eval runner 是新 CLI 面，报告格式打磨（条形图 / 对比表）容易吸收超预期时间。

**mitigate**：
1. 容量表 950 行（37% 余量）；markdown 报告样式以 stage doc 预先画定为锚（stage 1 ADR 附样式草案），实施不重新设计
2. 排序：执行循环 + 判定分类 → JSON → markdown → compare（前两项完成即有可用 eval，报告打磨可降级）
3. 上下文告急触发 Checkpoint 接力，不硬撑

### 风险 5：eval 与既有验收测试的口径漂移

**问题**：queries.toml 与 QUERY_TABLE 常量并存（同 50 query 两份数据源），未来改一处漏一处。

**mitigate**：
1. 明确分工：QUERY_TABLE 是**冻结回归锚**（不演进），queries.toml 是**演进数据源**（eval 专用）——stage 1 加一致性测试：50 query 文本逐字相等断言（锚不漂）
2. 失败分类 / 判定逻辑单一实现在 eval 模块（测试不复制逻辑）

## FAQ

### Q1: 为什么不上 LLM-as-judge 或 τ²-bench？

**A**: LLM-as-judge 引入第二个 LLM 的不确定性 + 本地无 judge 模型 + 无 API key；确定性口径（tool 命中 + 文本非空）可复现、可 diff、跨模型公平。τ²-bench 仅对照引用（v0.20 已用作 29.4% 基线参照）——proc 是 Windows 系统运维域，工具集与外部基准不匹配，完整适配成本高收益低（决策 6 预拍板延续）。

### Q2: 为什么 v0.22 只跑 E2B 一个模型？

**A**: 用户拍板不下载（本地仅 E2B 两变体，uncensored 非能力升级）。harness 的对比能力（`--compare`）不依赖第二个模型存在——未来下载更强模型后 1 条命令出对比列，数据即插即用。

### Q3: eval runner 为什么 report-only 不 gate？

**A**: eval 是测量工具；gate（L0 全过 / L1 ≥80%）保留在 stage_3b 既有 `#[ignore]` 验收测试（回归锚不动）。runner 若也 gate，两个入口两套阈值必然漂移；且 E2B 迭代期失败是常态数据不是回归。

### Q4: session log 为什么默认开？

**A**: 本地工具零上传、单会话几百 KB、观测价值依赖真实使用积累数据；`[session].log = false` 一键关。与 ADR-0008 隐私架构一致（数据不出本机）。

### Q5: L2 为什么用保序子序列口径？

**A**: 多步链中间允许插其他 tool（如 proc_ls 后先 proc_help 再 proc_kill），严格连续匹配会虚低；子序列口径宽松且实现简单（双指针 O(n)）。chain-step 口径进一步稀释「整链全中」的二值刚性。

### Q6: queries.toml 与 QUERY_TABLE 常量为什么允许重复？

**A**: QUERY_TABLE 是 v0.20 验收的冻结证据（回归锚，永不演进）；queries.toml 是 eval 演进数据源（v0.23+ 可能扩 query）。stage 1 一致性测试锁住 50 query 文本逐字相等——锚漂即测试红。

### Q7: record_start/stop 为什么又推迟？

**A**: 决策 6——零 tool 变更是 eval cycle 的基线纯净性要求（catalog 变更使跨 cycle 数据不可比）；且语义边界（录制范围 / 停止时机）需单独设计。v0.23+ 评估。

### Q8: eval 数据文件为什么编译进 binary？

**A**: include_str! 与 GBNF grammar 同款模式——版本与 binary 强一致（不出现「binary 升级了数据文件还是旧的」）、零运行时文件依赖、git 版本化天然。代价是改 query 要重编译（eval 表低频演进，可接受）。
