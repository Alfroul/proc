### 决策 4：record 暴露方案选 (a) spawn 子进程 vs (b) worker 持续采样

**v0.16 ADR-0025b** 推迟项：v0.17 cycle 评估 record 暴露的两个方案

| 方案 | 路径 | 优势 | 劣势 |
|---|---|---|---|
| **(a) spawn `proc record` 子进程** | MCP handler `std::process::Command::new("proc").args(["record", "--output", path]).spawn()` 拿 child handle，跨 tool call 保活；`proc_record_stop` kill child + 等待 `.prec` flush | 复用 v0.6 落地的 `run_record` TUI 路径全部逻辑（recorder / bookmark / anomaly detection）；MCP handler 不持 worker 状态；child 进程崩溃不影响 MCP server | 子进程开销（~50ms spawn + ~10MB 内存）；child 进程独立 TTY 但 MCP stdio 无 TTY，需 `--no-tui` flag 让 record 走 headless 路径（v0.6 落地的 `R` 键路径需重构）|
| **(b) MCP handler 启 worker 线程** | `ProcMcpHandler` 加 `record_worker: Arc<Mutex<Option<RecordWorkerHandle>>>` 字段，`proc_record_start` spawn worker 线程采 `SystemSnapshot → UiFrame` 喂 `Recorder::submit_frame` | 无子进程开销；worker 与 MCP server 同进程，lifecycle 简单 | 录制期间 worker 持续运行（~30 FPS × 165 µs/frame = ~5% CPU）影响 MCP server 主路径；recorder_worker 与 MCP stdio 生命周期管理复杂（client 关闭后 worker 仍跑？）；需重写 record 路径绕过 TUI |

**本 brainstorm 推荐 (a) spawn 子进程**，理由：
1. 复用 v0.6 落地的 `run_record` 路径全部业务逻辑（recorder / bookmark / anomaly detection），不重写
2. MCP handler 不持 worker 状态（与 v0.12 TD-36 持久 dns_collector 模式不同，dns_collector 是查询类 worker 持有成本低，record worker 是录制类 worker 持有成本高）
3. 子进程崩溃隔离（record worker 崩溃不影响 MCP server）
4. `--no-tui` flag 重构成本低（~50 行，让 record 走 headless 路径，与 v0.6 落地的 `R` 键路径并行）

**用户拍板**：方案 (a) spawn 子进程（推荐）/ 方案 (b) worker 持续采样 / (c) 仍推迟到 v0.18+ cycle？

### 决策 5：MCP-level confirm 机制设计

**v0.16 brainstorm FAQ Q2 + ADR-0025b** 推迟项：写操作 confirm 机制评估

**3 种候选方案**：
- **方案 A（参数 confirm: bool）**：`proc_record_start(confirm: bool, file_path: String)` 必传 confirm 参数，agent 显式确认录屏会捕获屏幕所有内容含 DNS 域名 / 进程 cmd。confirm=false 时返 `ok: false + error: "confirm=true 必传以确认录屏风险"`。与 v0.7 `proc_kill`/`proc_pkill` + v0.15 `proc_monitor_add`/`proc_monitor_remove` dry_run=false 默认契约**互补**（dry_run 是预演 / confirm 是确认风险）
- **方案 B（两次调用 confirm）**：agent 第一次调 `proc_record_start(file_path)` 返 `ok: false + warning: "录屏会捕获屏幕所有内容，确认请调 proc_record_confirm(token)"` + token；agent 第二次调 `proc_record_confirm(token)` 真正启动录屏。类似 2FA 但复杂
- **方案 C（仅文档警告，无参数）**：`proc_record_start` description 字段写明「录屏会捕获屏幕所有内容含 DNS 域名 / 进程 cmd」，agent 自行决策。surgical 默认

**本 brainstorm 推荐方案 A（参数 confirm: bool）**，理由：
1. 与 v0.6 落地的 `pending_record_confirm` TUI 路径同款契约（用户按 `R` 弹确认 / agent 传 `confirm=true` 显式确认）
2. 简单（一个 bool 参数，无需 token 状态机）
3. agent 视角明确（confirm=true 时才真正启动，false 时返 error 让 agent 知道需要确认）

**适用范围**：
- `proc_record_start`（录屏捕获屏幕内容）— confirm 必传
- `proc_usb_release`（kill 进程 + flush + eject 三步破坏性操作）— confirm 必传，与 dry_run 互补
- `proc_docker_rm` / `proc_docker_image_rm` / `proc_docker_volume_rm`（删除容器 / 镜像 / 卷）— confirm 必传

**用户拍板**：方案 A（参数 confirm: bool，推荐）/ 方案 B（两次调用）/ 方案 C（仅文档警告）？

### 决策 6：VT100 转码路径选 (a) 临时转码 vs (b) 永久转码

**TD-49 VT100 字节流转码 UiFrame** 两种转码路径：

| 方案 | 路径 | 优势 | 劣势 |
|---|---|---|---|
| **(a) 临时转码** | `proc replay <file>` 检测 VT100 文件 → 临时转码到 `<file>.tmp.v3` → 走 v3 Player 路径 → 退出时删临时文件 | 不污染原文件；转码失败可回退 VT100 路径 | 每次回放都转码（30 min × 30 FPS × 1000 进程 ~3s 转码开销）；MCP `proc_replay_info` / `proc_replay_search` 双路径每次都转码 |
| **(b) 永久转码** | `proc replay <file>` 检测 VT100 文件 → 转码并写新 `<file>.v3` 文件 → 后续回放走 v3 路径（VT100 原文件保留作为源） | 一次转码多次回放；MCP 路径也享受转码后能力 | 用户需手动管理 `.v3` 文件（或 proc 自动删除原 VT100？破坏性）；转码后文件 size 可能 2-3x（UiFrame 含 ProcessInfo 结构化数据）|

**本 brainstorm 推荐方案 (a) 临时转码**，理由：
1. 不破坏原 VT100 文件（与 v0.6 落地的 VT100 路径并行，用户可选 VT100 replay 或转码后 v3 replay）
2. 转码失败可回退（VT100 字节流损坏时仍走 VtPlayer 正向 replay）
3. 转码开销 ~3s 可接受（agent 一次性调用，与 `proc_replay_search` ~9s/30min session 同款可接受范围）
4. 永久转码如用户有需求可加 `proc replay --convert <file>` CLI 子命令（未来 v0.18+ cycle 候选）

**用户拍板**：方案 (a) 临时转码（推荐）/ 方案 (b) 永久转码 / (c) 仅 VT100 反向解释器（不转码，直接反向解释 VT500 序列，~1000+ 行独立实装）？

## ADR-0026 ~ ADR-0029 候选主题

stage 1 Spike 产出 4 份新 ADR（决策 7 拍板）：

### ADR-0026：MCP handler 持久字段策略（TD-54 落地）

**主题**：`ProcMcpHandler` 加 `snapshot: Arc<Mutex<SystemSnapshot>>` 字段 + 1s tick refresh；评估 `app_handle` 是否共享；与 v0.12 TD-36 持久 dns_collector 同款模式延续。

### ADR-0027：rmcp 0.11 Resource subscribe + SSE transport 设计

**主题**：暴露 system_metrics / process_list / docker_events 等资源 URI；client 订阅后 worker 1s tick 推送增量；SSE transport CLI 入口。

**决策**：
- Resource subscribe：impl `ResourceRoute` trait，暴露 `proc://metrics/system` / `proc://processes/list` / `proc://docker/events` 等 URI

- TD-52 sparkline：`ProcMcpHandler` 加 `system_history: Arc<Mutex<VecDeque<SystemSnapshot>>>` 字段，1s tick push，30s cap

### ADR-0028：VT100 字节流转码 UiFrame 路径（决策 6 拍板）

**主题**：临时转码路径设计（VT100 → UiFrame 转换器 + 30 FPS 切片 + 临时文件管理）。

**决策**：
- 路径选 (a) 临时转码（决策 6 拍板）

- VT500 序列解析器扩：CSI / SGR / cursor move / clear 全套反序列化
- replay 路径集成：`proc replay <file>` 检测 VT100 → 临时转码 → 走 v3 Player 路径

### ADR-0029：record 暴露 + 写操作 confirm 机制（决策 4 + 5 拍板）

**主题**：spawn `proc record` 子进程路径 + `--no-tui` flag + `confirm: bool` 必传参数契约。

**决策**：
- record 暴露方案 (a) spawn 子进程（决策 4 拍板）
- confirm 机制方案 A 参数 `confirm: bool`（决策 5 拍板）
- 适用范围：`proc_record_start` / `proc_usb_release` / `proc_docker_rm` / `proc_docker_image_rm` / `proc_docker_volume_rm`

- 默认推荐 (a) 全实装，理由：parent_chain Arc 重构（TD-47）已触及同款热路径，顺便修

### 风险 4：record 暴露方案 (a) spawn 子进程的 `--no-tui` flag 重构成本

**问题**：v0.6 落地的 `run_record` 路径走 `tui::setup_terminal() + tui::run_app()`，MCP server 是 stdio 无 TTY。方案 (a) spawn 子进程需 `--no-tui` flag 让 record 走 headless 路径，但 v0.6 路径深度耦合 TUI（recorder / bookmark / anomaly detection 都假设 TUI 上下文）。

**mitigate**：
- stage 1 Spike 评估 `run_record` 重构成本（如 > 200 行 → 决策 4 重新拍板选 (b) worker 持续采样）
- stage 6 实装时如 `--no-tui` 重构超预期 → 拆为 stage 6a（record 暴露）+ stage 6b（USB release + docker-rm 写操作）

### 风险 5：VT100 转码路径选 (a) 临时转码的转码开销

**问题**：30 min × 30 FPS × 1000 进程 VT100 文件转码到 UiFrame 预估 ~3s 开销。MCP `proc_replay_info` / `proc_replay_search` 双路径每次都转码（如 agent 多次调用 search 累积 ~3s × N）。

**mitigate**：
- 决策 6 让用户拍板选 (a) 临时转码 / (b) 永久转码 / (c) 仅 VT100 反向解释器
- 默认推荐 (a) 临时转码，理由：不破坏原文件 + 转码失败可回退
- 如 agent 反馈多次转码开销可感 → v0.18+ cycle 评估 (b) 永久转码 CLI 子命令

### 风险 6：MCP-level confirm 机制与既有 dry_run 契约的语义冲突

**问题**：v0.7 `proc_kill` / `proc_pkill` + v0.15 `proc_monitor_add` / `proc_monitor_remove` + v0.16 `proc_bookmarks_add` / `edit` / `delete` 都用 `dry_run: bool` 默认 false 契约。v0.17 cycle 加 `confirm: bool` 必传参数，agent 视角可能混淆（dry_run 是预演 / confirm 是确认风险）。

**mitigate**：
- ADR-0029 明确文档化 `dry_run` vs `confirm` 语义差异（dry_run 是「不真正执行」/ confirm 是「确认风险后再执行」）
- 适用范围明确：`proc_record_start`（录屏捕获屏幕内容）/ `proc_usb_release`（kill + flush + eject 三步破坏性）/ `proc_docker_rm` 系列（删除容器 / 镜像 / 卷）—— 这些都是**不可逆破坏性操作**，与 dry_run 默认 false 的**可逆写操作**（kill 进程可重启 / monitor_add 可 remove / bookmarks_add 可 delete）互补

### 风险 7：5 主题合并 cycle 的 review 复杂度

**问题**：v0.17 cycle 5 主题合并，stage 7 Review 需审查 5 个独立方向的代码质量 / 架构 / 性能 / 完整性 / 安全跨平台。REVIEW-v0.17.md 预计 ~400-500 行（vs v0.16 ~330 行 / v0.15 ~340 行），单会话工作量偏重。

**mitigate**：
- stage 7 Review 段按 5 主题分段审查（A 性能 / B 可观测性 / F VT100 / record / 写操作）
- 如 Review 工作量超预期 → 触发 Checkpoint 机制接力，stage 7 拆为 stage 7a Review + stage 7b 收尾

## FAQ

### Q1: 为什么 v0.17 cycle 不拆 5 个独立 cycle（每个主题一个）？

**A**: 三个理由：
1. **用户拍板全做**：用户 2026-07-07 启动指令明确「5 主题全做」，拆 5 个独立 cycle 违背用户意图
2. **5 主题有依赖关系**：stage 3 TD-54 MCP handler 持久字段是 stage 4 主题 B sparkline worker 的前置依赖；stage 5 VT100 转码与 stage 3 TD-45 record deserialize 同款 bincode 路径；拆独立 cycle 会增加跨 cycle 依赖管理成本
3. **cycle 节奏紧凑**：5 个独立 cycle 各 4 stage = 20 stage，v0.17 合并 cycle 7 stage = 7 stage，节奏紧凑 2.9x

### Q2: 7 stage 节奏会上下文溢出吗？

**A**: 不会显著溢出，但需严格容量控制：
- 单阶段容量上限 1500 行（含测试），stage 4/5/6 接近上限（73-80%）
- 每会话强制规则（开工前 8 步 + 执行中 7 步 + 完工后 8 步）保证上下文管理
- 自适应拆分规则（决策 8）让任一 stage 超预期时拆为 stage-N.M
- 1M 上下文存在 mid-context 注意力衰减（有效注意力约 600-700K），但每 stage 业务代码 ~500-1200 行 + 依赖文档 ~50K tokens + 工具调用 ~50 次，单 stage 上下文消耗 ~300-500K，在有效注意力范围内

### Q3: TD-46 为什么不实装？

**A**: TD-46（command_palette fuzzy 优化）是 **侦察报告误读**（[`tech-debt.md:485-492`](../tech-debt.md) 明确标 N/A）：
- v0.13 brainstorm 侦察报告说「`command_palette.rs:813, 912` 的 `to_lowercase().contains()` 每帧」
- 实际查证：line 813 / 912 在 `#[test]` 模块（`empty_query_matches_all_items` / `theme_items_in_matches` 等单元测试的 assert），**不是生产路径**
- 生产 fuzzy 用 nucleo（line 109-150 matcher 已复用避免每次按键重建），性能无问题
- 用户启动指令把 TD-46 列进范围是误读，本 brainstorm 明确不实装

### Q4: record 暴露为什么选 spawn 子进程而不是 worker 持续采样？

**A**: 详见决策 4。核心理由：
1. 复用 v0.6 落地的 `run_record` 路径全部业务逻辑（recorder / bookmark / anomaly detection），不重写
2. MCP handler 不持 worker 状态（与 v0.12 TD-36 持久 dns_collector 模式不同，dns_collector 是查询类 worker 持有成本低，record worker 是录制类 worker 持有成本高）
3. 子进程崩溃隔离（record worker 崩溃不影响 MCP server）
4. `--no-tui` flag 重构成本低（~50 行）

### Q5: VT100 转码路径为什么选临时转码而不是永久转码？

**A**: 详见决策 6。核心理由：
1. 不破坏原 VT100 文件（与 v0.6 落地的 VT100 路径并行，用户可选 VT100 replay 或转码后 v3 replay）
2. 转码失败可回退（VT100 字节流损坏时仍走 VtPlayer 正向 replay）
3. 转码开销 ~3s 可接受（agent 一次性调用，与 `proc_replay_search` ~9s/30min session 同款可接受范围）
4. 永久转码如用户有需求可加 `proc replay --convert <file>` CLI 子命令（未来 v0.18+ cycle 候选）

### Q6: confirm 机制为什么用参数而不是两次调用？

**A**: 详见决策 5。核心理由：
1. 与 v0.6 落地的 `pending_record_confirm` TUI 路径同款契约（用户按 `R` 弹确认 / agent 传 `confirm=true` 显式确认）
2. 简单（一个 bool 参数，无需 token 状态机）
3. agent 视角明确（confirm=true 时才真正启动，false 时返 error 让 agent 知道需要确认）

### Q7: v0.17 cycle 后 proc 还有哪些方向？

**A**: v0.17 cycle 末段（stage 7 Review）会评估 v0.18+ 候选方向，预计包括：
- **主题 C**：跨平台扩展 cycle（如 Linux/macOS 重新支持，与 v0.12 ADR-0022 Windows-only 决策可能翻盘）
- **主题 E**：插件系统 cycle（让用户扩展 inspector tab / worker / scoring rule）
- **主题 G**：分布式采集 cycle（多机 proc 联合分析，与 brainstorm §主题 B 可观测性 cycle 同款方向延续）
- **v0.17 cycle 残留项**：如 stage 4/5/6 拆分后某些子项推迟、TD-44/45 跳过后留 v0.18+ 评估、record 暴露方案 (b) worker 持续采样路径评估、VT100 永久转码 CLI 子命令评估

## 开发阶段计划执行手册（每个会话的强制规则）

> **本段替代 plan.md 角色**（proc v0.13+ cycle 改用 brainstorm.md 作为 cycle-level 项目宪法，详见 ADR-0001 phased-project skill adoption + v0.12 plan.md 历史归档）。

### 开工前必做（8 步）

1. **一次性读完所有依赖文档，再开始任何工具调用**（关键，mid-context 注意力衰减规则）：
   - 读 `CONTEXT.md`（领域词汇表，私有 .gitignore 文件）— 确保使用项目统一术语
   - 读 `docs/stages/v0.17-brainstorm.md`（本文件，cycle 总览 + 强制规则）
   - 读 `docs/stages/v0.17-stage-N.md`（当前阶段的完整任务清单）
   - 如存在 `docs/handoff-stage-N-checkpoint.md`，必须先读 Checkpoint，从中断点继续
   - 读相关 ADR（stage-N.md 顶部「开工前只需阅读」段已列出）
2. **确认前置依赖** — 检查本 brainstorm 7 stage 总览表中前置阶段是否已 `[x]` ✅，未完成则拒绝开始
3. **回归验证（分档）**：
   - **全量回归 summary**：`cargo test --release -q 2>&1 | grep "^test result:" | awk '{p+=$4; f+=$6; i+=$8} END {print p" passed / "f" failed / "i" ignored"}'`（只看 pass/fail 数字）
   - **依赖测试详情**：stage-N.md 顶部「依赖测试」字段声明的测试（看完整输出）
   - **前一阶段新增测试详情**：验证前一阶段质量
4. **基线三件套**：`cargo fmt --all -- --check` / `cargo clippy --release --all-targets -- -D warnings` / `cargo build --release --no-default-features` / `cargo bench --no-run`（任一失败先修复前一阶段遗留问题，不带着坏基础继续）

8. **开工前一次性把所有依赖文档读完**再调用任何工具（重申第 1 步，因为这是 proc cycle 跨会话最常见的失误）

### 执行中（7 步）

9. **一会话一个完整单元**（阶段或 Checkpoint 接力），完成后立即停止，**绝不允许自动继续下一阶段**

    - 小修（修 typo、加参数、修 bug、< 5 处改动）：在当前阶段内直接修复 + 在阶段完成报告中说明
    - 大改（改接口、改数据结构、删文件、> 5 处改动）：停止当前阶段，插入「阶段 N.M 回溯修复」任务（文件 `docs/stages/v0.17-stage-N.M.md`），硬停止并指示用户开新修复会话
