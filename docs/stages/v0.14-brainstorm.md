## 候选方向（录屏回放 v2 5 个子方向）

### 子方向 1：文件格式 v3 — 按需加载 + 索引 + 元数据 footer ⭐ **核心基础**

**现状调研**（`src/record/reader.rs:7-14`）：

```rust
pub struct Player {
    path: PathBuf,
    header: RecordingHeader,
    #[allow(dead_code)]
    frame_offsets: Vec<u64>,   // ← 已存在但未启用！
    frames: Vec<UiFrame>,       // ← 全量 deserialize 到内存
}
```

`Player::open` 把**整个录屏文件全部 deserialize 到 `Vec<UiFrame>`** 内存里。

**问题（PERF-BASELINE-v0.13.md §4 + TD-45 验证）**：
- 单帧 deserialize 165 µs @ 1000 进程
- 30 min session × 30 FPS × 1000 进程 = 54000 frames × 165 µs = **9 秒启动加载时间**
- 单帧体积 ~200 KB（1000 进程 UiFrame bincode）× 54000 frames = **10 GB RAM**（必 OOM）
- 文件体积：1000 进程 × 200 B/proc × 54000 frames ≈ **10 GB 磁盘**（bincode 不压缩）

**修复**：
- 启用 `frame_offsets`（已存在）做按需加载：`frame_at(idx)` 改为 `seek + read_exact + deserialize::one`
- 加 footer（offset 表 + 元数据）：start_time / end_time / duration / max_cpu / max_mem / anomaly_count / event_count
- `proc replay recording.prec --info` 显示 footer 元数据（不开 TUI）
- 兼容 v1/v2 老文件：自动转换 + 缓存 `.prec.idx` sidecar（不入 git，本机优化）

**ROI 评估**：
- 用户价值：**高**（解决长 session OOM + 启动加速 9s → < 100ms）
- 风险：**中**（文件格式改动，需严格向后兼容 v1/v2 老文件）
- 工作量：**~600 行**（reader 重构 + writer 加 footer + 兼容层 + .idx 缓存 + 测试）

### 子方向 2：书签系统 ⭐ **高频用户痛点**

**现状**：录屏启动后用户看到关键事件（如 CPU 飙升 / anomaly 触发 / docker 重启），无法标记。回放时无法跳转到关键事件，只能从头看到尾。

**修复**：
- 录制时按 `b` 添加书签（保存当前帧 idx + timestamp + 用户输入 label）
- 回放时按 `B` 打开书签列表（带搜索 / 编辑 / 删除）
- 书签持久化到 `.bookmarks.json` sidecar（与录屏同名 `.prec.bookmarks.json`）
- footer 元数据段含书签数（子方向 1 footer 设计预留位置）

**ROI 评估**：
- 用户价值：**高**（事后分析核心能力 — 「这段 anomaly 我标了，跳过去看」）
- 风险：**低**（独立模块，不动 record 格式主体）
- 工作量：**~400 行**（Bookmark 类型 + sidecar JSON + UI panel + 录制键位 + 回放键位 + 测试）

### 子方向 3：倒放（reverse playback）

**现状**：`ReplayController` 只有正向播放（`ReplaySpeed::Half / Normal / Double / Quad`），倒放只能手动 Left Left Left 单帧后退。

**修复**：
- `ReplayController` 加 `direction: ReplayDirection::Forward / Reverse` 字段
- 倒放速度档位同正向（Half / Normal / Double / Quad）
- 切方向键位：`r` 切方向（与录制键位冲突 → 录制时禁用）
- 倒放时进程列表 / 树 / 网络 / 系统指标反向迭代（视觉效果）
- timeline 显示方向箭头（▶ / ◀）

**ROI 评估**：
- 用户价值：**中**（事后分析「刚才发生了什么」，但用户痛点弱于书签）
- 风险：**低**（独立 tick 逻辑分支）
- 工作量：**~250 行**（ReplayController 加 direction + tick 逻辑双分支 + UI 标记 + 测试）

### 子方向 4：时间轴搜索 ⭐ **事后分析核心**

**现状**：录屏 timeline 只有帧索引 + timestamp 显示，无法搜索「CPU 第一次超 80% 的帧」或「chrome 进程出现的所有帧」。

**修复**：
- timeline 模式按 `/` 进入 search（与现有 FilterExpr 模式同款语义）
- 搜索维度：
  - timestamp 范围（`> 2024-01-01 12:30:00`）
  - cpu 阈值（`cpu > 80`）
  - mem 阈值（`mem > 500mb`）
  - process name（`name =~ /chrome/`）
  - anomaly 触发（`anomaly.severity == "critical"`）
- 命中帧在 timeline 高亮（小红点）
- `n` / `N` 跳转下一 / 上一命中（vim 同款）
- 搜索持久化到 `.bookmarks.json`（与子方向 2 共用 sidecar）

**ROI 评估**：
- 用户价值：**高**（事后分析 = 找关键帧，搜索是核心能力）
- 风险：**中**（需扩 FilterExpr 到时间维度 + UiFrame 字段索引）
- 工作量：**~500 行**（ReplaySearchState + FilterExpr 扩 timestamp / anomaly + timeline UI 高亮 + n/N 跳转 + 测试）

### 子方向 5：录屏文件元数据 footer（子方向 1 子集）

**说明**：子方向 1 的 footer 是「按需加载」的一部分。如选子方向 1 必含 footer；如不选子方向 1 可单独做 footer（轻量版，writer 末尾追加 footer，reader open 时只读 footer）。

**ROI 评估**：
- 用户价值：中（`proc replay recording.prec --info` 不开 TUI 看元数据）
- 风险：低
- 工作量：~200 行（如单独做）

## 推荐方案：A（完整 v2 cycle）

> **2026-07-05 用户拍板**：选**方案 A** — 完整 v2 cycle（5 stage，~1750 行）。理由：(1) 录屏是 proc 独有功能，做深是核心差异化；(2) 倒放虽然 ROI 低于书签 / 搜索，但实现成本仅 ~250 行，cycle 完整性收益大于成本；(3) v0.13 cycle 是 4 stage 不动业务代码的轻 cycle，v0.14 做完整 v2 是节奏对比（重 cycle / 轻 cycle 交替）。

**理由**：

1. **格式 v3 是 cycle 的核心价值**：解决 PERF-BASELINE TD-45 实测的「9s 启动加载 + 10 GB RAM」长 session OOM 问题。这个数据是真实瓶颈（不像 v0.13 的 parent_chain 是 worker 线程），用户感知极强。
2. **书签 + 搜索是用户最高频痛点**：录屏的核心使用场景是「事后分析」，书签和搜索是分析能力的两个支柱。
3. **倒放补完控件集**：与方案 B 推荐时不同（用户最终选 A），倒放补完 Forward / Reverse 双向播放控件集，与书签 / 搜索形成完整的事后分析体验。
4. **5 stage 节奏对比 v0.13**：v0.13 = 4 stage 轻 cycle（不动业务代码），v0.14 = 5 stage 重 cycle（业务代码 ~1750 行），节奏对比让 cycle 迭代有起伏。
5. **风险可控**：stage 1 格式 v3 需要严格向后兼容（v1/v2 老文件），但 .prec 文件格式简单（魔数 + 长度前缀 + bincode），改动可控。stage 4 倒放是独立控件分支，不依赖前 3 stage。

**与 v0.13 的衔接**：
- v0.13 PERF-BASELINE 实测 record deserialize 165 µs @ 1000 进程 → 格式 v3 按需加载让单帧 deserialize 仅在 seek 时发生
- v0.13 benchmark suite（bench_record_serialize）保留作为 v0.14 性能 guard（重构后跑 bench 对比 before/after）

## 录屏模块深度调研（cycle 设计基础）

> 本段是 brainstorm 起草阶段的录屏模块调研产出，供 stage 1-3 设计参考。

### 当前录屏架构（v0.6.0 阶段 4 落地，v0.6.0 阶段 5 拆 ReplayController）

**文件结构**：
```
src/record/
├── mod.rs           (10 行，module 声明)
├── frame.rs         (273 行，RecordingHeader + UiFrame + 14 个 Frame* 子类型)
├── writer.rs        (129 行，Recorder 单线程 mpsc::channel + bincode serialize)
├── reader.rs        (190 行，Player 全量 deserialize Vec<UiFrame>)
├── conversions.rs   (191 行，UiFrame ↔ ProcessInfo / ProcessFlow 双向转换)
└── vt100.rs         (469 行，VT100 字节流录制 — 独立子系统，不在 v0.14 cycle 范围)

src/replay/
├── mod.rs           (9 行，module 声明)
└── controller.rs    (232 行，ReplayController + TimelineState + ReplaySpeed + ReplayAction)
```

**录屏文件格式（v2，bincode + 长度前缀）**：
```
[8B header_len][header_bytes (RecordingHeader bincode)]
[8B frame_len_1][frame_bytes_1 (UiFrame bincode)]
[8B frame_len_2][frame_bytes_2]
...
[8B frame_len_N][frame_bytes_N]
```

`RecordingHeader`（frame.rs:7-12）：
- `magic: [u8; 4]` = `b"PREC"`
- `version: u16` = 2（v1 兼容）
- `start_time: u64`（unix epoch 秒）
- `hostname: String`

`UiFrame`（frame.rs:46-99）：~40 字段，含：
- timestamp / mode / status_message
- cpu_usage / memory_used/total / net_down/up / cpu_history / mem_history
- processes: Vec<FrameProcess> / search_query / sort_field / process_view_mode
- tree_nodes: Vec<FrameTreeNode>
- port_entries / port_view_mode / port_process_groups / port_remote_groups / connection_diff / anomalies
- usb_devices / usb_locks / monitors / docker_containers / docker_events / ops / nav

### 当前回放控件（controller.rs:121-185）

| 键位 | 行为 |
|---|---|
| `q` | 退出回放 |
| `space` | 暂停 / 播放切换 |
| `Left` / `Shift+Left` | 单帧后退 / 10 帧后退 |
| `Right` / `Shift+Right` | 单帧前进 / 10 帧前进 |
| `+` / `=` | 加速（Half → Normal → Double → Quad） |
| `-` | 减速 |
| `Home` / `End` | 跳首帧 / 末帧 |

**速度档**：Half=0.5x（每两 tick 推 1 帧）/ Normal=1x / Double=2x / Quad=4x

**缺什么**（v0.14 cycle 候选）：
- 无书签（无法标关键事件）
- 无倒放（只能正向播放）
- 无时间轴搜索（无法跳到「CPU 第一次超 80%」）
- 无元数据 footer（open 后才知道内容）
- 全量加载（长 session OOM）

### PERF-BASELINE-v0.13 实测（录屏路径）

来自 `docs/reviews/PERF-BASELINE-v0.13.md` §4：

| fixture | serialize mean | deserialize mean | 备注 |
|---|---|---|---|
| 100 进程 | 2.3 µs | 10.2 µs | serialize 13.6% ⚠ |
| 500 进程 | 9.0 µs | 61.0 µs | deserialize 29.0% ⚠ |
| 1000 进程 | **14.1 µs** | **165.4 µs** | 12× 慢于 serialize |

**长 session 累计成本**：
- 30 min × 30 FPS × 1000 进程 = 54000 frames
- 全量 deserialize：54000 × 165 µs = **9 秒启动加载**
- 单帧体积 ~200 KB（1000 进程）× 54000 = **10 GB RAM**（必 OOM）

**stage 1 按需加载预期效果**：
- 启动加载：只读 footer + frame_offsets → **< 100 ms**（无论 session 多长）
- 内存占用：仅当前帧 + 缓冲窗口（可配，默认 60 帧 = 2 sec @ 30 FPS）→ **~12 MB**（与 session 长度无关）
- seek：`frame_at(idx)` 单帧 seek + deserialize → 165 µs（用户无感）

### 已知限制（v0.6 落地至今）

1. **长 session OOM**（PERF-BASELINE 实测验证）— v0.14 stage 1 修
2. **录屏文件含屏幕显示的 VT100 字节**（ADR-0006 line 36 注释）— v0.14 cycle 不动 VT100 子系统，留 v0.15+ 评估
3. **录屏启动确认弹窗**（ADR-0008 line 107 `App::pending_record_confirm`）— 不动
4. **MCP 不暴露 proc_record / proc_replay**（ADR-0009 line 37）— 不动

## 常见问题 FAQ

### Q1: v0.14 cycle 与 v0.13 PERF-BASELINE 报告的关系？

**A**: v0.13 实测 record deserialize 165 µs @ 1000 进程（PERF-BASELINE §4），是 v0.14 stage 1 格式 v3 按需加载的核心 ROI 来源。stage 1 落地后跑 bench_record_serialize 对比 before/after（保留 v0.13 baseline 数字）。

### Q2: 文件格式 v3 与 v1/v2 兼容性怎么保证？

**A**: stage 1 设计原则：
- v3 文件 footer 含 magic `PREC3`，v1/v2 文件 footer 不存在（reader 检测 EOF 后回退到 v1/v2 全量加载路径）
- v1/v2 老文件首次 open 后自动生成 `.prec.idx` sidecar（包含 frame_offsets + 元数据），下次 open 走按需加载路径
- v3 文件 open 时 footer 已含 frame_offsets，不需要 sidecar
- v1/v2 文件**永远不重写**（只读，sidecar 单独管理）

### Q3: 录屏文件体积 10 GB 是不是要加压缩？

**A**: v0.14 cycle 不加压缩（推迟到 v0.15+ 评估）：
- 当前用户场景：单次录屏 5-10 min（< 1 GB），10 GB 是 30 min 极端场景
- zstd 压缩能让体积降 5-10×（bincode 数据冗余高），但运行时 CPU 成本（record 路径加 zstd encoder）
- v0.14 stage 1 优先解决 OOM（按需加载），压缩是独立维度，留 v0.15+ cycle 评估

### Q4: 录屏 v2 会破坏现有用户已录制的 .prec 文件吗？

**A**: 不会。stage 1 严格向后兼容：
- v1/v2 文件读取路径保留（fallback）
- v3 文件是新格式，与 v1/v2 共存
- 用户已有 .prec 文件继续可用（首次 open 自动生成 sidecar 加速后续 open）

### Q5: stage 1 失败了怎么办？

**A**: stage 1 是 cycle 基础，但失败模式可控：
- 文件格式改动在 reader.rs / writer.rs 两个文件，stage 1 落地后跑全量回归（≥ 1115 passed）+ bench 对比
- 若 stage 1 出现兼容性 bug → 立即停 cycle，fix stage 1 后再启 stage 2
- 若 stage 1 工作量超预期（> 800 行）→ 评估是否拆为 stage 1a（reader 按需加载）+ stage 1b（writer footer + 元数据）

### Q6: 录屏 v2 是不是要做录屏「实时流」或者「远程查看」？

**A**: 不在 v0.14 范围：
- 实时流 / 远程查看是 Theme F（可观测性 cycle）的范畴
- v0.14 仅做**事后分析能力**（书签 + 搜索 + 倒放候选）+ **底层格式优化**（按需加载 + 元数据）
- 实时流需要新的 transport（WebSocket / HTTP），是独立 cycle
