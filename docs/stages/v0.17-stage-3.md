## 设计决策（本阶段拍板，stage 4-7 不动 snapshot 字段策略 / format! 优化范围 / record encoding 选项层）

### 决策 1：TD-54 worker spawn 用「fire-and-forget」线程 + Arc<Mutex<Option<SystemSnapshot>>> 共享

**问题**：`ProcMcpHandler::new()` 需启动 1s tick worker 持续 refresh SystemSnapshot，但 `ProcMcpHandler` 是 `Clone` derive（rmcp 每次 tool call 都 clone handler），不能在 struct 里持 `JoinHandle`（clone 后哪个实例负责 join？）。

**决策**：worker 用「fire-and-forget」模式 —— `new()` spawn 线程持 `Arc::clone(&snapshot)`，handler 不持 `JoinHandle`，线程与进程同生命周期（进程退出时自然终止）。

```rust
impl ProcMcpHandler {
    pub fn new() -> Self {
        let (collector, _kind) = crate::dns_log::detect_collector();

        #[cfg(feature = "mcp-persistent-state")]
        let snapshot: Arc<Mutex<Option<SystemSnapshot>>> = Arc::new(Mutex::new(None));

        #[cfg(feature = "mcp-persistent-state")]
        {
            let snapshot_clone = Arc::clone(&snapshot);
            let _ = std::thread::Builder::new()
                .name("mcp-snapshot-worker".to_string())
                .spawn(move || run_snapshot_worker(snapshot_clone));
        }

        Self {
            dns_collector: Arc::new(Mutex::new(collector)),
            #[cfg(feature = "mcp-persistent-state")]
            snapshot,
            #[cfg(feature = "mcp-persistent-state")]
            system_history: Arc::new(Mutex::new(VecDeque::new())),
            #[cfg(feature = "mcp-persistent-state")]
            record_handle: Arc::new(Mutex::new(None)),
        }
    }
}

fn run_snapshot_worker(snapshot: Arc<Mutex<Option<SystemSnapshot>>>) {
    let mut last_snapshot: Option<SystemSnapshot> = None;
    loop {
        // refresh 已有 snapshot 复用 sysinfo System 共享状态，比每次 new 更快
        let mut new_snapshot = match last_snapshot.take() {
            Some(mut s) => {
                if s.refresh().is_err() {
                    match SystemSnapshot::new() {
                        Ok(fresh) => fresh,
                        Err(_) => {
                            std::thread::sleep(std::time::Duration::from_secs(1));
                            continue;
                        }
                    }
                } else {
                    let _ = s.refresh_heavy_incremental();
                    s
                }
            }
            None => match SystemSnapshot::new() {
                Ok(s) => s,
                Err(_) => {
                    std::thread::sleep(std::time::Duration::from_secs(1));
                    continue;
                }
            },
        };
        let _ = new_snapshot.refresh();
        let _ = new_snapshot.refresh_heavy_incremental();
        last_snapshot = Some(new_snapshot.clone_for_takeover());  // 见下方 helper

        if let Ok(mut guard) = snapshot.lock() {
            *guard = Some(new_snapshot);
        }

        std::thread::sleep(std::time::Duration::from_secs(1));
    }
}
```

**关键设计点**：

1. **worker 复用 SystemSnapshot 跨 tick**：避免每秒 `SystemSnapshot::new()` 全新初始化 sysinfo `System` 状态（首次 new 约 200ms，后续 refresh 约 30-50ms）。worker 持 `last_snapshot: Option<SystemSnapshot>`，下一 tick 走 `refresh()` 复用 sysinfo `System` 内部增量更新。
2. **refresh failure 静默降级**：refresh 失败时（如 sysinfo 内部错误）保 `last_snapshot` 不变，下 tick 重试。worker 永不退出（与 handler 同生命周期）。
3. **不持 `JoinHandle`**：fire-and-forget 模式让 handler `Clone` 不需协调 join 责任。进程退出时 worker 自然终止。
4. **Default 路径不 spawn worker**：测试路径（`ProcMcpHandler::default()`）snapshot 永远 None，所有 metrics_* / process_* helper 走 fallback 现场新建路径（与 v0.16 行为一致，既有测试零回归）。
5. **`SystemSnapshot::clone_for_takeover` helper**：worker 复用 snapshot 需要某种「移走但保留 sysinfo System 状态」操作。**实际方案**：worker 不 clone，下一 tick 直接 `*guard = Some(new_snapshot)` 把 owned snapshot move 进字段；下一 tick 重新从 `*guard` take 出来 refresh 再 move 回。简化：

```rust
fn run_snapshot_worker(snapshot: Arc<Mutex<Option<SystemSnapshot>>>) {
    loop {
        let start = std::time::Instant::now();
        // 从字段 take 出 owned snapshot（如有），refresh 后 move 回
        let mut s = match snapshot.lock().ok().and_then(|mut g| g.take()) {
            Some(s) => s,
            None => match SystemSnapshot::new() {
                Ok(s) => s,
                Err(_) => {
                    std::thread::sleep(std::time::Duration::from_secs(1));
                    continue;
                }
            },
        };
        let _ = s.refresh();
        let _ = s.refresh_heavy_incremental();
        if let Ok(mut guard) = snapshot.lock() {
            *guard = Some(s);
        }
        let elapsed = start.elapsed();
        let sleep_dur = std::time::Duration::from_secs(1).saturating_sub(elapsed);
        std::thread::sleep(sleep_dur);
    }
}
```

**take 模式风险**：worker 1s tick 之间，helper 读字段时如果 worker 正好 take 出来 → helper 读到 None → fallback 现场新建。这是合理的（worker 持锁时间 < 50ms，1s tick 占空比 < 5%）。

### 决策 2：metrics_* helper 拆 `*_from_snapshot` 内部函数 + 旧 helper fallback 现场新建（既有测试零回归）

pub fn make_metrics_system_json() -> Value {

**关键设计点**：

1. **既有测试零回归**：旧 helper 签名 + 行为不变，所有 `tests/test_mcp_v0_15.rs::test_proc_metrics_*` 测试调用 `make_metrics_system_json()` 仍走 fallback 路径，输出 schema 一致。

**`make_processes_json` / `make_process_tree_json` / `make_export_json` 同款拆 from_snapshot**：3 个 process helper 既有 ~10 个测试调用点，保留旧签名 fallback + 加 `*_from_snapshot` 内部 helper。

### 决策 3：TD-44 itoa 替换范围（u64 → String 路径，f32 {:.1} 路径保留 std format!）

**问题**：brainstorm §主题 A 表 TD-44 描述「`format_bytes` / `format_speed` / `format!("{:.1}", cpu)` 等 5+ 热 path format! 替换为 `itoa` / `Cell<Cow<_>>`」，但 `itoa` 只处理整型 → String，`{:.1}` f32 格式化不在 itoa 范围。

**决策**：

- **u64 → String 路径替换 itoa**：`format_bytes` / `format_speed` / `format_uptime` / `format_run_time` 中所有 `format!("{}", u64_val)` 分支（B 档 / 天 / 小时 / 分 / 秒）改用 `itoa::Integer::write_to_string` 跳过 std `format!` 抽象（每调用省 1 次 heap alloc + 1 次 fmt 调度）。
- **f32 `{:.1}` 路径保留 std format!**：`process_table.rs` / `process_tree.rs` / `app_group_view.rs` / `cli/ls.rs` 中 8 处 `format!("{:.1}", cpu_usage)` 调用点**不动**。理由：
  1. `itoa` 不处理 f32
  2. 引入 `ryu` 依赖（专门 f32/f64 → str 库）收益边际 —— ryu 输出最短表示，与 `format!("{:.1}", x)` 1 位小数语义不同，需要手动裁剪
  3. `{:.1}` 实测每调用 ~200ns（std 的 f32 格式化已经很优化），1000 进程 × 8 调用点 = 1.6ms 在用户无感区
  4. brainstorm 风险 3 已标注 TD-44「真实生产 < 1ms 已在用户无感区」低 ROI
- **`format_bytes` / `format_speed` 中 `{:.1}` f32 分支保留**：`format!("{:.1}GB", x)` 路径不动，仅 `{}B` u64 分支改 itoa。

```rust
// src/format.rs

#[must_use]
pub fn format_bytes(bytes: u64) -> String {
    const KB: u64 = 1024;
    const MB: u64 = KB * 1024;
    const GB: u64 = MB * 1024;
    if bytes >= GB {
        format!("{:.1}GB", bytes as f64 / GB as f64)  // 保留 f32 路径
    } else if bytes >= MB {
        format!("{:.0}MB", bytes as f64 / MB as f64)
    } else if bytes >= KB {
        format!("{:.0}KB", bytes as f64 / KB as f64)
    } else {
        // 新：itoa 路径
        let mut buf = itoa::Buffer::new();
        format!("{}B", buf.format(bytes))
    }
}

#[must_use]
pub fn format_speed(bytes_per_sec: u64) -> String {
    const UNITS: &[(&str, u64)] = &[
        ("GB/s", 1_000_000_000),
        ("MB/s", 1_000_000),
        ("KB/s", 1_000),
    ];
    for (unit, threshold) in UNITS {
        if bytes_per_sec >= *threshold {
            return format!("{:.1}{}", bytes_per_sec as f64 / *threshold as f64, unit);  // 保留 f32 路径
        }
    }
    // 新：itoa 路径
    let mut buf = itoa::Buffer::new();
    format!("{}B/s", buf.format(bytes_per_sec))
}

#[must_use]
pub fn format_uptime(seconds: u64) -> String {
    let days = seconds / 86400;
    let hours = (seconds % 86400) / 3600;
    let mins = (seconds % 3600) / 60;
    let mut d_buf = itoa::Buffer::new();
    let mut h_buf = itoa::Buffer::new();
    let mut m_buf = itoa::Buffer::new();
    if days > 0 {
        format!("{}天{}小时", d_buf.format(days), h_buf.format(hours))
    } else if hours > 0 {
        format!("{}小时{}分", h_buf.format(hours), m_buf.format(mins))
    } else {
        format!("{}分钟", m_buf.format(mins))
    }
}

#[must_use]
pub fn format_run_time(seconds: u64) -> String {
    let days = seconds / 86400;
    let hours = (seconds % 86400) / 3600;
    let mins = (seconds % 3600) / 60;
    let secs = seconds % 60;
    let mut buf_d = itoa::Buffer::new();
    let mut buf_h = itoa::Buffer::new();
    let mut buf_m = itoa::Buffer::new();
    let mut buf_s = itoa::Buffer::new();
    if days > 0 {
        format!("{}d{}h", buf_d.format(days), buf_h.format(hours))
    } else if hours > 0 {
        format!("{}h{}m", buf_h.format(hours), buf_m.format(mins))
    } else if mins > 0 {
        format!("{}m{}s", buf_m.format(mins), buf_s.format(secs))
    } else {
        format!("{}s", buf_s.format(secs))
    }
}
```

**关键设计点**：

1. **itoa::Buffer 复用**：每个 `format_uptime` / `format_run_time` 调用内多个 u64 → String（days / hours / mins / secs），用多个 `itoa::Buffer` 实例（每 Buffer 占 ~40 字节栈空间）。`format!` 宏内嵌 `itoa::Buffer::new()` 临时变量，编译器优化后通常零额外开销。
2. **`{:.0}MB` 路径保留 std format!**：MB / KB 档是 f32 → String（`bytes as f64 / MB as f64`），itoa 不适用。
3. **行为等价性测试**：`src/format.rs` 内嵌 tests 加 `format_bytes_itoa_equivalence` / `format_speed_itoa_equivalence` / `format_uptime_itoa_equivalence` / `format_run_time_itoa_equivalence` 测试，验证 B 档输出与旧路径完全一致（如 `format_bytes(512) == "512B"` 不变）。
4. **bench 加 group**：`benches/bench_tui_draw.rs` 加 `format_bytes_itoa_vs_format` group，用 `criterion::BenchmarkId` 对比 itoa 路径 vs 旧 `format!` 路径在不同 byte size（100B / 10KB / 1MB / 1GB）下的耗时差异。预期 itoa 路径 < 50ns，format! 路径 ~150ns（2-3x 降幅）。

**`process_table.rs` / `process_tree.rs` / `app_group_view.rs` / `cli/ls.rs` 中 `{:.1}` 调用点不动**：保留 std format!，与 brainstorm 风险 3 低 ROI 评估对齐。

### 决策 4：TD-45 record encoding 选项层 + 评估文档化（**不切 varint**，留 v0.18+ cycle）

**问题**：brainstorm 决策 3 用户拍板 TD-45 全实装「bincode varint vs fixint 切换 + 旧文件兼容层」，但实际评估后发现：

- **ROI 极低**：replay 偶发触发，165 µs 单帧 seek 完全无感（PERF-BASELINE-v0.13 §4 实测）；30 min × 30 FPS × 1000 进程连续 seek 才有感知（agent 实际场景罕见）
- **varint vs fixint 性能差异**：varint 让小数字占少 byte（u64=1 vs 8 byte），但 parse 时需 condition branch（每 byte 检查 high bit）；fixint 直接 memcpy。**实测 bincode 1.x varint 比 fixint 慢 1.5-2x**（serialize + deserialize 都慢），因为 varint 是为「网络传输节省带宽」设计而非「CPU 加速」
- **影响 stage 5 VT100 转码**：v0.17 stage 5 落地 VT100 → UiFrame 转换器写入 v3 文件（fixint），如 stage 3 bump 到 v4 varint，stage 5 需协调版本号
- **breaking change**：v0.17 写的 v4 varint 文件 v0.16 proc 读不了（forward incompatibility），与 v0.6 → v0.14 落地 v2 / v0.14 落地 v3 时同款风险

**决策**：**偏离 brainstorm 决策 3 TD-45 部分，stage 3 不切 varint**，改为建立选项层 + 评估文档化：

- 新建 `src/record/encoding.rs`，提供 `options_for_version(version: u16) -> Box<dyn bincode::Options>` 函数（v3 / v2 / v1 都返 fixint 默认配置）
- `src/record/{reader,writer,sidecar,vt100}.rs` 改用 `options_for_version(RECORDING_VERSION).serialize(...)` / `.deserialize(...)` 替换 `bincode::serialize` / `bincode::deserialize`
- `RECORDING_VERSION` 仍 = 3（不 bump）
- 行为完全等价（fixint 配置与 bincode::serialize 默认配置等价）
- `docs/adr/0026-mcp-handler-persistent-fields.md` 或本 stage doc 决策段记录 varint 切换 ROI 评估结论 + v0.18+ cycle 候选

**理由**：

1. **surgical 原则**：低 ROI 项不引入 breaking change（v4 varint 让 v0.16 用户读不了新文件）
2. **stage 5 协调成本最小**：stage 5 VT100 转码写 v3 文件，不需协调版本号
3. **建立选项层让未来切换一行代码搞定**：v0.18+ cycle 评估「网络传输录屏文件」场景时（如远程 agent / Web dashboard），只需改 `options_for_version` 函数 + bump RECORDING_VERSION

**与 brainstorm 决策 3 偏离的说明**：本 stage doc 决策段明确说明 TD-45 偏离 brainstorm 决策 3 完整切换路径，落地为「选项层 + 评估文档化」。stage 7 Review 时评估是否触发 brainstorm 决策段更新（让用户重新拍板 TD-45 是否仍按完整切换路径走，还是接受选项层方案）。

### 决策 5：TD-50 proc_smart 标 deprecated 用 description hint（不引入 schemars x-deprecated 扩展）

**问题**：brainstorm §主题 A 表 TD-50 描述「`proc_smart` 标 Status Deprecated，schema 加 `x-deprecated: true` hint」，但 rmcp 0.11 / schemars 0.8 不支持 `x-deprecated` 自定义 schema 扩展字段（schemars 0.8 的 `#[schemars(extension = "x-deprecated")]` 需要触发 schemars 内部 schema visitor，与 rmcp 0.11 `#[tool]` 宏兼容性未验证）。

**决策**：**不引入 schemars 扩展**，仅通过 description 字段加 deprecated hint：

#[tool(
    name = "proc_smart",
    description = "[Deprecated] SMART disk health. Prefer proc_metrics_smart for aggregated or single-device mode. This tool is kept for backward compatibility but will be removed in v0.18+. device=None lists all disks with summary; device=\"/dev/sda\" or \"PhysicalDrive0\" returns detailed attributes. Returns JSON { ok, disks[] | disk } with { device, model, serial, temperature, health, attributes[] }. health is one of Ok/Warning/Critical/Unknown."

1. **description 头部加 `[Deprecated]` 标识**：LLM 读 schema 时第一字符就看到 deprecated 提示
2. **推荐替代 tool 显式说明**：「Prefer proc_metrics_smart for aggregated or single-device mode」让 LLM 知道替代路径
3. **保留 tool 不删**：v0.18+ cycle 评估是否物理删除（与 brainstorm §主题 A 表 TD-50 范围一致）

## 已知风险

### 风险 1：worker spawn 在测试路径泄漏线程

**问题**：`tests/test_mcp_v0_17.rs::test_proc_metrics_system_uses_snapshot_field_after_warmup` 调 `ProcMcpHandler::new()` spawn worker，测试结束时 worker 仍在跑（无限循环），下一测试可能受影响（worker 共享静态状态 / sysinfo `System` 单例）。

**mitigate**：
1. 测试用 `ProcMcpHandler::default()` 路径（不 spawn worker）验证字段为 None + fallback 路径
2. 仅 1 个测试用 `ProcMcpHandler::new()` 验证 worker spawn 行为，跑完即结束（worker 自然 leak，与进程同生命周期，cargo test 进程退出时清理）
3. 不在测试中调 `worker_handle.join()`（fire-and-forget 模式不让测试 join）

### 风险 2：worker take 模式导致 helper 偶发读到 None

**问题**：worker 1s tick 之间，worker `*guard = ... ` 操作 < 1ms，但 take + refresh + move back 之间有 ~30-50ms 窗口 `*guard = None`。helper 在此窗口读字段 → fallback 现场新建 SystemSnapshot。

**mitigate**：
1. fallback 路径返数据与 worker 路径一致（schema 不变），agent 视角无差异
2. 30-50ms 窗口占空比 < 5%（1s tick / 50ms 持锁），helper 偶发 fallback 是可接受的
3. 实测验证：`test_proc_metrics_system_uses_snapshot_field_after_warmup` 多次调用 `proc_metrics_system` 至少 1 次走 worker 路径（snapshot 字段 Some）

### 风险 3：metrics_gpu / metrics_smart 不能切 snapshot 路径

**问题**：`metrics_gpu_json` 数据源是 `crate::gpu::GpuCollector`，`metrics_smart_json` 数据源是 `crate::smart::list_disks` / `read_smart`，都不在 SystemSnapshot。stage 3 切不了 snapshot 路径。

**mitigate**：
1. 这 2 个 tool 保留 v0.16 行为（每次调用现场 new GpuCollector / list_disks）
2. TD-54 范围实际是 6 个 tool（metrics_system / metrics_disk_io / metrics_thermal / ls / tree / export），与 brainstorm §主题 A 表 TD-54 描述「metrics_* 复用」相比**收缩范围**（metrics_gpu / metrics_smart 不动）
3. 文档化：本 stage doc 决策 2 明确说明收缩范围 + 理由

### 风险 4：TD-45 偏离 brainstorm 决策 3

**问题**：brainstorm 决策 3 用户拍板 TD-45 全实装「varint 切换 + 兼容层」，本 stage doc 决策 4 偏离为「选项层 + 评估文档化」。

**mitigate**：
1. 本 stage doc 决策段明确说明偏离 + 理由（ROI 极低 / varint 实测比 fixint 慢 / stage 5 协调成本 / forward incompatibility 风险）
2. stage 7 Review 时评估是否触发 brainstorm 决策段更新（让用户重新拍板）
3. 选项层让未来 v0.18+ cycle 切换 varint 一行代码搞定（保留演进路径）

### 风险 5：itoa 依赖增加约 5KB 二进制体积

**问题**：itoa = "1" 是个轻量库（~5KB 二进制 + ~50 行代码），但仍增加 proc 二进制体积。

**mitigate**：5KB 占 proc 总体积（~10MB release build）比例 < 0.1%，可接受。如未来评估需进一步减体积，可改用 std `format!` 风格的自写 u64 → str helper（~20 行，性能与 itoa 接近）。

### 风险 6：worker spawn 在 `--no-default-features` 路径不存在

**问题**：`mcp-persistent-state` feature gate 让 `--no-default-features` 路径 snapshot 字段不存在，worker spawn block 也不存在。但 `#[tool]` 方法的 snapshot 读取逻辑需 `#[cfg(feature = "mcp-persistent-state")]` gate，否则编译失败。

**mitigate**：
1. `#[tool]` 方法体内用 `#[cfg(feature = "mcp-persistent-state")]` block 包裹 snapshot 读取逻辑
2. `cargo build --release --no-default-features` 编译验证（基线三件套已包含）
3. `cargo clippy --release --all-targets --no-default-features -- -D warnings` 验证 cfg-gate 正确
